# Phase 3 — 실사용 시작 (발행·백업·리포트·점검)

작성: 2026-08-03. 전제: Phase 1(종이 루틴)·Phase 2(구구단 스프린트) 완료, 테스트 127개 통과.

**Phase 3의 한 줄 목표**: 실사용을 시작할 수 있는 상태를 만든다 — 발행하고, 데이터를 잃지 않게 하고, 일요일 루틴(확인·공유·백업)을 완성하고, 유창 판정이 낡지 않게 한다.

## 0. 범위 결정 경위 (브레인스토밍 합의)

| 질문             | 결정                                                              |
| ---------------- | ----------------------------------------------------------------- |
| Phase 3의 축     | **전부** — 발행 + 백업 + 리포트 + 점검을 한 Phase로               |
| 주간 리포트 형태 | **화면만 먼저.** 인쇄물(냉장고행)은 아이패드 실물 확인 후 Phase 4 |
| 점검의 날 형태   | **스프린트 점검만.** 종이 쪽 적응 off 구성은 하지 않는다          |
| 리포트 주기      | **주간 + 월간 둘 다** (월간의 근거인 점검이 이번 범위라서)        |
| 백업 방향        | **내보내기 + 가져오기 둘 다** (복구 못 하는 백업은 반쪽)          |
| 순서             | **안 A: 안전 우선 직렬** (아래 §1)                                |

## 1. 태스크 흐름

```
태스크 0  이음새 조사 — 새 코드가 쓸 필드를 이미 읽는 모든 곳 나열 (§10)
태스크 1  발행 + persist() (§2)
태스크 2  백업 엔진 — 직렬화·검증·원자적 교체 (§3)
태스크 3  리포트 화면(주간) — 백업 버튼의 집 (§4)
태스크 4  점검 스프린트 (§5)
태스크 5  월간 리포트 — 점검 결과 섹션 (§6)
태스크 6  requeueWrong 시뮬레이션 보강 (§7)
```

**순서의 근거**: 발행이 앞인 것은 origin 확정과 아이패드 실물 확인 4항목(HANDOFF)이 발행에 걸려 있어서다. 백업이 리포트보다 앞인 것은 실사용 데이터가 쌓이기 시작하는 시점과 "복구 불가능해지는 시점" 사이 공백을 최소화하기 위해서다. 월간이 점검 뒤인 것은 월간 리포트의 근거가 점검 결과이기 때문이다.

**마이그레이션 없음이 이번에도 성립한다.** 필요한 필드(`Day.kind`, `Settings.lastExportedAt`, `schemaVersion`)가 전부 Phase 1 `types.ts`에 이미 있고, 새로 저장하는 값이 없거나 optional이다. `Meta.derived`는 계속 아무도 읽지 않는다(배선하지 않는 것이 설계다 — `types.ts` 주석 참조).

## 2. 발행 + persist()

- 공개 레포 생성 → push → Pages Source 설정. 워크플로(`.github/workflows/deploy.yml`)는 이미 작성·리뷰 완료
- origin은 `https://<계정>.github.io/haruchi/`가 되며 **한 번 정하면 바꾸지 않는다** — IndexedDB가 origin별로 격리되므로 주소를 바꾸면 기존 기록에 접근할 수 없다
- `main.ts` 시작 시 `void navigator.storage?.persist?.()` 한 줄 — iOS의 저장공간 압박 evict 위험을 비용 0으로 줄인다. 반환값에 의존하는 코드는 두지 않는다(거부돼도 앱 동작은 같다)
- 발행 후 아이패드 실물 확인 4항목(HANDOFF)은 **사람이 하는 일**로 Phase 3와 병행한다. 그 결과(키패드 크기, 3분 소요, 지도 동기부여)는 Phase 4 범위에 입력이 된다

## 3. 백업 엔진 (내보내기·가져오기)

### 파일 형식

```json
{ "app": "haruchi", "schemaVersion": 1,
  "exportedAt": "2026-08-03T20:14:00+09:00",
  "days": [...], "meta": {...} }
```

들여쓰기 있는 JSON으로 쓴다. export 파일이 데이터를 들여다보는 유일한 수단(IndexedDB는 CLI로 열 수 없다)이라 사람이 읽을 수 있어야 하고, 5년치가 2.3MB(실측)라 크기는 문제가 아니다.

### 모듈 배치 — 순수 함수와 IO 분리

- **`engine/backup.ts`** (순수, 테스트 대상)
  - `serializeBackup(days, meta, exportedAt)` — `exportedAt`을 인자로 받아 결정적
  - `validateBackup(raw: unknown)` — 성공 시 `{ days, meta }`, 실패 시 **어디가 왜 틀렸는지** 담은 에러. 검사 항목: `app === 'haruchi'`, `schemaVersion === 1`(다른 값은 거부 — 마이그레이션 배열은 버전 2가 실제로 생길 때 만든다), `days`가 `date`/`kind`/`sheet`를 갖춘 배열인지 필드 단위 검사. 코드가 기대는 필드만 엄격히 보고, 모르는 여분 필드는 통과시킨다
- **`data/db.ts`에 `replaceAll(days, meta)` 추가** — days·meta **두 스토어를 한 트랜잭션**으로 clear → put. IndexedDB 트랜잭션은 실패 시 롤백되므로 "가져오기 도중 실패해도 기존 데이터 보존"이 공짜로 성립한다. 기존 헬퍼는 단일 스토어용이라 2-스토어 버전을 하나 추가한다

### 내보내기 흐름

버튼 탭 → `getAllDays()` + `getMeta()` → 직렬화 → Blob 다운로드(`haruchi-YYYY-MM-DD.json`) → 파일 앱/iCloud. `lastExportedAt` 갱신은 다운로드 트리거 직후에 한다 — 브라우저가 저장 완료를 알려주지 않으므로 "시도했음"의 기록이며, 이 한계는 주석에 남긴다. 다운로드 트리거 자체가 실패하면 갱신하지 않는다.

### 가져오기 흐름

파일 선택 → 파싱·검증 → **화면 내 2단계 확인** → `replaceAll` → 홈으로.

- 확인 단계는 네이티브 `confirm()` 대신 화면 안에서 **무엇을 무엇으로 덮는지** 숫자로 보여준다: "이 백업: 8월 2일, 45일치 — 현재 기록 52일치를 완전히 대체합니다" + 빨간 교체 버튼
- **병합하지 않는다** (아이패드 한 대만 쓰는데 병합 로직은 순수 부채다 — 설계 §10)
- 검증 실패 = 거부 + 기존 데이터 보존 + 구체적 사유 표시

## 4. 리포트 화면 (주간)

새 화면 `screens/report.ts`, 해시 `#/report`.

### 진입

- 홈 하단에 상시 링크
- **일요일 자동 전환**: `grade.ts`의 저장 성공 후 `navigate('#/')`를 "그날이 일요일이면 `#/report`"로 바꾼다. 요일 판정은 벽시계가 아니라 **`dayKey`(새벽 4시 경계)의 요일**로 한다 — 일요일 새벽 2시 채점은 토요일 몫이다

### 콘텐츠

설계 원문 §8의 절취선 구조를 화면에서는 "딸에게 보여주는 상단 / 아빠용 하단"으로 옮긴다. 전부 기존 파생 함수로 계산 가능한 것만 넣는다.

| 항목                                        | 데이터 출처                                                      |
| ------------------------------------------- | ---------------------------------------------------------------- |
| 🔥 연속일수 · ✅ 완료일수                   | `sprintStreak` + 홈의 완료일수 로직 재사용                       |
| 구구단 정복 지도 (이번 주 신규 굵은 테두리) | `factMapHtml` 재사용 — 강조할 식 집합을 옵션 인자로 추가         |
| 이번 주 새로 정복한 식                      | `deriveFacts(7일 전까지)` vs `deriveFacts(오늘까지)` 차집합      |
| 평균 반응시간 변화                          | 이번 주 `day.sprint` 시도들의 중앙값 vs 지난주                   |
| 유형별 정답률 (⚠️ 표시)                     | `deriveTypes` + `accuracy` — ⚠️는 표본 10회가 찼고 90% 미만일 때 |
| 가장 느린 식                                | 이번 주 **정답** 시도를 식별로 묶어 중앙값 ms가 가장 큰 식       |
| 다음 점검의 날                              | `nextCheckupDate` (§5)                                           |
| 30일 미백업 배지                            | `lastExportedAt` — **이 필드의 첫 독자**                         |

- "이번 주" = **오늘로 끝나는 최근 7일**, 비교 대상 "지난주" = 그 앞 7일. 롤링 창이라 평일에 홈 링크로 들어와도 창이 항상 꽉 차 있고 특수 분기가 없다. 일요일에 보면 자연히 한 주가 된다
- **주간 스냅샷을 저장하지 않고 매번 재계산한다** — `derived`를 배선하지 않는 것과 같은 원칙. 판정 규칙이 바뀌면 과거 주간도 소급 재해석된다. `deriveFacts` 두 번의 비용은 실측 16ms×2라 보이지 않는다

### 하단 버튼 3개

공유(Web Share, **텍스트 요약** — 파일·이미지 공유는 YAGNI) · 내보내기 · 가져오기 (§3의 UI가 여기 삽입). 일요일에 확인·공유·백업이 한 화면에서 끝난다.

### 빈 상태

데이터가 0~수일뿐이어도 죽지 않고 각 항목이 개별적으로 "아직 데이터가 부족해요"류로 강하한다. `sheet: []`인 스프린트-only 날이 이번 주에 섞여 있는 것이 정상 케이스다(빈 sheet 규칙 — HANDOFF).

## 5. 점검 스프린트

### 목적 — 실측에 맞춰 정직하게 다시 쓴다

설계 원문 §6.7은 "fluent가 14일 간격으로만 등장하는데 점검 장치가 없다"를 걱정했지만, Phase 2 실측은 일반 로테이션이 이미 모든 fluent 식을 **15~16일 안에 재등장**시킴을 보였다. 따라서 점검의 역할은 굶주림 방지가 아니라 둘이다:

1. **동질 조건의 측정 스냅샷** — 적응 off, 드릴 없이 fluent 식을 한 번씩. 월간 리포트의 "진짜 실력"의 근거
2. **집중 학습 검증** — 한 세션 안에서 빠르게 3연속으로 fluent가 된 식(실측이 확인한 경로)이 시간이 지나도 유지되는지 통제된 세션에서 확인

### 주기와 트리거

순수 함수 `checkupDue(days, fluentMs, today)` / `nextCheckupDate(days, fluentMs)` — fluent 판정에 `fluentMs`가 필요하므로 시그니처에 포함한다.

- 조건: **fluent 식 1개 이상** AND **마지막 점검일(없으면 첫 스프린트일)로부터 28일 경과**
- 28일 주기는 재등장 상한(15~16일)보다 길므로, 점검 사이에 모든 fluent 식이 최소 한 번 일반 로테이션으로도 검증된다 — 점검은 그 위의 스냅샷이다
- due가 되면 홈의 스프린트 버튼이 **"🔍 점검 스프린트"로 대체**된다. 아빠가 기억하거나 개입할 일은 없다(설계 원칙)

### 구성 — `composeCheckup(facts, count, rand)`

`composeSprint`와 별도 함수다.

- 대상은 **fluent 식 전부, 각 한 번씩** (중복 없음 — 드릴이 아니라 측정). 순서만 섞는다
- fluent가 `count`(30)를 넘으면 **마지막 유창 판정이 오래된 순**으로 자른다. 판정일은 `shiftDay(nextDue, -interval)`로 `FactState`에서 역산한다 — 새 저장 없음
- fluent가 30개 미만이면 **세션이 그만큼 짧아진다.** learning으로 채우지 않는다 — 채우면 적응 off 원칙이 흐려지고, 점검의 날이 짧고 가볍다는 것은 아이에게 나쁠 게 없다
- **`requeueWrong`을 끈다.** 틀리면 기록만 하고 넘어간다. 틀린 식은 derive가 자연히 learning으로 내리고, 다음날 일반 스프린트가 알아서 드릴한다

### 저장과 판정 — 이 설계의 심장

- 시도는 여느 날처럼 `Day.sprint`에 저장하고, 그날 `Day.kind = 'checkup'`으로 표시한다. **`kind:'checkup'`의 최초 생산자**다. 의미는 "이날의 스프린트는 점검이었다"로 재정의한다 — 원문의 종이 점검 의미는 스프린트-only 결정에 따라 폐기한다
- **강등 로직이 없다.** `deriveFacts`는 kind를 보지 않고 로그를 재생하므로, 점검에서 느리거나 틀린 시도가 연속 3회 조건을 깨면 fluent가 스스로 내려간다. 점검은 측정을 로그에 넣을 뿐이다
- **점검의 날엔 스프린트는 점검 한 번으로 끝** — 완료 후 버튼은 "오늘 점검 완료 ✓". 같은 날 일반 시도가 `Day.sprint`에 섞이면 월간 리포트가 점검 세션을 식별할 수 없기 때문이다
- 🔥 연속일수는 점검도 "스프린트를 한 날"로 세므로 그대로 이어진다 (`sprintStreak`은 `day.sprint` 유무만 본다)

## 6. 월간 리포트 (점검 결과 섹션)

**리포트 화면 안의 섹션**이다 (별도 화면 아님). 가장 최근 `kind:'checkup'`인 날이 있으면 표시된다.

- **재검증 결과**: `deriveFacts(점검일 전날까지)`의 fluent 집합 vs `deriveFacts(점검일까지)`의 fluent 집합
  - 교집합 = **유지** (진짜 실력)
  - 차집합 = **탈락** (판정이 낡았던 식) — 목록으로 표시하고, 다음 스프린트가 자동으로 다시 드릴함을 함께 안내한다
- 점검 세션의 중앙값 반응시간 — 지난 점검과의 비교 (두 번째 점검부터)
- 다음 점검 예정일

**진입 흐름**: 점검 스프린트의 결과 화면에 "월간 리포트 보기" 버튼 → `#/report`. 원문의 "점검의 날 이후 자동 전환"은 스프린트 결과 화면(저장 재시도 버튼이 살아야 하는 화면)을 건너뛰지 않기 위해 **버튼 경유**로 조정한다.

**저장 없음**: 주간과 같은 원칙 — 점검 결과도 매번 로그에서 재계산한다. 판정 규칙이 바뀌면 과거 점검도 소급 재해석된다.

## 7. 테스트 전략

실패 패턴 1~6(HANDOFF) 준수. 특히:

- **`engine/backup.ts`** — 왕복 테스트(직렬화 → 검증 → 동일), 검증 거부 케이스를 **필드 단위로**(app 다름, 버전 2, date 형식 오류, sprint에 문자열 등). 생성기가 거른 값을 같은 술어로 재검사하지 않도록 손으로 만든 깨진 입력을 쓴다
- **`replaceAll`** — 원자성: 중간 실패 시 기존 데이터가 보존되는지 fake-idb 수준에서 확인
- **`checkupDue` / `composeCheckup`** — 중복 없음, fluent만, 30개 초과 시 오래된 판정 우선, fluent 0개면 due 아님
- **점검 강등 통합 테스트** — 점검에서 틀린 식이 derive 후 learning이 되는 것. §5의 심장을 **이음새에서** 검증한다 (가장 값진 결함은 태스크 사이에 있다 — 실패 패턴 6)
- **시뮬레이션 보강** (Phase 2가 명시적으로 미룬 것) — `requeueWrong`을 시뮬레이션에 모델링(세션이 30+W가 된다) + 4주마다 checkup 날 삽입. 굶주림 상한(15~16일)·적체 실측이 점검 도입 후에도 유지되는지 확인
- **리포트 화면** — 빈 데이터·스프린트-only 주간·`sheet: []` 혼재에서 죽지 않음

## 8. 에러 처리

설계 원문 §11 원칙("조용히 실패하지 않는다") 그대로.

- 가져오기 실패 = 거부 + 기존 데이터 보존 + 구체적 사유 표시
- 내보내기 실패(Blob/다운로드 예외) = `showError`, `lastExportedAt` 갱신 안 함
- 리포트 화면 첫 `await`는 `try` 안 (갇힘 경로 — 실패 패턴 4), 화면 이탈 시 리스너·지연 콜백 정리 (실패 패턴 5)

## 9. 이번에 하지 않는 것

코드 주석의 스테일 "Phase 3" 참조는 이번에 정정한다.

- **인쇄물 주간 리포트** — Phase 4. 아이패드 실물 확인(지도가 동기가 되는지) 결과가 입력이 된다
- **종이 쪽 적응 off 점검 구성** — 스프린트-only 결정으로 폐기
- **`deriveTypes` attempts 성장 대응·inverse 태그 배선** — 실측상 비용 0이라 급하지 않다. `derive.ts` 주석의 "(Phase 3)"을 정정한다
- **마이그레이션 배열** — `schemaVersion` 2가 실제로 생길 때
- **초기 진단** — 원문 §6.7의 1주차 진단은 종이 로직이었고, 스프린트는 자체적으로 신규 식을 순서대로 도입하므로 별도 진단이 필요 없다

## 10. 태스크 0 — 이음새 조사 대상

새 코드가 쓰거나 처음 읽는 필드와, 그것을 이미 읽고 있는 모든 곳을 계획서 작성 전에 나열한다. Phase 2의 Critical이 정확히 이 이음새(`sprint.ts`의 쓰기 × `home.ts`의 읽기)에서 나왔다.
