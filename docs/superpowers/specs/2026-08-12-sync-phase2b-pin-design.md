# 동기화 2B — 채점 화면 PIN 설계

작성: 2026-08-12 · 상태: 승인 대기

2단계 설계(`2026-08-09-sync-phase2-design.md`) §4가 2B로 미뤄 둔 PIN을 확정한다. 그 절이
정한 것 중 상당수를 이 문서가 **줄이는 쪽으로** 고쳤다 — 무엇이 달라졌는지는 §7에 모았다.

## §0 왜 만드나

채점 화면(`#/grade`)은 그날 모든 문항의 정답을 표시한다. 지금 이 화면을 지키는 것은
**아이/부모 소속 규칙 하나뿐이다** — 아이 화면에서 부모 화면으로 가는 링크를 만들지
않는다는 규율이고, 잠금은 없다. 주소(`#/grade`)를 알고 치면 열린다.

위협 모델은 **아이의 우연한 접근**이다. 공격자가 아니라 여덟 살이고, 목표는 "실수로
정답을 보는 일"을 막는 것이다. 그래서 무차별 대입 방어·지연·잠금이 없고 PIN은 평문이다.

**PIN은 두 번째 방어선이지 첫 번째의 대체가 아니다.** 소속 규칙은 그대로 유효하고, 새
화면을 만들 때 「← 홈」의 목적지를 소속에 맞추는 규율도 그대로다.

## §1 결정 요약

| 질문                       | 결정                                                       |
| -------------------------- | ---------------------------------------------------------- |
| PIN을 앱에서 설정·변경하나 | **아니오. SQL로만 한다**(§5)                               |
| 게이트를 어디에 거나       | `#/grade` · `#/report` 둘. 진입점은 `main.ts` 한 곳(§2)    |
| 통과를 얼마나 기억하나     | **포그라운드 세션** — 앱이 배경에 들어가면 지운다(§4)      |
| PIN이 아직 없으면          | 게이트 없음 — 오늘과 똑같이 열린다                         |
| 서버 값 형식을 검증하나    | **아니오.** 문자열인지만 본다(§3)                          |
| 4자리는 어디서 강제하나    | 입력 다이얼로그의 UI 제약으로만(`maxlength=4`)             |
| 동기화가 꺼져 있으면       | **캐시가 있으면 건다** — 게이트는 네트워크를 안 만진다(§4) |
| 통과 못 하면 어디로        | `#/parent`                                                 |
| 틀린 입력                  | 다이얼로그를 닫지 않고 즉시 재입력. 잠금·지연 없음         |
| 테스트                     | `db.test.ts` 둘(§6)                                        |

## §2 구조

```
서버 app_config(id=1, pin)
        │ GET (pull마다, 커서 없음 — 행이 하나다)
        ▼
   sync.ts  pullConfig()
        │
        ▼
   db.ts  DeviceState.pin        ← 이 기기가 마지막으로 본 서버 PIN
        │ 읽기
        ▼
   main.ts  route()              ← #/grade·#/report면 게이트, 실패하면 #/parent
        │
        ▼
   ui.ts  unlockGate(expected)   ← 포그라운드 세션 통과 플래그 + 입력 오버레이
```

파일별 책임:

- **`src/data/sync.ts`** — `pullConfig()`. `app_config` GET과 캐시 갱신. `fetch`를 직접
  부르지 않고 이 파일의 `req()`를 쓴다(헤더·타임아웃의 단일 출처)
- **`src/data/db.ts`** — `DeviceState`에 `pin: string | null` 한 필드. 쓰기는
  `updateDeviceState`로만 — `getDeviceState()` 뒤에 `putDeviceState({...})`를 잇는 형태는
  await를 가로질러 2A가 고쳤던 사고를 되살린다
- **`src/ui.ts`** — `unlockGate(expected: string): Promise<boolean>`. 모듈 스코프 플래그가
  통과 캐시이고 앱이 배경에 들어가면 지워진다(§4 「포그라운드 세션」). **`db.ts`를 import하지
  않는다** — 공유 UI 유틸이 데이터 계층을 알면 "`db.ts`는 앱의 나머지가 IndexedDB를 모르게
  한다"는 경계가 무너진다. 값은 호출자가 넘긴다
- **`src/main.ts`** — 보호 해시 표와 호출. `PARENT_HASHES` 옆에
  `GATED_HASHES = ['#/grade', '#/report']`

**게이트가 라우터에 사는 이유.** 진입점이 하나면 새 부모 화면이 생겨도 표에 한 줄이 전부다.
화면마다 두는 방식은 이 레포가 이미 한 번 실패했다 — 소속 불변식이 사람 규율에 의존해서
`grade.ts:188`의 삼항연산자 속 `navigate`가 계획서 작성 뒤 구현 중에야 발견됐고, 화면
테스트가 없어 누락을 잡을 방법도 없었다.

**순서는 pull 대기 → 게이트 → 렌더다.** `route()`는 이미 부모 화면에서
`pullAndWait(PARENT_WAIT_MS)`를 한다. 게이트를 그 뒤에 두면 낡은 캐시로 판정하는 창이
줄어든다 — **제거되지는 않는다**(`pullAndWait`는 3초에 포기하고 비행은 계속 돈다. 4초에
도착한 새 PIN은 이 판정을 놓친다). 늦은 도착은 §4의 재게이트가 수습한다 — 그래서 §3이
**pin 캐시 변경을 `PullResult.changed`에 싣는 것이 이 수습의 전제 조건이다.**

## §3 pull

`pullConfig()`를 `pullPass`에 끼우되, 자리는 「`pullMeta` 뒤」가 아니라 정확히
**`'unauthorized'`·`'rebase'` 가드 뒤, `pullDays()` 앞**이다.

```ts
const meta = await pullMeta()
if (meta === 'rebase' || meta === 'unauthorized') return { status: 'failed', changed: false }
if (suspendCount > 0) return { status: 'failed', changed: meta }
const config = await pullConfig() // ← 여기. 이 줄 위로 올리면 아래 보안 판정이 깨진다
return { status: 'ok', changed: (await pullDays()) || meta || config }
```

```
GET /rest/v1/app_config?id=eq.1&select=pin
```

**순서가 곧 보안 판정이다.** 폐기된 기기 키의 RLS 응답은 401이 아니라 200 + 빈 배열이다(이
코드베이스가 실측으로 확인해 스스로 경고해 둔 함정). `pullMeta`가 「행이 항상 하나인 meta가
비어 보이면 키가 거부된 것」으로 판정하고 위 가드가 패스를 끊으므로, **가드 뒤까지 온 빈
배열은 진짜 미설정이다.** `pullMeta` 호출 직후·가드 앞에 끼우면 키가 폐기된 기기가 빈 응답을
「PIN 없음」으로 읽고 캐시를 지워 게이트를 스스로 연다 — 「pullMeta 뒤」라는 서술만으로는 이
두 자리가 구분되지 않아 정확한 줄을 위에 박아 둔다.

같은 이유로 `pullMeta`와 **병렬로 쏘지 않는다.** 응답 하나를 아끼자고 판정 근거를 잃는다.

**`pullConfig`는 캐시를 실제로 바꿨는지를 돌려주고, 그 값이 `changed`에 실린다.** 이것이
없으면 SQL로 PIN만 넣은 직후의 pull(다른 변경이 하나도 없는 패스)에서 `notifyPullApplied`가
안 쏘여 재렌더가 없고, **정답이 다 보이는 채점 화면이 다음 hashchange까지 게이트 없이 떠
있는다.** §4의 재게이트는 이 한 줄에 걸려 있다.

**실패는 삼키고 캐시를 유지한다.** `pullConfig` 안에서 try/catch로 감싼다 — `req()`는
네트워크 실패·타임아웃에 throw하는데, 그것이 `pullPass`를 끊으면 `app_config`만의 장애
(일시 5xx)가 그 패스의 days pull 전체를 죽여 push는 되는데 pull만 안 되는 반쪽 동기화가
된다. PIN 캐시가 한 패스 낡는 것은 아무 비용이 아니다. 실패한 `pullConfig`는 `false`
(변경 없음)를 돌려주고 `status`에도 관여하지 않는다.

적용:

```ts
const pin = typeof row?.['pin'] === 'string' && row['pin'] ? row['pin'] : null
await updateDeviceState((s) => (s.pin === pin ? s : { ...s, pin }))
```

**형식을 검증하지 않는다.** 설계 2단계 §2는 "meta·app_config payload도 백업과 같은 등급으로
검증한다"고 적었지만, 그 규정의 근거("기형 settings가 앉으면 `deriveFacts`가 전 기기에서
죽는다")가 PIN에는 성립하지 않는다 — PIN은 파생에 쓰이지 않고 `===` 비교 한 번에서 끝나므로
기형 값이 도달할 넓이가 없다. 오히려 SQL 전용 설정에서는 **검증이 해롭다**: 사람이
`pin='12345'`로 잘못 넣었을 때 거부는 옛 PIN을 조용히 유지해 "SQL로 바꿨는데 안 먹는다"가
되고, 그대로 받으면 최소한 증상이 드러난다.

잠금이 없는 상태는 두 모양으로 온다. **빈 배열**(행이 아직 없다 — 최초 INSERT 전. DELETE
정책이 없으므로 이 모양은 최초 설정 전에만 존재한다)과 **`pin: ''`인 행**(사람이 SQL로
지웠다 — `pin text not null`에 `''`는 적법하다). 위 스니펫이 둘을 같은 분기로 받는다 —
빈 배열은 `row`가 `undefined`, `''`는 truthiness에서 떨어져 둘 다 `null`이 된다. 어느
쪽이든 캐시가 `null`로 돌아가 게이트가 꺼진다.

**아웃박스 표식을 만들지 않는다.** 이 기기는 `app_config`에 쓰지 않는다(§5) — 올릴 것이 없다.

## §4 게이트

`main.ts`:

```
route(hash)                        ← hash는 92행에서 캡처된 이 route의 해시
  ├ 부모 화면이면 pullAndWait(3초)
  ├ GATED_HASHES에 걸리고 pin(캐시)이 있으면:
  │    플래그가 이미 서 있으면 → 통과 (비우지 않는다)
  │    아니면:
  │      #app을 비운다            ← 다이얼로그는 body 오버레이라 화면을 가리지 않는다
  │      ok = await unlockGate(pin)
  │      실패 시:
  │        location.hash === hash(캡처본)이면 navigate('#/parent')
  │        어느 분기든 여기서 route를 즉시 종료 — 렌더로 떨어지지 않는다
  └ 화면 렌더
```

의사코드의 줄들이 각각 방어선이다.

- **실패는 어느 분기든 route를 즉시 종료한다 — 렌더로 떨어지지 않는다.** `navigate`는
  `location.hash`만 바꾸고 hashchange는 다음 태스크다 — 종료 없이 흘러 내려가면 지금 route가
  캡처해 둔 해시(`#/grade`)로 **renderGrade가 그대로 실행돼 정답 전부가 `#app`에 그려지고**,
  다음 태스크의 route가 부모 홈으로 덮기 전까지 화면에 있다. 게이트가 실패했는데 렌더가
  이긴다면 게이트는 없는 것이다
- **실패 후 `navigate('#/parent')`의 술어는 「이 route가 캡처한 해시와 지금 해시가 같은가」다
  — 「게이트 대상 집합에 속하는가」가 아니다.** 다이얼로그는 `hashchange`에 스스로 닫고
  `false`로 resolve하는데(아래), 그 `false`를 무조건 navigate로 받으면 **화면을 떠나서 닫힌
  경우**(아이가 뒤로가기로 `#/`에 가려던 참)까지 부모 홈으로 배달한다. 집합 소속으로 판정하면
  반례가 남는다 — `#/grade` 게이트 중에 히스토리 스와이프로 `#/report`(역시 게이트 대상)에
  가면 조건이 참이 되어, 떠나려던 사용자를 부모 홈으로 끌고 가며 `#/report`를 위해 돌기 시작한
  새 route와 충돌한다. 캡처본과의 동일 비교만이 "취소·포기했고 화면은 그대로"를 정확히 잡는다
- **`#app` 비우기는 다이얼로그가 실제로 뜰 때만 한다.** 다이얼로그는 `document.body`에 붙는
  오버레이라 `#app`을 가리지 않는다 — 비우지 않으면 재게이트 경로(PIN 없이 열어 둔 채점
  화면에 pull이 처음으로 PIN을 내려준 때)에서 **모든 문항의 정답이 다이얼로그 뒤에 그대로
  떠 있다.** 잠그는 순간의 화면 내용이 잠기지 않으면 게이트는 장식이다. 단, 플래그가 이미 선
  경우(위 의사코드의 첫 분기)에는 비우지 않는다 — 배경 pull 재렌더(`route(false)`)가 게이트를
  지날 때마다 비우면, 리포트를 보고 있는 동안 pull이 적용될 때마다 화면이 깜빡인다(오늘의
  `replaceChildren` 단일 스왑에는 없던 회귀다). 이를 위해 `ui.ts`가 플래그 조회를 동기로
  노출한다(`gateUnlocked(): boolean`)

상황별 동작:

| 상황                             | 게이트                                      |
| -------------------------------- | ------------------------------------------- |
| PIN 캐시 없음(미설정·pull 전)    | 없음 — 오늘과 같다                          |
| 캐시 있음 + 온라인               | 건다                                        |
| 캐시 있음 + 오프라인             | 건다(캐시로 검증 — 캐시가 있다는 것이 요점) |
| 캐시 있음 + `configured()` false | **건다** — 게이트는 네트워크를 안 만진다    |
| 이번 세션에 이미 통과            | 안 묻는다                                   |

**동기화 스위치가 잠금 스위치를 겸하지 않는다.** `sync-config.ts`가 비면 모든 네트워크
진입점이 inert가 된다는 규칙은 요청에 대한 것이지, 이미 로컬에 있는 값에 대한 것이 아니다.
설정 파일 한 줄을 지우면 채점 화면이 열리는 구조는 아무도 예상하지 못한다.

부작용 하나를 적어 둔다: HANDOFF의 사람 확인 항목 「`sync-config.ts`를 비운 빌드에서 화면
다섯 개가 오늘과 같은지」에서, **PIN을 이미 캐시한 기기는 다이얼로그를 본다.** 그 항목의
판정 기준은 `fetch` 0건이므로 여전히 통과다.

**입력 다이얼로그**(`ui.ts`):

- `confirmDialog`의 형제다 — 같은 오버레이 규약(`.overlay` 클래스로 인쇄에서 숨김,
  `document.body`에 붙음, `settle`로 정확히 한 번만 resolve)
- **단일 비행이다** — 이미 떠 있으면 같은 Promise를 돌려준다(`pullOnce`와 같은 패턴). 게이트는
  `route()` 한가운데서 사람 입력을 무기한 기다리므로, 그동안 배경 pull이 적용되면
  `onPullApplied → route(false)`가 **또** 게이트에 닿는다 — 단일 비행이 없으면 다이얼로그가
  다이얼로그 위에 쌓이고, 하나에 PIN을 넣어도 다른 하나가 남는다. 겹친 호출은 한 다이얼로그의
  결과를 공유하고, 실패 시의 `navigate`도 위 조건(캡처한 해시와 동일) 덕에 한 번만 효력이
  있다. **비행 중에 도착한 새 `expected`는 무시된다** — 다이얼로그가 떠 있는 동안 pull이 PIN을
  바꾸면 그 판정은 옛 PIN으로 끝난다(감수: 창이 초 단위이고 위협이 여덟 살이다. 다음 게이트가
  새 값으로 판정한다). `route()` 자기 중첩 자체는 이 레포의 알려진 미해결 항목이다(HANDOFF) —
  이 설계는 그 창을 넓히는 만큼(3초 → 사람 입력 무기한) 다이얼로그 층위에서 겹침을 흡수한다
- 입력은 `type="password"` · `inputmode="numeric"` · `maxlength=4`. **마스킹은 원설계 §4
  그대로다** — 위협이 "옆에 있는 여덟 살"인데 아빠가 칠 때마다 화면에 평문 4자리가 보이면
  우연한 관찰 한 번으로 게이트 전체가 끝난다. 4자리는 UI 제약일 뿐 검증기가 아니다 —
  서버 값과 입력 길이를 두 곳에서 맞추는 결합을 만들지 않는다
- 틀리면 닫지 않는다. 입력을 비우고 「다시 입력해 주세요」. 잠금·지연 없음
- **`hashchange`에 스스로 닫고 `false`로 resolve한다.** `#app` 밖에 사는 것은 자기 수명을
  스스로 관리해야 한다 — SEED 도입 때 이 규약이 없어서 "이미 떠난 화면의 확인 버튼이 눌려
  되돌릴 수 없는 작업이 도는" 경로가 실제로 생겼다. 이 규약이 위 조건부 `navigate`의 짝이다
- 값은 어디에도 렌더되지 않는다(`textContent`만) — XSS 경계는 `confirmDialog`와 같다

**배경 pull이 잠금을 켜는 경우.** `onPullApplied`의 재렌더는 `route(false)`를 부르므로 게이트를
다시 지난다. 이 신호가 실제로 오는 것은 §3이 pin 변경을 `changed`에 실어서다 — 그 한 줄이
없으면 "PIN만 넣은 pull"은 재렌더를 못 깨우고 이 문단 전체가 공문이 된다. 이미 통과한 세션은
플래그가 있어 안 묻는다. 다이얼로그가 새로 뜨는 경우는 **PIN 없이 열어 둔 화면에 pull이
처음으로 PIN을 내려준 때**이고, 그것이 옳은 동작이다 — 방금 잠금이 켜졌고, 위 규칙대로 `#app`을
비운 뒤 묻는다. 채점 중(`isGrading()`)에는 재렌더 자체가 일어나지 않으므로 O/X를 쥔 화면이
PIN을 묻는 일은 없다.

**통과 플래그는 포그라운드 세션이다 — 탭 수명이 아니다.** 플래그는 `ui.ts` 모듈 스코프에 살되,
앱이 배경에 들어가면 지운다. "앱 세션(탭 수명)"으로 두면 이 앱의 주 사용 기기에서 게이트가
사실상 일회성이 된다 — 아이패드 홈 화면 앱은 새로고침이 없고 며칠씩 떠 있다(이 코드베이스가
스스로 그렇게 서술한다). 아빠가 저녁에 채점하면 플래그가 서고, 다음날 아침 아이가 히스토리
스와이프로 `#/grade`에 닿아도 안 묻는 것이다. 배경 진입에 지우면 "아빠가 쓰는 동안은 한 번만
묻고(채점 → 리포트 동선 유지), 내려놓으면 다시 잠긴다"가 된다 — 원설계 "화면을 떠날 때까지"가
막으려던 위협(시간이 지난 뒤의 우연한 접근)을 같은 강도로 막으면서 동선은 끊지 않는다.

지우는 자리를 정확히 한다: **`main.ts`의 기존 `visibilitychange` 핸들러가 hidden 분기에서
`ui.ts`의 `lockGate()`(플래그 삭제)를 부른다.** 그 핸들러는 지금
`if (visibilityState !== 'visible') return`으로 hidden에서 일찍 나가므로, return **앞에**
`lockGate()` 호출을 넣는 모양이다. `ui.ts`가 import 시점에 리스너를 스스로 걸지 않는다 —
모듈 부작용이고, window 리스너는 지금까지 전부 `main.ts`가 소유해 왔다.

**플래그만 지우면 반쪽이다 — 떠 있는 화면도 다시 게이트한다.** 게이트는 `route()`에서만
도는데, visible 복귀 핸들러는 push·pull만 차므로 서버에 변경이 없으면 route가 돌지 않는다 —
아빠가 `#/grade`를 띄운 채 내려놓으면 플래그는 지워져도 **`#app`에는 정답이 렌더된 채
그대로이고**, 다음날 아이가 집어 들면(홈 화면 앱은 마지막 화면으로 복귀) 아무것도 안 눌러도
정답이 보인다 — 이 문단이 막으려는 위협의 가장 짧은 경로다. 그래서 visible 복귀 분기에 한
줄을 더한다: **현재 해시가 게이트 대상이고, pin 캐시가 있고, `!gateUnlocked()`면
`void route(false)`.** 조건과 인자가 각각 이유를 갖는다.

- **`route(false)`다 — `route()`가 아니다.** 평소 순서대로 돌리면 `pullAndWait`(최대 3초)가
  게이트보다 먼저 돌아, 잠그러 가는 길에 정답이 렌더된 채 아무것도 가리지 않는 창이 생긴다 —
  깨어난 그 순간이 정확히 아이가 집어 든 순간이다. visible 핸들러는 같은 자리에서 이미
  `pullOnce()`를 차므로 route가 pull을 또 기다릴 이유도 없다(`route(false)`의 존재 이유와
  같은 논리다). 낡은 캐시로 판정하는 것은 §2가 이미 감수한 성질이고, 늦게 도착한 PIN 변경은
  `changed` → 재게이트 레일이 수습한다
- **pin 캐시가 없으면 아무것도 안 한다.** 이 조건이 빠지면 PIN 미설정 기기에서 플래그가
  영원히 false라 매 복귀마다 재렌더가 돌아, §1의 「PIN이 아직 없으면 오늘과 똑같이」가 깨진다
  (리포트에서 보고 있던 지난달이 wake마다 초기화되는 회귀)
- **`isGrading()`이면 건너뛴다**(`onPullApplied`와 같은 이유 — 복귀 재렌더가 메모리의 O/X를
  날린다). 그 가드가 남기는 잔여를 감수로 적는다: **채점 도중** 배경에 들어간 화면은 복귀 시
  다시 잠기지 않는다 — 저장하지 않은 채점이 걸려 있는 좁은 창이고, 저장하는 순간 화면이
  떠나며 다음 진입은 게이트를 지난다

**통과 못 하면 `#/parent`.** 아빠는 바로 옆이라 다시 들어가기 쉽고, 아이가 주소를 치고 들어온
경우에도 부모 홈에는 정답이 없다. 화면을 안 옮기는 선택지는 안 된다 — 해시는 이미 `#/grade`인데
화면이 이전 것이면 둘이 어긋난다.

## §5 설정과 변경은 SQL로만

앱에는 PIN을 정하거나 바꾸는 화면이 **없다.**

```sql
-- 설정·변경 (Supabase SQL Editor)
insert into app_config (id, pin, device) values (1, '1234', 'sql')
on conflict (id) do update set pin = excluded.pin, device = 'sql';

-- 잠금 해제
update app_config set pin = '' where id = 1;
```

`supabase/README.md`에 이 두 줄과 "정확히 4자리 숫자로 정한다"를 적는다.

**왜 UI를 안 만드나.** 분실 복구가 이미 SQL이라 경로가 하나로 모인다. 앱에 만들면 딸려 오는
것이 전부 평생 한 번 쓰이고 죽는 코드다 — 「`serverStatus` 정상 + 성공한 pull의 빈 응답」
판정, INSERT PK 충돌(두 기기가 동시에 최초 설정) 시 pull로 받아 재검증, 입력 두 번 확인, 부모
홈 블록, 변경 화면. 기기 등록도 같은 판단을 이미 한 번 했다(완성형 등록 화면 대신 부모 홈
인라인 블록 + 대시보드, 제대로 된 화면은 2C로).

**감수하는 것**: 아이패드만 들고 있을 때 PIN을 바꾸기 번거롭다(대시보드는 브라우저로 열리니
가능은 하다). 그리고 **사람이 SQL을 치기 전까지 PIN은 없다** — 지금도 잠금이 없으니 나빠지는
것은 없고, 켜지는 순간이 명시적이라는 편이 낫다.

**초기화·가져오기·되돌리기가 PIN을 건드리지 않는다.** 서버 쪽: `replace_all` RPC는 `days`·
`meta`·`snapshots`·`write_log`만 만지고 `app_config`는 스키마상 대상이 아니다(확인함). 로컬
쪽은 서술을 정확히 한다 — `replaceAll`은 `device` 스토어를 **건드린다**: `seededAt`과
`quarantine`을 되돌리고 나머지 필드는 `{ ...state, seededAt: null, quarantine: [] }`
스프레드로 보존한다(`db.ts` 확인). `pin`의 생존은 그 스프레드에 기댄 것이라, 누가 이 쓰기를
명시 필드 나열로 바꾸면 조용히 깨진다 — **그래서 §6의 테스트가 이 보존을 직접 고정한다.**
같은 모양의 device 쓰기가 재기준화(`replaceFromServer`)에도 하나 더 있다 — 같은 테스트
대상이다. **파괴적 작업이 잠금을 푸는 경로가 없다**는 불변식은 이 두 스프레드 + 다음 pull의
재충전으로 지켜진다.

## §6 테스트

**`db.test.ts`에 둘.**

1. `pin`이 없던 상태를 읽으면 `null`로 채워지고, `updateDeviceState`로 쓴 값이 살아남는다.
   기존 필드 넷(`seededAt`·`generation`·`lastPulledAt`·`quarantine`)이 이미 밟은 패턴이고,
   변이 검증도 성립한다 — `normalizeDeviceState`에서 `pin` 줄을 지우면 그 테스트만 빨개진다
2. **`replaceAll`·`replaceFromServer` 뒤에 `pin`이 살아남는다.** §5의 불변식("파괴적 작업이
   잠금을 푸는 경로가 없다")을 직접 고정하는 테스트다 — 그 보존이 스프레드 한 줄에 기대고
   있어서, 명시 필드 나열로 리팩터하는 순간 조용히 깨지는 종류다. `replaceAll`이 `seededAt`을
   비우는 기존 테스트에 단언을 더하는 모양이라 싸다. 변이 검증: 스프레드를
   `{ seededAt: null, quarantine: [] }`로 바꾸면 이 테스트만 빨개진다

그 밖에는 테스트하지 않는다. 게이트·다이얼로그는 화면이고(설계 §12), `pullConfig`에는
`engine/`으로 뽑을 순수 부분이 없다 — 형식 검증기를 두지 않기로 했으므로 뽑을 로직 자체가
사라졌다. **없는 순수 함수를 만들어 테스트를 붙이는 것은 테스트를 위한 코드다.** 반면 2번은
그 논리 밖이다 — 이미 있는 트랜잭션 경로의 필드 보존이고, 불변식이 걸려 있다.

## §7 2단계 설계 §4에서 달라진 것

| §4 원문                                         | 이 문서                        | 이유                                                                                                  |
| ----------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 앱에서 최초 설정(`serverStatus` + 빈 응답 판정) | SQL 전용                       | 평생 한 번 쓰이는 코드(§5)                                                                            |
| PIN 변경은 `#/report`에서 현재 PIN 확인 후      | SQL 전용                       | 같음                                                                                                  |
| 게이트는 `#/grade` 하나                         | `#/grade` · `#/report`         | 파괴적 작업 방어(아래)                                                                                |
| 세션 캐시는 화면을 떠날 때까지                  | 포그라운드 세션                | 동선(채점→리포트)은 안 끊으면서, 며칠씩 떠 있는 아이패드 홈 화면 앱에서 플래그가 밤을 넘기지 않게(§4) |
| `app_config` payload도 같은 등급으로 검증       | 문자열인지만 확인              | 기형 값이 도달할 넓이가 없다(§3)                                                                      |
| PIN 4자리                                       | 유지하되 UI 제약으로만         | 두 곳에서 길이를 맞추지 않는다                                                                        |
| 입력 마스킹                                     | **유지**(`type="password"`)    | 원문 그대로 — 달라진 것이 아니라 §4에 명시했다                                                        |
| 진입 순서: pull 대기 → PIN 게이트 → 렌더        | 유지 + 게이트 전 `#app` 비우기 | 재게이트에서 정답이 다이얼로그 뒤에 남지 않게(§4)                                                     |

**`#/report`를 넣은 이유.** 그 화면에는 「모든 기록 지우기」·가져오기·되돌리기가 있다. 지금
방어선은 확인 배너와 「지우기」 타이핑인데 여덟 살이 글자를 옮겨 적지 못할 이유가 없고, 되돌리는
길이 서버 스냅샷뿐이라 사고 비용이 크다. 코드 비용은 배열에 문자열 하나라 사실상 0이고, 세션
캐시가 공유라 아빠 마찰도 실질 0이다(채점하러 한 번 친 뒤에는 리포트가 그냥 열린다).

**`#/parent`·`#/print`는 게이트 밖이고, 그것이 사용자 결정이다(2026-08-12).** 같은
파괴적-작업 잣대를 대면 부모 홈의 격리 배너 두 버튼과 인쇄 화면의 「다시 만들기」도 후보다 —
후보로 검토했고("부모 화면 네 전부" 선택지), 아빠가 매일 인쇄할 때마다 PIN을 치게 된다는
비용으로 기각됐다. 남는 노출을 정직하게 적는다: 아이 홈에는 `#/parent`로 가는 버튼이 **원래
있으므로**(역할 분리가 "실수를 막을 뿐 의도를 막지 못한다"고 스스로 선언한 구조 그대로다),
게이트 실패 리다이렉트가 새 경로를 만드는 것이 아니다. 격리 배너 버튼과 「다시 만들기」의
방어는 오늘과 같다 — 각자의 확인 절차. PIN 도입 전보다 나빠지는 화면은 하나도 없고, 나아지는
화면이 둘이다.

## §8 이 문서가 다루지 않는 것

- **2C(초대 기반 기기 등록)** — 별개다. 새 기기는 등록 후 첫 pull에서 PIN을 받는다
- **2D(PC·폰 화면)**
- 무차별 대입 방어·시도 횟수 제한·해시 저장 — 위협 모델 밖(§0)
- `app_config`에 PIN 말고 다른 설정을 얹는 것 — 지금 열이 `pin` 하나다. 필요해지면 그때
