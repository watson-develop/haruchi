# 동기화 백엔드 — 아이패드 한 대에만 있던 기록을 서버에 이중화하고 다기기 쓰기를 연다

**날짜:** 2026-08-06 **상태:** 승인됨(사용자), 구현 대기

서버 없는 정적 PWA라는 성질은 유지한 채, Supabase(Postgres)를 **복제본**으로 붙인다.
IndexedDB는 계속 원본이고 앱은 오프라인에서 지금과 동일하게 동작한다. 이 문서의 쉬운 말
버전은 [2026-08-06-sync-backend-plain.md](2026-08-06-sync-backend-plain.md)에 있다.

## 왜 — 두 가지를 풀고 두 가지를 미룬다

### 푸는 것

**A-1. 원본 사본이 하나뿐이고, 백업이 실패해도 알 수 없다.**

딸의 기록은 아이패드 IndexedDB에만 있다. 방어가 셋인데 셋 다 새는 구석이 있다.

- `navigator.storage.persist()`는 iOS의 evict **위험을 낮출 뿐** 보장이 아니다
- 백업은 **수동**이다 — 아빠가 안 누르면 안 생긴다
- `lastExportedAt`은 "내보내기를 눌렀다"에 되돌리기가 붙은 값이고(PR #18), 파일이 실제로
  저장됐는지는 여전히 알 수 없다. HANDOFF가 이 시나리오를 이미 적어 뒀다 — iOS 업데이트로
  blob 다운로드가 조용히 no-op이 되면 _"서버 사본이 없어 되돌릴 수 없다"_

이것은 **되돌릴 수 없는 종류**의 문제라 나머지와 무게가 다르다.

**B-1. 다기기 쓰기.** 노트북·폰에서도 채점·인쇄를 하고 싶다. 지금은 IndexedDB가 origin별로
격리돼 아이패드 밖에서는 기록에 닿을 수 없다.

### 미루는 것

- **A-2. 백업 파일 재검증** — 실제 export 파일로 복구를 검증한 것은 Phase 3 시점이고, 그
  파일에는 채점·스프린트·`kind:'checkup'`·`mood`·`doneAt`이 하나도 없었다(HANDOFF). 서버
  사본이 생기면 복구 경로가 둘이 되므로 **긴급도가 내려간다**
- **B-2. 과거 데이터 분석** — Postgres를 고른 덕에 스키마 변경 없이 나중에 열린다

### 미룰 수 없는 것 — B-1이 데려오는 세 문제

이것들은 별도 기능이 아니라 다기기 쓰기가 켜지는 순간 자동으로 생기는 문제다. 이번 설계
안에서 함께 푼다.

- **C-1. 재인쇄 동일성이 깨질 수 있다.** `print-sheet.ts`의 게이트
  `if (!day || day.sheet.length === 0)`는 "이 기기에 오늘 Day가 없다"만 본다. 동기화가 붙으면
  노트북이 아이패드보다 먼저 오늘 Day를 만들 수 있고, 그러면 아이 손의 종이와 다른 `sheet`가
  생겨 **데이터가 조용히 오염된다**
- **C-2. 접근 통제가 처음 필요해진다.** 배포 URL은 공개이고 서버는 인터넷에서 직접 호출된다
- **C-3. 빈 `sheet`가 병합을 헷갈리게 한다.** 스프린트만 한 날은 `sheet: []`인 `Day`이고,
  길이 0이 "아직 안 만듦"인지 "만들 일이 없는 날"인지 서버는 구분할 수 없다

## 기술 선택 — Supabase + `fetch` 직접 호출

`supabase-js` SDK를 쓰지 않고 PostgREST 엔드포인트를 `fetch`로 부른다.

- **실행 의존성 0개가 유지된다.** SDK가 하는 일이 사실상 `fetch` 래핑인데 수백 KB가 붙는다
- Postgres라 **B-2가 스키마 변경 없이 열린다** (`payload->'sheet'` 같은 `jsonb` 연산자)
- 무료 티어로 충분하다(하루 수십 KB)

**버린 안**

- **Firebase Firestore** — 오프라인 동기화가 SDK에 내장돼 편하지만, 수백 KB의 실행 의존성이
  붙고 SQL이 없어 B-2가 약해지며, 계정 전제라 키 인증이 어색하다
- **Cloudflare Workers + D1** — 비밀키 인증과 가장 잘 맞고 의존성도 0개지만, 서버 코드를
  우리가 소유하게 되어 "관리형 BaaS"를 고른 취지에서 벗어난다

## §1 아키텍처와 데이터 모델

### 로컬 우선

IndexedDB가 계속 원본이고 서버는 복제본이다. 오프라인에서 앱은 지금과 완전히 동일하게
동작하며 동기화는 배경에서만 돈다. 네트워크 실패가 딸의 저녁 연습을 막아서는 안 된다.

### 동기화 대상은 `days`·`meta`·`app_config` 셋뿐이다

앞의 둘이 기록이고, `app_config`는 가족 전체가 공유하는 설정 한 줄이다(현재는 PIN 하나).
**`Derived`는 올리지 않는다.** `Meta.derived`를 배선하지 않는다는 기존 원칙 덕에 파생값은
`days`의 결정적 함수이고, 두 기기가 같은 `days`를 갖는 순간 파생값은 **자동으로 일치한다** —
동기화할 필요가 없는 것이 아니라 동기화할 대상이 아니다. 저장했더라면 "아이패드의
`nextDue`와 노트북의 `nextDue`가 다르면 누가 이기나"라는 답 없는 병합 문제가 생겼을 것이다.

`Meta.derived` 필드 자체는 `meta.payload`에 실려 올라간다 — 항상 빈 객체로. `validateBackup`이
스키마 호환으로 이 필드를 기대하므로 벗겨내지 않는다.

### 서버 스키마

```sql
days (
  date           text primary key,        -- 'YYYY-MM-DD'
  payload        jsonb not null,          -- Day 전체
  rev            bigint not null,         -- 낙관적 동시성 (아래 rev 프로토콜)
  schema_version int not null,            -- 쓴 클라이언트의 스키마 버전
  sheet_at       timestamptz,             -- 묶음별 타임스탬프 (쓴 기기의 시계)
  grades_at      timestamptz,
  sprint_at      timestamptz,
  updated_at     timestamptz not null,    -- pull 커서 (서버 시계)
  device         text not null
)

meta (
  id         int primary key default 1 check (id = 1),
  payload    jsonb not null,
  rev        bigint not null,         -- days와 같은 낙관적 동시성
  generation bigint not null,         -- 전체 교체 세대
  updated_at timestamptz not null,
  device     text not null
)

app_config (
  id         int primary key default 1 check (id = 1),
  pin        text not null,            -- 채점 화면 잠금. 암호가 아니다(§4)
  updated_at timestamptz not null,
  device     text not null
)

devices (
  id           text primary key,
  label        text not null,
  key_hash     text not null,         -- pgcrypto. 평문은 서버에 없다
  created_at   timestamptz not null,
  last_seen_at timestamptz,
  revoked_at   timestamptz            -- 값이 들어가면 즉시 차단
)

snapshots  (id, at, device, reason, day_count, payload)   -- 강제 백업, 지우지 않는다
write_log  (id, at, device, target, action)               -- append-only, 사후 확인용
```

**`Day`를 컬럼으로 쪼개지 않는 이유.** 쪼개면 `types.ts` 스키마를 서버에 복제하게 되는데,
그것은 `validateBackup`이 겪어서 의도적으로 피한 함정이다 — 검증기에 스키마를 복제했더니
Phase 4에서 문항 종류가 늘 때 정상 데이터를 거부하게 되는 문제였다. 서버가 같은 실수를
반복하면 Phase 5에 스키마 마이그레이션이 생긴다.

**묶음별 타임스탬프가 핵심이다.** `updated_at` 하나만 두면 필드 단위 병합이 불가능해져,
아이패드의 스프린트와 노트북의 채점 중 하나가 반드시 사라진다.

## §2 병합

### 병합 로직은 한 곳에만 둔다

`src/engine/merge.ts`의 순수 함수 `mergeDay(local, remote)`·`mergeMeta`가 유일한 주인이다.
`engine/`에 있으므로 기존 관례대로 속성 기반 테스트와 변이 검증을 건다.

**서버는 병합하지 않는다.** 서버가 강제하는 것은 우회되면 안 되는 **안전장치 둘**뿐이다.

1. **낙관적 동시성** — `PATCH /days?date=eq.X&rev=eq.N`. 갱신된 행이 0개면 충돌이므로
   클라이언트가 다시 읽고 `mergeDay`를 돌린 뒤 재시도한다. PostgREST 기본 기능이라 서버
   코드가 없다
2. **`sheet` 불변 트리거** — 아래 C-1

안전장치는 병합 규칙이 아니므로 단일 출처 복제가 아니다.

### 필드별 규칙

화면이 형제 관계라 필드 소유권이 이미 갈라져 있다. 이것이 필드 단위 병합을 가능하게 한다.

| 필드                     | 쓰는 곳                                                                               | 병합 규칙                                    |
| ------------------------ | ------------------------------------------------------------------------------------- | -------------------------------------------- |
| `sheet`                  | `print-sheet.ts`만                                                                    | **최초 1회만.** 비어 있을 때만 채워진다      |
| `grades`·`mood`·`doneAt` | `grade.ts`만 (셋을 항상 함께 씀)                                                      | 한 묶음 LWW (`grades_at` 비교)               |
| `sprint`                 | `sprint.ts`만                                                                         | LWW (`sprint_at` 비교)                       |
| `kind`                   | `print-sheet.ts`가 `'normal'`로 만들고, `sprint.ts`가 점검일이면 `'checkup'`으로 덮음 | **단조.** `'checkup'`은 절대 되돌리지 않는다 |

`grades`·`mood`·`doneAt`을 쪼개지 않는 이유는 `grade.ts`가 셋을 한 번에 쓰기 때문이다 —
쪼개면 실제로 존재한 적 없는 조합이 만들어진다.

`kind`가 단조인 이유는 `sprint.ts`가 `'checkup'`의 유일한 생산 지점이고 이 표시가 월간
리포트의 점검 세션 식별자이기 때문이다.

**LWW의 시계는 쓴 기기의 시계다(사용자 결정, 2026-08-06 그릴미).** Apple 기기는 자동 시각
동기라 실질 어긋남이 초 단위이고, 같은 칸을 두 기기가 몇 초 차이로 고치는 상황이 이 가족의
사용 패턴에 없다(채점하는 사람이 아빠 한 명). 서버 도착 시각으로 "개선"하지 말 것 —
오프라인 기기의 편집이 "도착이 늦었다"는 이유로 지게 되어, 로컬 우선 앱에서는 실제 편집
순서와 반대로 뒤집힌다. `*_at`을 찍는 것도 쓴 클라이언트다.

**LWW 비교 키는 `(타임스탬프, deviceId)` 쌍이다** (Fable 리뷰 17). 타임스탬프 동률에서
타이브레이크가 없으면 `mergeDay(a,b)`와 `mergeDay(b,a)`가 다른 답을 내 교환법칙 자체가
성립하지 않는다 — 약속한 속성 테스트가 그 케이스를 생성하는 순간 빨개지고, 구현자가 문서에
없는 규칙을 지어내게 된다.

**`mergeDay`는 모르는 필드를 통과시킨다** (Fable 리뷰 8). 결과를 아는 묶음만으로 조립하면,
서비스워커에 갇힌 옛 클라이언트가 새 필드(Phase 5의 `Day` 확장)를 병합 결과에서 깎아 내고
그 깎인 Day를 서버로 push해 새 기기의 데이터를 지운다 — `validateBackup`이 겪은 함정을
병합기에서 반복하는 꼴이다. 구현은 스프레드 기반(`{ ...base, 아는 묶음만 교체 }`)으로 하고,
**모르는 필드 보존을 속성 테스트로 고정한다.** 같은 이유로 서버 행의 `schema_version`이
자기 것보다 크면 그 행은 **pull만 하고 push하지 않는다** — 낡은 코드가 새 데이터를 이길 수
있는 경로를 봉한다.

**`mergeMeta`의 규칙** (Fable 리뷰 10 — days만 표를 받고 meta는 구현자 임의였다):
`settings`는 통째 LWW(`updated_at` 비교), 단 `lastExportedAt`만 **max()** — "가족이 마지막으로
백업한 시각"은 나중 값이 아니라 최신 사실이 이겨야 한다. `derived`는 항상 빈 것으로 정규화.
`meta`도 `rev` 낙관적 동시성을 탄다.

**감수한 것 — 같은 날 스프린트 둘** (Fable 리뷰 9): 두 기기가 각각 오프라인에서 같은 날
스프린트를 완주하면 LWW가 한쪽 세션을 버린다. 스프린트는 실사용에서 아이패드 전용이라 발생
조건이 현실에 없고, 두 세션을 합치면(`sprint` 배열 연결) 하루 통계가 오염되므로 병합이 더
틀리다. 수용하고 기록한다.

### C-1 — `sheet` 불변. 방어는 세 겹이고, 서버 트리거만으로는 부족하다

**서버 트리거는 종이를 보호하지 못한다** (Fable 리뷰 1 — 이 문서의 초안이 "재인쇄 동일성이
강화된다"고 썼으나 거짓이었다). 반례: 아침에 노트북이 sheet A를 만들어 올림 → 아이패드가
오프라인인 채 저녁에 인쇄 → 로컬에 오늘 Day가 없으니 sheet B를 생성·인쇄 → 아이가 B를 품 →
접속 순간 "서버가 먼저" 규칙이 A를 이기게 하면 채점 화면은 A의 정답표를 그리고 아이 종이는
B다. 트리거는 서버 행만 지킬 뿐, **이미 인쇄된 종이와 로컬의 어긋남**은 잡지 못한다.

그래서 세 겹으로 막는다(사용자 결정, 2026-08-06 그릴미).

1. **생성 게이트(클라이언트).** `#/print`가 새 문제지를 만들기 **전에** pull을 기다린다.
   서버에 닿지 못하면 자동 생성하지 않고 묻는다 — _"서버를 확인하지 못했어요 — 다른 기기에서
   오늘 문제지를 만들었다면 겹칠 수 있어요. 그래도 만들까요?"_ 평소(온라인)엔 수백 ms 지연,
   오프라인엔 버튼 한 번. **기존 게이트의 정신과 같다 — 확신 없이는 자동으로 만들지 않는다.**
   이 대기는 `#/print` 한정이다 — §1의 "오프라인 동작 동일"은 아이 화면의 약속이고, 인쇄는
   부모 행위라 서버 확인의 비용을 물릴 수 있는 자리다
2. **서버 트리거.** `payload->'sheet'`가 비어 있지 않은데 새 값이 다르면 거부. 예외는
   `다시 만들기`(`action=sheet-rewrite` 명시 + 채점 있는 날 거부 — 지금 코드와 같은 조건)
   하나이고 `write_log`에 남는다
3. **충돌 시 조용히 해소하지 않는다.** 그래도 양쪽이 인쇄한 경우(둘 다 버튼으로 강행),
   어느 종이를 아이가 풀었는지 코드는 알 수 없다 — 어느 쪽 `sheet`도 자동으로 이기지 않고,
   **로컬을 유지한 채 부모 홈에 요란한 배너**를 띄운다: _"오늘 문제지가 두 기기에서 따로
   만들어졌어요 — 아이가 푼 종이가 어느 쪽인지 확인해 주세요."_ 해소는 아빠가 한쪽 기기에서
   `다시 만들기`(채점 전) 또는 그대로 채점을 진행하는 것으로 한다

1번 게이트 덕에 3번은 사실상 도달 불가능한 최후 방어선이다 — 도달했다는 것 자체가 두 번의
명시적 강행이 있었다는 뜻이다.

### C-3 — 빈 `sheet`

`sheet: []`는 "아직 안 만듦"으로 취급한다. `print-sheet.ts`가 이미 그렇게 판단하고 있어
새 규칙이 생기는 것이 아니라 **기존 판단을 서버에 복사**하는 것이다. 스프린트만 한 날의
`Day`에 나중에 문제지가 붙어도 충돌하지 않는다.

## §3 동기화 트리거와 오류 처리

### 아웃박스 패턴

`putDay`가 IndexedDB에 쓸 때 **같은 트랜잭션으로** `outbox` 스토어에 표식을 남긴다.

```
outbox  { key: autoIncrement, target: 'day:2026-08-06' | 'meta', bundles: ['sprint'], at }
```

`payload`는 담지 않는다 — 보낼 때 현재 값을 다시 읽으면 되고, 담으면 같은 로그가 두 벌
생긴다. 같은 `target`이 여러 번 쌓이면 하나로 접되 **`bundles`는 합집합**으로 접는다.

**`bundles`가 없으면 묶음별 타임스탬프 전체가 무너진다** (Fable 리뷰 2). push가 "현재 값을
다시 읽기"만 하면 이번에 어느 묶음이 바뀌었는지 알 수 없고, 구현자가 "바뀐 행이니 `*_at`
전부 갱신"으로 가면 아이패드가 스프린트만 올리면서 `grades_at`까지 밀어올려 — 노트북의
오프라인 채점이 "더 낡았다"로 판정돼 조용히 사라진다. **push는 `bundles`에 든 묶음의 `*_at`
만 갱신한다.** §1의 "묶음별 타임스탬프가 핵심이다"는 이 규칙으로만 실현된다.

**push 완료 후 아웃박스 정리는 push 시작 시점 이하의 `key`만 지운다** (Fable 리뷰 5).
fetch가 나가 있는 동안 생긴 새 표식까지 지우면, 보낸 payload에 없던 변경이 영원히 안
올라간다 — 같은 트랜잭션 아웃박스로 막았다고 자부한 바로 그 종류의 조용한 손실이다.

**같은 트랜잭션인 것이 핵심이다.** 쪼개면 "로컬 쓰기는 성공했는데 큐 등록이 실패해 영원히
안 올라가는 기록"이 생기고, 그것은 조용한 데이터 손실이라 A-1을 정면으로 배신한다. 그리고
이 하나로 오프라인 큐 문제가 같이 풀린다 — 오프라인은 아웃박스가 안 비워지는 상태일 뿐
특별한 경로가 아니다.

덕분에 화면은 동기화를 전혀 모른다. `db.ts` 바깥이 IndexedDB를 모르는 것과 같은 이유로
네트워크도 몰라야 한다.

### 기기 안에도 동시성이 생긴다 — 모든 로컬 쓰기가 병합을 거친다

이 설계는 배경 pull이라는 **두 번째 쓰기 주체를 기기 안에** 만든다 (Fable 리뷰 3). 그런데
화면들은 수 분짜리 read-modify-write를 한다 — `grade.ts`는 렌더 시점의 `day`를 읽고 아빠가
몇 분 채점한 뒤 `{ ...day, grades, mood, doneAt }`을 통째로 put하고, `sprint.ts`도 세션 시작
시의 `existing`을 3~5분 뒤에 스프레드한다. 채점 도중 pull이 서버의 스프린트를 로컬 Day에
병합해 넣으면, 저장 버튼의 낡은 스냅샷이 그 스프린트를 덮어쓴다.

해소: **`putDay`(pull 적용 포함)는 항상, 같은 IndexedDB 트랜잭션 안에서, 현재 저장된 값과
`mergeDay`를 거친 결과를 쓴다.** 화면의 낡은 스냅샷이 들고 온 묶음은 `*_at` 비교로 자연히
진다 — 기기 간 병합과 기기 안 병합이 같은 함수 하나로 처리되고, 화면 코드는 여전히 아무것도
모른다. 화면이 이번에 실제로 고친 묶음은 새 `*_at`을 받으므로 정당하게 이긴다.

### 기기별 상태는 `Meta`에 넣지 않는다

키·`deviceId`·`lastPulledAt`·`generation`은 기기마다 달라야 하는데 `Meta`는 동기화 대상이라
서로 덮어쓴다. 아이패드가 노트북의 `lastPulledAt`을 받아 자기가 이미 받았다고 착각하면
**못 받은 변경이 영원히 안 내려온다.** 별도 `device` 스토어에 두고 동기화·백업 어느 쪽에도
포함하지 않는다.

**새 값을 둘 때마다 세 자리 중 어디인지 판단한다.**

| 성격                          | 자리            | 예                                      |
| ----------------------------- | --------------- | --------------------------------------- |
| 기기마다 다르다               | `device` 스토어 | 기기 키, `deviceId`, `lastPulledAt`     |
| 가족이 공유하되 기록이다      | `Meta`          | `Settings.lastExportedAt`, 문제 수 설정 |
| 가족이 공유하되 기록이 아니다 | `app_config`    | PIN                                     |

`Settings.lastExportedAt`이 `Meta`인 이유는 "이 가족이 마지막으로 백업한 시각"이지 기기
속성이 아니기 때문이다. PIN이 `Meta`가 아닌 이유는 아래 §4에 있다.

### 언제 올리나 — 재접속은 반드시 pull부터

아웃박스에 항목이 생기면 즉시 시도한다. 실패하면 그대로 두고 다음 기회를 기다린다.
**주기 타이머는 두지 않는다** — 트리거만으로 충분하고 타이머는 배터리와 복잡도를 쓴다.

**순서가 규칙이다: 오프라인에서 복귀한 push는 `meta` pull(= `generation` 확인)을 먼저
통과해야 한다** (Fable 리뷰 4). 이 순서가 없으면 오프라인 기기가 접속하자마자 push부터
나가고, `replace_all`이 지운 날짜에 대한 PATCH가 0행 매치 → "다시 읽고 병합" 경로가 행이
없으니 INSERT → **가져오기가 버린 데이터가 부활한다.** §6이 "generation이 막는다"고 주장한
바로 그 구멍이 비교 시점 미명시로 열려 있었다. 온라인 상태에서 연속 push할 때는 매번 pull할
필요 없다 — `rev` 가드가 그 사이의 경합을 잡는다.

**`rev` 프로토콜** (Fable 리뷰 11 — 전부 미명시였다):

- INSERT 시 `rev = 1`. **upsert는 쓰지 않는다** — `merge-duplicates`류는 `rev` 가드 없이
  통째로 덮어써 낙관적 동시성 전체를 우회한다
- 갱신은 `PATCH ?date=eq.X&rev=eq.N`에 `rev = N+1`을 실어 보낸다. 0행 매치면 충돌 —
  그 행을 다시 받아 `mergeDay` 후 재시도, 3회까지. 그래도 안 되면 아웃박스에 남긴다
- 두 기기가 같은 날짜를 동시에 INSERT하면 PK 충돌 — 진 쪽은 그 행을 pull해 `mergeDay` 후
  PATCH 경로로 재시도한다

### 언제 내리나

- 앱 시작 시 (`main.ts` — `navigator.storage.persist()` 옆)
- **부모 화면 진입 시**(`#/parent`·`#/print`·`#/grade`·`#/report`) — 다기기 쓰기가 실제로
  일어나는 곳이다
- 탭 복귀 시 (`visibilitychange`)
- push가 `rev` 충돌로 실패했을 때

커서는 `updated_at > lastPulledAt - 여유창`이다. 규칙 둘 (Fable 리뷰 7):

- **`lastPulledAt`은 클라이언트 시계가 아니라 서버 응답의 최대 `updated_at`으로만 갱신한다.**
  클라이언트 시계가 서버보다 앞서면 그 차이만큼의 행을 영영 놓친다
- **여유창(수 분)을 두고 겹쳐 받는다.** Postgres의 `now()`는 트랜잭션 시작 시각이라, 긴
  트랜잭션이 커밋되기 전에 다른 기기가 커서를 올리면 그 행이 커서 뒤에 숨는다. 병합이
  멱등이므로 재수신은 무해하다 — 겹침이 정확함보다 싸다

**pull로 내려온 payload는 백업 파일과 같은 등급으로 검증한다** (Fable 리뷰 16). `validateBackup`
의 day 단위 검증을 통과하지 못한 행은 **적용하지 않고 로컬을 유지**하며 부모 홈에 경고를
남긴다 — 기형 payload가 IndexedDB에 앉으면 `deriveFacts`가 모든 화면에서 죽고, 동기화가 그
오염을 전 기기로 복제한다. XSS 경계(`escapeHtml`)만으로는 부족하다.

`app_config`는 행이 하나라 커서 없이 pull 때마다 같이 읽어 로컬 캐시를 갱신한다. **아이
화면은 pull 트리거에 넣지 않는다** — 로컬 우선이라 필요가 없고, 넣으면 딸이 앱을 열 때마다
네트워크를 기다린다.

**iOS는 백그라운드 fetch를 수 초 안에 죽인다** (Fable 리뷰 15). 스프린트 저장 직후의 push는
결과 화면이 떠 있는 동안 나가므로 대부분 성공하지만, 딸이 저장 직후 커버를 닫으면 아웃박스에
남는다 — 다음 포그라운드가 다음 기회이고, 그 사이 iOS가 IndexedDB를 evict하면 그 세션은
서버 사본 없이 사라진다. Background Sync가 iOS에 없어 닫을 수 없는 창이다. 수용하고, 부모 홈
경고("아직 안 올라간 기록 N건")가 이 상태를 보이게 하는 것으로 갈음한다.

### 첫 연결

서버가 비었으면 전량 업로드, 아니면 양방향 병합이다. 분기로 두지 않고 `mergeDay`를 양쪽에
돌리면 한 경로로 처리된다 — 빈 쪽은 병합 결과가 그냥 상대편 값이 된다.

5년치라도 1,800행 남짓이라 한 번에 받아도 되지만 PostgREST의 `Range` 헤더로 나눠 받는다.

### 실패했을 때

기본은 **조용한 재시도**다. 로컬 우선이므로 실패해도 앱은 정상 동작하고 **아이 화면에는
어떤 경우에도 아무것도 뜨지 않는다.** 예외는 셋이다.

| 상황                      | 어떻게                                                                                                                                       |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `sheet` 거부·충돌         | **즉시 알린다** — C-1의 3겹 방어 참고. 아이 손의 종이와 직결된다                                                                             |
| 인증 실패(키 폐기·오타)   | **부모 홈에 명시한다.** 조용히 넘기면 아빠는 동기화되는 줄 알고 몇 주를 보낸다                                                               |
| 아웃박스가 안 비워짐      | 부모 홈에 _"아직 안 올라간 기록 N건"_                                                                                                        |
| 서버 무응답이 며칠째 지속 | 부모 홈에 _"서버에 N일째 못 올렸어요"_ — Supabase 무료 티어 일시정지가 여기로 드러난다(감수한 것 참고). 5xx의 조용한 재시도에 묻히면 안 된다 |

## §4 접근 통제 (C-2)

### 기기별 키 붙여넣기

계정을 쓰지 않는다. PostgREST가 요청 헤더를 RLS에서 읽을 수 있다는 점을 이용한다.

```sql
exists (
  select 1 from devices d
  where d.key_hash = crypt(current_setting('request.headers',true)::json->>'x-device-key', d.key_hash)
    and d.revoked_at is null
)
```

번들에는 Supabase URL과 `anon` 키만 들어간다 — 둘 다 공개되어도 무방하다. RLS가
`x-device-key` 헤더가 맞지 않으면 한 행도 내주지 않기 때문이다. 아빠는 기기마다 랜덤
문자열을 만들어 해시만 `devices`에 넣고 평문은 그 기기에 한 번 붙여 넣는다.

JWT 발급보다 나은 점이 둘이다. **폐기가 즉시 된다** — `revoked_at`에 값 하나면 그 기기가 그
순간부터 막힌다(JWT는 상태가 없어 취소가 어렵다). 그리고 **서명 스크립트가 필요 없다** —
랜덤 문자열 하나면 되므로 레포에 비밀을 다루는 코드가 생기지 않는다.

키는 **헤더로만** 보낸다. 쿼리스트링에 실으면 각종 로그에 평문으로 남는다.

### 등록 흐름

**미등록 기기에서도 아이 화면은 그냥 열린다.** 등록 진입점은 `#/parent` 쪽에만 둔다 — 앱
첫 진입에 등록 화면을 세우면 그것이 곧 아이 화면에 부모 것이 새는 것이다.

미등록 아이패드는 서버에 쓰지 못하므로 딸이 푼 스프린트가 로컬에만 남는다. 로컬 우선이라
아이에게는 아무 문제가 없고, **부모 홈에서만** "아직 안 올라간 기록"으로 보인다.

미등록 상태의 부모 홈은 진행 상태(`✅ 0일 완료`) 대신 **"이 기기는 아직 연결되지 않았어요"**
를 보여주고 등록으로 안내한다. 노트북에서 처음 열었을 때 딸의 기록이 사라진 것처럼 보이는
것을 막는다 — 이 레포는 같은 종류의 혼동을 이미 겪었다(CLAUDE.md의 "두 번째 워크트리에서
앱이 비어 보이는 것은 정상이다" 경고).

### 채점 화면 PIN

`#/grade`에만 4자리 PIN을 건다. 세 부모 화면 중 **문항별 정답을 실제로 화면에 뿌리는 곳이
채점 화면 하나**이기 때문이다 — `#/print`는 문제만 인쇄하고 `#/report`는 집계만 본다.

- **게이트는 버튼이 아니라 화면에 건다.** `#/grade` 진입 경로가 둘이다(부모 홈의 `채점하기`,
  밀린 채점 배너의 `#/grade/${pending}`). 버튼에 걸면 배너 경로가 뚫린다. `renderGrade`
  진입에서 묻는 방식이면 두 경로가 다 막히고 세 번째 진입점이 생겨도 자동으로 막힌다
- **유지 범위는 그 화면에 있는 동안**이다. 해시가 `#/grade`를 벗어나면 초기화한다. 타이머를
  두지 않으므로 관리할 상태가 없다
- **틀렸을 때 잠금이나 지연을 두지 않는다.** 상대가 딸이라 여러 번 틀리는 것 자체가 목적
  달성이고, 잠금은 아빠를 가둘 뿐이다
- **값은 소스에 박지 않는다** — 공개 레포이고 빌드 산출물에도 그대로 들어간다. 첫 기기를
  등록할 때 아빠가 입력한다

#### 저장 위치 — 서버의 `app_config`, 로컬에는 캐시

PIN은 가족이 공유하는 값이므로 서버에 둔다. 기기마다 따로 입력할 필요가 없고, 바꾸면 모든
기기가 다음 동기화에 따라온다.

**`Meta`에 넣지 않는 이유가 중요하다.** `Meta`는 `serializeBackup`이 그대로 담으므로, 넣는
순간 네 자리가 백업 JSON을 타고 나간다. 백업 파일은 사람 손을 타고 파일 앱·클라우드·메일을
오간다. `app_config`는 별도 테이블이라 백업 대상이 아니다.

**로컬에는 캐시만 둔다**(`device` 스토어). 오프라인에서도 채점해야 하므로 검증은 로컬에서
한다 — 서버에 물어보는 방식이면 인터넷이 끊긴 날 채점이 막힌다. 그 대가로 아이패드가 오래
오프라인이면 옛 PIN이 그 기기에서 계속 통한다. 화면 잠금이라 감수한다.

**해시하지 않는다.** 4자리는 해시해도 즉시 역산되고, 오프라인 검증을 위해 그 해시가 어차피
기기에 캐시돼야 하므로 방어가 되지 않는다. **이것은 암호가 아니라 화면 잠금**이고, 같은
origin의 IndexedDB를 읽을 수 있는 사람에게는 애초에 소용이 없다.

**`replace_all`이 `app_config`를 건드리지 않는다.** 기록을 지웠다고 화면 잠금이 풀리면 안
된다. 잊어버렸을 때는 Supabase에서 값을 보거나 바꾼다 — 데이터와 무관하다.

### 아이 전용 키는 만들지 않는다

서버에서 아이 키의 권한을 좁혀 정답 열람을 막는 안을 검토했으나, **아이패드 한 대가 부모
역할과 아이 역할을 겸하므로** 그 기기에는 어차피 부모 키가 있어야 한다. 키를 둘로 나눠도
같은 저장소에 나란히 놓여 얻는 것이 적다. 정답 노출 방어는 기존 소속 분리 규칙 + PIN 게이트
둘이 맡는다 — 지금(규칙 하나)보다는 나아진다.

### 이상 징후 확인

계정이 없으니 로그인 기록이라는 단서가 없다. 그 자리를 `write_log`와 `devices.last_seen_at`이
메운다 — 어느 기기가 언제 무엇을 바꿨는지가 남으므로 사후에라도 확인할 수 있다.

## §5 키 관리

**가장 강한 방어는 키가 파일이 될 이유를 안 만드는 것이다.** 이 설계에서 기기 키는 앱 화면에
붙여넣는 값이지 빌드에 들어가는 값이 아니다. 레포에도 `.env`에도 CI에도 키가 필요한 순간이
없다.

| 값                     | 레포·번들 | 이유                                                     |
| ---------------------- | --------- | -------------------------------------------------------- |
| Supabase 프로젝트 URL  | 가능      | 공개 전제                                                |
| `anon` 키              | 가능      | 공개 전제. RLS가 막으므로 이것만으로는 한 행도 못 읽는다 |
| **기기 키(평문)**      | **절대**  | 이것 하나로 전체 읽기·쓰기가 된다                        |
| **`service_role` 키**  | **절대**  | **RLS를 통째로 우회한다.** 가장 위험하다                 |
| DB 비밀번호·JWT 시크릿 | **절대**  | 프로젝트 전체 장악                                       |

`anon` 키가 "공개돼도 된다"는 것과 "비밀이 아니다"는 다르다. 뭉뚱그리면 대시보드에서 키를
복사할 때 `service_role`을 집어 오는 사고가 난다 — 두 키가 나란히 있어서 실제로 흔한
실수다. **앱 코드는 `service_role`을 어떤 경우에도 쓰지 않는다.**

**레포 차원 조치**

- `.gitignore`에 `.env*`를 더한다(`.env.example`은 예외). 지금은 `*.local`만 있어
  `.env.local`은 걸리지만 `.env`·`.env.production`은 안 걸린다
- **`deploy.yml`은 바뀌지 않는다.** 빌드에 비밀이 필요 없으므로 GitHub Secrets에 넣을 것도
  없다. CI에 비밀이 없다는 것 자체가 방어다 — 워크플로 로그로 새는 경로가 존재하지 않는다
- **문서에 실제 값을 쓰지 않는다.** 이 레포는 문서가 두껍고 전부 커밋되며, 설계 문서에
  "예시로" 실제 키를 적는 것이 가장 흔한 유출 경로다. 플레이스홀더만 쓴다
- **백업 파일에 키가 들어가면 안 된다.** `serializeBackup`은
  `{ app, schemaVersion, exportedAt, days, meta }`만 담으므로 지금은 안전하지만, `device`
  스토어를 나중에 백업에 포함시키면 키가 JSON 파일로 걸어 나간다. 그 파일은 사람 손을 타고
  파일 앱·클라우드·메일을 오간다. **`device` 스토어는 동기화 대상도 백업 대상도 아니다**

기기 키의 평문은 서버에 없다(해시만). 아빠가 비밀번호 관리자에 보관하고, 잃어버리면 그
기기를 폐기하고 새로 발급한다 — 데이터는 서버에 있으므로 기록은 잃지 않는다.

## §6 파괴적 경로 (초기화·가져오기)

### 서버에도 파괴적 쓰기 경로를 하나만 둔다

```sql
replace_all(payload jsonb)
-- 트랜잭션 하나 안에서 순서대로:
--   1. 지금 서버 상태를 snapshots에 뜬다 (reason: 'auto')  ← Fable 리뷰 12
--   2. days 전부 삭제 후 payload의 것으로 삽입
--   3. meta 행의 payload를 교체하고 generation을 +1        ← 행을 지우지 않는다
```

- 가져오기 = `replace_all(파일 내용)`
- 초기화 = `replace_all(빈 것)`

로컬에서 `resetAll`이 `replaceAll([], defaultMeta())`인 것과 같은 모양이다. 경로가 둘이면
`replaceAll`의 `tx.abort()` 함정 같은 자리를 서버에서 새로 만들게 된다.

**스냅샷이 RPC 안에 있는 이유** (Fable 리뷰 12): 클라이언트가 스냅샷을 먼저 뜨고 확인
다이얼로그를 거쳐 삭제를 부르는 사이에는 수십 초가 있다 — 그 사이 다른 기기가 push한 채점은
스냅샷에도 없고 삭제도 당한다. 같은 트랜잭션 안이면 이 창이 0이 된다. 확인 화면에 보여줄
스냅샷 정보는 별도의 가벼운 사전 스냅샷(§ 실행 순서 2)으로 유지한다 — 그 스냅샷이 낡아도
`replace_all`의 자동 스냅샷이 최종 안전망이다.

**`meta` 행은 절대 지우지 않는 이유** (Fable 리뷰 13): 행이 사라지면 `generation` 카운터의
출처가 사라진다 — 다음 클라이언트가 낮은 값으로 재삽입하면, 높은 generation을 쥔 오프라인
기기의 비교가 미정의가 되어 아래 부활 방어 자체가 무너진다. generation은 **행과 함께 영속하는
단조 증가 카운터**다.

**가져오기는 upsert가 아니라 전체 교체다.** upsert면 파일에 없는 날이 서버에 남아 파일과도
원래 상태와도 다른 잡종이 된다. REST 호출 두 번(DELETE 후 INSERT)으로 하지 않는 이유는
원자성이다 — 중간에 끊기면 서버가 빈 상태로 남는다. 이것은 병합 규칙이 아니라 원자성
보장이므로 §2의 "서버에 로직을 두지 않는다"와 어긋나지 않는다.

**`replace_all`은 `sheet` 트리거의 예외를 겸한다는 것을 명시해 둔다** (Fable 리뷰 12): 낡은
백업을 가져오면 오늘 `sheet`도 파일의 것으로 갈린다. 가져오기는 "이 파일이 전부다"라는
명시적 선언이고 지금의 로컬 `replaceAll`도 같은 의미이므로 의도된 동작이다 — 다만 가져오기
확인 다이얼로그가 이미 날짜 범위를 보여주므로, **오늘 채점이 있는데 파일이 오늘을 포함하지
않으면** 그 사실을 경고 줄로 더한다.

### `meta.generation`

`replace_all`이 이 값을 올린다. 자기 `generation`이 낡은 클라이언트는 서버에서 통째로 다시
받는다. **단, 로컬 미동기 변경을 버리기 전에 그 `Day`들을 스냅샷으로 올린다**(`reason:
'generation-conflict'`) — 미동기분에는 딸이 오프라인에 푼 스프린트(이 앱에서 유일하게 복구
불가능한 데이터)가 들어 있을 수 있다. 무조건 버리는 규정은 A-1이 정의한 "조용한 데이터
손실"을 설계가 직접 명령하는 꼴이다(Fable 리뷰 4). 스냅샷 후 부모 홈에 알린다 — 필요하면
아빠가 스냅샷에서 수동 복원한다.

이것이 없으면 오프라인 기기가 나중에 올라와 자기 변경을 병합해 올리고, **가져오기가 버리려던
데이터가 되살아난다.** `rev` 충돌은 이것을 잡지 못한다 — 각 행은 정상적으로 병합되기
때문이다. 비교 시점은 §3 "재접속은 반드시 pull부터"가 못 박는다.

### 강제 백업은 파일이 아니라 서버 스냅샷이다

파일 다운로드는 iOS에서 조용히 no-op이 될 수 있는 바로 그 경로라 게이트로 쓰면 옛 문제가
되살아난다. 서버 스냅샷은 앱이 존재를 **직접 확인**할 수 있어, `lastExportedAt`을 강제
게이트로 쓰지 않기로 했던 2026-08-04 결정(`specs/2026-08-04-data-reset-design.md`)의 전제가
해소된다. 그때 거부한 이유는 자기신고라서 거짓 안전감을 준다는 것이었다.

### 실행 순서 — 순서 자체가 안전장치다

1. **온라인인지 확인한다.** 오프라인이면 초기화·복구 버튼을 비활성으로 둔다
2. **스냅샷을 서버에 올리고 `id`를 받는다.** 실패하면 여기서 중단하고 **아무것도 지우지
   않는다**
3. **`confirmDialog`를 띄운다.** 지금 보여주는 것(지울 일수·날짜 범위·채점 안 된 문제지 수·
   마지막 백업)에 방금 만든 스냅샷의 시각과 일수를 더하고, 오조작 방지로 **"지우기"를 직접
   입력**하게 한다. 확인 버튼 한 번은 실수로 눌릴 수 있지만 세 글자를 실수로 입력할 수는 없다
4. **로컬을 먼저 지운다**(`resetAll`). 이미 원자적임이 `db.test`로 고정돼 있다
5. **`replace_all`을 부른다.** RPC가 자동 스냅샷 → `days` 교체 → `meta` payload 교체 +
   `generation` 증가를 한 트랜잭션으로 한다. `snapshots`·`app_config`는 건드리지 않는다
6. `write_log`에 남기고 `#/report`에 **스냅샷에서 되돌리기** 경로를 둔다

4→5 순서인 이유: 5가 실패하면 다음 동기화에서 서버 사본이 도로 내려온다 — 헷갈리지만
**데이터를 잃지 않는 실패**다. 반대 순서였다면 서버가 비고 로컬만 남은 상태에서 다음
동기화가 로컬을 도로 올려 초기화가 조용히 취소되는데, 그것은 알아채기 어렵다.

스냅샷 업로드는 `resetBusy`/`importBusy` 가드 **안쪽**에 들어간다. 업로드가 도는 동안 다른
파괴 경로가 열려 있으면 PR #18이 방금 정리한 경합이 되살아난다.

가져오기도 같은 경로를 탄다(`reason: 'import'`).

**스냅샷은 지우지 않고 쌓는다**(하루 수 KB).

**고아 스냅샷은 고치지 않는다.** `confirmDialog`는 해시가 바뀌면 `false`로 resolve하므로,
확인을 취소하거나 화면을 옮기면 아무 데도 안 쓰인 스냅샷이 남는다. 그것은 **백업이 하나 더
있는 것**일 뿐이라 무해하고 오히려 이 기능이 지키려는 방향이다. 이 문장이 없으면 다음
사람이 누수로 보고 "취소 시 스냅샷 삭제"를 넣는다 — 그게 진짜 위험이다.

## §7 UX 변경

### 반드시 바뀌는 것

- **초기화·가져오기 확인** — `confirmDialog`(PR #18)에 스냅샷 정보 한 줄과 "지우기" 입력이
  더해지고, 오프라인이면 버튼이 비활성된다
- **인쇄 화면의 생성 게이트** — 새 문제지를 만들기 전에 서버 확인을 기다리고, 닿지 못하면
  확인 버튼을 거친다(C-1 방어 1). 이미 만들어진 문제지의 재인쇄는 지금과 똑같이 즉시다
- **`다시 만들기`에 새 실패 경로** — 지금은 "채점이 있는 날은 거부"가 로컬 판단이라 즉시
  알 수 있지만, 이제 **다른 기기 때문에** 거부될 수 있다
- **기기 등록 화면 신설** (`#/parent` 소속)
- **되돌리기 경로 신설** — `#/report` 하단에 스냅샷 목록과 복구

### `confirmDialog` 확장이 두 곳을 동시에 푼다

PIN 입력과 초기화의 "지우기" 타이핑이 똑같이 "다이얼로그 안의 입력 필드"를 필요로 한다. 지금
`confirmDialog`는 `description`이 `textContent` 전용이라 입력이 들어갈 자리가 없다 — `ui.ts`에
입력 슬롯 하나를 여는 작업이 한 번 생기고 두 기능이 나눠 쓴다.

### 백업 경고의 기준을 옮긴다

`report.ts`의 `backupLine`(`⚠ 아직 백업한 적이 없어요` / `⚠ 마지막 백업은 …이에요`)과 30일
배너가 `daysSinceExport(meta, today)`를 본다. 서버 동기화가 상시 돌면 이 경고는 **사실과
어긋난 겁을 준다** — 매일 서버에 사본이 쌓이는데 파일을 30일 안 내보냈다고 경고하는 꼴이다.

기준을 **마지막 동기화 시각**으로 옮긴다. 파일 내보내기는 없애지 않는다 — 서버도 단일 실패
지점이고(계정 정지·서비스 종료), "가족 손에 있는 사본"의 가치는 그대로다. 다만 주역이
동기화로 바뀌고 파일 내보내기는 권장 기능으로 내려온다.

부수 효과로 PR #18이 감수한 위험("토스트를 놓치면 배지가 백업됨으로 거짓말한다")이 **줄어든다**
— 배지가 거짓말해도 서버 사본이 실재한다.

### 동기화 상태 표시

`#/parent`에만, **평소에는 조용히**. 정상이면 한 줄(_"마지막 동기화: 방금 전"_), 실패했거나
안 올라간 항목이 있으면 눈에 띄게. **아이 화면에는 어떤 형태로도 두지 않는다.**

### 일부러 안 바꾸는 것

- **아이 화면 전부** — 홈·스프린트·지도·EBS. 동기화 표시도 등록 진입점도 두지 않는다
- **인쇄 화면 레이아웃** — A4 인쇄 전제라 노트북에서 오히려 자연스럽다
- **오프라인 동작** — 로컬 우선이므로 지금과 완전히 동일하다
- **노트북용 채점 조작(키보드 단축키)** — 목적은 다기기 "가능"이지 "최적화"가 아니다. 실제로
  노트북에서 채점해 본 뒤에 판단할 값이다

## 감수한 것

- **기기 키가 기기 저장소에 평문으로 있다.** 저장소를 직접 읽을 수 있는 사람은 PIN과
  무관하게 키를 얻는다. 아이패드는 iOS 스탠드얼론 PWA라 개발자도구에 닿는 경로가 실질적으로
  없지만, **노트북에서는 F12 한 번 거리다**(Fable 리뷰 14) — "개발자도구 없음" 논리는
  아이패드 한정이다. 노트북은 아빠의 로그인 계정 안이므로 OS 계정 잠금이 그 층의 방어이고,
  가족 공용 계정에 이 앱을 등록하지 않는 것으로 갈음한다. **"PIN이 데이터를 암호화한다"는
  오해는 하지 않는다** — PIN이 막는 것은 화면이지 데이터가 아니고, 기기 키를 쥔 사람은 PIN
  읽기·쓰기도 된다(같은 RLS 전부-아니면-전무 안에 있다)
- **계정이 없어 유출을 알아채기 어렵다.** 로그인 기록이라는 단서가 없다. `write_log`와
  `last_seen_at`이 사후 확인 수단의 전부다
- **외부 업체에 딸의 기록이 올라간다.** 관리형 BaaS를 고른 대가다
- **Supabase 무료 프로젝트는 일주일가량 요청이 없으면 자동 일시정지되고, 오래 방치하면
  삭제될 수 있다** — 손실 방어로 만든 것이 스스로 손실 지점이 되는 역설. 유료 전환 대신
  두 겹으로 받는다(사용자 결정, 2026-08-06 그릴미): ① 부모 홈 경고("서버에 N일째 못
  올렸어요")를 눈에 띄게 ② GitHub Actions cron이 주 1회 anon 키로 ping해 일시정지를
  예방한다 — 이미 쓰는 인프라이고 비밀이 필요 없다. Actions가 실패해도 ①이 사람에게
  알리고, 파일 내보내기가 3중째 방어로 남는다. Supabase가 일시정지 정책을 바꾸면 이
  완화책을 재검토할 것
- **CLAUDE.md의 첫 줄이 더 이상 사실이 아니게 된다** — "서버가 없고 데이터는 아이패드의
  IndexedDB에만 있다". 구현과 함께 갱신해야 한다

## 불변식 확인

- **재인쇄 동일성** — 다기기가 이 불변식을 위협하는 것이 이 설계의 최대 위험이고, C-1의
  3겹(생성 게이트·서버 트리거·충돌 비자동해소)이 방어다. 기존 로컬 게이트는 그대로 둔다.
  초안이 "서버 트리거로 강화된다"고 썼던 것은 Fable 리뷰 1이 반증했다 — 트리거만으로는
  오프라인 인쇄 한 번에 깨진다
- **`derived` 비배선** — 동기화 대상이 아니다. 오히려 이 원칙이 있어 병합 문제가 안 생겼다
- **소속 분리** — 등록 진입점·동기화 표시·PIN 모두 부모 화면에만. 아이 화면의 `navigate()`
  호출은 하나도 바뀌지 않는다. PIN이 방어선을 하나에서 둘로 늘린다
- **단일 출처** — 병합 로직은 `engine/merge.ts` 하나. 서버의 두 안전장치는 병합 규칙이 아니다
- **XSS 경계** — 서버에서 내려온 값은 백업 파일과 같은 등급의 신뢰할 수 없는 값이다.
  `el()` 템플릿에 들어가는 모든 서버 유래 값은 `escapeHtml`을 거친다
- **실행 의존성 0개** — `fetch` 직접 호출로 유지된다
- **배포 URL 고정** — 바뀌지 않는다. 오히려 서버가 생기면서 origin 종속성이 완화된다(기록이
  IndexedDB에만 있지 않게 되므로)

## 배포 단계 (사용자 결정, 2026-08-06 그릴미)

두 단계로 나눠 배포한다. 병합 코드의 버그가 이 설계에서 가장 개연성 높은 결함인데, 그것이
손실 방어(A-1)와 운명을 같이할 이유가 없다. Phase를 나눠 실사용으로 확인하고 다음을 얹는
기존 방식(phase3-real-use)과 같다.

**1단계 — 업로드. A-1이 먼저 산다. 충돌이 존재하지 않는다.**

- 아웃박스 push, 서버 스키마 전체, 기기 키 입력(등록의 최소형 — 키 붙여넣기 하나)
- §6 파괴 경로 보호 전부(스냅샷·`replace_all`·"지우기" 타이핑·되돌리기). 서버 사본이 생기는
  바로 그 순간부터 "로컬만 지우면 서버에 지운 기록이 남는다"는 의미 변화가 시작되므로
  미룰 수 없다 — 미루면 그 기간 동안 초기화 버튼의 약속("모든 기록 지우기")이 조용히
  거짓이 된다. §6은 pull·병합과 독립이라 1단계에 넣어도 병합 위험을 끌어들이지 않는다
- 부모 홈 경고(아웃박스 미소진·서버 미도달 일수), Actions 주 1회 ping
- pull 없음. 아이패드 실물에서 며칠 굴려 실측 확인 후 2단계로

**2단계 — 양방향 + 다기기.**

- pull, `engine/merge.ts`(기기 간·기기 안 공용), `rev` 충돌 처리, `generation`,
  `sheet` 불변 트리거의 실전 검증, 인쇄 생성 게이트(C-1 방어 1)
- 등록 화면 완성형(라벨·미등록 안내), `app_config` PIN, 백업 경고 기준 전환(§7)

1단계는 push 전용이고 등록 기기가 아이패드 하나라 병합·게이트·충돌이 실행될 조건 자체가
없다 — 그 코드가 1단계에 없어도 안전한 이유다.

- `engine/merge.ts`의 속성 기반 테스트 — 무작위 `Day` 쌍에 대해 병합의 교환법칙(타이브레이크
  포함 — `(타임스탬프, deviceId)` 쌍이라 동률 케이스도 성립한다)·멱등성, `sheet` 규칙,
  `kind` 단조성, **모르는 필드 통과**
- **변이 검증** — 병합 규칙을 일부러 틀리게 바꿔 그 테스트만 빨개지는지 확인하고 원복한다
- 서버 규칙(RLS·트리거·`replace_all`)은 Supabase에서 직접 확인한다. 자동 테스트를 두지
  않으므로 **무엇을 확인했는지 HANDOFF에 남긴다**

사람 확인이 필요한 것:

1. 두 기기에서 같은 날을 각각 채점·스프린트하고 둘 다 남는지 — **한쪽은 스프린트만
   push하게 해서 채점 `*_at`이 밀려 올라가지 않는 것도**(아웃박스 `bundles` 검증)
2. 노트북에서 문제지를 만든 뒤 아이패드에서 인쇄하면 **같은 문제**가 나오는지
3. **오프라인 아이패드에서 `#/print`에 들어가면** 자동 생성 대신 확인 버튼이 뜨는지, 강행 후
   접속하면 부모 홈에 sheet 충돌 배너가 뜨고 어느 쪽도 조용히 덮이지 않는지
4. 아이패드에서 `다시 만들기`가 거부되고 안내가 뜨는지
5. 기기 키를 폐기하면 그 기기가 즉시 막히는지
6. 오프라인에서 딸이 스프린트를 풀고, 온라인이 되면 올라가는지 — 결과 화면에서 바로 커버를
   닫는 경우도(다음 포그라운드에 올라가는지)
7. 초기화가 스냅샷을 만든 뒤에만 진행되고, 되돌리기로 복구되는지
8. 가져오기 직후, 미동기 변경을 쥔 오프라인 기기가 접속하면 — 부활하지 않고
   `generation-conflict` 스냅샷 + 부모 홈 알림이 생기는지
9. `#/grade`의 두 진입 경로가 모두 PIN을 묻는지
10. 채점 도중 다른 기기가 스프린트를 올려도, 채점 저장이 그 스프린트를 지우지 않는지
    (기기 안 병합 검증)
