# 하루치 — 설계 문서

작성일: 2026-08-02
상태: 1차 스펙 확정

> **이름 메모** — 초기 후보는 `하루한장`이었으나, 공간 확보를 위해 매일 인쇄물이 2장이 되면서 이름이 사실과 어긋났다. 아이에게 "오늘 하루 한 장 하자"라고 말하며 두 장을 주는 상황을 피하기 위해 `하루치`로 변경했다. **분량이 정해져 있다는 뜻이면서 장수를 특정하지 않아**, 이후 구성이 바뀌어도 이름이 거짓이 되지 않는다.

---

## 1. 개요

초등 2학년 딸의 사칙연산 연습을 위한 개인용 학습 도구. 매일 저녁 A4 2장을 인쇄해 손으로 풀고, 아이패드에서 3분 구구단 스프린트를 하고, 아빠가 채점 결과를 입력한다. 일요일에 주간 리포트 1장을 인쇄해 냉장고에 붙인다.

눈높이·구몬 같은 학습지의 작동 원리(① 매일 짧게 ② 스몰스텝 ③ 반복 ④ 속도 측정 ⑤ 통과 게이트 ⑥ 즉시 채점)를 가져오되, 종이가 구조적으로 못 하는 것과 화면이 구조적으로 못 하는 것을 매체로 분리한다.

| 영역        | 훈련 목표                            | 매체     | 이유                          |
| ----------- | ------------------------------------ | -------- | ----------------------------- |
| 구구단      | 인출 **속도** (2.5초 내 무의식 반응) | 아이패드 | 반응시간 측정은 종이로 불가능 |
| 세로셈      | 자릿수 정렬 + 절차 수행              | 종이     | 손으로 쓰는 과정 자체가 훈련  |
| 전략·문장제 | 수 감각, 상황→식 번역                | 종이     | 시간을 들여 생각해야 함       |

핵심 전제: **8살이 구구단을 못 외우는 건 81개 전부가 약해서가 아니라 특정 10~15개만 약한 것이다.** 전면 반복은 아이 시간의 대부분을 이미 아는 걸 다시 푸는 데 쓴다. 이 낭비를 없애는 것이 종이 문제집 대비 이 도구의 존재 이유다.

## 2. 목표와 비목표

### 목표

- 매일 12~15분 안에 끝나는 루틴이 **끊기지 않고 지속**될 것
- 약한 지점(느린 구구단 식, 취약한 세로셈 유형, 안 되는 전략)을 **데이터로 특정**할 것
- 아빠의 일일 개입을 **1~2분** 이내로 유지할 것
- 딸이 자기 진척을 **눈으로** 볼 것

### 비목표 (1차 범위 밖)

- **나눗셈** — 3학년 과정. 구구단 자동화 이전에는 의미 없음. 유형 추가가 가능한 구조만 열어두고 구현하지 않음
- 사진 채점(OCR/비전), 서버·기기 간 동기화, 멀티유저, 계정
- 소마식 교구·토론·발표 — 매체가 맞지 않음
- 문해력·심화수학 확장 — 스코프를 넓히면 15분 루틴이 무너짐

### 2학년 교육과정 전제

2학년 범위는 `+`, `−`, `×`(2-2 곱셈구구)의 3종이다. 나눗셈은 3학년 1학기다. "사칙연산 연습"이라는 요구는 실제로는 이 3종 + 덧셈과 뺄셈의 관계(역연산)를 의미한다.

## 3. 사용자와 일일 루틴

사용자는 **딸(초2)**과 **아빠** 둘뿐이다. 계정·로그인 없음.

```
19:00  [아빠]  아이패드에서 인쇄 → AirPrint로 2장
19:05  [딸]    1장 계산 (세로셈 8 + □ 채우기 2)      ~6분
19:11  [딸]    2장 생각하는 문제 (전략 2 + 문장제 2)  ~5분
19:16  [딸]    아이패드 구구단 스프린트 30문제        3분
19:19  [아빠]  채점 — 틀린 것만 탭 + 오늘 어땠어 1탭  ~1분
────────────────────────────────────────────────
       딸 스크린타임 3분 · 아빠 개입 1~2분
```

일요일에는 채점 저장 직후 주간 리포트로 자동 전환된다.

## 4. 아키텍처

**서버 없음.** 정적 파일을 GitHub Pages에서 HTTPS로 서빙하고, 아이패드 홈 화면에 추가한 PWA로 실행한다. 데이터는 아이패드의 IndexedDB에만 존재한다.

```
git push → GitHub Actions(빌드/테스트) → GitHub Pages(HTTPS)
                                              ↓
                                  아이패드 홈 화면 아이콘
                                              ↓
                              Service Worker 캐시 → 오프라인 동작
                                              ↓
                                    IndexedDB (로컬 데이터)
```

### 서버를 두지 않은 이유

매일 저녁 루틴에서 가장 무서운 것은 마찰이다. "어? 안 열리네"가 두 번 나오면 그 앱은 끝난다. 서버 구성은 마찰 지점을 3개(맥 전원 / 네트워크 / 프로세스) 만들고, 서버리스는 0개다.

유지보수 관점에서도 같은 결론이다. 앞으로 발생할 변경은 전부 "문제 생성 로직"과 "인쇄 레이아웃"이며 인프라를 하나도 건드리지 않는다. 그 변경을 위해 서버·DB·배포 파이프라인을 유지하는 것은 순손해다.

### 대가와 완화

- **아빠 폰에서 리포트를 볼 수 없다** → 리포트 화면의 공유 버튼(Web Share API)으로 텔레그램 전송
- **데이터가 아이패드에 묶인다** → 주 1회 JSON 내보내기(일요일 리포트 화면), 30일 이상 미백업 시 배지 표시

### origin 고정 원칙

IndexedDB는 origin(프로토콜+호스트+포트)별로 격리된다. **배포 주소를 바꾸면 기존 데이터에 접근할 수 없다.** 배포 URL은 처음에 확정하고 변경하지 않는다. 불가피하게 옮길 경우 옛 주소에서 export → 새 주소에서 import로 이전한다.

부수 효과로, 개발 중 `http://localhost:5173`에 쌓이는 테스트 데이터는 실제 데이터와 완전히 분리된다.

## 5. 기술 스택

| 구분          | 선택                                        | 비고                                          |
| ------------- | ------------------------------------------- | --------------------------------------------- |
| 언어          | TypeScript (`strict`)                       |                                               |
| 프레임워크    | **없음** (바닐라 DOM)                       | 화면 5개, 상태 거의 없음. 해시 라우팅         |
| 런타임 의존성 | **0개**                                     |                                               |
| 빌드          | Vite                                        | dev 서버, HMR, 해시 파일명                    |
| PWA           | vite-plugin-pwa                             | manifest + Service Worker + 업데이트 흐름     |
| 테스트        | Vitest                                      | Vite 설정 공유                                |
| 포맷          | Prettier만 (ESLint 없음)                    | `strict`가 실질적인 건 다 잡음                |
| 패키지 매니저 | npm                                         | Node에 딸려 옴 — 설치할 부품이 하나 적음      |
| Node          | mise로 `24` 고정                            | `mise.toml`                                   |
| 저장          | IndexedDB                                   | 얇은 래퍼 4함수                               |
| 인쇄          | `window.print()` + `@page` / `@media print` | PDF 라이브러리 없음                           |
| 배포          | GitHub Pages (public repo) + Actions        | private 필요 시 Cloudflare Pages, 코드는 동일 |

`vite-plugin-pwa`가 스택 선택의 결정적 이유다. PWA의 대표적 실패는 *"코드를 고쳐 배포했는데 아이패드는 계속 구버전"*이며, 원인 파악이 극도로 어렵다(내 코드는 맞는데 화면만 옛것). 캐시 버저닝·업데이트 감지를 직접 짜지 않는다.

## 6. 콘텐츠 엔진

두 엔진이 서로 다른 신호로 굴러간다. 구구단은 **반응시간**, 종이 문항은 **정오답**이다.

### 6.1 구구단 엔진 (`facts.ts`)

**대상**: 81개 식 (`1×1` ~ `9×9`). 순서쌍이므로 `7×8`과 `8×7`은 별개 레코드다.

**목표는 정답률이 아니라 속도다.**

| 상태       | 판정                                                | 스프린트 30문제 중 비중 |
| ---------- | --------------------------------------------------- | ----------------------- |
| `fluent`   | 최근 3회 연속 정답 **AND** 반응시간 중앙값 ≤ 2500ms | 25% (간격 반복 대상만)  |
| `learning` | 정답은 나오지만 느리거나 불안정                     | **60%**                 |
| `new`      | 아직 출제되지 않음                                  | 15%                     |

**반응시간 정의**: 문제 표시 → **첫 숫자 키 터치**까지. 확인 버튼까지의 시간은 손가락 속도라 노이즈이므로 제외한다.

**간격 반복**: `fluent` 판정 후 1일 → 3일 → 7일 → 14일 간격으로만 재등장. 오답이 나오면 `learning`으로 강등하고 간격을 리셋한다.

**도입 순서**: 교과서 순서를 따른다 — `2 → 5 → 3 → 6 → 4 → 8 → 7 → 9`단. (`1`단은 초기부터 열림.) 경험적 병목인 `6×7`, `7×8`, `8×6`, `9×7` 부근이 자연히 뒤로 밀려, 앞에서 자신감을 쌓은 뒤 만나게 된다.

**배분 폴백**: 해당 상태의 식이 부족하면(예: due인 `fluent` 식이 7개 미만) `learning`에서 채운다.

**입력 방식**: 숫자 키패드 직접 입력. **4지선다는 쓰지 않는다** — 재인(recognition)이지 인출(recall)이 아니라 훈련 효과가 사라진다.

**오답 처리**: 빨간 X 대신 정답을 1.5초 노출하고 진행. 해당 식은 **같은 세션 뒤쪽에 재등장**한다. 즉시 재도전은 단기기억으로 맞히는 것이라 훈련이 되지 않는다.

**타이머는 화면에 표시하지 않는다.** 8살에게 시간 압박은 독이며, 불안해지면 인출이 느려져 측정하려던 값이 측정 행위 때문에 오염된다.

**세션 결과**는 정답 개수가 아니라 속도 변화로 보여준다 ("어제보다 0.4초 빨라졌어 🚀"). 정답 개수를 강조하면 아이가 안전한 식만 빨리 누르고 어려운 식에 시간을 쓰지 않는다.

### 6.2 세로셈 엔진 (`vertical.ts`)

**유형 9종** (내부 도입 순서. 화면에는 표시하지 않음):

| #   | 태그            | 내용                              |
| --- | --------------- | --------------------------------- |
| 1   | `add2-nocarry`  | 두 자리 + 두 자리, 받아올림 없음  |
| 2   | `sub2-noborrow` | 두 자리 − 두 자리, 받아내림 없음  |
| 3   | `add2-carry`    | 받아올림 1회                      |
| 4   | `sub2-borrow`   | 받아내림 1회                      |
| 5   | `add3-carry1`   | 세 자리, 받아올림 1회             |
| 6   | `add3-carry2`   | 세 자리, 받아올림 2회             |
| 7   | `sub3-borrow1`  | 세 자리, 받아내림 1회             |
| 8   | `sub3-borrow2`  | 세 자리, 받아내림 2회             |
| 9   | `sub-zero`      | **0이 낀 받아내림** (`300 − 147`) |

`sub-zero`는 2학년 오답의 최대 산지이므로 열린 뒤에는 매일 1~2문항이 섞인다.

**도입 조건**: 현재 열린 유형들의 최근 10문제 정답률이 90% 이상이면 다음 유형이 열린다. **열린 유형은 사라지지 않고** 계속 출제 풀에 남는다(유지 복습).

> **표본이 10회 미만이면 정답률을 0으로 본다 — 의도된 규칙이다.** 결과적으로 9문제를 전부 맞힌 아이(9/9)는
> 다음 유형이 열리지 않고, 10문제 중 9개를 맞힌 아이(9/10)는 열린다. 10번째 시도에서 0 → 0.9로 튀는
> 불연속이 생기는데, 이는 **적은 표본을 숙련의 증거로 인정하지 않겠다**는 선택이다. 3~4문제 연속 정답만으로
> 다음 유형을 열면 운으로 통과한 아이가 준비 없이 어려운 유형을 만난다.
>
> 열린 유형은 회수되지 않으므로 이 규칙이 아이를 되돌려 잠그는 일은 없다 — 다음 유형의 도입을 늦출 뿐이다.
> 매끄러운 평균으로 "고치지" 말 것.

**8문항 배분**: 정답률이 낮은 유형에 가중치를 주고, 신규 유형이 열렸으면 1~2문항 배정.

**진단 트릭**: 아빠는 O/X만 입력하지만 **문항마다 유형 태그가 이미 붙어 있으므로**, X만 모아도 `"0이 낀 받아내림 — 이번 주 6문제 중 3개 오답"`이 자동으로 나온다. 아빠가 아무것도 분류하지 않았는데 진단이 나오는 구조다.

### 6.3 역연산 (`inverse.ts`)

**템플릿 4종**: `a + ? = c`, `? + b = c`, `a − ? = c`, `? − b = c`

2학년 1학기 교육과정의 "덧셈과 뺄셈의 관계"에 해당하며, 나중에 나눗셈(`? × 7 = 56`)으로 가는 다리다.

**가로식으로 출제한다.** 세로 형식(`+ □□`)은 각 자릿수를 받아올림까지 고려해 역추론해야 해서 2학년에게 과하다.

**하루 2문항.** 첫 문항에만 문장 힌트를 붙인다 (`27에 얼마를 더하면 45가 될까요?`). 매번 힌트를 주면 힌트를 읽고 푸는 습관이 생긴다.

**제약**: 답은 자연수, 모든 수는 1000 미만.

### 6.4 전략 존 (`strategy.ts`)

세로셈이 *절차 숙달*이라면 전략은 ***수 감각(number sense)***이다. 세로셈만 훈련한 아이는 막히면 길이 하나뿐이지만, 방법을 여러 개 아는 아이는 우회할 수 있다.

**카탈로그 8종**

| 연산 | 전략                              | 예                      | 강한 조건                     |
| ---- | --------------------------------- | ----------------------- | ----------------------------- |
| 뺄셈 | `split-place` 자리로 나누어 빼기  | `68−25 → (60−20)+(8−5)` | 받아내림 **없을 때**          |
| 뺄셈 | `anchor` 기준수 만들어 빼기       | `52−19 → 52−20+1`       | 빼는 수가 9, 19처럼 애매할 때 |
| 뺄셈 | `split-subtrahend` 빼는 수 가르기 | `63−28 → 63−20−8`       | 언제나 안전                   |
| 뺄셈 | `count-up` 채워 세기              | `28에서 63까지 얼마?`   | 두 수가 가까울 때             |
| 덧셈 | `make-ten` 10 만들어 더하기       | `27+15 → 27+3+12`       |                               |
| 덧셈 | `round-adjust` 어림하고 고치기    | `27+19 → 27+20−1`       |                               |
| 곱셈 | `double` 두 배 하기               | `7×8 = 7×4×2`           |                               |
| 곱셈 | `minus-one` 하나 빼기             | `9×7 = 70−7`            |                               |

**하루 2문항**: "오늘의 방법" 1 + "어제의 방법" 1. **하루에 새 방법은 최대 1개만 소개**한다 — 한 번에 여러 개를 들이밀면 8살은 아무것도 안 쓴다.

**과정을 빈칸으로 인쇄한다.** 여러 방법 훈련의 함정은 답이 아니라 과정을 봐야 한다는 것인데, 전략의 뼈대를 빈칸으로 찍어내면 아이는 채우기만 하고 아빠는 최종 답 하나만 O/X 하면 된다.

**전략은 데이터로 정의한다.** 이것이 유지보수의 핵심이다:

```ts
type StrategyStep = { text: string; blanks: number[] }

// split-place, 68 − 25
steps: [
  { text: '60 − 20 = {}', blanks: [40] },
  { text: '8 − 5 = {}', blanks: [3] },
  { text: '합치면  68 − 25 = {}', blanks: [43] },
]
```

전략마다 단계 구조가 다르지만 **렌더러는 하나면 된다.** 새 전략을 추가할 때 `steps` 생성 함수만 쓰면 되고 인쇄 코드는 손대지 않는다.

**같은 수식을 두 방법으로 배치**하는 경우를 섞는다. 답이 똑같이 나오는 것을 눈으로 보는 것이 수 감각의 출발점이다.

**전략은 레벨이 아니라 체크리스트다.** `split-place`와 `count-up` 사이에 위계가 없으므로 순서가 아니라 수집으로 다룬다 (리포트에 `3 / 8`).

**중요한 분리**: 전략은 단기적으로 계산 속도를 떨어뜨린다("어떤 방법으로 풀까?" 고민하는 순간 느려진다). 따라서 딸에게 명시적으로 나눠서 말한다 — _"종이는 천천히 생각하는 시간, 아이패드는 빨리 하는 시간."_ 이걸 안 나누면 스프린트에서 전략을 떠올리려다 반응시간 데이터가 오염된다.

```
   [이해 단계]              [자동화 단계]
   종이 · 전략 존     →      아이패드 · 스프린트
   "왜 그렇게 되지?"          "생각 없이 튀어나오게"
```

### 6.5 문장제 (`word.ts`)

**하루 2문항.** 곱셈 개념(묶어 세기, `~의 몇 배`)을 템플릿으로 생성한다.

**이름 슬롯**: 등장인물에 딸 이름(`childName`)과 친구 이름(`friendNames`)이 들어간다. 사소해 보이지만 8살에게는 몰입도 차이가 크다.

> **2026-08-04 결정: 이름 입력 화면 제거, 이름은 코드가 출처.** 첫 실행 때 이름을 묻던 셋업 화면(홈 진입 게이트)은 사용자가 불필요하다고 판단해 제거했다. 이 절을 근거로 셋업 화면을 되살리지 말 것.
>
> 화면을 없애자 **기기에 남은 옛 `childName`을 고칠 방법이 사라지는** 문제가 곧바로 드러났다 — 실제로 `'○○'`이 저장돼 있던 기기에서 문장제가 `○○이가 …`로 나왔다. 그래서 등장인물 이름은 `engine/word.ts`의 `WORD_NAMES`(딸 `서아`, 친구 지호·민아)를 유일한 출처로 삼고, `Settings.childName`·`friendNames`는 **읽지 않는다**(백업 스키마 호환으로만 남는 필드 — `derived`와 같은 취급). 이름을 바꾸려면 그 상수를 고친다.
>
> 이름은 상수를 직접 참조하지 않고 `composeWordItems`의 인자로 흐른다. 받침 있는 이름의 조사 활용(`서연이가`)은 받침 없는 `서아`로 검사할 수 없어 테스트가 다른 이름을 주입할 수 있어야 하기 때문이다.

**첫 문항에 그림 칸**을 둔다. 2학년 곱셈은 "묶어 세기를 그림으로 나타내기"가 교육과정의 핵심이며, 식만 쓰게 하면 이 단계를 건너뛴다.

> **2026-08-04: 그림 칸에 라벨을 붙였다.** 라벨 없는 빈 네모는 목적을 전달하지 못한다 — 사용자가 인쇄물을 보고 "빈 네모 공간을 둔 이유가 있냐"고 먼저 물었다. 아빠가 모르면 8살은 더 모른다. `묶어 세기를 그림으로 나타내 보세요`를 칸 위에 작게 얹어, 이 절의 의도가 종이 위에서 스스로 말하게 한다.

### 6.6 하루 조립 (`compose.ts`)

| 장                      | 구성                | 문항 | 예상 시간 |
| ----------------------- | ------------------- | ---- | --------- |
| **1장 — 계산**          | 세로셈 8 + 역연산 2 | 10   | ~6분      |
| **2장 — 생각하는 문제** | 전략 2 + 문장제 2   | 4    | ~5분      |
| 아이패드                | 구구단 스프린트     | 30   | 3분       |

**총 14문항 · 12~15분.** (§6.8의 하향 조정이 걸리면 세로셈이 6문항으로 줄어 총 12문항.)

1장과 2장은 성격이 다르므로 종이로 분리한다. "1장 끝!"이라는 중간 성취감이 생기고, 2장은 문항이 4개뿐이라 받았을 때 부담이 아니라 안도가 된다.

**단면 2장으로 인쇄한다.** 집 프린터가 양면(duplex)을 지원하지 않으므로 선택지가 없다. 양면이 가능해지면 종이·잉크가 절반이 되고 분실 위험도 줄므로 전환을 검토할 만하다 — 1장과 2장을 동시에 볼 일이 없는 순차 구조이므로 뒤집기가 부담이 되지 않는다.

**조립 규칙**

- 같은 수식이 하루 안에 중복되지 않는다
- 생성 실패 시 재시도 N회 → 더 쉬운 유형으로 폴백. **빈 문제지는 절대 내지 않는다**

**결정성**: 그날 문제는 생성 시점에 `days[date].sheet`에 못박힌다. 재인쇄는 저장된 것을 다시 렌더할 뿐 새로 만들지 않는다. 이것이 지켜지지 않으면 종이를 다시 뽑았을 때 문제가 달라지고, 채점 화면이 **어느 종이 기준인지 모르는 채로** O/X를 받아 데이터가 조용히 오염된다.

### 6.7 진단과 점검의 날

|               | 시점    | 동작                                          |
| ------------- | ------- | --------------------------------------------- |
| **초기 진단** | 1주차   | 적응 off. 전 범위를 얕게 훑어 기준선 확보     |
| **점검의 날** | 4주마다 | 적응 off. 전 범위 얕게 → **유창 판정 재검증** |

점검의 날이 필요한 이유: `fluent` 판정된 식은 14일 간격으로만 등장하는데, 8살은 2주 쉬면 잊는다. **판정이 낡아가는데 확인할 장치가 없으면** 리포트의 `37/81`이 실제로는 `30/81`일 수 있다.

점검의 날 결과가 **월간 리포트**의 근거가 된다. 주간 리포트는 "이번 주 변화", 월간은 "진짜 실력"이다.

두 경우 모두 `Day.kind = 'checkup'`으로 기록하며 초기 진단과 같은 출제 로직을 재사용한다.

### 6.8 안전장치

**① 분량은 늘리지 않는다.** 잘한다고 문항을 늘리면 "잘하면 벌 받는" 구조가 되고 루틴이 죽는다. 상향 조정은 존재하지 않는다.

**② 아빠의 1탭 신호로 하향 조정한다.** 채점 화면 하단:

```
오늘 어땠어?    😀 여유    😐 딱 맞음    😫 힘들어함
```

- `😫` 3일 연속 → 세로셈 8 → 6으로 자동 하향
- `😀` 5일 연속 → 8로 복구

아빠가 판단할 필요 없이 탭 하나만 늘어난다.

**③ 연속 실패 시 난이도 하향.** 좌절 방지가 정확도보다 우선한다.

**④ 연속일수(streak) 규칙**

| 지표            | 기준                           |
| --------------- | ------------------------------ |
| 🔥 **연속일수** | **스프린트 완료**만으로 인정   |
| ✅ **완료일수** | 종이 채점 + 스프린트 **둘 다** |

여행이나 늦은 날에도 3분은 할 수 있으므로 아이에게 보이는 불꽃은 꺼지지 않고, 아빠 리포트의 완료일수는 정직하게 남는다. **관대함과 정직함을 두 숫자로 분리**한다.

**하루 빠진 것은 봐준다. 이틀 연속 빠지면 리셋.** 아픈 날·외출은 한 달에 한두 번 반드시 생기며, 그때마다 13일이 0이 되면 다시 쌓을 의욕을 잃는다.

**⑤ 하루의 경계는 새벽 4시(로컬).** 저녁이 늦어져 자정을 넘겨도 전날로 기록된다.

- 문장제 2문항 — 첫 문항에 그림 칸

### 일요일 · 주간 리포트

**절취선으로 딸용/아빠용을 나눈다.** `0이 낀 받아내림 3/6 ⚠️` 같은 정보는 아이가 냉장고에서 매일 볼 것이 아니다.

**절취선 위 (냉장고행)**

- 🔥 연속일수 · ✅ 완료일수
- **구구단 정복 지도** — 9×9 격자
- 이번 주 새로 정복한 식 목록
- 평균 반응시간 변화
- 배운 방법 `3 / 8`

**구구단 정복 지도의 설계**

| 상태         | 표시                         |
| ------------ | ---------------------------- |
| `fluent`     | 검게 채우고 **답 숫자 표시** |
| 이번 주 신규 | 굵은 테두리 + 답 숫자        |
| `learning`   | 연한 회색, 빈칸              |
| `new`        | 흰 칸, 빈칸                  |

**정복한 칸에만 답이 보인다.** 아직 못 외운 칸은 비어 있어 벽에 붙여둬도 컨닝이 안 되고, 목표가 "구구단 외우기"에서 **"빈칸을 채워 나가기"**로 바뀐다. 부수 효과로 `3×5`를 정복하면 `5×3`도 함께 칠해져 대각선 대칭이 드러나며, 아이가 교환법칙을 스스로 발견할 가능성이 있다.

**절취선 아래 (아빠용)**

- 세로셈·역연산·전략의 유형별 정답률 (⚠️ 표시)
- 가장 느린 식
- 다음 점검의 날
- **다음 주 자동 조정** — 시스템이 이미 무엇을 바꿨는지 알려준다. 아빠가 할 일은 없다

**레벨 표시는 두지 않는다.** 6단계 사다리를 시안까지 만들어 검토했으나 2학년 한 학년을 쪼갠 것이라 한 단계가 몇 주씩 움직이지 않아 제거했다. 진도감은 **구구단 지도(37/81) · 연속일수 · 반응시간 개선** 세 축이 담당한다. 유형 도입 순서는 내부 로직으로만 존재한다.

```ts
      kind: 'inverse'
      tag: InverseTag
      template: 'a+?=c' | '?+b=c' | 'a-?=c' | '?-b=c'
      a?: number
      b?: number
      c: number
      hint?: string
      answer: number
    }
  | {
      id: string
      kind: 'strategy'
      tag: StrategyId
      a: number
      b: number
      op: '+' | '−'
      steps: StrategyStep[]
      answer: number
    }
  | {
      id: string
      kind: 'word'
      tag: WordTag
      text: string
      needsDrawing: boolean
      expression: string
      unit: string
      answer: number
    }
```

```ts
// ─── 파생 상태 (캐시. 지워도 복구됨) ───
type Derived = {
  facts: Record<string, FactState> // 81개
  types: Record<VerticalTag | InverseTag, TypeState>
  strategies: Record<StrategyId, StrategyState>
}

type FactState = {
  status: 'new' | 'learning' | 'fluent'
  medianMs: number | null
  streak: number
  interval: 1 | 3 | 7 | 14
  nextDue: string | null
}
```

**이 분리가 핵심이다.** 유창 기준을 `2500ms → 2200ms`로 바꾸고 싶어지는 날이 온다(6개월 데이터를 보면 지금 기준이 헐거웠음을 알게 된다). 로그가 원본으로 남아 있으면 `recompute(days) → derived` 한 번으로 과거 전체가 새 기준으로 재해석된다. 파생 상태만 저장했다면 과거는 영영 되돌릴 수 없다.

**규칙: `derived`는 캐시다. 언제든 지우고 다시 만들 수 있어야 한다.**

### 저장소

| store  | keyPath     | 내용                   | 크기                    |
| ------ | ----------- | ---------------------- | ----------------------- |
| `days` | `date`      | 원본 로그              | 하루 ≈ 3KB, 1년 ≈ 1.1MB |
| `meta` | 단일 레코드 | `derived` + `settings` | 수십 KB                 |

앱 시작 시 `meta`만 읽는다. `days`는 재계산·과거 조회 시에만 로드한다.

**IndexedDB를 선택한 이유**: localStorage는 5MB 천장(3~4년 후 도달)과 동기 동작(저장 시 UI 정지)이 문제다.

**API는 `db.ts` 안에 가둔다.** IndexedDB는 이벤트 콜백 기반이라 장황하므로, 밖으로는 `getDay` / `putDay` / `getMeta` / `putMeta` 4개만 노출한다. 앱 코드 어디에서도 IndexedDB라는 사실을 알지 못해야 한다.

### 재계산 트리거

- 저장할 때마다 증분 업데이트
- `ALGO_VERSION` 상수가 저장된 값과 다르면 전체 재계산
- 설정 화면에 수동 "다시 계산" 버튼

## 10. 백업과 마이그레이션

```json
{ "app": "haruchi", "schemaVersion": 1,
  "exportedAt": "2026-08-02T20:14:00+09:00",
  "days": [...], "meta": {...} }
```

- **내보내기** — Blob → 다운로드 → 파일 앱(iCloud Drive). 일요일 리포트 화면에서
- **가져오기** — 파일 선택 → **전체 교체**. 병합하지 않는다 (아이패드 한 대만 쓰는데 병합 로직은 순수 부채다). 확인 다이얼로그 필수
- `lastExportedAt`이 30일 이상 지나면 리포트 화면에 배지
- 마이그레이션은 `schemaVersion` + 함수 배열

서버가 없으므로 **백업을 잊는 것이 유일한 실질 리스크**다. export한 JSON은 데이터를 들여다보는 실질적 수단이기도 하다(IndexedDB는 SQLite처럼 CLI로 열 수 없다).

## 11. 에러 처리

### 원칙: 조용히 실패하지 않는다

사용자는 매일 저녁 15분을 쓰는 8살과 지친 아빠다. 뭔가 안 될 때 그 자리에서 보이지 않으면 안 되는 채로 며칠이 흘러간다.

| 상황                   | 대응                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| IndexedDB 열기 실패    | 앱은 뜨되 "저장 안 되는 상태"를 명시. 인쇄는 허용, 채점 저장은 차단                         |
| 저장 실패 (Quota)      | 즉시 알림 + 백업 유도. 1년 이상 지난 `days` 정리 제안                                       |
| 잘못된 import 파일     | 스키마 검증 후 거부, **기존 데이터 보존**                                                   |
| Service Worker 새 버전 | "새 버전이 있어요" 배너 → 탭하면 reload. **자동 reload 금지** (스프린트 중 새로고침은 재앙) |
| 시계 역행              | 오늘이 마지막 기록보다 과거면 경고, 덮어쓰기 방지                                           |
| 문제 생성 실패         | 재시도 N회 → 더 쉬운 유형으로 폴백. 빈 문제지 금지                                          |

**스프린트 중단 → 그 세션은 없던 일로 한다.** 문항마다 저장하면 데이터가 남지만 **부분 세션이 반응시간 통계를 오염시킨다** (전화 받다가 8초 뒤에 누른 값이 `7×8은 8초`로 박힌다). 3분짜리이므로 다시 하면 된다. 재진입 시 "이어하기" 선택지는 두지 않는다 — 8살에게 선택지 자체가 마찰이다.

**채점 누락은 반드시 다시 묻는다.** 아빠가 깜빡하는 일은 반드시 생기고, 채점이 없으면 적응 엔진이 굶는다. 홈 화면 배너 + 며칠 밀린 것도 소급 입력 가능.

## 12. 테스트 전략

인쇄 레이아웃 버그는 눈에 보이지만, **`503 − 276`의 정답을 227이 아니라고 채점하는 버그는 보이지 않는다.** 딸이 맞게 풀고 X를 받는다. 따라서 테스트는 전부 `engine/`에 집중한다(순수 함수이므로 DOM 불필요).

### 속성 기반 테스트 — 문제 생성기

가장 값어치 있는 테스트다. 유형 정의와 생성기가 어긋나면 *"0이 낀 받아내림을 연습시킨다"*는 전제 자체가 거짓말이 되는데, 종이를 눈으로 봐서는 잡을 수 없다.

```
1000회 생성해 전부 만족하는지:
  sub-zero     → 피감수에 0이 실제로 있고 받아내림이 실제로 발생
  add2-carry   → 받아올림이 정확히 1회
  모든 뺄셈    → 결과가 음수가 아님
  inverse      → 답이 자연수, 1000 미만
```

### 단위 테스트

- **`facts`** — 유창 판정 경계값(2500ms는 fluent, 2501ms는 아님 / 3회는 되고 2회는 안 됨), 간격 `1→3→7→14`, 오답 시 강등·리셋, 30문제 60:25:15 배분과 폴백
- **`strategy`** — `steps`의 `blanks`가 실제 계산과 일치. 각 전략이 자기가 강한 조건에서만 출제되는지
- **`word`** — 렌더 결과의 답이 `expression`과 일치, 이름 슬롯이 비지 않음
- **`compose`** — `settings`의 문항 수대로 구성(기본 14, 하향 시 12), 같은 수식 중복 없음, 점검의 날엔 적응 off
- **`derive`** — ⓐ 같은 `days` → 항상 같은 `derived` (결정성) ⓑ **증분 업데이트 결과 == 처음부터 재계산 결과**. ⓑ가 깨지면 "로그만 있으면 복구된다"는 설계 전제가 무너진다. 30일치 가상 로그로 골든 테스트

### 하지 않는 것

- DOM·화면 단위 테스트 (개인 앱에 비용 대비 값이 나오지 않음)
- **인쇄 레이아웃 자동 검증** — A4에 실제로 뽑아 딸이 연필로 풀어봐야 여백이 충분한지 알 수 있다. 첫 주에 몇 차례 조정 예상

### CI

GitHub Actions 한 파일에 `npm test` → 통과해야 배포.

## 14. 첫날 실물 확인 체크리스트

자동화로 잡을 수 없고 실물로만 알 수 있는 항목. **실사용을 시작하기 전에** 확인한다(이름 설정 단계는 2026-08-04에 제거됐다 — §6.5).

1. **iOS 홈화면 웹앱 ↔ Safari 탭의 IndexedDB 공유 여부** — iOS 버전에 따라 저장소가 분리되어 "사파리에서 쓰다가 홈 화면에 추가했더니 데이터가 없다"가 발생한 전례가 있다. 결론과 무관하게 대응은 동일하다: **처음부터 홈 화면 아이콘으로만 사용하는 규칙**을 둔다
2. **AirPrint 실제 여백** — 프린터마다 인쇄 불가 영역이 다르므로 `@page margin` 조정
3. **아이패드 키패드 터치 크기** — 8살 손가락 기준
4. **반응시간 측정의 타당성** — 아빠가 직접 30문제를 풀어 자기 값이 1초 안쪽으로 나오는지 확인. 측정 코드가 틀렸다면 여기서 드러난다
