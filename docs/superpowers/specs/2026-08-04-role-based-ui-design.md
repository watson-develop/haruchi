# 역할별 화면 분리 — 부모 홈과 아이 홈

작성: 2026-08-04 · 대상: 기본 설계 문서(`2026-08-02-haruchi-design.md`) §7 「화면 · 홈」을 대체한다

## 0. 결정 경위

기본 설계 §7의 홈 그림에는 처음부터 버튼마다 역할이 달려 있었다 — `문제지 인쇄`=아빠, `구구단 스프린트`=딸, `채점하기`=아빠. 그런데 구현된 홈은 그 역할을 무시하고 여섯 버튼을 한 줄로 세웠다. 사용자가 2026-08-04에 이 불일치를 지적했다: "기능적 나열의 버튼들이 보면 롤베이스로 나눠서 각자 롤에 맞는 인터페이스가 필요할 것 같아."

**분리 목적(사용자가 고른 넷 전부)**

1. 아이가 정답을 못 보게 — 채점 화면은 모든 문항의 정답을 표시한다(§7 「채점」: "정답을 문항 옆에 표시해 아빠가 암산하지 않게 한다"). 지금은 아이가 그 화면에 닿는 것을 막는 것이 하나도 없다
2. 아이 화면을 단순하게 — 8살에게 버튼 여섯 개는 많다
3. 아이 화면을 아이답게 — 색과 카드까지 쓴다
4. 부모 도구를 아이 눈에서 치우기

**잠금은 두지 않는다(사용자 결정).** PIN을 검토했으나 매일 두 번 쓰는 아빠에게 마찰이 남는다는 이유로 기각했다. 그 대신 **목적 1의 달성 범위가 좁아진다** — §8에 한계로 명시한다.

## 1. 범위

**한다**

- 홈을 두 화면으로 나눈다: 아이 홈(`#/`)과 부모 홈(`#/parent`)
- 아이 홈에 색과 카드를 도입한다
- 각 화면의 "← 홈"이 자기 역할의 홈으로 돌아가게 한다
- `pendingGradeDate`를 화면에서 엔진으로 옮기고 테스트를 붙인다

**하지 않는다**

- 잠금·PIN·역할 기억(§0 참고)
- 저장 스키마 변경 — `Settings`에도 `Day`에도 새 필드가 없다
- 부모 화면(인쇄·채점·리포트) 자체의 재설계 — 홈에서의 배치만 바뀐다
- 다크 모드

## 2. 구조 — 라우팅과 파일

역할은 **저장하지 않는다.** 기억해야 할 데이터가 아니라 지금 보고 있는 주소일 뿐이다. 이 선택 덕분에 "아이 화면이 기본"이 규칙이 아니라 구조로 보장된다 — PWA 아이콘·새로고침·앱 재시작이 모두 `#/`로 떨어진다.

| 파일                         | 내보내기           | 경로        | 로딩                                                               |
| ---------------------------- | ------------------ | ----------- | ------------------------------------------------------------------ |
| `src/screens/home-child.ts`  | `renderChildHome`  | `#/` (기본) | 정적 import — 첫 화면이라 지연 로딩하면 흰 화면이 한 프레임 스친다 |
| `src/screens/home-parent.ts` | `renderParentHome` | `#/parent`  | 지연 import — 다른 화면과 같은 패턴                                |

기존 `src/screens/home.ts`는 삭제한다. `main.ts`에는 `#/parent` 분기 한 줄이 늘고 기본 분기가 `renderChildHome`으로 바뀐다.

**PWA manifest는 손대지 않는다.** `start_url`이 `/haruchi/`(해시 없음)라 그대로 `#/` → 아이 홈이 된다.

### 2.1 곁들여 옮기는 것 — `pendingGradeDate`

지금 `home.ts` 안에 있는 순수 함수다. 부모 홈으로 옮기는 김에 `src/engine/report.ts`로 빼고 단위 테스트를 붙인다. 화면 안에 있어서 지금은 테스트가 하나도 없는데, "빈 `sheet`인 날은 제외"라는 미묘한 규칙을 담고 있다(스프린트만 한 날에 미채점 배너가 영영 안 사라지던 문제의 수정 흔적이다).

## 3. 아이 홈 (`#/`)

```
    하루치
    8월 4일 화요일

        🔥 3일 연속

  ┌──────────────────────┐
  │                      │
  │   ▶ 구구단 스프린트     │   ← 화면 절반을 쓰는 큰 카드
  │      30문제 · 3분      │
  │                      │
  └──────────────────────┘

  ┌─────────┐  ┌─────────┐
  │ 구구단   │  │  EBS    │
  │  지도    │  │  강의   │
  └─────────┘  └─────────┘

                  부모 →
```

- **`🔥` 연속일수만 둔다. `✅` 완료일수는 부모 홈으로 보낸다.** 기본 설계 §6.8이 "관대함과 정직함을 두 숫자로 분리한다"고 이미 못박아 뒀는데, 구현된 홈은 두 숫자를 한 줄에 나란히 놓아 그 분리를 화면에서 지키지 못하고 있었다. 역할을 나누면 저절로 갈라진다
- 스프린트 카드의 3-상태(오늘 완료 `✓` / 점검의 날 `🔍` / 평소 `▶`)는 기존 `home.ts` 로직을 그대로 옮긴다. 점검 due 판정이 "오늘 스프린트를 이미 했으면 광고하지 않는다"까지 포함하는 것도 그대로다
- **인쇄·채점·리포트 버튼이 없다.** 아이가 정답에 닿는 경로가 화면에서 사라진다
- 하단의 `부모 →`는 작게 둔다. 목적 4를 지키되, 아빠가 매번 찾아 헤매지 않을 만큼은 보인다

## 4. 부모 홈 (`#/parent`)

```
  하루치 · 부모
  8월 4일 화요일
  ✅ 12일 완료 · 🔥 3일 연속

  [8월 3일 채점이 안 됐어요 — 지금 하기]

  ✓ 문제지 인쇄
    채점하기
    주간 리포트

  구구단 지도 · EBS 강의
  ← 아이 화면
```

- **미채점 배너는 부모 홈에만 둔다.** 아이 홈에 있으면 아이가 아빠 할 일을 독촉받는 꼴이 된다
- 인쇄·채점 버튼의 완료 표시(`✓`)와 "문제지를 먼저 인쇄해주세요" 안내는 기존 동작 그대로다
- **지도·EBS는 아이 홈이 주인이지만 부모 홈에도 한 줄 링크로 둔다**(사용자 결정). EBS 화면은 "어느 강까지 보고 그 이후는 보류"를 담은 진도 계획표라 실제로 부모가 읽는 것이고, 지도는 부모도 진도를 확인한다. 아이 홈처럼 카드로 크게 두지는 않는다
- 부모 홈은 담백한 기존 톤(`app.css`)을 그대로 쓴다. 색과 카드는 아이 홈에만 들어간다

## 5. 화면 소속과 "← 홈"의 목적지

지금 여섯 화면의 "← 홈"이 전부 `#/`로 간다(호출 지점은 12곳 — 한 화면이 정상 경로와 오류 경로 양쪽에 두는 경우가 있다). 분리 후 그대로 두면 **아빠가 채점을 마치고 홈을 눌러도 아이 화면으로 떨어져** 부모 흐름이 매번 끊긴다.

**규칙: 화면은 자기 소속 홈으로 돌아간다.** 소속은 하나로 고정한다.

| 화면                  | 소속 | "← 홈"의 목적지 |
| --------------------- | ---- | --------------- |
| 인쇄 (`#/print`)      | 부모 | `#/parent`      |
| 채점 (`#/grade`)      | 부모 | `#/parent`      |
| 리포트 (`#/report`)   | 부모 | `#/parent`      |
| 스프린트 (`#/sprint`) | 아이 | `#/`            |
| 지도 (`#/map`)        | 아이 | `#/`            |
| EBS (`#/ebs`)         | 아이 | `#/`            |

**받아들이는 마찰 하나**: 부모 홈에서 지도나 EBS를 열면 나올 때 아이 홈으로 떨어진다. 소속이 아이이기 때문이다. 부모 홈으로 돌아가려면 `부모 →`를 한 번 더 누른다. 대안은 "어디서 왔는지 기억하기"인데, 그것은 §2가 없애기로 한 상태를 되살리는 일이라 택하지 않았다. 예측 가능한 규칙 하나가 상태 없는 구조보다 비싸지 않다.

일요일 채점 저장 직후 `#/report`로 자동 전환되는 동작(기본 설계 §7)은 그대로다 — 리포트도 부모 소속이라 흐름이 끊기지 않는다.

## 6. 스타일

아이 홈 전용 스타일시트 `src/styles/kid.css`를 새로 만들어 `index.html`에 연결한다. `app.css`에 섞지 않는 이유는 **파일 경계로 오염을 막기 위해서**다 — 아이 화면에만 색과 큰 카드를 쓰기로 했으니, 부모 화면과 인쇄물의 담백한 톤이 실수로 물드는 일이 구조적으로 없어야 한다. 클래스는 전부 `.kid-` 접두사를 쓴다.

**색은 둘만 쓴다.**

| 색   | 출발값    | 쓰임                                       |
| ---- | --------- | ------------------------------------------ |
| 주황 | `#F2760C` | 주색 — 스프린트 카드 배경. `🔥`과 이어진다 |
| 초록 | `#1F9D55` | 완료 상태                                  |

두 값은 **출발점이지 확정이 아니다.** 아이패드 실물에서 보고 조정한다 — 흰 글씨를 얹었을 때 대비가 충분한지가 기준이다.

나머지는 기존 흑백을 유지한다. 8살용이라고 색을 늘리면 "오늘 뭘 눌러야 하는지"가 오히려 흐려진다. **완료된 스프린트는 지금처럼 회색으로 죽이지 않고 초록 체크로 바꾼다** — 아이 화면에서 완료는 비활성이 아니라 성취다.

인쇄 CSS(`print.css`)는 이 변경과 무관하다. 홈은 인쇄 대상이 아니다.

## 7. 데이터 흐름과 오류 처리

두 홈 모두 **읽기만 한다.** `getMeta()`와 `getAllDays()`를 읽고 각자 필요한 것만 계산한다.

| 홈      | 계산하는 것                                                               |
| ------- | ------------------------------------------------------------------------- |
| 아이 홈 | `sprintStreak`, `checkupDue`, 오늘 스프린트 여부                          |
| 부모 홈 | `completedCount`, `sprintStreak`, `pendingGradeDate`, 오늘 인쇄·채점 여부 |

저장하는 것도, 역할을 기록하는 것도 없다.

오류 처리는 기존 `home.ts` 패턴을 두 파일 모두 유지한다: 조회 실패를 전부 잡아 `showError` 배너를 띄우고, **`#app` 안에도 조작 수단을 남긴다.** 주소창이 없는 스탠드얼론 PWA에서는 이것이 없으면 강제 종료 말고 빠져나갈 길이 없다. 아이 홈은 재시도 버튼을, 부모 홈은 재시도와 `← 아이 화면`을 둘 다 둔다.

## 8. 테스트 전략과 한계

기본 설계 §12의 "DOM·화면 단위 테스트를 하지 않는다"를 그대로 따른다. 화면 분리 자체에는 자동 테스트를 만들지 않는다.

**엔진으로 옮기는 `pendingGradeDate`에는 단위 테스트 네 개를 붙인다.**

1. 미래 날짜와 오늘은 후보가 아니다
2. `sheet`가 빈 날(스프린트만 한 날)은 제외한다
3. 이미 채점한 날은 제외한다
4. 후보가 없으면 `null`

각 단언은 **변이 검증**으로 효력을 확인한다 — 구현을 일부러 틀리게 바꿔 그 테스트가 실제로 빨개지는지 보고 원복한다(HANDOFF 교훈 7번: "테스트가 자기가 검사한다고 주장하는 것을 실제로는 검사하지 못한다").

**정직하게 남기는 한계 둘**

- **분리는 실수를 막을 뿐 의도를 막지 못한다.** 잠금이 없으므로 §0의 목적 1은 "아이가 우연히 정답 화면에 들어가는 일이 없다"까지만 달성된다. 주소(`#/grade`)를 알고 치면 여전히 열린다. 이 범위를 넘으려면 PIN이 필요한데, 그것은 이번에 기각된 선택지다
- **역할 분리는 사람이 눌러 봐야 확인된다.** 두 홈의 버튼이 각각 맞는 화면으로 가는지, "← 홈"이 소속대로 돌아오는지는 실기기 확인 항목으로 HANDOFF에 남긴다

## 9. 이음새 조사 대상 (구현 계획의 태스크 0)

HANDOFF 교훈 6번("가장 값진 결함은 태스크 사이의 이음새에 있다 — 새 코드가 쓸 필드를 이미 읽고 있는 모든 곳을 나열하는 단계를 태스크 0으로 둘 것")에 따라, 계획을 쓰기 전에 아래를 훑는다.

- **`navigate('#/')` 호출 지점 전부**(현재 여섯 화면 12곳: `ebs` 1 · `grade` 2 · `map` 2 · `print-sheet` 2 · `report` 3 · `sprint` 2) — §5의 표대로 목적지를 나눈다. 한 화면 안에서도 정상 경로와 오류 경로가 따로 있으니 파일 단위가 아니라 호출 지점 단위로 훑는다. 하나라도 빠뜨리면 그 경로만 엉뚱한 홈으로 간다. **`sprint.ts:105`의 `navigate('#/')`는 주석 안이라 세지 않는다** — 단순 검색은 13곳으로 잡힌다
- **`renderHome`을 부르거나 import하는 곳** — `main.ts`의 기본 분기와 `home.ts` 자신의 재시도 경로
- **`pendingGradeDate`를 옮긴 뒤 `report.ts`의 기존 내보내기와 이름이 겹치지 않는지** — `completedCount`·`weeklyReport`·`latestCheckupReport`가 이미 있다
- **`checkupDue`·`sprintStreak`·`completedCount`의 호출자** — 두 홈으로 갈라지며 어느 쪽도 계산을 중복하지 않는지
- **`app.css`에서 홈 전용이던 규칙**(`.streak`, `.banner`, `.step`) — `.step`은 다른 화면도 쓰므로 아이 홈으로 가져가지 말고 `kid.css`에 별도 클래스를 만든다
