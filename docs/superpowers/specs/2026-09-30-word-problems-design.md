# 문장제 단계형 연습 설계

2026-09-30. 상태: 브레인스토밍 합의(사용자 승인 1~4절). 적대적 리뷰 전. 선행:
`2026-09-30-retire-paper-sheet-design.md`(종이 은퇴 — 옛 `word.ts`는 git 이력 `d80bfd1^`에만 있다).

## 1. 왜

딸은 연산 자체는 잘한다. 그래서 종이 세로셈·□ 채우기가 쉬워져 은퇴했다. 약한 곳은 **응용·문장제**이고
실수가 잦은데, 어디서 틀리는지는 부모도 아직 모른다(사용자 답: "섞여 있거나 잘 모르겠음").

근거(`docs/reference/learning-science-evidence.md`): 유창성 훈련은 문장제로 전이되지 않는다(Douglas 2026).
효과가 가장 큰 조합의 핵심은 스키마 기반 지도다(네트워크 메타분석 2025). 옛 종이 문장제는 곱셈 두 문형뿐이라
"숫자 두 개를 곱하면 맞는" 구조였고 연산 선택 훈련이 일어나지 않았다.

목표 둘: **서로 다른 구조의 문장제를 섞어 풀게 한다**, **틀렸을 때 어느 단계에서 무너졌는지를 기록한다**.

구조는 가족(`family`)이 늘어나는 것을 전제로 하되, ②·③을 위한 코드는 미리 만들지 않는다.

## 3. 유형 정의

유형은 **연산이 아니라 상황의 구조**로 나눈다. 유형 하나 = 구조 × 모르는 자리. 함정 장치는 유형이 아니라
수식어다.

| 가족      | 유형 id                                                                                   | 예                                                   |
| --------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `schema`  | `join:whole` `join:part`                                                                  | 남 27명, 여 35명. 모두 몇 명?                        |
|           | `change+:end` `change-:end` `change+:diff` `change-:diff` `change+:start` `change-:start` | 몇 장 있었는데 14장 받아 41장. 처음엔?               |
|           | `compare:diff` `compare:more` `compare:less` `compare:rev`                                | 우리 반 24명, 옆 반보다 3명 적다. 옆 반은?           |
|           | `mult:group` `mult:times`                                                                 | 한 상자 6개씩 7상자. 모두?                           |
|           | `two:mult-sub` `two:mult-add` `two:add-sub`                                               | 5개씩 4봉지, 9개 먹음. 남은 것?                      |
| `reverse` | `unknown:sub` `unknown:add` `wrong-calc` `box:max`                                        | 어떤 수에 18을 더할 것을 뺐더니 25. 바르게 계산하면? |

- `change+:start`·`compare:rev`처럼 **단서어와 실제 연산이 반대인 유형**이 스키마 지도의 핵심 과녁이다. 구조
  자체가 함정이라 따로 표시하지 않는다.
- 함정 수식어는 첫 출시에 `extra-number`(풀이에 필요 없는 수, 예: "8살 지우가") 하나다. 어느 문형에나
  확률적으로 얹힌다.
- 유형 id 목록의 유일한 주인은 `engine/word.ts`의 `WORD_TYPES`, 부모용 이름은 그 옆 `WORD_TYPE_LABELS`다.
  구조 단위 묶음(합병·변화·비교·곱셈·두 단계·거꾸로 풀기)은 id의 `:` 앞부분(`change+`·`change-`는 변화로)에서
  계산한다.

## 4. 아이 화면 흐름 (`#/word`, 아이 소속)

**진입.** 스프린트 결과 화면에 「문장제 풀러 가기」 버튼. 아이 홈에는 오늘 스프린트가 있고 문장제가 3문항
미만인 날에만 「문장제 N개 남았어요」 카드. `#/word`의 `navigate()` 목적지는 `#/`뿐이다(부모 화면 금지 —
CLAUDE.md 「아이 소속 화면은 부모 소속 화면으로 링크하지 않는다」).

**한 문항.**

```
문장
식 [ 5 × 4 = 20 ]          ← 처음엔 한 줄
   + 식 한 줄 더
답 [ 11 ] 개               ← 단위는 미리 적혀 있다
전용 키패드: 0~9 + − × = 지우기, 「다 풀었어요」
```

- 식 칸은 **한 줄로 시작한다.** 처음부터 두 줄을 주면 두 단계 문제라는 힌트가 샌다.
- 식은 원문 문자열로 저장하고 **파싱하지 않는다.** 채점은 답 숫자 하나로 한다.
- 식을 한 줄도 안 써도 답을 낼 수 있다(식 입력은 강제하지 않는다).

**되짚기(첫 답이 틀렸을 때).** 문제에 박제된 `review` 단계를 차례로 묻는다.

| 가족                 | 단계                                                             |
| -------------------- | ---------------------------------------------------------------- |
| `schema`             | 무엇을 묻나(보기 3) → 어떤 식(보기 3, 두 단계는 단계마다) → 계산 |
| `reverse`            | 되돌리는 식(보기 3) → 계산                                       |
| `reverse:wrong-calc` | 어떤 수를 구하는 식 → 바른 식 → 계산                             |

- 각 선택 단계는 **한 번만 고른다.** 틀린 보기를 골라도 정답을 보여 주고 다음 단계로 간다(오답 반복 루프 없음).
- 계산 단계는 고른 식이 아니라 **정답 식**을 직접 계산하게 한다(앞 단계에서 틀렸어도 계산 실력을 따로 본다).
- 끝나면 모범 풀이(`steps`)를 보여 주고 다음 문제로.
- 문구는 `docs/reference/karrot-DESIGN.md` 보이스(`-어요` 체). 「틀렸어요」 대신 「같이 다시 볼까요?」.

**저장.** 문항 하나가 끝날 때(되짚기 포함) 한 번 `putDay(day, ['sprint'])`. 되짚기 도중 앱을 닫으면 그 문항은
기록되지 않고 다음에 새 문항이 나온다 — 틀린 문항을 피할 여지가 있지만 받아들인다(8살·부모가 푼 수를 본다).
그날 `word` 시도가 3개 이상이면 완료다. 다시 열면 남은 개수만큼 새로 출제한다.

## 5. 엔진 (`src/engine/word.ts`, 순수 함수)

**문제 모양.**

```ts
type ReviewStep =
  | { kind: 'ask'; options: string[]; correct: number } // 무엇을 묻나
  | { kind: 'expr'; options: string[]; correct: number } // 어떤 식
  | { kind: 'calc'; expr: string; value: number } // 계산

type WordProblem = {
  type: WordTypeId
  trap?: 'extra-number'
  text: string
  unit: string
  answer: number
  steps: { expr: string; value: number }[] // 모범 풀이 1~2줄
  review: ReviewStep[]
  wrongs: { value: number; cause: 'keyword' | 'extra-number' | 'one-step' | 'op' }[] // 예상 오답
}
```

- **예상 오답표(`wrongs`)는 한 번 만들어 두 번 쓴다.** 되짚기 `expr` 단계의 오답 보기가 여기서 나오고,
  리포트의 「단어만 보고 연산 추정」도 첫 답을 이 표와 대조해 센다. 같은 출처라 둘이 어긋날 수 없다.
- 오답 값이 정답과 같거나 서로 겹치면 그 항목은 버린다(보기 중복 방지).

**수 범위.**

- 덧셈·뺄셈: 피연산자와 결과가 10~99. 받아올림·받아내림 문항이 섞이게 생성한다.
- 곱셈 인수: `engine/facts.ts`의 `DAN_MIN`·`DAN_MAX`를 import한다(구구단 풀 경계 복제 금지).
- 두 단계의 중간값도 같은 범위. 범위를 벗어나면 다시 뽑는다.
- `box:max`는 `a × □ < n`에서 □의 최댓값(□는 1~9, 답이 1 이상이 되게 n을 고른다).

**이름·조사.** 가상 이름 풀(실명 금지 — HANDOFF 2026-08-26 실명 제거 전례). 받침 조사 `personJosa`와 사물
조사 `josa`는 `d80bfd1^:src/engine/word.ts`의 구현을 되살린다.

**출제(하루 3문항).** `pickWordProblems(days, today, n, rand)`.

- 유형 가중치 = `1 + 2 × (유형별 최근 5회 첫 시도 오답률)`, 한 번도 안 나온 유형은 `3`. **매번 `Day.word`
  로그에서 계산하고 저장하지 않는다**(`derived` 비배선 원칙).
- 3문항은 **서로 다른 구조 묶음**에서 뽑는다(인터리빙).
- `rand`는 인자로 받는다. 문장제는 다른 생성기와 난수 스트림을 공유하지 않는다(HANDOFF 2026-08-26: 공유
  스트림 때문에 무관한 테스트가 흔들린 전례).

**정답 판정과 원인 계산(파생).**

- `isCorrect(att) = att.answer === att.problem.answer`.
- `firstFailedStep(att)`: 틀린 시도에서 `picks`를 `review`와 대조해 처음 틀린 선택 단계의 `kind`
  (`'ask'`|`'expr'`), 모두 맞았으면 `'calc'`.
- `keywordGuess(att)`: 첫 답이 `wrongs` 중 `cause: 'keyword'`의 값과 같으면 참.

## 6. 저장·병합·동기화

**시도 모양.**

```ts
type WordAttempt = {
  sid: string // `${deviceId}:${Date.now()}` — 시도 하나에 하나
  problem: WordProblem // 통째로 박제
  answer: number | null // 첫 답
  exprs: string[] // 아이가 쓴 식, 원문
  picks: number[] // 되짚기 선택 단계에서 고른 보기 인덱스. 맞은 문항은 []
  ms: number // 문제를 본 순간부터 첫 답까지
}
// Day에 선택 필드로 추가
word?: WordAttempt[]
```

- **원인·정답 여부를 저장하지 않는다.** 사실(무엇을 골랐나)만 남기고 해석(원인)은 리포트가 계산한다. 원인
  분류를 바꾸면 과거 기록 전체가 소급 재해석된다 — `deriveFacts`와 같은 원칙.
- **문제를 통째로 박제한다.** 엔진이 바뀌어도 그날 아이가 본 문장·보기로 `picks`를 해석할 수 있어야 한다.
- **sid는 시도마다 새로 만든다(스프린트처럼 세션마다가 아니다).** 같은 sid의 두 벌이 만나면 `mergeSprint`는
  값 직렬화가 작은 쪽 하나만 남긴다. 한 세션의 시도를 문항마다 늘려 가며 저장하면 그 규칙이 "짧은 벌"과
  "긴 벌" 중 하나를 임의로 골라 시도를 잃을 수 있다. 시도 하나 = sid 하나면 그룹은 늘 한 원소라 문제가 없다.

**병합(`src/engine/merge.ts`).**

- `mergeSprint`의 sid 그룹 합집합 로직을 sid를 가진 배열 일반으로 뽑아 `sprint`·`word`가 같이 쓴다.
  legacy sid 물질화(`materializeSids`)는 `sprint`에만 적용한다(`word`는 처음부터 sid가 있다).
- `DAY_KNOWN`에 `'word'`를 넣는다. 빠지면 모르는 필드로 떨어져 통째 LWW가 된다.

**묶음.** 새 묶음을 만들지 않는다. `word`는 **`sprint` 묶음의 일원**이다 — `putDay(day, ['sprint'])`로
선언하고 스탬프도 `sprint_at`/`sprint_by`를 함께 쓴다. 서버 `days.payload`가 jsonb라 **서버 스키마 변경
없음.**

**`hasSprintBundle(d)` — 판정의 주인을 하나로.** 지금 `day.sprint`를 직접 보고 "sprint 묶음 있음"을
판정하는 자리가 흩어져 있다. `hasGradesBundle`처럼 `merge.ts`에 `hasSprintBundle`을 두고 전부 이것을 거치게
한다. 하나라도 빠지면 문장제만 한 날(또는 문장제가 더해진 날)의 변경이 서버로 안 올라간다.

| 자리                            | 바뀌는 것                                             |
| ------------------------------- | ----------------------------------------------------- |
| `db.ts` `declaredDay`           | `sprint` 선언 시 `word`도 싣는다(빈 배열은 싣지 않음) |
| `db.ts` `bundlesOf`             | `hasSprintBundle`                                     |
| `db.ts` 아웃박스 접기(~85–92)   | 같은 판정 사용 확인                                   |
| `sync.ts` `withoutEmptyBundles` | `word: []`도 지운다                                   |
| `sync.ts` push 스탬프(~367)     | `hasSprintBundle`                                     |
| `sync.ts` `adoptServerSheet`    | `word`도 서버와 다르면 sprint 표식                    |
| `merge.ts` `mergeDay`           | `word` 병합, 결과에 붙이기                            |

구현계획 단계에서 `grep -n "\.sprint"`로 src 전체를 다시 세어 이 표를 확정한다(위 목록은 설계 시점 관측).

**백업 검증(`src/engine/backup.ts`).** `validateDay`에 `word` 검사: 배열, 각 원소의 `sid`(문자열)·
`answer`(숫자|null)·`exprs`(문자열 배열)·`picks`(정수 배열)·`ms`(숫자), 그리고 리포트가 읽는 `problem.type`·
`problem.text`·`problem.unit`(문자열)·`problem.answer`(숫자)·`problem.review`(배열)·`problem.wrongs`(배열).
`backupPayload` 모양은 그대로(`days` 안 필드가 하나 는다).

**XSS.** `problem.text`·`unit`·`exprs`·보기 문자열은 가져오기로 임의 문자열이 들어올 수 있다. `el()` 템플릿에
넣을 때 **항상 `escapeHtml`**.

**🔥(`src/engine/streak.ts`).** `WORD_START`(출시일, 구현 커밋에서 확정) 상수. `date < WORD_START`인 날은
스프린트만으로 완료, 그 이후는 스프린트 비어 있지 않음 ∧ `word` 3개 이상. 규칙을 그냥 바꾸면 과거 전체가
소급해 미완료가 되어 🔥가 꺼진다 — 파생 재계산의 부작용을 상수 하나로 막는다.

## 7. 부모 리포트 (`#/report`)

`wordReport(days, today)`(`src/engine/report.ts`, 순수 함수) → 화면 `report.ts`에 「문장제」 절.

- **이번 주**: 문장제 한 날 수, 첫 시도 정답 x/y.
- **최근 4주 유형표**: 구조 묶음 6줄(정답 x/y 막대). 그 안의 세부 유형은 표본 ≥ 3이고 정답률이 구조 평균보다
  낮을 때만 「← 약해요」로 펼친다. 표본 < 3인 줄은 「표본 부족」.
- **어디서 틀렸나(최근 4주)**: `firstFailedStep` 분포(묻는 것 놓침·식 세우기·계산) + 보조 지표 「단어만 보고
  연산 추정」(`keywordGuess` 수).
- **최근 틀린 문제**: 최대 3개, 날짜·문장 앞부분·아이 답 → 정답·막힌 단계. 부모가 그 문제로 대화하라고 둔다.
- **공유 텍스트**: 한 줄 추가(`문장제 11/15 · 약한 유형: …`).

주 단위가 아니라 4주인 이유: 하루 3문항이면 주 최대 21문항이라 유형 20여 개의 칸이 대부분 한두 문항이다.
