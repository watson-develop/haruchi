# 문장제 단계형 연습 설계

2026-09-30. 상태: 적대적 리뷰 2라운드 반영. 1라운드(엔진·화면·리포트 blocker 4·major 12·minor 6, 저장·병합
major 3·minor 8), 2라운드(blocker 2·major 5·minor 7 — 1라운드 수정이 만든 회귀 3건 포함), 3라운드(blocker·major 0, minor 5 반영) — **합의**.
선행: `2026-09-30-retire-paper-sheet-design.md`(종이 은퇴 — 옛 `word.ts`는 git 이력 `d80bfd1^`에만 있다).

## 1. 왜

딸은 연산 자체는 잘한다. 그래서 종이 세로셈·□ 채우기가 쉬워져 은퇴했다. 약한 곳은 **응용·문장제**이고
실수가 잦은데, 어디서 틀리는지는 부모도 아직 모른다(사용자 답: "섞여 있거나 잘 모르겠음").

근거(`docs/reference/learning-science-evidence.md`): 유창성 훈련은 문장제로 전이되지 않는다(Douglas 2026).
효과가 가장 큰 조합의 핵심은 **스키마 기반 지도** — 문제의 구조를 이름 붙여 알아보게 하는 것이다(네트워크
메타분석 2025). 옛 종이 문장제는 곱셈 두 문형뿐이라 "숫자 두 개를 곱하면 맞는" 구조였고 연산 선택 훈련이
일어나지 않았다. 이 설계가 스키마 지도에서 가져오는 것은 **구조 섞기**와 **구조 이름 붙이기**(§4)다.
그림 표상은 확장 ②로 미룬다.

목표 둘: **서로 다른 구조의 문장제를 섞어 풀게 한다**, **틀렸을 때 어느 단계에서 무너졌는지를 기록한다**.

## 3. 유형 정의

유형은 **연산이 아니라 상황의 구조**로 나눈다. 유형 id는 항상 `묶음:변형`이고 **`:` 앞부분이 곧 구조
묶음**이다(묶음 목록 `WORD_GROUPS`, 테스트가 모든 id의 앞부분이 그 안에 있는지 지킨다). 함정 장치는 유형이
아니라 수식어다.

| 묶음 (아이용 이름) | id                   | 문형(수는 예)                                          | 답      |
| ------------------ | -------------------- | ------------------------------------------------------ | ------- |
| `join` 모으기      | `join:whole`         | 남 a명, 여 b명. 모두 몇 명?                            | a+b     |
|                    | `join:part`          | 모두 c송이, 그중 a송이는 튤립. 장미는?                 | c−a     |
| `change` 바뀌기    | `change:inc-end`     | a장 있었는데 b장을 받았어요. 몇 장?                    | a+b     |
|                    | `change:dec-end`     | a장 있었는데 b장을 썼어요. 몇 장 남았나?               | a−b     |
|                    | `change:inc-diff`★   | a장 있었는데 몇 장을 받아 c장이 됐어요. 몇 장 받았나?  | c−a     |
|                    | `change:dec-diff`    | a장 있었는데 몇 장을 쓰고 c장 남았어요. 몇 장 썼나?    | a−c     |
|                    | `change:inc-start`★  | 몇 장 있었는데 b장을 받아 c장이 됐어요. 처음엔?        | c−b     |
|                    | `change:dec-start`★  | 몇 장 있었는데 b장을 쓰고 c장 남았어요. 처음엔?        | c+b     |
| `compare` 비교하기 | `compare:diff`       | A는 a번, B는 b번. A가 몇 번 더?                        | a−b     |
|                    | `compare:more`       | B는 b개, A는 B보다 d개 더 많아요. A는?                 | b+d     |
|                    | `compare:less`       | B는 b개, A는 B보다 d개 더 적어요. A는?                 | b−d     |
|                    | `compare:rev-less`★  | A는 a명이고, B보다 d명 적어요. B는?                    | a+d     |
|                    | `compare:rev-more`★  | A는 a명이고, B보다 d명 많아요. B는?                    | a−d     |
| `mult` 묶음        | `mult:group`         | 한 상자에 a개씩 b상자. 모두?                           | a×b     |
|                    | `mult:times`         | 동생은 a자루, 형은 동생의 b배. 형은?                   | a×b     |
| `two` 두 번 계산   | `two:mult-sub`       | a개씩 b봉지, 그중 c개를 먹었어요. 남은 것?             | a×b−c   |
|                    | `two:mult-add`       | a개씩 b봉지, 낱개 c개가 더 있어요. 모두?               | a×b+c   |
|                    | `two:add-sub`        | a개 있었는데 b개를 받고 c개를 줬어요. 몇 개?           | a+b−c   |
| `reverse` 거꾸로   | `reverse:after-sub`★ | 어떤 수에서 b를 뺐더니 c. 어떤 수는?                   | c+b     |
|                    | `reverse:after-add`★ | 어떤 수에 b를 더했더니 c. 어떤 수는?                   | c−b     |
|                    | `reverse:wrong-add`  | b를 더해야 할 것을 잘못해서 뺐더니 c. 바르게 계산하면? | (c+b)+b |
|                    | `reverse:wrong-sub`  | b를 빼야 할 것을 잘못해서 더했더니 c. 바르게 계산하면? | (c−b)−b |

- ★ = **단서어 함정 유형**(`WORD_TYPES`의 메타데이터 `keyword: true`). 문장 속 동사·비교어(받다·뺐더니·적어요)가
  가리키는 연산과 실제 연산이 반대다. 스키마 지도의 핵심 과녁이고, 리포트의 「단어만 보고 연산 추정」은 이
  유형들에서만 센다.
- 문형 표의 문장은 예시이고, 실제 문장·소재·인물은 유형마다 2개 이상의 템플릿에서 고른다. **답 공식은 id마다
  고정**이다(이 표가 계약).
- 함정 수식어는 첫 출시에 `extra-number` 하나다: 풀이에 필요 없는 수를 한 절 끼워 넣는다(예: "8살 도윤이가").
- 유형 id 목록의 유일한 주인은 `engine/word.ts`의 `WORD_TYPES`, 부모용 세부 이름은 `WORD_TYPE_LABELS`,
  아이용 묶음 이름은 `WORD_GROUP_LABELS`(모으기·바뀌기·비교하기·묶음·두 번 계산·거꾸로)다.

## 4. 아이 화면 흐름 (`#/word`, 아이 소속)

**진입.**

- 스프린트 결과 화면: 오늘 끝난 문장제가 3개 미만일 때만 「문장제 풀러 가기」 버튼(결과 화면은 재진입·저장
  재시도 화면이기도 하다 — `sprint.ts`의 `renderResult` 경로 전부에 같은 조건).
- 아이 홈 메인 카드 판정 순서: ① 오늘 스프린트 전 → 기존 상태, ② **오늘 스프린트는 했고 끝난 문장제가 3개
  미만 → 「✓ 스프린트 끝! 문장제 N개 남았어요」 + `#/word` 버튼**, ③ 그 외 → 「✓ 오늘 끝!」·「✓ 오늘 점검 끝!」.
  ②는 `wordStart`(§6)와 무관하게 먼저 본다 — 그래야 첫날에도 홈이 문장제를 권한다. 🔥 계산은 `dayDone`이 따로
  한다(첫날 이전의 날은 문장제 없이도 완료). **점검일도 문장제 3개가 필요하다.**
- `#/word`의 `navigate()` 목적지는 `#/`뿐이다(CLAUDE.md 「아이 소속 화면은 부모 소속 화면으로 링크하지
  않는다」). 오늘(`dayKey`) 스프린트가 없으면 `#/word`는 `#/`로 돌려보낸다.
- `main.ts`의 `onPullApplied` 재렌더 예외(지금 `#/sprint`만, `main.ts:243-244`)에 `#/word`를 더한다. 그렇지
  않으면 부모가 설정만 바꿔도 풀던 문제의 입력과 되짚기 위치가 날아간다.

**한 문항.**

```
문장
식 [ 5 × 4 = 20 ]          ← 처음엔 한 줄
   + 식 한 줄 더
답 [ 11 ] 개               ← 단위는 미리 적혀 있다(거꾸로 묶음은 단위 없음)
전용 키패드: 0~9 + − × = 지우기, 「다 풀었어요」
```

- 식 칸은 **한 줄로 시작한다.** 처음부터 두 줄을 주면 두 단계 문제라는 힌트가 샌다.
- 식은 원문 문자열로 저장하고 **파싱하지 않는다.** 채점은 답 숫자 하나로 한다. 식 입력은 강제하지 않는다.
- 답 칸에 초점이 있으면 `+ − × =`는 비활성. 답은 **최대 3자리** — 정답은 10~99이거나(덧셈·뺄셈) 구구단 곱이지만,
  단서어 반응 오답(예: 41+14=55, 85+27=112)은 100을 넘을 수 있고 그 값이 잘리면 리포트가 그 실수를 못 센다.
- **맞히면** 「바뀌기 이야기였어요」처럼 구조 이름 한 줄을 보여 주고 다음 문제로.

**되짚기(첫 답이 틀렸을 때).** 문제에 박제된 `review` 단계를 차례로 한다. **식을 고른 직후 그 식을 계산한다** —
2단계 식의 보기에는 1단계 값이 적혀 있으므로(예: 「20 − 9」), 1단계 계산을 뒤로 미루면 답을 보고 베낄 수 있다.

| 묶음                             | 단계 순서                                                     |
| -------------------------------- | ------------------------------------------------------------- |
| `join`·`change`·`compare`·`mult` | `story` → `expr` → `calc`                                     |
| `two`                            | `story` → `expr`(1) → `calc`(1) → `expr`(2) → `calc`(2)       |
| `reverse:after-*`                | `expr`(되돌리는 식) → `calc`                                  |
| `reverse:wrong-*`                | `expr`(어떤 수 구하는 식) → `calc` → `expr`(바른 식) → `calc` |

- `story`의 보기는 **고정 5개**: 모으기·바뀌기·비교하기·묶음·두 번 계산(`WORD_GROUP_LABELS`에서 `reverse`
  제외, 순서 고정). 매번 같은 이름표를 보게 해서 구조 이름을 익힌다. `two` 문제의 정답은 「두 번 계산」이다.
  거꾸로 묶음에는 `story`가 없다.
- `expr`의 보기는 2~3개(§5 오답 후보표), 섞은 순서.
- 선택 단계는 **한 번만 고른다.** 틀린 보기를 골라도 정답을 보여 주고 다음 단계로(오답 반복 루프 없음).
- `calc`는 아이가 고른 식이 아니라 **정답 식**을 직접 계산해 입력한다(비워 둔 채 넘어갈 수 없다). 입력값을
  저장한다. 틀려도 정답을 보여 주고 넘어간다.
- 끝나면 모범 풀이(`steps`)를 보여 주고 다음 문제로.
- 문구는 `docs/reference/karrot-DESIGN.md` 보이스(`-어요` 체). 「틀렸어요」 대신 「같이 다시 볼까요?」.

**저장과 이어 하기.** 한 문항의 기록은 한 `sid`로 여러 번 덮어쓴다.

1. 문제를 **보여 준 순간**: `answer: null`
2. 첫 답을 낸 순간: `answer`, `exprs`, `ms`
3. 되짚기 **단계 하나가 끝날 때마다**: `picks` 또는 `calcs`에 한 칸 추가

- 기록의 날짜는 **`#/word` 화면이 그려질 때 한 번 정해진다**(`sprint.ts:77`처럼). 그 화면에서 보여 준 문항은
  전부 그 날짜에 저장된다 — 자정을 넘겨도 한 번의 풀이가 두 날로 쪼개지지 않는다.
- `sid`는 문항을 **보여 주는 순간** 하나씩 만든다(n개를 미리 만들지 않는다). 같은 밀리초에 두 sid가 나와 두
  문제가 하나로 병합되는 일을 막는다.
- 다시 `#/word`에 오면 오늘 기록 중 **끝나지 않은 문항**(§5 `stage`)을 새 문제보다 먼저, **아직 하지 않은
  단계부터** 이어서 보여 준다. 앱을 닫아 어려운 문제나 되짚기를 피할 수 없고, 이미 본 정답을 들고 앞 단계를
  다시 하는 일도 없다. 닫았다고 벌점도 없다.
- 이어 한 문항의 `ms`는 이어 보여 준 순간부터 잰다(수용한 한계).
- 어제의 끝나지 않은 문항은 이어 하지 않는다. 끝나지 않았으므로 출제 가중치·리포트·🔥 어디에도 세지 않는다.
- 새로 낼 문항 수 `n = 3 − (오늘의 모든 문항 수 — 끝나지 않은 것 포함)`. 끝나지 않은 문항도 자리를 차지하고
  먼저 이어 한다.
- 저장 실패는 `sprint.ts`의 `pending`·`savePending` 재시도 패턴을 그대로 따른다.

「오늘 끝난 문장제」 = `stage === 'done'`인 문항 수. 3개가 되면 완료.

## 5. 엔진 (`src/engine/word.ts`, 순수 함수)

**문제 모양.**

```ts
type ReviewStep =
  | { kind: 'story'; correct: number } // 보기는 고정 WORD_GROUP_LABELS
  | { kind: 'expr'; options: string[]; correct: number }
  | { kind: 'calc'; expr: string; value: number }

type WordProblem = {
  type: WordTypeId
  trap?: 'extra-number' // 없으면 키 자체를 넣지 않는다(§6)
  text: string
  unit: string // 거꾸로 묶음은 ''
  answer: number
  steps: { expr: string; value: number }[] // 모범 풀이 1~2줄
  review: ReviewStep[]
  wrongs: {
    expr: string
    value: number
    cause: 'keyword' | 'op' | 'order' | 'one-step' | 'extra-number'
  }[]
}
```

**오답 후보표 — `expr` 보기와 `wrongs`의 유일한 출처.** 각 `expr` 단계의 정답 식 `x ∘ y`에 대해 아래 후보를
순서대로 만들고, **식 문자열이 정답·앞 후보와 다른 것**을 최대 2개 취한다(값이 같아도 식이 다르면 다른 보기다 —
고르는 단계는 구조를 묻지 값을 묻지 않는다). 첫 후보는 항상 존재하므로 보기는 **최소 2개**가 보장되고,
「다시 뽑기」 루프는 없다.

| 순서 | 후보                                | 식                                           | `cause`                                     |
| ---- | ----------------------------------- | -------------------------------------------- | ------------------------------------------- |
| 1    | 연산 바꾸기(같은 수, 반대 연산)     | `+` ↔ `−`(뺄셈은 큰 수 − 작은 수), `×` → `+` | ★ 유형 마지막 단계면 `keyword`, 아니면 `op` |
| 2    | 한 단계에서 멈춤(2단계 식만)        | 1단계 정답 식 그대로                         | `one-step`                                  |
| 3    | 끼워 넣은 수 사용(`extra-number`만) | 정답 식의 한 수를 끼워 넣은 수로 바꿈        | `extra-number`                              |
| 4    | 빼는 순서 뒤집기(뺄셈 정답만)       | `y − x`(작은 수 − 큰 수)                     | `order`                                     |

- 뺄셈 정답 식은 늘 보기 3개(앞선 후보 2·3이 있으면 `order`는 빠진다). 덧셈·곱셈 정답 식은 함정이 없으면 보기
  2개(「더할까, 뺄까」 — 그 단계가 묻는 것이 정확히 그것이다).
- `wrongs`의 `value`는 식을 계산한 값이고, 음수(`order`)면 `wrongs`에 넣지 않는다(보기로는 남는다).
- 리포트의 `keywordGuess`는 `cause: 'keyword'`의 `value`만 본다. 연산 바꾸기의 뺄셈을 큰 수 − 작은 수로 쓰므로
  이 값은 항상 0 이상이다. 나머지 `cause`(`op`·`order`·`one-step`·`extra-number`)는 첫 출시의 리포트가 읽지
  않는다 — 나중에 다시 해석할 수 있게 사실로 남겨 둘 뿐이다. 이 값들로 첫 답을 분류하는 리포트를 새로 만들면
  「2 + 2」처럼 정답과 값이 같은 오답이 정답을 실수로 세므로, 그때는 값이 정답과 같은 항목을 빼야 한다.

**수 범위.**

- 덧셈·뺄셈: 피연산자·중간값·답이 10~99. 받아올림·받아내림이 있는 문항이 섞이게 생성한다.
- 곱셈 인수: `engine/facts.ts`의 `DAN_MIN`·`DAN_MAX`(구구단 풀 경계 복제 금지). `mult` 묶음의 곱은 10 미만이어도
  허용한다(구구단 식 그대로). `two:mult-*`는 곱이 10 이상인 것만.
- `reverse:wrong-*`는 어떤 수·답 모두 10~99.
- 생성은 **답 공식에서 거꾸로** 한다(예: `compare:less`는 답 b−d를 10~99에서 먼저 정하고 d를 고른 뒤 b를 만든다) —
  범위를 벗어난 조합을 버리고 다시 뽑는 대신 처음부터 범위 안에서 만든다. 테스트가 모든 유형의 생성 가능성을
  시드 여러 개로 확인한다(§8).
- `extra-number`의 수는 범위 규칙에서 **면제**하되, 그 문항의 피연산자·중간값·답 어느 것과도 같지 않아야 한다.

**이름·조사.** 가상 이름 풀. 실명 금지(HANDOFF 2026-08-26), 사물로 읽히는 이름 금지(예: 지우 → 지우개 —
옛 코드 주석). `d80bfd1^:src/engine/word.ts`에서 `personJosa`·`josa`·`copula`·`personStem`을 되살린다.
**숫자 뒤 조사는 새로 만든다**(`numJosa`): 옛 `hasBatchim`은 한글이 아닌 글자를 받침 있음으로 봐서
"12을"이 나온다. 끝자리 2·4·5·9(이·사·오·구)만 받침 없음, 0은 십·백이라 받침 있음. 두 인물을 잇는
「와/과」도 필요하면 추가한다.

**출제.** `pickWordProblems(days, today, n, doneGroups, rand)`.

1. 유형 가중치: 그 유형의 끝난 기록이 2개 미만이면 `3`, 아니면 `1 + 2 × (최근 5회 첫 시도 오답률)`.
   **매번 `Day.word` 로그에서 계산하고 저장하지 않는다**(`derived` 비배선 원칙). 끝나지 않은 문항은 세지 않는다.
2. 묶음 가중치 = 그 묶음 유형 가중치의 최댓값. `doneGroups`(오늘의 모든 문항 — 끝났든 진행 중이든 — 의 묶음)는
   제외.
3. 묶음을 가중치로 뽑고(비복원), 그 안에서 유형을 가중치로 뽑는다. 묶음 크기가 달라도(2~6개) 묶음 노출이
   유형 수에 끌려가지 않는다.
4. `n`(§4)개를 채운다.

`rand`는 인자로 받는다. 문장제는 다른 생성기와 난수 스트림을 공유하지 않는다(HANDOFF 2026-08-26 전례).

**판정과 원인(파생).**

- `isCorrect(att) = att.answer === att.problem.answer`
- 선택 단계 수 `P` = `review`의 `story`+`expr` 개수, 계산 단계 수 `C` = `calc` 개수.
- `stage(att)`: `answer === null` → `'shown'`; 틀렸고 (`picks.length < P` ∨ `calcs.length < C`) → `'answered'`;
  그 외 → `'done'`.
- `firstFailedStep(att)`(틀리고 `'done'`인 시도만): `review`를 순서대로 걸으며 선택 단계는 `picks`의 다음 칸,
  계산 단계는 `calcs`의 다음 칸과 대조해 처음 틀린 단계의 `kind`(`'story'`|`'expr'`|`'calc'`). 모두 맞았으면
  `'slip'`(구조·식·계산을 다 아는데 첫 답만 틀림 — 옮겨 적기·서두름). 모르는 `kind`의 단계는 건너뛰고, 범위 밖
  인덱스(가져오기)는 그 단계 틀림으로 본다.
- `keywordGuess(att)`: 유형이 ★이고 첫 답이 `cause: 'keyword'` 항목의 `value`와 같으면 참.

## 6. 저장·병합·동기화

**시도 모양.**

```ts
type WordAttempt = {
  sid: string // `${deviceId}:${Date.now()}` — 문항 하나에 하나
  problem: WordProblem // 통째로 박제
  answer: number | null // 첫 답. null = 보여 줬지만 아직 답 안 함
  exprs: string[] // 아이가 쓴 식, 원문
  ms: number // 보여 준 순간부터 첫 답까지(answer null이면 0)
  picks: number[] // 되짚기 선택 단계(story·expr)에서 고른 인덱스, 순서대로
  calcs: number[] // 되짚기 계산 단계 입력, 순서대로
}
// Day에 선택 필드로 추가
word?: WordAttempt[]
```

- **원인·정답 여부를 저장하지 않는다.** 사실(무엇을 고르고 무엇을 썼나)만 남기고 해석은 매번 계산한다. 원인
  분류를 바꾸면 과거 기록 전체가 소급 재해석된다 — `deriveFacts`와 같은 원칙.
- **문제를 통째로 박제한다.** 엔진이 바뀌어도 그날 아이가 본 문장·보기로 `picks`를 해석할 수 있어야 한다.
- **서버를 한 바퀴 돈 값과 같은 모양으로 저장한다.** 선택 키에 `undefined`를 쓰지 않는다(키를 뺀다). 숫자는
  유한수만, 배열 안에 `null`을 두지 않는다. 그렇지 않으면 로컬·서버 값이 영영 같지 않아 `skipUnchangedPush`·
  `applyPulledDay`의 비교가 늘 다름을 본다(`sprint.ts`의 sid 주석과 같은 경고).

**병합 — `mergeWord`(`src/engine/merge.ts`).** `mergeSprint`를 일반화하지 않고 따로 둔다(시도가 sid마다 하나라
그룹 로직이 필요 없고, 같은 sid의 두 벌을 고르는 규칙이 다르다).

- sid로 모은다. 같은 sid가 둘이면 **더 진행된 쪽**(`stage` 순위 shown < answered < done, 같으면
  `picks.length + calcs.length`가 큰 쪽 — 단계마다 저장하므로 실재하는 경우다)이 이기고, 그래도 같으면 값
  직렬화가 작은 쪽.
- 결과 순서: sid의 마지막 `:` 뒤가 유한수인 것들을 그 수 오름차순(같으면 sid 사전순), 그 뒤에 나머지를 sid
  사전순. 비교가 전순서라야 교환 법칙이 선다(`NaN` 비교 금지).
- `mergeWord`는 sid가 문자열이라고 가정한다. 들어오는 길은 우리 코드(`putDay`)와 `validateDay`(pull·가져오기)
  둘뿐이고, 후자가 sid 없는 원소를 거부한다는 것을 테스트로 고정한다(`materializeSids` 같은 대체는 두지 않는다).
- `DAY_KNOWN`에 `'word'`. 빠지면 모르는 필드로 떨어져 통째 LWW가 된다.
- 교환·결합·멱등: `merge.test.ts`의 `genDay`에 word 생성기(같은 sid 다른 진행 단계, `[]`, 없음, 비숫자 sid 꼬리)를
  넣어 기존 속성 검사가 덮게 한다.

**백업·pull 검증(`src/engine/backup.ts` `validateDay`).** `validateDay`는 pull 행도 지키고, 거부된 행은 pull
커서를 멈춰 이후 모든 날의 동기화를 막는다(`sync.ts:787·841`). 그래서 **모양은 원소 단위로 검사하되 값의 목록은
검사하지 않는다**(미래 버전이 새 유형·단계·원인을 더해도 이 버전이 멈추지 않게).

- `word`: 배열. 각 원소: `sid` 문자열, `answer` 유한 정수|null, `exprs` 문자열 배열, `ms` 유한수, `picks` 정수
  배열, `calcs` 유한수 배열.
- `problem`: 객체. `type`·`text`·`unit` 문자열, `answer` 유한수, `steps` 원소 `{expr 문자열, value 유한수}`,
  `review` 원소는 `kind` 문자열 + (`options` 있으면 문자열 배열) + (`correct` 있으면 정수) + (`expr` 있으면
  문자열) + (`value` 있으면 유한수), `wrongs` 원소 `{expr 문자열, value 유한수, cause 문자열}`. `trap`은 있으면
  문자열.
- `type`·`kind`·`cause`를 목록과 대조하지 않는다. 대신 **화면은 이 값들을 문자열로 내보내지 않는다** — 고정 라벨
  표를 거치고(`WORD_TYPE_LABELS[t] ?? '기타'`), 모르는 유형은 어느 묶음에도 넣지 않고, 모르는 `kind`의 단계는
  원인 계산에서 건너뛴다.
- **XSS**: `problem` 안의 모든 문자열(`text`·`unit`·`steps[].expr`·`review[].options`·`review[].expr`·
  `wrongs[].expr`)과 `exprs`는 `el()` 템플릿에 넣을 때 **항상 `escapeHtml`**. 이어 하기로 pull에서 온 문제를
  그릴 수 있으므로 아이 화면도 예외가 아니다. 리포트의 「문장 앞부분」은 **자른 뒤에** 이스케이프한다.

**🔥 — `dayDone`(`src/engine/streak.ts`).**

- `wordStart(days)` = `stage === 'done'`인 문장제가 **3개 이상**인 가장 이른 날짜(없으면 null). 매번 로그에서
  계산한다. 「하나라도」로 잡으면 첫 문항을 끝낸 순간 그날이 3개를 요구하게 되어, 더 했는데 🔥가 하나 줄어든다.
  3개로 잡으면 새 규칙이 켜지는 날은 이미 새 규칙으로도 완료인 날이다.
- `dayDone(d, start)` = 스프린트 비어 있지 않음 ∧ (`start`가 null ∨ `d.date < start` ∨ 끝난 문장제 ≥ 3).
- `sprintStreak`과 아이 홈이 **같은 `dayDone`을 쓴다**. `sprintStreak`은 부모 홈(`home-parent.ts:158`)과 리포트
  엔진(`engine/report.ts:89`)도 먹으므로 **부모 화면의 🔥도 같은 규칙으로 바뀐다**(PRD에 적는다).
- 고정 날짜 상수를 쓰지 않는 이유: 업데이트는 배너를 눌러야 적용된다(`main.ts:80-86`). 아이패드가 옛 코드로 며칠
  더 돌면 그 날들이 소급해 미완료가 되어 🔥가 끊기고, 부모 폰은 같은 데이터로 끊긴 🔥를 먼저 보여 준다.
  "처음 푼 날"은 새 코드가 실제로 돈 날이라 이 틈이 없다.
- 수용한 한계: 문장제를 한 번도 끝내지 않으면 규칙이 옛 것으로 남는다(홈 ② 상태가 매일 권하므로 기본 경로는
  아니다). 첫 날 이후 문장제를 건너뛴 날은 미완료다.

**옛 버전 앱과의 공존 — `SCHEMA_VERSION`은 올리지 않는다.** 옛 앱은 `word`를 모르는 필드로 보고 값 직렬화가
작은 쪽을 통째로 고른다(`merge.ts:218-227`, 키는 정렬돼 직렬화된다 — `merge.ts:32-34`).

- 같은 원소가 진행된 경우: 키 순서가 `answer` → `calcs` → `exprs` → `ms` → `picks` → `problem` → `sid`이고,
  `"answer":17` < `"answer":null`, `"calcs":[12]` < `"calcs":[]`, `"picks":[0]` < `"picks":[]`라 **더 진행된 쪽이
  작게 직렬화된다**(배열에 `null`을 두지 않는 규칙이 이것을 지킨다). 한쪽이 다른 쪽의 앞부분인 배열도 긴 쪽이
  이긴다. 이 두 경우에는 옛 앱도 잃지 않는다.
- 잃는 경우: 두 배열의 같은 자리에 **서로 다른 sid**가 있을 때(늦게 동기화된 기기가 더 이른 ms의 시도를 끼워
  넣은 경우). 옛 앱 기기가 그날을 push하면(재등록 시 모든 날에 표식 — `db.ts:770`) 서버가 한쪽을 잃는다.
  문장제를 쓰는 기기는 아이 아이패드 하나라 끼워 넣기가 생기지 않는다.
- 버전을 올리면 옛 기기가 새 기기가 올린 모든 날의 업로드를 못 하게 되는 비용이 더 크다. 위 두 경우를
  `merge.test.ts`에 옛 규칙(`DAY_KNOWN`에 word 없음) 병합으로 문서화하는 테스트를 둔다(진행된 원소 + 끼워 넣기).

**크기.** 문항당 0.6~1KB(박제), 하루 ~3KB, 백업(2칸 들여쓰기) 연 ~2MB. 서버 페이지·스냅샷은 문제없다. 늘어나는
것은 매 화면 이동의 `getAllDays()`다 — 지금 설계하지 않고 1년 뒤 아이패드에서 잰다.

## 7. 부모 리포트 (`#/report`)

`wordReport(days, today)`(`src/engine/report.ts`, 순수 함수) → 화면 `report.ts`에 「문장제」 절. 끝난 문항만 센다.

- **이번 주**: 문장제 한 날 수, 첫 시도 정답 x/y.
- **최근 4주 묶음표**: 6줄(모으기·바뀌기·비교하기·묶음·두 번 계산·거꾸로), 정답 x/y 막대. **묶음 줄**의 표본이
  3 미만이면 막대 대신 「표본 부족」.
- **약한 세부 유형**: 세부 유형 중 표본 ≥ 4이고 정답률 ≤ 50%인 것만 그 묶음 아래 「← 약해요」로 펼친다(절대
  기준 — 상대 기준은 어떤 분포에서도 누군가를 약하다고 만든다).
- **어디서 틀렸나(최근 4주)**: `firstFailedStep` 분포 — 이야기 구조 · 식 세우기 · 계산 · 실수. 거꾸로 묶음에는
  이야기 구조 단계가 없다는 한 줄을 붙인다. 보조 지표 「단어만 보고 연산 추정 N / 함정 유형 오답 M」.
- **최근 틀린 문제**: 최대 3개. 날짜, 문장 앞부분, 아이가 쓴 식(`exprs`), 아이 답 → 정답, 막힌 단계. 부모가 그
  문제로 아이와 이야기하라고 둔다. 전부 `escapeHtml`.
- 절 끝 한 줄: 「약한 유형이 더 자주 나와서 정답률이 실제보다 낮게 보일 수 있어요.」 (적응 출제라 주간 비교가
  공정하지 않다.)
- **공유 텍스트**: 한 줄 추가(`문장제 11/15 · 약한 유형: …`).

4주인 이유: 하루 3문항이면 주 최대 21문항, 유형 21개라 칸 대부분이 한두 문항이다.

## 8. 테스트

`src/engine/word.test.ts` — 시드 고정 난수 여러 개로 속성 검사. **생성기의 필드끼리 비교하지 않는다** — 테스트가
식 문자열을 직접 계산한다(`+`·`−`(U+2212)·`×`).

- 모든 문제: 각 `steps[i].expr`을 테스트가 계산하면 `steps[i].value`, 마지막 값 = `answer`
- 모든 `expr` 단계: 보기가 2~3개이고 식 문자열이 서로 다르며, 정답 인덱스의 식을 테스트가 계산하면 그 단계
  값이고, 정답 식이 모범 풀이(`steps`)의 같은 단계 식과 같다
- 뺄셈 정답 단계는 보기 3개(후보표 1·4)
- 정답 인덱스가 늘 같은 자리에 있지 않다(시드 분포)
- `review` 단계 순서가 §4 표와 같다(`expr` 뒤에 곧바로 `calc`)
- 수 범위(§5), 곱셈 인수가 `DAN_MIN..DAN_MAX`, `extra-number`의 수가 피연산자·중간값·답과 다름
- `text`에 `NaN`·`undefined`·`null`이 없다, 잘못된 조사 목록(`12을`·`14을`·`5을`·`9을`·`이가가` 등)이 없다
- 모든 `WORD_TYPES` id가 시드 여러 개에서 한 번 이상 생성된다, 모든 id의 앞부분이 `WORD_GROUPS`에 있다
- ★ 유형의 `keyword` 오답 값이 0 이상이고 정답과 다르다
- `pickWordProblems`: 묶음이 서로 다르고 `doneGroups`를 피한다, `n < 3`(이어 하기)도 지킨다
- 약한 유형이 더 자주 나온다 — 수치 임계값은 계획이 시드 실측으로 정하고, **변이 검증**(가중치 균등 강제 시
  빨개짐)으로 검출력을 확인한다
- `firstFailedStep`·`keywordGuess`·`isCorrect`·`stage`: 표 기반, 범위 밖 인덱스·모르는 `kind`·되짚기 중간 상태 포함
- `numJosa`: 0~999 전부

`merge.test.ts` — `mergeWord` 진행 순위(단계 중간 저장 포함)·비숫자 sid 꼬리 정렬, 교환·결합·멱등 속성에 word
포함, `DAY_KNOWN` 누락 시 실패 사례, 옛 규칙 공존 두 경우(§6). `backup.test.ts`(또는 기존 위치) — `word` 기형
원소 거부(sid 없음 포함), 모르는 `type`·`kind`·`cause` 통과. `streak`/`simulation` — `wordStart` 전·후, 점검일,
문장제가 끝나지 않은 날. `db.test.ts`/`sync.test.ts` — `word`만 바뀐 `putDay(…, ['sprint'])`가 아웃박스 표식과
push 스탬프를 남긴다, sheet 충돌 자동 채택 뒤 `word` 보존.

## 10. 리뷰에서 닫은 것 (근거 기록)

**1라운드**

- 묶음 판정을 id 앞부분으로 했는데 거꾸로 묶음 id 앞부분이 제각각이라 8묶음이 나왔다 → id를 `묶음:변형`으로 통일.
- `wrongs`가 값만 가져 `expr` 보기를 만들 수 없었다 → 식·값·원인을 함께.
- 되짚기 계산 입력을 저장하지 않아 「계산」 원인이 계산을 보지 않았다 → `calcs` 저장, `'slip'` 분리.
- 되짚기 중 닫기가 오답만 지워 리포트를 위로 편향시켰다 → 여러 번 저장 + 이어 하기.
- 「무엇을 묻나」 보기의 출처가 없고 스키마 지도의 핵심(구조 이름)이 빠져 있었다 → `story` 단계(고정 보기) +
  맞힌 뒤 구조 이름 한 줄.
- 고정 날짜 🔥 컷오프는 업데이트 지연 날을 소급 미완료로 만든다 → 로그에서 `wordStart` 계산.
- 홈 카드와 🔥가 다른 판정을 봤다 → `dayDone` 하나.
- 검증이 얕으면 리포트가 죽고, 목록 대조로 깊으면 미래 행이 pull을 멈춘다 → 모양은 깊게, 값 목록은 안 본다.
- `box:max`는 역연산이 아니라 되짚기 모양이 다르다 → 확장 ②로.

**2라운드**

- 오답을 값으로 중복 제거하면 덧셈·뺄셈에서 `keyword`와 `op`가 같은 값이 되어 대부분 유형이 오답 1개뿐이었고
  「다시 뽑기」가 끝나지 않았다 → 식 문자열로 구분하는 오답 후보표, 보기 2~3개 허용, 다시 뽑기 없음.
- `onPullApplied`가 `#/word`를 풀이 도중 재렌더했다 → 재렌더 예외에 추가.
- (회귀) 되짚기 결과를 끝에만 저장해 중간에 닫으면 정답을 본 채로 처음부터 다시 했다 → 단계마다 저장, 안 한
  단계부터 이어 하기.
- 2단계 식 보기에 1단계 값이 적혀 있어 뒤에 오는 1단계 계산을 베낄 수 있었다 → 식 고른 직후 계산.
- (회귀) 첫날 홈 카드가 「오늘 끝!」과 「문장제 남았어요」 둘 다에 해당했다 → 판정 순서 명시, ② 먼저.
- 답 2자리 제한이 100 넘는 단서어 오답을 잘라 리포트가 그 실수를 못 셌다 → 3자리.
- 이어 하기 때 새로 낼 문항 수가 정해지지 않았다 → `n = 3 − 오늘의 모든 문항 수`.
- (회귀) 옛 앱 공존 논증이 원소가 바뀌지 않는다고 가정했다 → 진행된 원소가 작게 직렬화됨을 확인하고, 배열에
  `null`을 금지해 그 성질을 지킨다. 테스트가 두 경우를 덮는다.
- 그 밖에 `stage` 정의, 자정 경계, `#/word` 스프린트 전 진입, XSS 대상 목록, `.sprint` 목록 누락,
  `mergeWord` 비숫자 sid 정렬, `numJosa` 범위.

**3라운드** — blocker·major 없음(합의). minor 5건 반영: `wordStart`를 「끝난 문장제 3개 이상인 첫날」로(첫 문항
직후 🔥가 줄던 문제), 뺄셈 보기 설명 정정, 리포트가 읽지 않는 `cause` 명시, 화면 단위 날짜 고정, sid를 보여
주는 순간 하나씩 발급.
