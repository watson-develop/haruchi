# 동기화 2단계 — pull·병합, 그리고 여러 기기

2026-08-09. 1단계(업로드, `2026-08-06-sync-backend-design.md`)의 후속. 1단계 문서가 이미
2단계의 골격(§2 병합, pull 커서, generation)을 규정해 뒀으므로, 이 문서는 그 골격을
**확정**하고, 그 사이 바뀐 전제 두 개를 **뒤집고**, 새로 결정된 세 가지(스프린트 세션
보존·기기 등록 승인 흐름·화면 대응)를 더한다. 두 문서가 어긋나면 **이 문서가 맞다.**

개정 이력:

  항상 병합 결과, 자동 `rewrite_sheet` 폐지, 서버 버전 트리거, invites RLS
- → 2라운드(Critical 4·Important 4·Minor 2 수용): sheet 충돌은 적용 계층 격리로, 무sid

- → 3라운드(Critical 3·Important 8·Minor 4 수용): 레거시 sid 물질화, 격리 탈출 절차,

- → 4라운드(Critical 2·Important 5·Minor 6 수용): **업그레이드 스탬프 시딩**(무음 채점

  지점 명시. 리뷰어 판정: 잔여는 구현 계획 단계에서 흡수 가능한 수준

## §1 병합 — `engine/merge.ts`가 유일한 주인

### 병합의 입력은 Day가 아니라 "Day + 묶음 스탬프"다

병합 규칙표는 묶음별 타임스탬프와 기기를 비교하는데, 로컬 `Day` 타입에는 그 값이 없고
어디에도 영속되지 않는다(아웃박스의 `bundleAt`은 push 후 삭제되는 일시 값). 비교할
값이 없는 LWW는 미정의 연산이다(1라운드). 해소 — **로컬에 묶음 스탬프를 영속한다**:

```ts
type BundleStamps = {
  sheetAt: string | null
  sheetBy: string // ISO(기기 시계) | null, deviceId('' 가능)
  gradesAt: string | null
  gradesBy: string
  sprintAt: string | null
  sprintBy: string // 정보용 — 병합 판정에 쓰지 않는다(합집합)
  settingsAt?: string | null
  settingsBy?: string // meta 전용
}
```

`*By`가 묶음별로 분리된 이유(2라운드): 병합 결과는 묶음별 승자가 다른 기기일 수 있다.
같은 이유로 **서버 `days`에도 `sheet_by`·`grades_by`·`sprint_by` 열을 추가한다**(기존
`device` 열은 "마지막으로 쓴 기기"라는 별개 사실로 남는다). 값이 없던 행·옛
클라이언트가 쓴 행의 `*_by`는 `''`로 읽는다.

- 새 IndexedDB 스토어 `stamps`(키 = 날짜 문자열, 값 = `BundleStamps`). `meta`의
  스탬프는 같은 스토어의 `'meta'` 키
- DB_VERSION 3. 업그레이드 시 기존 날들의 스탬프는 null(모름)로 시작하되, **아웃박스에
  표식이 남아 있는 날짜·묶음은 그 표식의 `bundleAt`으로 스탬프를 시딩한다**(4라운드
  Critical — 시딩이 없으면 "아직 못 올린 로컬 채점(스탬프 null)"이 "서버의 더 낡은
  채점(`grades_at` 실재)"에게 공통 규칙 2로 반드시 져서, 업그레이드 첫 동기화가 미푸시
  변경을 무음으로 지운다. 표식이 없는 날짜는 이미 push된 상태라 null이 무해하다 — 첫
  pull이 같은 내용으로 수렴시킨다)
- 서버 `meta`에 `settings_at timestamptz`·`settings_by text` 열을 추가하고,
  마이그레이션에서 `settings_at`이 null인 기존 행을 `updated_at`으로 백필한다(백필이
  없으면 null 스탬프끼리의 타이브레이크가 "새 기기의 기본 설정 vs 가족 설정"을
  복권으로 정한다). 기존 `updated_at`은 서버 시계라 LWW에 쓰지 않는다 — pull 커서
  전용이다

서명:

```
type Stamped<T> = { value: T; at: BundleStamps }
mergeDay(a: Stamped<Day>, b: Stamped<Day>): Stamped<Day>
mergeMeta(a: Stamped<Meta>, b: Stamped<Meta>): Stamped<Meta>
```

`src/engine/merge.ts`. DOM·저장소·네트워크를 모른다. 속성 테스트로 **교환·결합·멱등**을
고정하고, **왕복 속성 둘**을 추가한다: ① 병합 결과를 다시 병합 입력으로(로컬-로컬),
② **서버 비대칭 왕복**(4라운드) — 서버의 무sid 행을 pull해 물질화한 로컬과 서버 원본을
재병합해도 멱등(증식 0)이어야 한다. applyPulled의 물질화는 무표식이라 서버 배열은
무sid로 남을 수 있는데, 왕복 안정성은 "배열 영속"이 아니라 **재물질화의 결정성**(같은
무sid 배열 → 항상 같은 파티션·같은 sid)에 의존한다 — 이 성질을 테스트가 직접 고정한다.
생성기는 null 스탬프·모르는 필드·무sid 그룹·기형 sid·같은 다중집합 다른 순서·묶음별
승자 갈림을 반드시 포함한다.

**출력 스탬프의 정의**: LWW 묶음(sheet·grades·settings)은 그 묶음 승자의 스탬프
그대로 — 재스탬프하지 않는다(병합은 편집이 아니라 사실의 종합이다). 예외 하나(4라운드):
**존재-승리(상대에 묶음 자체가 없음)로 이긴 결과를 push할 때, 승자 스탬프가 null이면
지금 시각·자기 deviceId로 찍는다** — 최초 기입은 종합이 아니라 편집이다. 이 예외가
없으면 새(빈) 서버에 기존 데이터를 올리는 첫 push가 `meta_guard_stamp`("payload 변경 시
스탬프 전진 요구")에 영구 거부된다. **sprint는 합집합이라 승자가 없다**:
`sprintAt`·`sprintBy`는 양쪽 `(at, by)` 중 큰 쪽 — 병합 판정에 쓰지 않는 정보용이다.
push가 PATCH하는 `*_at`·`*_by`는 이 출력 스탬프다.

**서버 행 → `Stamped<Day>` 변환**: `payload` → `value`, `sheet_at`/`sheet_by`… →
`at`(null·부재는 null/`''`). 변환 규칙은 `sync.ts`의 한 함수에만 있다.

**서버는 병합하지 않는다** — 서버가 강제하는 것은 안전장치(sheet 불변 트리거, `rev`
낙관적 동시성, 버전·스탬프 가드 트리거)뿐이다.

### 직렬화는 두 가지고, 서로 다르다

4라운드가 잡은 용어 이중 정의의 해소 — 이름을 분리한다:

- **값 직렬화** `serializeValue(v)`: 객체 키만 정렬하고 **원소 순서는 보존**하는 JSON.
  용도: 동률 사슬의 마지막 타이브레이크, sheet 구조적 동치 판정
- **세션 정규화 키** `legacyKey(attempts)`: 각 시도를 `serializeValue`로 문자열화한 뒤
  **그 문자열들을 사전순 정렬**해 결합한 것. 용도: 무sid 그룹의 sid(`legacy:` 접두)
  계산 전용. 원소 정렬은 **키 계산에만** 쓰이고 저장 배열은 절대 정렬하지 않는다

같은 다중집합·다른 순서의 두 무sid 그룹은 `legacyKey`가 같아 같은 세션으로 접히고,
남는 쪽은 **값 직렬화(비정렬) 사전순 작은 쪽**이다 — 교환법칙 유지.

### 묶음 공통 비교 규칙

1. **묶음이 한쪽에만 있으면 있는 쪽이 이긴다.** 값의 존재가 스탬프보다 먼저다. 존재
   판정은 값 자체로 한다(sheet 비어 있지 않음, grades 키 있음…) — 스탬프로 판정하면
   잔류 스탬프가 "빈 묶음 실재"를 위조한다
2. **둘 다 있으면 `(at, by)` LWW.** null `at`은 항상 진다. `at` 동률(둘 다 null 포함)
   이면 `by` 코드포인트 오름차순 큰 쪽. `by`까지 같으면 **값 직렬화 사전순 작은 쪽**
   — DB v3 업그레이드 직후·가져오기 직후는 "at 둘 다 null, by 둘 다 `''`"이 일상이라
   사슬이 끝까지 닫혀야 속성이 성립한다
3. 스탬프는 값이 실린 묶음에만 찍힌다(1단계 `bundlesOf` 원칙 유지)

### 병합 규칙표 (개정판 — 이 표가 1단계 표를 대체한다)

| 필드                     | 규칙                                                                                                                                    | 1단계 대비 |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| `sheet`                  | **최초 1회만.** 비어 있을 때만 채워진다. 둘 다 비어 있지 않고 다르면 함수는 공통 규칙 2로 결정하되, **적용 계층이 가로채 격리한다**(§2) | 재설계     |
| `grades`·`mood`·`doneAt` | 한 묶음, 공통 규칙                                                                                                                      | 그대로     |
| `sprint`                 | **세션 합집합** — sid 물질화. 아래                                                                                                      | **바뀜**   |
| `kind`                   | 단조. `'checkup'`은 되돌리지 않는다. **묶음이 아니라 Day 고유 필드 — 병합 입력에 항상 실린다**(경로 1)                                  | 명시 보강  |
| `date`                   | 동일해야 한다(다르면 호출부 버그)                                                                                                       | 명시       |
| 모르는 필드              | **필드 단위**: 한쪽에만 있으면 있는 쪽, 둘 다 있으면 **값 직렬화 사전순 작은 쪽**. 스탬프를 보지 않는다                                 | 재설계     |

모르는 필드가 "base 통째"가 아니라 필드 단위인 이유(3라운드): base를 스탬프 최대값
쪽으로 잡으면 경로 1의 입력이 항상 지금-스탬프라 항상 base가 되어, 몇 분 전 pull이
들여온 새 필드를 화면의 낡은 스냅샷이 깎아 낸다. "있으면 남는다"가 통과 규칙의 원래
의도다.

둘 다 있을 때 스탬프를 보지 않는 이유(6라운드 — 구현이 잡았다): 초안은 "그 레코드의
묶음 스탬프 최대값이 큰 쪽"이었는데, 그 최대값은 **그 필드의 스탬프가 아니고 병합에
대해 단조도 아니다.** 모르는 필드가 없는 레코드와 병합하면 살아남은 값이 상대의 큰
스탬프를 업고 다음 비교에 나서고(승격), 공통 규칙 1이 진 쪽의 더 큰 스탬프를 통째로
버리면 병합 결과의 최대값이 입력들의 최대값보다 작아진다(소실). 어느 쪽이든 같은 세 값이
묶는 순서에 따라 다르게 수렴하므로, **이 절이 요구하는 결합과 양립할 수 없다**(속성
테스트가 두 방식 모두의 최소 반례를 들고 있다). 어차피 양쪽 기기 다 뜻을 모르는
필드다 — 최신을 따지는 것보다 어느 기기에서 계산해도 같은 답이 나오는 편이 낫다.
같은 이유로 `mergeMeta`도 `settingsAt`을 보지 않는다(같은 규칙이 두 함수에 있다).

`sheet` LWW가 함수에 남는 이유: `mergeDay`는 전역 정의여야 속성 테스트가 성립한다.
실행 경로에서는 §2의 격리가 먼저 가로채므로 이 분기는 "격리를 뚫고 들어온 경우의
결정적 폴백"이다.

시계는 **쓴 기기의 시계**다 — 서버 도착 시각으로 "개선"하지 말 것(1단계 사용자 결정
유지). 이 규칙은 서버 함수에도 적용된다 — `rewrite_sheet`·`replace_all`이 스탬프를
찍을 때도 클라이언트가 넘긴 값을 쓴다(스키마 변경 요약).

### meta — settings 한 묶음, lastExportedAt은 동기화에서 뺀다

**사용자 결정(2026-08-09, 4라운드 후): `lastExportedAt`은 기기 로컬 값으로 강등한다.**
4라운드가 잡은 모순 — `report.ts`의 「저장 안 했어요」 되돌리기(PR #18)는 이 값을 이전
값으로 되돌리는데, max() 병합 아래에서 되돌림은 서버로 못 가고 다음 pull이 큰 값을
도로 얹는다. PR #18이 고친 "저장 취소했는데 백업됨 배지"라는 가짜 안전감이 동기화
경로로 부활하는 것이다. 강등으로: 되돌리기는 그대로 동작하고, 30일 백업 배지의 의미는
"이 기기에서 마지막 파일 백업"이 된다 — 서버 이중화가 이미 도는 지금 오히려 정확한
의미다.

- **동기화되는 meta = `settings` 한 묶음**(`lastExportedAt` 제외), `(settingsAt,
settingsBy)` LWW — 공통 규칙 적용
- v2의 pull은 서버 payload의 `lastExportedAt`을 **무시**하고(적용 직전에 로컬 값을
  접붙인다), push는 서버에 있던 값을 그대로 되돌려 보낸다(송신 직전에 서버 값을
  접붙인다). **두 접붙임은 `mergeMeta` 밖의 방향별 후처리다**(5라운드 —
  lastExportedAt은 settings 객체 내부라 병합 함수 안에서 처리하면 순수성과 속성
  테스트가 깨진다). settings 동률 타이브레이크의 값 직렬화에서도 이 필드는 제외한다.
  서버 payload에서 필드를 지우지 않는 이유는 옛 클라이언트가 아니라(**v1 앱은 pull이
  없어 서버 meta를 영원히 읽지 않는다**) v2 자신의 pull 검증이다 — `validateBackup`이
  필드 부재를 거부한다
- `putMeta`는 `putDay`처럼 **바뀐 묶음을 선언한다**: `putMeta(meta, changed:
('settings'|'export')[])`. `'settings'`만 `settingsAt`을 찍고 아웃박스 표식을
  남긴다. `'export'`(내보내기·되돌리기)는 스탬프도 표식도 없다 — 로컬 기록일 뿐이다
- `derived`는 항상 빈 것으로 정규화(배선하지 않는 것이 설계)

초안의 "settingsAt null이면 meta push 안 함"은 폐기됐다(3라운드) — 병합-우선 push +
서버 백필 아래에서 null 스탬프는 LWW에서 항상 지므로 불필요하고, 남기면 흐름만 막는다.

### 스프린트 세션 보존 — 이번 설계의 가장 큰 변경

**결정(사용자, 2026-08-09): 같은 날의 스프린트 세션을 전부 남긴다.** 하루 기록의
의미가 "마지막 세션"에서 "그날의 모든 시도"로 바뀐다.

1단계가 LWW를 택한 근거("스프린트는 실사용에서 아이패드 전용")는 "아이가 여러 기기를
번갈아 쓴다"로 깨졌다. 현행 코드에서 같은 기기의 재도전은 일어나지 않는다 —
`sprint.ts`의 진입 가드가 스프린트 있는 날은 결과 화면만 그린다(초안의 "한 기기에서도
덮어쓰고 있었다"는 오류였다 — 1라운드 정정). **같은 기기 재도전 허용은 범위 밖, 진입
가드는 현행 유지.**

구현:

```ts
type SprintAttempt = { fact: string; correct: boolean; ms: number; sid?: string }
```

- **`sid`는 세션 하나에 하나.** 새 세션은 `${deviceId}:${세션 시작 epoch ms}`
- **무sid 시도는 만나는 즉시 sid를 물질화한다**: v2 코드가 무sid 배열을 손에 쥐는 모든
  시점 — 구체적으로 **`mergeDay` 입력 정규화(경로 1·2·push 병합 전부 이걸 지나간다)와
  백업 가져오기** — 에서, 무sid 시도들의 각 최대 연속 구간을 하나의 세션으로 보고
  `legacy:${legacyKey(구간)}`을 sid로 배열에 기록한다. 이후 그룹핑은 sid로만 한다.
  DB v3 업그레이드 자체는 물질화하지 않는다 — 첫 병합이 커버하며, 이 의존은 의도된
  것이다(물질화 지점을 병합 입구 하나로 모은다)
  - 왜 물질화인가(3라운드): 내용 키를 매번 재계산하면 병합 출력에서 인접해진 두 레거시
    그룹이 다음 그룹핑 때 한 구간으로 융합되고, 부분집합 그룹을 쥔 기기와 만나는 순간
    같은 세션이 두 벌로 증식한다. sid가 배열에 영속되면 파티션이 고정된다
  - "로그를 고치지 않는다"와의 관계: 시도의 사실(fact·correct·ms)은 그대로다 — sid는
    출처 표기의 추가이고 `deriveFacts`는 sid를 읽지 않는다(4라운드 검증: facts.ts는 세
    필드만 읽고, validateBackup도 여분 필드를 통과시킨다)
- **병합은 sid 그룹의 합집합.** 같은 sid는 한 번만(재수신 멱등). 같은 `legacyKey`에
  다른 순서면 값 직렬화 사전순 작은 쪽이 남는다. **그룹 내부 시도 순서는 절대 정렬하지
  않는다** — `deriveFacts`가 순서 의존이다
- **그룹 순서**: `legacy:` 그룹 맨 앞(sid 사전순) → 일반 sid 그룹(세션 시작 ms
  오름차순, 동률이면 deviceId 사전순) → **기형 sid 그룹 맨 뒤(그들끼리 sid 사전순)**
  (5라운드 — 정상 그룹 대비 위치까지 정해야 전순서가 완성된다). NaN 비교가
  comparator를 깨는 것을 막는다
- **`sprint.ts` 쓰기는 이어붙이기로**: `sprint: [...(existing?.sprint ?? []), ...attempts]`
- `sprintAt`·`sprintBy`는 정보용(커서·표시)으로만

파생 계산(`facts.ts`·`streak.ts`·`report.ts`)은 손대지 않는다.

### 쓰기 경로는 둘이고, 계약이 다르다

**경로 1 — `putDay(day, changed)` (화면 쓰기):** 선언된 묶음은 지금 시각·자기
deviceId로 스탬프하고, 미선언 묶음은 입력에 넣지 않는다(공통 규칙 1로 저장본이
이긴다). `date`·`kind`는 항상 실린다(`kind`는 `putDay(day, ['sprint'])`로 저장되는
checkup 표시의 유일한 운반로 — 단조라 안전). **모르는 필드는 입력에서 제거한다**
(5라운드 — v2 코드는 모르는 필드를 생성할 수 없으므로 정보 손실이 없고, 실으면 화면
스냅샷의 낡은 값이 지금-스탬프에 업혀 pull이 들여온 새 값을 이기고 그 역행이 push로
서버까지 전파된다. 규칙표의 모르는-필드 양쪽-실재 규칙은 기기 간 병합(경로 2·push)
전용이다).
같은 트랜잭션에서 저장본과 `mergeDay` → 결과 쓰기 + 스탬프 갱신 + 아웃박스 표식.
CLAUDE.md의 "putDay 선언" 불변식은 이 경로의 계약으로 재서술된다. 화면 코드는 바뀌지
않는다.

**경로 2 — `applyPulled(rows)` (pull 적용, 신설):** 서버 행을 변환해 저장본과
`mergeDay` → 결과 쓰기 + 출력 스탬프 보존 — 같은 트랜잭션, **아웃박스 표식 없음**
(로컬이 앞서는 묶음은 경로 1이 이미 표식을 남겼고, push가 지웠다면 병합-우선 push라
서버에 이미 흡수돼 있다). sheet 충돌 격리의 가로채기가 병합 앞에 있다.

병합 함수는 하나, 두 경로의 차이는 입력 조립과 부수 효과뿐이다. `pushDay`는 병합
결과를 서버에 보낼 뿐 **로컬에 쓰지 않는다** — 제3의 로컬 쓰기 경로를 만들지 않는다.

### schema_version — 가드는 서버에 있어야 한다

sid 도입과 함께 **`SCHEMA_VERSION`을 2로 올린다.** 클라이언트 가드는 정작 막아야 할
옛 클라이언트에 실리지 않는 코드다(1라운드) — 서버 트리거가 유일한 자리:

- **`days_guard_version`**: `new.schema_version < old.schema_version`인 UPDATE 거부
- **`meta_guard_stamp`**: `lastExportedAt`을 제외한 payload가 **값으로**
  바뀌는데(`(new.payload #- '{settings,lastExportedAt}') is distinct from
(old.payload #- '{settings,lastExportedAt}')` — jsonb 값 비교라 키 순서 무관.
  4라운드: 비교 의미를 못 박지 않으면 옛 pushMeta의 통과 여부가 구현 복불복이 된다)
  `settings_at`이 전진하지 않는 UPDATE 거부. 옛 앱의 내보내기(lastExportedAt만 변경)는
  통과하고, 옛 앱의 설정 편집만 PWA 갱신까지 지연된다
- **`replace_all` 수정 넷**: ① days `schema_version` 하드코딩 제거 — 스냅샷 payload의
  `schemaVersion`에서. ② **자동 스냅샷의 `'schemaVersion', 1` 리터럴도 함께**(4라운드
  — 남기면 v2 데이터가 v1 라벨을 달고 스냅샷에 앉아 옛 기기의 버전 게이트가 뚫린다):
  교체 전 days의 `max(schema_version)`(없으면 1)로 기록. ③ meta 교체 시
  `p_settings_at`·`p_settings_by` **인자**(default `now()`/`''` — 혼재 호환)로 스탬프
  기록 — v2 클라이언트는 로컬 `settingsAt`(null이면 지금 시각)을 넘긴다. ④ **자기
  meta UPDATE는 `meta_guard_stamp`에서 면제한다**(5라운드 — 트리거는 security definer
  안이라고 봐주지 않으므로, 면제가 없으면 가져오기·초기화의 서버 경로 전체가 자기
  가드에 거부된다. `rewrite_sheet`가 이미 쓰는 `set_config` 세션 플래그 패턴으로).
  가드의 "전진" 판정에는 null → 값 도 포함한다
- **`rewrite_sheet` 수정**: `p_sheet_at`·`p_sheet_by` 인자 추가 + **`p_schema_version`
  인자(default 1)로 `schema_version` 갱신**(4·5라운드 — Day payload에는 버전 필드가
  없어 인자가 필요하다. v2 payload가 v1 라벨 행에 앉으면 혼재 기간 옛 앱의 통째
  PATCH가 가드를 1→1로 통과해 물질화 배열을 되덮는다)

**backup.ts도 함께 올린다**: `backupPayload`의 `schemaVersion` = 상수
`SCHEMA_VERSION`(2), `validateBackup`은 1..SCHEMA_VERSION 수용 + **sid가 있으면 문자열
타입 검사**(4라운드 — 그룹핑·정렬 코드의 전제). 옛 기기가 v2 파일을 가져오면 자기
validateBackup(`=== 1`)이 시끄럽게 거부한다 — 조용한 오염이 아니라 명시적 실패.

옛 클라이언트의 새 날짜 INSERT(v1)는 허용한다 — 새 행은 아무것도 덮지 않고, v2 기기가
pull해 병합하면 된다.

## §2 pull 엔진 — `data/sync.ts`에 붙는다

### push가 먼저 바뀐다 — 보내는 것은 항상 병합 결과다

현행 push는 rev만 읽고 payload를 통째 PATCH한다. 두 기기가 쓰면 이것만으로 데이터가
사라진다(1라운드 — rev는 "동시에 눌린 두 쓰기"용이지 "그 사이 다른 기기가 쓴 것"용이
아니다). 해소: **`pushDay`는 서버 행 전체(payload + `*_at`·`*_by`)를 읽어 로컬과
`mergeDay`한 결과를 PATCH한다.** 항상 병합이다. `pushMeta`도 같은 규칙(`mergeMeta` 후
PATCH, settings 승자 스탬프 기록 — 존재-승리 시 §1의 지금-스탬프 예외).

### sheet 충돌은 병합하지 않고 격리한다

병합-우선 push 아래에서 sheet LWW는 `sheet_immutable`을 영원히 발화시키지 않는다 —
로컬이 지면 병합 결과가 서버와 같아 조용히 통과하고 pull이 로컬 종이를 교체한다.
아이가 품은 종이가 채점 화면과 어긋나는데 배너가 없다(2라운드). 해소:

- push·pull 양쪽에서 병합 호출 전에 판정: 로컬과 원격의 sheet가 **둘 다 비어 있지
  않고 서로 다르면**(다름 = 구조적 동치의 부정 — 객체 키 순서 무시. jsonb가 키 순서를
  보존하지 않아 나이브한 문자열 비교면 첫 pull에서 전면 오탐 격리된다. 서버 트리거의
  `is distinct from`과 같은 의미다) 그 날짜를 격리한다
- **격리가 막는 것은 적용이지 판정이 아니다**(4라운드) — pull은 격리 날짜의 행도 계속
  받아 판정을 재실행한다. 서버가 한 sheet로 수렴하면(상대 기기가 해소하면) 판정
  조건("서로 다름")이 사라져 **자연 해제**된다. 행을 통째 건너뛰는 구현은 자연 해제를
  없앤다
- 격리된 날짜(`device` 스토어 목록): push와 pull **적용**을 하지 않는다. 다른 날짜는
  정상 동기화. 부모 홈에 요란한 배너: "다른 기기에서 오늘 문제지를 먼저 만들었어요 —
  어느 종이로 채점할지 골라 주세요"

**격리 탈출**(4라운드 재서술 — 이전 판은 탈출 push가 격리 자신의 push 금지·격리
판정에 걸려 실행 불가능했다):

- **`rewrite` 의도 표식은 격리의 push 금지와 격리 판정 양쪽을 명시적으로 면제한다.**
  이 면제가 탈출의 성립 조건이다(「다시 만들기」의 rewrite push도 같은 면제를 탄다)
- **rewrite 계열의 송신 payload는 `mergeDay(로컬, 서버)` 출력에 sheet만 로컬로 강제한
  것이다**(5라운드 — "sprint만 얹는" 조립은 서버의 `kind:'checkup'`·모르는 필드를
  통째 교체로 되돌린다. 병합 출력을 쓰면 kind 단조·모르는 필드 통과·sprint 합집합이
  전부 기존 병합 규칙을 그대로 탄다). 로컬에는 쓰지 않는다 — 로컬에 쓰면 rewrite가
  거부되는 분기에서 "다른 종이에 대한 채점이 로컬 sheet에 붙은" 오염이 영속된다. rev
  재시도마다 서버를 다시 읽어 재조립한다
- **`sheet_rewrite_graded` 거부의 처리**(5라운드 — 이 규정이 없으면 rewrite 표식이
  격리 판정을 면제하는 탓에 배너 없이 매 패스 거부만 반복되는 영구 미동기가 된다):
  rewrite push가 이 거부를 받으면 **rewrite 플래그를 소거하고 그 날짜를 격리에
  넣는다** — 배너는 "다른 기기에서 이미 채점까지 마쳤어요" 변형으로, 「채택」만 남는다.
  `rev` 충돌과 이 거부는 응답 본문으로 구분한다(현행 `isSheetImmutable` 패턴과 동일 —
  일괄 `!res.ok` 처리 금지)
- **「이 기기 종이 유지」**: ① 서버 행을 읽어 서버 grades 존재를 먼저 확인 — 있으면
  「유지」는 불가능하므로 push를 시도하지 않고 위 「채택」만 남는 배너로 전환. ② 없으면
  위 조립 규칙대로 rewrite 표식 push(①과 ② 사이에 grades가 도착하면 위 거부 처리로
  합류한다). ③ 성공 시 격리 해제
- **「다른 기기 것 채택」**: sheet·grades는 서버 것을 받고(로컬의 어긋난 grades는 함께
  버려진다 — 다른 문제지의 정답표에 채점이 붙는 오염이 재인쇄 불변식이 막으려는 것),
  sprint는 평소대로 합집합, kind 단조, 스탬프는 서버 것 보존. 로컬에만 있던 sprint
  세션이 있으면 그 묶음 표식을 남긴다. **격리 해제와 함께 그 날짜의 잔존 rewrite
  플래그를 제거한다**(5라운드 — 남으면 채점 있는 행에 대한 RPC가 payload 동일 여부와
  무관하게 거부라 표식이 영원히 소진 불가)

격리는 기기별 상태다 — 상대 기기는 각자 판정으로 각자 격리되고, 한쪽의 해소가 서버를
수렴시키면 다른 쪽은 자연 해제된다. 서로를 기다리는 교착은 없다.

### 자동 `rewrite_sheet` 추론을 명시적 의도로 바꾼다

아웃박스 표식에 `rewrite: true` 플래그. 찍는 곳은 둘 — 「다시 만들기」, 격리 배너의
「유지」. `foldOutbox`는 같은 날짜 표식을 접을 때 rewrite를 OR로 합친다. 플래그 없는
push가 `sheet_immutable`에 거부되면 우회하지 않고 격리 목록에 넣는다(배너 경로 합류).

### 커서

`GET /rest/v1/days?updated_at=gt.<lastPulledAt − 5분>&order=updated_at.asc`. 규칙 둘:
**`lastPulledAt`은 서버 응답의 최대 `updated_at`으로만 갱신**(클라이언트 시계가 앞선
만큼의 행을 영영 놓친다), **여유창 5분 겹쳐 받기**(Postgres `now()`는 트랜잭션 시작
시각 — 긴 트랜잭션의 행이 커서 뒤에 숨는다. 병합이 멱등이라 재수신은 무해).

`updated_at`은 서버 시계다 — pull 커서는 "서버에서 언제 바뀌었나"의 물음이라 서버
시계가 맞고, 병합 LWW는 "누가 나중에 편집했나"라 기기 시계가 맞다. 섞지 않는다.

`lastPulledAt`은 `device` 스토어. `meta`·`app_config`는 행이 하나라 커서 없이 pull
때마다 같이 읽는다.

### 언제 내리나

| 트리거                                                     | 기다리나                     |
| ---------------------------------------------------------- | ---------------------------- |
| 앱 시작 (`main.ts`)                                        | 아니오 — 배경                |
| 부모 화면 진입 (`#/parent`·`#/print`·`#/grade`·`#/report`) | **예** — 렌더 전에 완료 대기 |
| 아이 화면 진입 (`#/`·`#/sprint`·`#/map`·`#/ebs`)           | **아니오** — 배경, 오면 갱신 |
| 탭 복귀 (`visibilitychange`)                               | 아니오 — 배경                |
| push가 `rev` 충돌로 실패했을 때                            | 예 — 재시도 경로의 일부      |

부모 화면 대기 3초 타임아웃 — 넘기면 로컬로 그리고 도착 시 갱신. **이 대기는 화면
표시용이지 안전장치가 아니다** — 안전이 걸린 곳(문제지 생성, PIN 설정)은 각자의
게이트가 전체 타임아웃(15초)으로 따로 기다린다. 아이 화면이 기다리지 않는 이유: 세션
합집합 덕분에 낡은 로컬로 시작해도 손실이 없다.

**배경 pull 후 화면 갱신**: pull이 실제로 로컬을 바꾼 경우에만 재렌더(같은 해시
재렌더는 안전 — 화면이 매번 IndexedDB에서 다시 읽는다). 예외 — **미커밋 입력을 쥔
화면은 재렌더하지 않는다**: `#/sprint` 진행 중, `#/grade` 채점 진행 중(수 분치 O/X가
메모리에만 있고, PIN 세션 규칙과 겹쳐 PIN까지 다시 묻게 된다). 저장 시점의 경로 1
병합이 수습한다.

### 내려온 것을 믿지 않는다

pull payload는 백업 파일과 같은 등급으로 검증한다. `validateBackup`의 day 단위 검증을
통과하지 못한 행은 적용하지 않고 로컬 유지 + 부모 홈 경고. **meta·app_config payload도
같은 등급으로 검증한다**(5라운드 — 기형 settings가 앉으면 스프린트 판정이 전 기기에서
오염된다). 기형 payload가 앉으면 `deriveFacts`가 모든 화면에서 죽고 동기화가 오염을 전
기기로 복제한다. **거부한 행이 있으면 `lastPulledAt`을 그 행의 `updated_at` 직전으로
멈춘다**(5라운드 — 커서가 지나치면 거부 행은 서버에서 다시 바뀌기 전까지 영영
재수신되지 않는다. 서버 쪽이 고쳐지는 즉시 다음 pull이 다시 받는다).

### push 충돌 경로

- INSERT는 조회 0행일 때만, `rev = 1`. upsert 금지. **INSERT 직전 서버
  `meta.generation` 재확인** — 다르면 중단하고 §3 재기준화로("조회 0행"이 "방금 지워진
  날"일 수 있다). 재확인과 INSERT 사이 밀리초 창은 감수
- PATCH rev 불일치 0행 → 다시 받아 `mergeDay` 후 재시도 3회 → 실패 시 아웃박스 유지
- 동시 INSERT PK 충돌 → 진 쪽은 pull해 `mergeDay` 후 PATCH 재시도

### 재인쇄 동일성 — 생성 게이트

- 게이트는 「문제지 만들기」 **버튼**에 있다 — 누르면 pull을 전체 타임아웃(15초)으로
  기다린다
- pull 성공 + 오늘 sheet 존재 → 생성하지 않고 그것을 보여준다
- pull 실패 → 경고 후 명시적 진행 선택 요구
- 확인 통과해도 **쓰기 직전 로컬 오늘 sheet 재검사**(다이얼로그 사이 배경 pull 도착
  가능) — 존재하면 중단하고 보여준다
- 남는 창은 격리가 받아낸다 — 무음이 아니라 배너로

## §3 generation — 파괴적 경로와 pull의 만남

**순서 규칙: 오프라인 복귀 push는 `meta` pull(generation 확인)을 먼저.** INSERT 직전
재확인(§2)이 보강한다.

**재기준화(generation 증가 관찰 시):**

0. 관찰한 비행 안에서 시작하지 않는다 — suspendSync의 비행 대기를 자기에게 걸어
   교착한다. 플래그만 세우고 비행 종료 후 별도 태스크
1. 전체를 `suspendSync`(push + pull 적용)로 감싼다
2. 로컬 전체를 서버 스냅샷으로(`snapshots`, reason `'rebase'`)
3. 스냅샷 이후 로컬 변경 재확인(신호: 아웃박스 새 key) — suspendSync는 로컬 쓰기를
   막지 않는다. 바뀌었으면 재스냅샷(최대 2회, 초과 시 중단·연기)
4. 서버 상태로 로컬 통째 교체(days·meta·stamps)
5. 아웃박스·격리 목록 비우고 `generation`·`lastPulledAt` 서버 값으로, **`seededAt`은
   지금 시각**(null이면 seedOutbox가 서버 사본 전체를 재업로드한다). resumeSync

**로컬 통째 교체 공통 규정** — 재기준화·파일 가져오기·스냅샷 되돌리기(restore) 셋 모두:
같은 트랜잭션에서 **stamps 교체**(재기준화 = 서버 스탬프, 가져오기·되돌리기 = null —
파일·스냅샷에는 스탬프가 없고 공통 규칙 1이 내용을 지킨다), **격리 목록 비움**, 전체
`suspendSync` 감싸기(push 정지만으로는 clear와 `serverReplaceAll` 사이의 배경 pull이
옛 행을 되살리고 seedOutbox가 전량 재업로드한다).

재기준화가 오프라인 신규 기록을 자동으로 살리지 않는 것은 감수 — 자동 선별은 시계
비교가 틀리면 지운 데이터를 부활시킨다. 복구 경로(스냅샷 되돌리기)가 화면에 있고,
부모 홈에 알린다: "다른 기기에서 기록이 교체되어 이 기기를 맞췄어요."

**초기값**: generation 필드가 없던 기기의 첫 관찰은 재기준화 없이 서버 값 채택(1단계
기기가 하나라 서버 상태가 곧 그 기기 상태 — 첫 관찰을 "증가"로 오인해 통째 교체하는
쪽이 더 큰 사고).

**로컬 파괴적 교체 뒤의 `generation`**: `replace_all`을 성공시킨 기기는 자기 `generation`을
`null`로 되돌린다 — 그 증가의 출처가 자기 자신이므로 관찰할 남의 변경이 없고, 위 「초기값」
분기가 다음 pull에서 서버 값을 재기준화 없이 채택한다(그대로 두면 초기화·가져오기·되돌리기
때마다 자기 업로드에 대한 재기준화가 한 번씩 돌아 아직 못 올린 로컬 쓰기를 버린다).

`generation`·`lastPulledAt`·격리 목록은 `device` 스토어(기기마다 다른 값).

## §4 채점 화면 PIN (2B)

1단계 §4 유지: 게이트는 `#/grade` 하나. PIN 4자리, 서버 `app_config.pin`(레포가
공개라 소스에 하드코딩하지 않는다), 로컬 캐시, 오프라인은 캐시로. `replace_all`은
`app_config`를 건드리지 않는다.

2단계 확정:

- 진입 순서: pull 대기 → PIN 게이트 → 렌더
- 설정 흐름: **`serverStatus` 정상 + 성공한 pull의 빈 응답일 때만** 설정을 연다(폐기된
  키의 RLS 응답도 200 + 빈 배열 — 이 코드베이스가 스스로 경고해 둔 함정). pull 실패·
  인증 이상이면 캐시로 검증, 캐시도 없으면 "서버에 연결한 뒤 다시 시도". INSERT PK
  충돌(동시 최초 설정) 시 pull로 기존 행을 받아 그 PIN으로 재검증
- 입력 UX: `confirmDialog` 계열 오버레이 + `inputmode="numeric"` 마스킹 4자리
- 세션 캐시: 화면을 떠날 때까지만. 시간 캐시 없음
- PIN 변경: `#/report`에서 현재 PIN 확인 후. 분실 시 SQL(`update app_config set
pin=...`) — supabase/README에 기록
- 틀린 입력: 즉시 재입력, 잠금·지연 없음(위협 모델: 아이의 우연한 접근). 평문 저장

아이/부모 소속 불변식: PIN은 두 번째 방어선 — 첫 번째(소속 분리)를 대체하지 않는다.

## §5 기기 등록 — 기존 기기가 승인 (2C)

**결정(사용자, 2026-08-09): 승인 코드 방식.** 평문 키를 사람이 만지지 않는다.

```
등록된 기기(부모 홈)                     새 기기
  [새 기기 추가] → issue_invite()
  → 코드 6자리 표시 (10분 유효)
                                        코드 입력 → claim_invite(code, deviceId, label)
                                        → 응답: 평문 키 (이 한 번만)
                                        → device 스토어 저장, 즉시 pull 시작
```

등록 직후는 **pull 먼저** — 로컬이 비어 있으니 서버 채택이 곧 초기화다. meta는
병합-우선 push + 백필로 새 기기의 null 스탬프가 항상 지므로 가족 설정이 안전하다.

```sql
create table if not exists invites (
  id         bigserial primary key,
  code_hash  text not null,            -- crypt(6자리, salt)
  created_by text not null,
  created_at timestamptz not null default now(),
  expires_at timestamptz not null,     -- +10분
  fail_count int not null default 0,   -- 5회면 즉시 만료
  used_at    timestamptz,
  used_by    text
);
alter table invites enable row level security;
-- 정책 없음: RPC(security definer)만 접근. 빠지면 anon 키로 code_hash 오프라인 대입
-- 또는 아는 코드의 해시 직접 INSERT로 기기 등록이 가능해진다.
```

- **`issue_invite()`**: `haruchi_device()` null이면 거부. 한 트랜잭션에서 기존 활성
  invite 전부 만료 + 새 행(동시 발급에도 활성 최대 1). 평문 코드 반환
- **`claim_invite(p_code, p_device_id, p_label)`**: 익명 호출. 사용 처리는
  원자적(`update ... where used_at is null` 0행이면 경쟁 패배 거부). 실패 시
  `fail_count`++, 5면 만료. 성공 시 32바이트 키 생성·해시 저장·평문 반환(이 한 번뿐).
  `p_device_id` 중복 거부(재등록은 수동 경로)

무차별 대입: 6자리·10분·활성 1·일회용·5회 만료·`write_log` — 10분 창 5번 추측(5/10⁶),
가족 위협 모델에서 충분. **전 기기 폐기 복구**: SQL 수동 insert를 README "복구" 절로.

## §7 1단계→2단계 전환 (혼재 기간의 안전)

sync-config가 채워져 있어 실기기가 배포 즉시 새 스키마와 통신한다. **순서: 스키마
먼저, 앱 배포는 직후.** 혼재 기간(스키마 v2 + 앱 v1):

- `*_by`·`settings_at` 열: 옛 앱은 모르고 안 쓴다 — nullable이라 무해
- `meta_guard_stamp`: lastExportedAt 제외 + 값 비교 덕분에 옛 앱의 내보내기는 계속
  동작. 설정 편집만 지연(현재 설정 편집 UI가 없어 실질 영향 없음)
- `days_guard_version`: 옛 앱 push는 v1 → v1이라 통과
- `rewrite_sheet`: 새 인자 default + **옛 3인자 시그니처 drop**(안 지우면 자동 우회의
  진입점인 옛 함수가 오버로드로 잔존). 옛 앱의 3인자 호출은 default로 새 함수에 해석
- 옛 앱의 자동 rewrite 추론은 혼재 기간에 살아 있다 — 기기가 하나인 동안이라 실질
  위험 없음. **2C는 반드시 2A 앱 배포 후** — 이 순서가 혼재 기간에 기기가 늘지 않음을
  보장한다

## 클라이언트 변경 요약 (`db.ts` DB_VERSION 3, `backup.ts`, `sync.ts`)

- `stamps` 스토어 신설. 업그레이드 시 null 시작하되 **아웃박스 표식의 `bundleAt`으로
  해당 날짜·묶음 스탬프를 시딩**(§1 — 미푸시 변경 보호). 같은 날짜의 표식 여럿은
  `foldOutbox`(묶음별 최신)로 접은 뒤 시딩하고, `*By`는 자기 deviceId다. **meta는
  시딩할 수 없다**(v1 표식의 `bundleAt`이 `{}`) — 미푸시 settings 변경은 보호되지
  않으나 현재 설정 편집 UI가 없어 실해 없음(감수 목록)
- `device` 스토어: `generation`·`lastPulledAt`·격리 목록 추가
- 아웃박스 표식: `rewrite` 플래그(`foldOutbox` OR 접기)
- `putDay` 경로 1 계약, `applyPulled` 신설, `pushDay` 로컬 미기록 (§1)
- `putMeta(meta, changed: ('settings'|'export')[])` — `'export'`는 스탬프·표식 없음,
  `lastExportedAt`은 동기화 제외(pull 무시·push 통과) (§1)
- 로컬 통째 교체 3경로 공통 규정: stamps 교체·격리 목록 비움·suspendSync (§3)
- `suspendPush` → `suspendSync`
- `backupPayload` = `SCHEMA_VERSION`(2), `validateBackup` 1..2 수용 + sid 문자열 타입
  검사 (§1)

## 불변식 확인 (CLAUDE.md 대조)

- **재인쇄 동일성**: 생성 게이트 + 격리(무음이 아니라 배너) + 탈출 절차가 타기기
  기록을 지키며 수렴. 자동 재생성 없음
- **빈 `sheet` 실재**: 공통 규칙 1 + sheet 규칙이 보장
- **로그는 사실, 파생은 해석**: 병합은 로그끼리의 연산, 파생 저장 없음. 스탬프는 "언제
  누가 썼나"라는 사실. sid 물질화는 사실을 바꾸지 않는 출처 표기(`deriveFacts`는
  sid를 읽지 않는다 — 코드로 검증됨)
- **`attempts` 잘라내지 않기**: 합집합은 늘리기만 한다
- **단일 출처**: 병합은 `merge.ts` 하나, 서버 행 변환은 `sync.ts` 한 함수
- **`putDay` 선언**: 경로 1 계약으로 재서술, `putMeta`도 선언 계약. pull 적용은 별도
  진입점
- **`backupPayload` 단일 주인**: 스냅샷·`replace_all` 버전·`validateBackup` 수용
  범위가 전부 이것을 따른다
- **아이/부모 소속**: `navigate` 추가 없음. PIN은 두 번째 방어선
- **배포 URL 불변**: 변경 없음

## 감수한 것

- 재기준화가 오프라인 신규 기록을 자동으로 살리지 않음(재확인 2회 + 중단·연기, 스냅샷
  복구 존재). 마지막 재확인과 교체 사이 비원자 창 포함
- INSERT 직전 generation 재확인과 INSERT 사이 밀리초 창
- 옛 클라이언트의 설정 편집·v2 행 갱신이 PWA 갱신까지 지연(잃는 것이 아니라 늦는 것)
- 격리 중 그 날짜의 grades 동기화도 멈춤(날짜 단위가 설명하기 쉽고 배너로 드러난다.
  sprint는 탈출 시 합집합 합류)
- 「유지」가 서버 채점 존재로 불가능한 경우 이 기기 종이의 답안은 자동으로 못
  살린다(사람 개입)
- 레거시 그룹은 정렬 맨 앞 — 실제로는 늦었을 수 있어 유창 판정 재생이 역사적 순서와
  어긋나는 날 가능(옛 데이터 한정, 시작 시각 정보 자체가 없다)
- v1의 미푸시 settings 변경은 업그레이드 시딩으로 보호되지 않는다(v1 meta 표식에
  `bundleAt`이 없다 — 설정 편집 UI가 없어 실해 없음)
- v1의 미푸시 「다시 만들기」 표식은 rewrite 플래그가 없어 업그레이드 후 첫 push에서
  격리로 떨어진다 — 데이터는 안전하나 배너 문구("다른 기기에서…")가 사실(자기 기기
  재작성)과 어긋난다. 아빠가 「유지」를 누르면 그대로 수렴한다
- 30일 백업 배지가 기기별 판정이 된다(`lastExportedAt` 로컬 강등 — 사용자 결정. 서버
  이중화가 도는 지금 파일 백업 경고의 무게 자체가 줄었다)
- iOS 백그라운드 fetch 조기 종료(1단계와 동일), PIN 평문·무지연, claim_invite 잔여
  5/10⁶, 오프라인 이중 인쇄의 종이 둘(격리로 드러낼 뿐 봉할 수 없다), 혼재 기간 자동
  rewrite 잔존(기기 하나인 동안)

- `merge.ts` 속성 테스트: 교환·결합·멱등 + 왕복 둘(로컬-로컬, **서버 비대칭** — 무sid

  검증
