## Phase 1이 만든 것

매일 A4 1장(세로셈 8 + □ 채우기 2)을 인쇄해 풀고, 아빠가 탭 몇 번으로 채점하면 다음날 문제 구성이 조정된다. 홈 화면에 추가하면 오프라인으로 돈다.

**지켜야 할 두 불변식** — 코드 곳곳이 여기에 기대고 있다.

- **재인쇄는 같은 문제를 낸다.** `src/screens/print-sheet.ts`의 `if (!day || day.sheet.length === 0)`이 `sheet`를 **자동으로** 쓸 수 있는 유일한 게이트다. 이게 깨지면 아이 손의 종이와 채점 화면이 어긋나 데이터가 조용히 오염된다
  - **예외는 아빠가 직접 누르는 `다시 만들기` 하나뿐이다**(2026-08-04 추가). 종이가 이미 아이 손에 있는지는 코드가 알 수 없으므로 사람만 이 불변식을 깰 수 있게 했다 — 확인 배너를 거치고, **채점이 있는 날은 아예 거부**한다(저장된 grades가 다른 문항에 붙어 버린다). 문항 생성 로직이 바뀌었는데 그날 문제지가 이미 만들어져 있을 때(예: 이름을 서아로 바꾼 날의 `○○` 문제지) 쓰라고 만든 탈출구다. **자동 재생성을 새로 만들지 말 것** — 이 버튼이 그 자리를 이미 채운다
- **`derived`는 버릴 수 있는 캐시다.** 실제로 `Meta.derived`를 읽는 코드가 하나도 없고, 매번 `days` 로그에서 재계산한다. 덕분에 판정 규칙을 바꾸면 과거 전체가 새 규칙으로 재해석된다 — 마이그레이션이 필요 없다

## Phase 2가 만든 것

홈에서 `구구단 스프린트`를 누르면 30문제를 풀고, 반응시간 중앙값이 `fluentMs`(2500ms) 이하로 3회 연속 맞으면 그 식이 "정복"된다. 정복한 칸만 답이 채워지는 지도가 결과 화면과 `#/map`에 뜬다 — **지금은 72칸이다**(Phase 2 당시엔 81칸이었고 Phase 4에서 1단이 빠졌다). 홈에 `🔥 연속일수`가 붙었다.

**Phase 2가 세운 것 중 기억할 것**

- **`engine/facts.ts`가 식 id 형식의 유일한 주인이다.** `factId`가 만들고 `factAnswer`가 푼다. 곱셈 기호는 U+00D7이며 화면은 절대 직접 파싱하지 않는다. `factAnswer`는 형식이 어긋나면 **던진다** — `deriveFacts`가 알 수 없는 id를 조용히 건너뛰는 것과 의도적으로 반대다. `deriveFacts`는 오염됐을 수 있는 과거 로그를 재생하므로 던지면 앱이 안 열리고, `factAnswer`의 입력은 엔진이 방금 만든 큐라 어긋났다면 엔진이 자기모순인 것이다. 이 비대칭은 두 곳 주석에 적혀 있다
- **스프린트만 한 날은 `sheet: []`인 `Day`를 만든다.** 이게 코드베이스 최초의 빈 sheet 생산자다. `home.ts`의 `pendingGradeDate`와 `grade.ts`가 둘 다 `sheet.length === 0`을 검사해야 하는 이유다 — 최종 리뷰가 이 조합에서 Critical을 찾았다. **`sheet`를 읽는 코드를 새로 쓸 때마다 빈 sheet를 어떻게 다룰지 정하라**
- **세션은 끝났을 때만 저장한다.** 중간에 나가면 없던 일이 된다(부분 세션이 반응시간 통계를 오염시킨다). 반대로 **다 푼 세션은 저장 실패해도 버리지 않는다** — 결과 화면에 재시도 버튼이 뜬다
- **반응시간은 문제가 보인 순간부터 첫 숫자 키까지다.** 확인 버튼까지의 시간은 손가락 속도라 노이즈다. 진행 중에는 타이머를 표시하지 않는다 — 시간 압박이 인출을 느리게 만들어 측정하려던 값을 오염시킨다
- **`navigate()`는 같은 해시로 불려도 `hashchange`를 쏜다.** 안 그러면 이미 `#/`인 화면의 "← 홈" 버튼이 죽고, 주소창 없는 아이패드에서는 강제 종료 말고 길이 없다

## Phase 3이 만든 것

시작 시 `navigator.storage.persist()`를 불러(`src/main.ts`) iOS의 저장공간 압박에 의한 evict 위험을 줄였다. 백업 내보내기·가져오기로 데이터 왕복이 가능해졌고(`src/engine/backup.ts`), 28일 주기 점검 스프린트(`src/engine/checkup.ts`)와 주간·월간 리포트 화면(`#/report`, `src/screens/report.ts`)이 생겼다. 일요일에 채점을 저장하면 `#/report`로 자동 전환된다.

**이번 Phase가 세운 것 중 기억할 것**

- **점검에는 강등 로직이 없고, 없는 것이 설계다.** 점검 시도도 그냥 `Day.sprint`에 기록될 뿐이고, `deriveFacts`가 로그를 재생하며 연속 3회가 깨지면 스스로 내린다. 강등 코드를 새로 쓰면 이중 처리가 된다
- **리포트는 아무것도 저장하지 않는다.** `weeklyReport`·`latestCheckupReport`(`src/engine/report.ts`) 모두 매번 로그에서 재계산한다 — `Meta.derived`를 배선하지 않는 것과 같은 원칙이다. 판정 규칙을 바꾸면 과거 주간·과거 점검이 소급 재해석된다. `derived`는 여전히 아무도 읽지 않는다
- **`kind: 'checkup'`은 그 날 스프린트가 점검이었다는 표시이고, 점검의 날엔 스프린트가 점검 하나뿐이어야 한다.** 월간 리포트가 "점검일 전날까지 vs 점검일까지"의 차이를 점검 세션으로 간주하기 때문이다
- **가져오기는 병합하지 않고 전체 교체다.** `src/data/db.ts`의 `replaceAll`이 `days`·`meta` 두 스토어를 한 트랜잭션으로 바꾼다. **`tx.abort()`가 없으면 "clear만 커밋"되어 데이터가 조용히 사라진다** — 이 함정이 테스트로 고정돼 있다. 검증 실패 시에는 기존 데이터가 보존된다(원자성 테스트로 고정)
- **월간 리포트의 유지/탈락은 그 세션이 실제로 물어본 식만 분모로 삼는다.** `latestCheckupReport`(`src/engine/report.ts`)의 `kept`는 "이전에 fluent였고, 이 점검 세션이 실제로 물어봤고, 지금도 fluent"인 식만 센다 — `composeCheckup`이 fluent가 `sprintCount`를 넘으면 오래된 판정부터 잘라내므로, "이전에 fluent였던 전부"를 분모로 쓰면 그날 안 물어본 식까지 "유지"로 잡힌다(최종 리뷰가 잡은 Important: 구구단을 다 뗀 뒤가 정확히 이 상태였다). `CheckupReport.tested`가 분모를 담고, 화면(`#/report`)은 "점검한 N개 중 유지 K · 다시 연습 M"으로 분모를 함께 보여준다
- **점검은 fluent가 `CHECKUP_MIN_FLUENT`(현재 10) 이상 쌓인 뒤에만 돈다.** `nextCheckupDate`(`src/engine/checkup.ts`)의 게이트가 원래 "fluent 1개 이상"이었는데, 그러면 드릴이 가장 필요한 더디게 크는 아이일수록 점검일에 fluent가 한두 개뿐이라 한두 문제짜리 점검을 받았다 — 그 하루를 통째로 잃는데 `sprintStreak`은 스프린트가 있었다는 사실만 보고 🔥 연속일수로 정상 보상해줬다(최종 리뷰가 잡은 Important). 앵커 로직(마지막 점검일 ?? 첫 스프린트일)은 그대로다 — 게이트는 "측정할 게 쌓일 때까지 미루는" 역할만 한다
- **내보내기는 "저장했나요?" 확인을 받고서야 `lastExportedAt`을 갱신한다.** Download API에는 완료 신호가 없어서, 무조건 갱신하면 `EXPORT_OVERDUE_DAYS`(30일) 배지가 거짓이 된다 — 사용자 결정
- **백업 검증은 계량돼 있다.** `grades` 값은 전수 boolean 검사, `sheet` 항목은 `id`+`kind`만, `settings`는 코드가 실제로 읽는 필드만 본다. **변형별 sheet 필드는 의도적으로 미검사** — types.ts 스키마를 검증기에 복제하면 Phase 4에서 문항 종류가 늘 때 정상 백업을 거부하게 된다. 그 트레이드오프로 **손상된 sheet 항목은 복구 후 렌더 시점에 throw할 수 있다**
- **`el()`이 `innerHTML`을 쓰므로 신뢰할 수 없는 값(가져온 백업 등)은 반드시 `ui.ts`의 `escapeHtml`을 통과시켜야 한다.** 리뷰가 실제로 이스케이프 누락 XSS를 한 건 잡았다
- **배포됐다.** `main` 머지 후 push하여 Pages 워크플로가 성공했고(커밋 `ff30e3c`), `https://watson-develop.github.io/haruchi/`가 Phase 3 코드를 서빙한다 — 배포된 번들에 리포트 화면 청크(`report-*.js`)가 들어 있는 것까지 확인했다. **origin은 한 번 정했으니 바꾸지 않는다** — IndexedDB가 origin별로 격리되므로 주소를 바꾸면 딸의 기록에 접근할 수 없다

## Phase 4가 만든 것

구구단 지도 옆에 "생각하는 문제"를 얹었다. 매일 세로셈 8 + □ 채우기 2 뒤에 전략 2문항 + 문장제 2문항이 이어져 **하루 14문항, 2장짜리 문제지**가 된다. 구구단 풀은 81식에서 72식으로 줄었다. 12개 태스크 + 전체 브랜치 최종 리뷰 + 수정 웨이브까지 끝났다.

**이번 Phase가 세운 것 중 기억할 것**

- **구구단 풀이 81식(1×1부터 9×9까지)에서 72식(2×1부터 9×9까지)으로 줄었다(사용자 결정).** 1단은 규칙이 하나뿐이라 반복 인출 훈련의 대상이 아니다 — 0단을 뺐던 Phase 2의 사유를 1단에 적용했다. 곱하는 수 ×1은 남겼다 — 외우는 구구단이 "2×1은 2"부터 시작해서다. 신규 식 도입도 무작위로 바뀌었다 — 교과서 도입 순서(옛 `FACT_ORDER`, 인천교육청 지도서 근거)는 폐기했다(사용자 결정). 과거 로그의 1×n 시도는 `deriveFacts`가 모르는 id로 조용히 건너뛴다 — **마이그레이션이 필요 없다**
- **풀 경계가 `engine/facts.ts` 한 곳으로 좁혀졌다(사용자 결정).** `DAN_MIN`/`DAN_MAX`/`FACTOR_MIN`/`FACTOR_MAX`를 export하고 `FACT_IDS` 생성 루프가 그 값을 쓴다. 지도 화면(`src/screens/fact-map.ts`)은 그 네 상수와 `FACT_IDS.length`를 import해 행·열·칸 수를 유도하고, 리포트 문구(`src/screens/report.ts`)는 **`FACT_IDS.length`만** import한다(분모, 즉 칸 수만 필요해서다 — 경계 상수는 안 쓴다). 어느 쪽도 숫자를 자기 것으로 복제하지 않는다 — `facts.ts` 하나만 바꾸면 지도와 리포트가 따라온다(변이 검증으로 확인)
- **전략 존(하루 2문항)은 `engine/strategy.ts`의 선언적 카탈로그 `STRATEGY_CATALOG`가 유일한 출처다.** 이름·도입 순서·조건(`applicable`)·빈칸 뼈대(`steps`)가 배열 하나에 모여 있고, 렌더러·채점·리포트는 이 카탈로그 내부를 모른 채 `steps`가 돌려주는 `{}`와 `blanks`만 본다. **새 전략을 추가하려면 배열에 항목 하나 + `StrategyId` 유니온에 멤버 하나만 더하면 된다** — 인쇄·채점 코드는 손대지 않는다
- **전략 도입 게이트는 등장 횟수(3회)이지 채점이 아니다.** `composeStrategyItems`는 `strategies[latest.id].appearances`만 보고 다음 전략으로 넘어간다 — 숙련 판정이 아니라 노출 페이스 조절이라, 아빠가 채점을 며칠 밀려도 새 전략 도입이 멈추지 않는다. 문항2는 어제의 방법(도입된 것 중 `lastAppearedAt`이 가장 오래된 것)이다. 낮은 확률(`SAME_EXPR_CHANCE` = 0.2)로 두 문항이 같은 수식을 다른 방법으로 푼다. 곱셈 전략 2종(`double`·`minus-one`)은 fluent가 `MUL_STRATEGY_MIN_FLUENT`(10) 미만이면 열리지 않는다 — 구구단표가 머리에 없으면 7×4×2는 우회로가 아니라 짐이다
- **문항1("오늘의 방법")은 새 전략을 열 수 있을 때만 고정석이다 — 사용자 결정(2026-08-03)으로 스펙 §3의 "문항1 = 최신 도입"이 갱신됐다.** 이 결정은 이후 스펙 본문에도 반영됐다(§0 개정 ⑥ · §3 "정착기" 절 — 2026-08-04 교육과정 리뷰 개정에 실려 들어갔고, ⑥의 출처가 사용자 결정임은 §0에 명시돼 있다). 스펙 §3과 코드가 이제 같은 말을 하니, 세부 근거는 `composeStrategyItems`의 주석을 볼 것. 갓 도입한 전략은 등장 3회를 채울 때까지 문항1에 머물지만(도입 페이스는 이 게이트가 정한다), 더 열 게 없으면(카탈로그 소진이거나 곱셈 게이트가 닫힘) **문항1도 로테이션에 합류**해 두 문항 모두 `lastAppearedAt`이 오래된 순으로 뽑힌다. 최종 리뷰 실측이 이유다: 옛 동작에서는 8종 도입 후 `minus-one`이 60일 중 40일 문항1을 독점했는데 그 전략의 유효 문제는 총 8개(`b === 9`, `2 ≤ a ≤ 9`)뿐이라 같은 문제가 계속 재등장했고, 곱셈 게이트가 영영 안 열리는 아이(정답률 0.45)는 `count-up`이 15일째부터 영구 고정됐다. 변경 후 실측(fluent 20, 60일): `make-ten:22, split-place:17, round-adjust:16, split-subtrahend:14, anchor:14, count-up:13, double:12, minus-one:12`(전에는 `minus-one:40 … double:8`). **도입 페이스는 불변**임을 확인했다 — 8종 도입일이 d1·d3·d6·d9·d12·d15·d18·d21로 변경 전과 같고, `simulation.test.ts`의 6종 도달일도 9개 시드 전부 15일 그대로다
- **전략 step의 표기는 "2학년이 이미 배운 형식"만 쓴다 — 값이 아니라 표기가 기준이다(2026-08-04 교육과정 리뷰).** `double`의 두 배 step은 `28 × 2`가 아니라 **`28 + 28`**로 찍는다(두 자리 × 한 자리는 3-1 [4수01-04]라 배운 적 없는 형식이고, 실제 행위도 "두 번 더하기"다). `minus-one`의 첫 step은 `10 × 7`이 아니라 **`10씩 7묶음`**으로 찍는다(10단은 곱셈구구 밖이지만 묶어 세기는 2-1 완료 개념 [2수01-10]이라, 같은 값을 배운 표기로 묻는다). **바뀐 것은 `steps[].text`뿐이다** — `blanks`도 `answer`도 그대로라 채점 계약(마지막 빈칸 == 최종 답)이 움직이지 않았고, 렌더러가 텍스트를 파싱하지 않고 `{}`만 치환하므로 인쇄·채점 코드는 한 줄도 안 건드렸다. 같은 리뷰가 `count-up`의 스펙 예시(`63−28`)도 `62−58`로 교체했다 — 차 35는 `applicable`(차 3\~15) 밖이라 `gen`이 절대 만들지 않는 조합이었다(예시가 다시 영역 밖으로 새지 않도록 테스트에 `applicable` 단언을 함께 뒀다). **반면 수의 크기는 좁히지 않았다** — 같은 리뷰의 "피연산자·결과 두 자리 제한"(⑧)은 사용자 결정으로 철회됐고, 코드는 의도적으로 세 자리를 낸다(`make-ten`·`round-adjust` 두 종뿐, 최대 179). 근거는 스펙 §3에 적어 뒀다 — **그 절을 읽고 코드를 좁히지 말 것**
- **등장인물 이름의 유일한 출처는 `word.ts`의 `WORD_NAMES`다(2026-08-04).** 이름 입력 화면을 없앤 직후, 기기에 남아 있던 `childName`(`'○○'`)을 고칠 방법이 없어 문장제가 `○○이가 …`로 나왔다. 그래서 `Settings.childName`·`friendNames`는 **읽지 않는다** — `derived`처럼 스키마 호환으로만 남은 필드다. `compose.test.ts`가 settings에 `○○`을 넣고 출력에 새지 않는지 고정한다(변이 검증 완료). 이름은 상수 직참조가 아니라 `composeWordItems`의 인자로 흐른다 — 받침 있는 이름(`서연이가`)의 조사 회귀 테스트가 받침 없는 `서아`로는 아무것도 못 잡기 때문이다
- **문장제 텍스트는 생성 시점에 완성돼 `sheet`에 박제된다.** `word.ts`가 그날 세션에 텍스트를 만들어 저장하므로, 이름을 나중에 바꿔도 이미 만든 날의 문제지는 그대로다(**이름을 바꾼 당일에는 옛 이름 문제지가 그대로 나온다** — 다음 날 문제지부터 반영된다) — Phase 1의 재인쇄 불변식이 문장제에도 그대로 적용된다. 하루 두 문항 중 하나엔 반드시 딸 이름이 들어가고, 받침 있는 이름엔 접미사 '이'를 붙인다(서연이가/서연이는/서연이를/서연이의 — 사용자 결정). 사물은 `josa`의 일반 조사 규칙을, 사람은 `personJosa`를 따로 쓴다. 몇 배의 배수는 2~5로 제한한다(시뮬레이션이 "8배 줄넘기"의 부자연을 잡았다)
- **하루 문제지가 2장이 됐지만, 옛 sheet를 재인쇄하면 2장을 만들지 않는다.** `print-sheet.ts`는 전략·문장제 항목이 하나도 없는 sheet(Phase 4 배포 전에 만들어진 10문항짜리 구버전 `composeSheet` 산출물)를 만나면 2쪽 자체를 그리지 않는다 — 재인쇄 불변식이 "이 날은 이제 2장짜리여야 한다"는 새 기대보다 우선한다. 인쇄 순서(세로셈→역연산→전략→문장제, ①~⑭)는 `compose.ts`의 id 순서, 채점 화면(`grade.ts`의 `markMap`)의 번호 순서와 셋 다 일치하도록 맞춰져 있다. **번호표 자체(`ITEM_MARKS`)는 `src/ui.ts`가 유일한 출처다** — 두 화면에 사본을 두면 어긋나도 잡을 방법이 없다(설계 §12가 화면 테스트를 두지 않는다). 두 화면이 각자 지켜야 하는 것은 **순서**뿐이다
- **`composeSheet`의 `seen`(수식 중복 회피 집합)을 세로셈·전략·문장제가 한 집합으로 공유한다.** 키 형식(`` `${a}${op}${b}` ``)이 같아서, 세로셈에 이미 나온 27+15가 전략에서 다시 나오는 것도 자동으로 막힌다. **역연산(□ 채우기)은 이 집합에 참여하지 않는다** — `compose.ts`의 역연산 루프(98~111행)는 `seen`을 읽지도 쓰지도 않는다. 즉 "한 집합"은 세 종류의 이야기이고, 역연산은 세로셈과 같은 수식을 낼 수 있다
- **`sheet` 항목의 값은 타입이 `number`여도 렌더 지점에서 이스케이프한다.** `validateBackup`은 `sheet[]`의 `id`(문자열)와 `kind`(4종)만 검사하고 **변형별 필드는 의도적으로 전부 미검증**이므로(위 Phase 3 항목의 트레이드오프), `a`·`b`·`c`·`answer`·`op` 같은 숫자·기호 필드에도 가져오기로 임의 문자열이 들어올 수 있다. 최종 리뷰가 정확히 여기서 Critical을 찾았다 — 문자열 필드(`text`·`unit`·`steps[].text`·`tag`·`expression`)만 이스케이프하고 숫자 필드는 "타입이 number니까"로 넘겼는데, 실제로는 `a = '<img src=x onerror=…>'`가 인쇄 화면에서 그대로 발화했고 채점 화면에서는 `id`가 `data-id="…"` **속성을 깨고 나왔다**. 그래서 `escapeHtml`의 인자를 `unknown`으로 넓혀(내부에서 `String()`) 렌더 지점 전부를 `escapeHtml(...)` 한 형태로 통일했다. **`src/screens/print-sheet.ts`·`src/screens/grade.ts`의 템플릿에 이스케이프 없이 들어가는 값은 우리가 만든 리터럴뿐이어야 한다** — 새 필드를 찍을 때마다 확인할 것

**제품 신호 — 작은 풀이 점검 이후 회복을 못 한다(단일 시드, 미해결로 남김)**

`simulation.test.ts`가 저성취 프로필(정답률 0.45, 반응시간 2450ms, 시드 2026, 200일)로 72식 풀과 81식 풀을 나란히 재현했다. 72식 풀은 첫 점검 게이트(fluent 10)에 **day 32**로 도달해 81식(day 49)보다 **17일 빠르다** — 풀이 작을수록 매일의 신규 배분이 더 적은 후보에 집중돼 초기 습득이 빠른 것으로 보인다("닻이 늦어진다"는 가설은 기각). 그런데 점검이 적응 없이 fluent 식을 전부 재검증하면서 fluentCount가 day 32 직후 4까지 무너지고, **72식 풀은 남은 168일 동안 한 번도 다시 10에 도달하지 못한 채 시뮬레이션이 끝난다**(81식 풀은 같은 붕괴를 겪고도 day 188에 한 번 더 게이트를 재통과했다). 더 적은 절대 식 수가 회복 속도에 실제로 영향을 주는지, 이 시드·프로필의 우연인지는 이번 범위 밖이다 — `simulation.test.ts`에 열린 질문으로 남겨뒀다. **표본이 시드 하나뿐이다** — 정답률이 조금만 더 낮아지면 점검 자체가 한 번도 안 열려 이 테스트가 결함이 아닌 이유로 실패할 수 있다는 것도 같은 주석에 적어 두었다.

**Phase 4 전체 브랜치 최종 리뷰가 "나중에"로 분류한 후속 작업**

리뷰는 Critical 1건(백업 경유 값의 이스케이프 누락)과 Important 3건을 잡았고 그 넷은 병합 전 수정 웨이브에서 고쳤다(수정 리포트는 세션 로컬 산출물이라 레포에 없다 — 무엇을 고쳤는지는 위 "Phase 4가 만든 것"에 반영돼 있다). 아래는 **일부러 안 고치고 넘긴 것들**이다 — 데이터 손실·죽은 화면·아이가 보는 오류로 이어지지 않는다고 판단했다. 다음 Phase가 관련 코드를 건드릴 때 함께 처리하면 싸다.

- **교환법칙 짝이 하루에 같이 나올 수 있다.** 곱셈식 `seen` 키가 `` `${a}×${b}` ``라 3×8과 8×3은 다른 키다. 실측: 전략↔문장제 2.6%, 문장제끼리 1.1%, **정확 문자열 중복은 0%**. 2학년에게 3×8("3개씩 8묶음")과 8×3은 의도적으로 다른 문제라 동작 자체는 수용한다. 다만 **스펙 §4의 "겹치지 않는다"와 이 문서의 예전 문구가 과잉 주장**이었다 — "같은 수식 문자열이 겹치지 않는다"가 정확한 서술이다
- ~~비한글·공백으로 끝나는 `childName`이 `Emma이가`·`서연 이가`를 만든다~~ — **경로 자체가 사라졌다**(2026-08-04). 이름이 코드 상수(`word.ts`의 `WORD_NAMES`)가 되어 임의 문자열이 들어올 자리가 없다. `hasBatchim`이 `!isHangul`을 "받침 있음"으로 되돌려주는 동작(조사 선택으로는 맞는 근사, 접미사 '이' 규칙에는 안 맞음)은 그대로이므로, **`WORD_NAMES`에 비한글·공백으로 끝나는 이름을 넣으면 그때 되살아난다** — 그때 고치면 된다(`isHangul`을 밖으로 꺼내 `personStem`을 게이트하면 2줄)
- **`grade.ts`의 `label()` 철저성이 구조적으로만 강제된다.** `inverse`의 `template`이 손상되면 switch를 그대로 빠져나가 마지막 `` return `문장제 ${item.expression}` ``에 도달해 **`문장제 undefined`**로 렌더된다(리뷰어가 실제 확인). 채점은 되지만 아빠가 무슨 문제인지 알 수 없다
- **`strategy.ts`의 `sample()`이 tag 없는 일반 `Error`를 던진다.** 아빠의 오류 배너에 `문제지를 만들지 못했어요: 전략 생성 실패: 표집 한도 초과`가 그대로 뜬다. `vertical.ts`의 `GenerationError`처럼 종류를 구분할 수 있게 하고 사람 말로 바꾸는 편이 낫다

시점까지 붙인 판은 `integrated-arithmetic-ladder.md` §8에 있다. 요약하면 **2027-01 역연산 확장(작음) → 2027-05 나눗셈 엔진(큼) → 2027-07 분수·소수(큼)**.

- **나눗셈이 첫 번째 벽이고, 시점이 확정됐다.** 개념 도입 **3-1**, 나머지 있는 나눗셈·(두 자리)÷(한 자리) **3-2**, (세 자리)÷(두 자리) **4-1**. `vertical.ts`의 `Spec`은 `op: '+' | '−'`로 닫혀 있고 판정 술어가 `carryCount`/`borrowCount`다. 세로 나눗셈은 레이아웃도 완전히 다르다. 태그 추가가 아니라 새 엔진이다
- **분수·소수는 `answer: number`를 깨뜨린다.** 다만 `answer`는 채점 화면 표시 전용이고 `derive`가 쓰지 않아 파급은 제한적이다
- **`print-sheet.ts`는 문항 종류별 분기 구조**라 새 종류마다 손대야 한다
- 유형이 20개를 넘으면 하루 8문항으로는 회전 전략이 필요해진다
- 마이그레이션은 `Day`에 **필수** 필드가 생길 때 처음 필요해진다. `schemaVersion`/`algoVersion`은 쓰이기만 하고 읽는 곳이 없다

## Phase 3이 알아야 할 실측값

Phase 2 최종 리뷰가 엔진을 레포 밖으로 복사해 최대 5년치를 시뮬레이션하고 측정한 값이다. 추정이 아니다.

- **로그를 안 잘라도 비용이 없다.** 5년치(54,750 시도)에서 `deriveFacts` 16ms, `sprintStreak` 0.32ms, JSON 2.3MB. 선형이고, 화면 한 번 그리는 데 16ms는 안 보인다. "이력을 자르지 말 것" 제약은 공짜다
- **간격 반복이 식을 굶기지 않는다.** 도입 이후 재등장까지의 최대 공백이 60·120·365·730일 어디서나 **15일로 평평하다.** due가 밀린 fluent 식의 적체도 평균 0.1개·최대 3개이고 시간이 갈수록 줄어든다
- **다만 상한은 14일이 아니라 15~16일이다.** 설계 302행이 "8살은 2주 쉬면 잊는다"를 걱정하면서 14일 천장을 전제하는데, due가 된 식이 8칸을 두고 경쟁하므로 실제 천장은 하루이틀 높다. 적체가 쌓이지 않으므로 결함은 아니다 — **Phase 3의 점검의 날은 14일이 아니라 15~16일 기준으로 설계할 것**
- **한 세션 안에서 유창 판정이 날 수 있다.** `composeSprint`가 같은 식을 반복 출제하므로 한자리에서 빠르게 3번 맞으면 `fluent`가 된다. 설계 §6.1의 "최근 3회 연속 정답"을 문자 그대로 지킨 것이고 1→3→7→14 사다리가 이후의 지속성을 요구하므로 결함은 아니지만, **분산이 아니라 집중 학습의 증거**다. 점검의 날을 조율할 때 알고 있을 것
- **Phase 2는 마이그레이션이 필요 없다 — 확인됐다.** Phase 2가 쓰는 모든 필드(`Day.sprint`, `SprintAttempt`, `Settings.sprintCount`/`fluentMs`, `FactState`)가 Phase 1의 `types.ts`에 이미 있었고 전부 optional이거나 기본값이 있다. `schemaVersion`을 건드릴 일이 없었다. Phase 3이 이걸 다시 유도하지 않아도 되도록 적어 둔다

## Phase 1에서 리뷰가 반복해서 잡은 실패 패턴

테스트를 쓸 때마다 확인할 것.

1. **자기 자신을 검사하는 테스트** — 생성기가 이미 술어로 거른 값을 같은 술어로 단언하면 무엇을 바꿔도 통과한다
2. **느슨한 상한** — 실측 16에 상한 150이면 완전 정지만 잡힌다
3. **실패할 수 없는 단언** — `expect(x).toBeTruthy()`
4. **화면의 갇힘 경로** — 첫 `await`가 `try` 밖이면 실패 시 `#app`이 빈 채로 남는다. `showError`는 `document.body`에만 붙는다

Phase 2가 여기에 둘을 더했다.

5. **매달린 비동기 콜백도 갇힘 경로를 만든다.** 4번은 `await` 위치 문제라 정적으로 보이지만, Phase 2에서는 취소되지 않은 `setTimeout`이 이미 교체된 `#app`을 덮어써서 같은 결과에 도달했다. 화면을 떠날 수 있는 지연 작업에는 취소 경로를 붙일 것
6. **가장 값진 결함은 태스크 사이의 이음새에 있다.** Phase 2의 Critical은 `sprint.ts`의 쓰기가 `home.ts`의 읽기를 만나야 보였고, `✅` 결함은 구현이 아니라 *설계문서와 계획서*를 대조해야 보였다. 태스크별 리뷰는 각자 범위 안에서 모두 옳았다. **다음 계획을 세울 때, 새 코드가 쓸 필드를 이미 읽고 있는 모든 곳을 나열하는 단계를 태스크 0으로 둘 것**

Phase 3가 여기에 하나를 더했다(실은 반복이라 하나로 묶는다) — 이번엔 6건 중 5건이 같은 종류였다.

7. **테스트가 자기가 검사한다고 주장하는 것을 실제로는 검사하지 못한다.** 구현 로직은 옳았는데도: 검증기가 컨테이너 타입만 보고 값을 안 봄 / "기존 값이 살아남았다"를 단언하는데 새 값과 기존 값이 같은 객체라 항진명제 / `getMeta()`의 빈 스토어 폴백이 기본값과 구조적으로 같아 2차 마스킹 / 정렬 픽스처가 올바른 키와 그럴듯한 오류를 구별 못 함 / 자기증명 단언에 상한이 없어 폭주 회귀를 못 잡음. **각 단언마다 "구현이 그럴듯하게 틀렸다면 이 값이 무엇이 되는가"를 묻고, 같으면 픽스처를 고칠 것.** 고친 뒤에는 **변이 검증**(구현을 일부러 틀리게 바꿔 테스트가 실패하는지 확인하고 원복)으로 실제 효력을 확인할 것 — 이번 Phase에서 이 방법이 여러 번 값을 냈다
8. 나머지 1건은 다른 종류였다: 가져온 백업 데이터가 이스케이프 없이 `innerHTML`에 들어가던 XSS. 신뢰할 수 없는 값(가져오기·사용자 입력)을 다루는 코드를 새로 쓸 때는 `escapeHtml`을 거쳤는지 항상 확인할 것
