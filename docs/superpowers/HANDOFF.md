## Phase 1이 만든 것

매일 A4 1장(세로셈 8 + □ 채우기 2)을 인쇄해 풀고, 아빠가 탭 몇 번으로 채점하면 다음날 문제 구성이 조정된다. 홈 화면에 추가하면 오프라인으로 돈다.

**지켜야 할 두 불변식** — 코드 곳곳이 여기에 기대고 있다.

- **재인쇄는 같은 문제를 낸다.** `src/screens/print-sheet.ts`의 `if (!day || day.sheet.length === 0)`이 `sheet`를 쓸 수 있는 유일한 게이트다. 이게 깨지면 아이 손의 종이와 채점 화면이 어긋나 데이터가 조용히 오염된다
- **`derived`는 버릴 수 있는 캐시다.** 실제로 `Meta.derived`를 읽는 코드가 하나도 없고, 매번 `days` 로그에서 재계산한다. 덕분에 판정 규칙을 바꾸면 과거 전체가 새 규칙으로 재해석된다 — 마이그레이션이 필요 없다

## Phase 2가 만든 것

홈에서 `구구단 스프린트`를 누르면 30문제를 풀고, 반응시간 중앙값이 `fluentMs`(2500ms) 이하로 3회 연속 맞으면 그 식이 "정복"된다. 정복한 칸만 답이 채워지는 81칸 지도가 결과 화면과 `#/map`에 뜬다. 홈에 `🔥 연속일수`가 붙었다.

**Phase 2가 세운 것 중 기억할 것**

- **`engine/facts.ts`가 식 id 형식의 유일한 주인이다.** `factId`가 만들고 `factAnswer`가 푼다. 곱셈 기호는 U+00D7이며 화면은 절대 직접 파싱하지 않는다. `factAnswer`는 형식이 어긋나면 **던진다** — `deriveFacts`가 알 수 없는 id를 조용히 건너뛰는 것과 의도적으로 반대다. `deriveFacts`는 오염됐을 수 있는 과거 로그를 재생하므로 던지면 앱이 안 열리고, `factAnswer`의 입력은 엔진이 방금 만든 큐라 어긋났다면 엔진이 자기모순인 것이다. 이 비대칭은 두 곳 주석에 적혀 있다
- **스프린트만 한 날은 `sheet: []`인 `Day`를 만든다.** 이게 코드베이스 최초의 빈 sheet 생산자다. `home.ts`의 `pendingGradeDate`와 `grade.ts`가 둘 다 `sheet.length === 0`을 검사해야 하는 이유다 — 최종 리뷰가 이 조합에서 Critical을 찾았다. **`sheet`를 읽는 코드를 새로 쓸 때마다 빈 sheet를 어떻게 다룰지 정하라**
- **세션은 끝났을 때만 저장한다.** 중간에 나가면 없던 일이 된다(부분 세션이 반응시간 통계를 오염시킨다). 반대로 **다 푼 세션은 저장 실패해도 버리지 않는다** — 결과 화면에 재시도 버튼이 뜬다
- **반응시간은 문제가 보인 순간부터 첫 숫자 키까지다.** 확인 버튼까지의 시간은 손가락 속도라 노이즈다. 진행 중에는 타이머를 표시하지 않는다 — 시간 압박이 인출을 느리게 만들어 측정하려던 값을 오염시킨다
- **`navigate()`는 같은 해시로 불려도 `hashchange`를 쏜다.** 안 그러면 이미 `#/`인 화면의 "← 홈" 버튼이 죽고, 주소창 없는 아이패드에서는 강제 종료 말고 길이 없다

## Phase 3이 만든 것

시작 시 `navigator.storage.persist()`를 불러(`src/main.ts`) iOS의 저장공간 압박에 의한 evict 위험을 줄였다. 백업 내보내기·가져오기로 데이터 왕복이 가능해졌고(`src/engine/backup.ts`), 28일 주기 점검 스프린트(`src/engine/checkup.ts`)와 주간·월간 리포트 화면(`#/report`, `src/screens/report.ts`)이 생겼다. 일요일에 채점을 저장하면 `#/report`로 자동 전환된다.

**이번 Phase가 세운 것 중 기억할 것**

- **점검에는 강등 로직이 없고, 없는 것이 설계다.** 점검 시도도 그냥 `Day.sprint`에 기록될 뿐이고, `deriveFacts`가 로그를 재생하며 연속 3회가 깨지면 스스로 내린다. 강등 코드를 새로 쓰면 이중 처리가 된다
- **리포트는 아무것도 저장하지 않는다.** `weeklyReport`·`latestCheckupReport`(`src/engine/report.ts`) 모두 매번 로그에서 재계산한다 — `Meta.derived`를 배선하지 않는 것과 같은 원칙이다. 판정 규칙을 바꾸면 과거 주간·과거 점검이 소급 재해석된다. `derived`는 여전히 아무도 읽지 않는다
- **`kind: 'checkup'`은 그 날 스프린트가 점검이었다는 표시이고, 점검의 날엔 스프린트가 점검 하나뿐이어야 한다.** 월간 리포트가 "점검일 전날까지 vs 점검일까지"의 차이를 점검 세션으로 간주하기 때문이다
- **가져오기는 병합하지 않고 전체 교체다.** `src/data/db.ts`의 `replaceAll`이 `days`·`meta` 두 스토어를 한 트랜잭션으로 바꾼다. **`tx.abort()`가 없으면 "clear만 커밋"되어 데이터가 조용히 사라진다** — 이 함정이 테스트로 고정돼 있다. 검증 실패 시에는 기존 데이터가 보존된다(원자성 테스트로 고정)
- **내보내기는 "저장했나요?" 확인을 받고서야 `lastExportedAt`을 갱신한다.** Download API에는 완료 신호가 없어서, 무조건 갱신하면 `EXPORT_OVERDUE_DAYS`(30일) 배지가 거짓이 된다 — 사용자 결정
- **백업 검증은 계량돼 있다.** `grades` 값은 전수 boolean 검사, `sheet` 항목은 `id`+`kind`만, `settings`는 코드가 실제로 읽는 필드만 본다. **변형별 sheet 필드는 의도적으로 미검사** — types.ts 스키마를 검증기에 복제하면 Phase 4에서 문항 종류가 늘 때 정상 백업을 거부하게 된다. 그 트레이드오프로 **손상된 sheet 항목은 복구 후 렌더 시점에 throw할 수 있다**
- **`el()`이 `innerHTML`을 쓰므로 신뢰할 수 없는 값(가져온 백업 등)은 반드시 `ui.ts`의 `escapeHtml`을 통과시켜야 한다.** 리뷰가 실제로 이스케이프 누락 XSS를 한 건 잡았다
- **레포·Pages·배포 워크플로 자체는 검증됐다 — 다만 지금 나가 있는 건 Phase 2다.** origin은 `https://github.com/watson-develop/haruchi`로 확정됐고 Pages workflow가 성공한 실행이 있어 `https://watson-develop.github.io/haruchi/`가 뜬다. 그런데 그 성공 실행의 대상 커밋은 `58ecb90`(Phase 2 마지막)이고, 원격 `main`도 여전히 거기 있다 — **Phase 3 커밋은 아직 하나도 푸시되지 않았다.** `phase3-real-use`를 `main`에 머지해 푸시해야 실제로 나간다(미해결 항목 참고). **origin은 한 번 정했으니 바꾸지 않는다** — IndexedDB가 origin별로 격리되므로 주소를 바꾸면 딸의 기록에 접근할 수 없다

## 아직 안 한 것 — 아이패드 실물 확인

계획서 마지막 절의 4항목이 그대로 남아 있다. 코드로는 확인할 수 없는 것들이다.

- 스프린트 30문제를 **아빠가 직접** 끝까지 해본다. 자기 반응시간이 1초 안쪽으로 나오는지 — 측정 코드가 틀렸다면 여기서 드러난다
- 8살 손가락 기준으로 키패드가 충분히 큰지
- 3분 안에 끝나는지. 크게 넘으면 `sprintCount`를 줄인다. **오답이 있으면 30문제가 아니라 30+W문제다**(틀린 식이 뒤에 재투입되고 진행바도 그만큼 늘어난다)
- 지도의 검은 칸이 아이에게 실제로 동기가 되는지 — 되지 않으면 Phase 4의 인쇄 지도 설계를 다시 본다

## 미해결 항목

- **Phase 3 전체 브랜치 최종 리뷰가 아직 안 돌았다.** 태스크별 리뷰만 끝난 상태다. 계획서 마지막 절이 지목한 이음새 3가지를 특히 확인해야 한다: (a) 점검 저장(`sprint.ts`) × 홈 버튼 3-상태(`home.ts`) × 월간 리포트(`report.ts`)가 `kind:'checkup'` 하나를 두고 일관되는지 (b) 가져오기(`replaceAll`) 후 모든 화면이 새 데이터로 렌더되는지 (c) 스펙 §5의 "점검의 날엔 점검 한 번으로 끝"이 `renderSprint`의 기존-결과 게이트와 실제로 맞물리는지
- **Phase 3가 아직 배포되지 않았다.** `phase3-real-use`를 `main`에 머지하고 push해야 배포 워크플로가 돌아 실제로 나간다. 레포 생성·Pages Source 설정·워크플로 자체는 이미 검증 끝(위 "Phase 3이 만든 것" 참고) — 남은 건 머지 + push뿐이다
- **브라우저 실물 검증을 아무도 못 했다.** 이 환경에 Chrome 확장이 연결되지 않아 화면 동작을 직접 보지 못했다. 확인 못 한 항목: 빈 데이터 렌더 / 내보내기 다운로드·저장 확인·배지 갱신 / 가져오기 확인 패널·교체 / 깨진 JSON 사유 배너 / 일요일 자동 전환 / 홈 버튼 3-상태
- **CI의 `prettier --check`가 `docs/`까지 검사한다.** `.prettierignore`가 없으므로 문서를 커밋하기 전 `npm run format`을 돌릴 것. 안 그러면 마크다운 포맷 흠 하나로 앱 배포가 막힌다
- **0의 곱을 앱이 다루지 않는다.** 교과 범위(2-2 17차시)에는 있으나 81식(`1×1`~`9×9`)에 0이 없다. **의도된 선택**이며 `facts.ts`의 `DAN_ORDER` 주석에 사유를 적어 두었다 — 결함으로 오인하지 말 것
- **`✅ 완료일수`가 당분간 0으로 보인다.** 설계 §6.8대로 "종이 채점 + 스프린트 둘 다"로 바꿨는데 기존 로그에는 스프린트가 없다. 결함이 아니다 — 오늘 둘 다 하면 1이 된다
- **자잘한 이월.** 내보내기 확인 배너와 가져오기 확인 패널이 `#confirm`을 공유해, 가져오기 확인 중 내보내기를 누르면 파일 입력이 리셋되지 않은 채 패널만 사라진다 / `#confirm-replace`에 이중 클릭 가드가 없다 / 시뮬레이션의 점검 주기 상한(6)은 주기가 20~28일로 퇴행하는 회귀는 못 잡는다

### Phase 2 최종 리뷰가 남긴 잔여 (병합 승인됨, 데이터 손실·죽은 화면·리스너 누수 없음)

- **`ui.ts` — 홈 버튼 연타 시 대상 화면에 재진입한다.** 가드가 `location.hash === hash`를 보는데 해시는 첫 탭에서 동기적으로 바뀌고 버튼은 동적 import 동안 살아 있다. 결과는 전부 무해함이 추적으로 확인됐다(고아 스프린트 세션은 진행되지도 저장되지도 않고 다음 해시 변경에 리스너가 자진 제거된다). **어떤 화면이 자기 해시로 `navigate`하게 되면 다시 볼 것**
- **`sprint.ts`의 `retrySave` 해시 스냅샷은 래치되지 않는다.** `cancelled` 플래그를 쓸 수 없어서다(`finish()`가 재시도 버튼이 생기기 전에 리스너를 제거한다). `#/sprint → #/ → #/sprint`를 IndexedDB 쓰기 하나가 도는 동안 해내야 재현되고, 최악이어도 "← 홈"이 살아 있는 낡은 결과 화면이다
- **`simulation.test.ts`의 등장 횟수 관련 주석 숫자("9/10 vs 7/10")가 재현되지 않는다.** 결론은 맞고, 단언이 실제로 기대는 숫자(건강 15~16, 결함 20)는 정확히 재현된다. 주석만의 문제
- **`facts.test.ts`의 `factAnswer` 왕복 테스트가 `FACT_IDS` 대신 하드코딩 `1..9`를 돈다.** 식 집합이 확장되면 빨간 테스트 대신 죽은 스프린트 화면으로 드러난다. `FACT_IDS`를 돌면 공짜로 막힌다
- ~~시뮬레이션이 `requeueWrong`을 모델링하지 않는다~~ — **Phase 3에서 메꿔졌다.** `simulation.test.ts`가 이제 `requeueWrong`과 점검의 날(`checkupDue`/`composeCheckup`)을 함께 모델링한다

- `docs/reference/korean-math-programs-curricula.md` — EBS·소마·기탄·구몬·눈높이. EBS 만점왕 연산이 학기 단위로 교과서와 대응하는 것까지 확인. 구몬은 학년 대응표를 **정책적으로 비공개**
- `docs/reference/integrated-arithmetic-ladder.md` — **위 둘을 하나의 학습 계획으로 종합한 문서.** 절마다 `[사실]`/`[도출]`/`[해석]`을 붙여 종합 과정의 판단을 분리했다. 선수학습 의존 그래프, 초2~초6 통합 사다리, 딸의 현재 좌표에서 출발하는 18개월 로드맵, 앱 확장 데드라인이 들어 있다. 시각 요약본은 `arithmetic-ladder-page.html`
  - **`DAN_ORDER`의 출처를 여기서 확정했다** (§2). 인천광역시교육청 「손에 잡히는 곱셈구구 2학년 교사용 지도서」(인천교육-2025-0247)의 20차시 표가 **2 → 5 → 3·6 → 4·8 → 7 → 9**를 제시하며 코드와 일치한다. 1단 위치와 0의 곱만 의도적으로 다르다
  - 적대적 리뷰를 한 차례 받아 out-degree 계수 기준, 소마 대응 주장, 라벨링 규율을 수정했다. 수정 이력은 git log 참조

세 문서 모두 확인하지 못한 항목을 "확인 못 함 / 미공개"로 명시해 두었다. 그 목록 자체가 결과다 — 빈칸을 추측으로 채우지 말 것.

## 3~6학년 확장에서 깨지는 지점

시점까지 붙인 판은 `integrated-arithmetic-ladder.md` §8에 있다. 요약하면 **2027-01 역연산 확장(작음) → 2027-05 나눗셈 엔진(큼) → 2027-07 분수·소수(큼)**.

- **나눗셈이 첫 번째 벽이고, 시점이 확정됐다.** 개념 도입 **3-1**, 나머지 있는 나눗셈·(두 자리)÷(한 자리) **3-2**, (세 자리)÷(두 자리) **4-1**. `vertical.ts`의 `Spec`은 `op: '+' | '−'`로 닫혀 있고 판정 술어가 `carryCount`/`borrowCount`다. 세로 나눗셈은 레이아웃도 완전히 다르다. 태그 추가가 아니라 새 엔진이다
- **분수·소수는 `answer: number`를 깨뜨린다.** 다만 `answer`는 채점 화면 표시 전용이고 `derive`가 쓰지 않아 파급은 제한적이다
- **`print-sheet.ts`는 문항 종류별 분기 구조**라 새 종류마다 손대야 한다
- 유형이 20개를 넘으면 하루 8문항으로는 회전 전략이 필요해진다
- 마이그레이션은 `Day`에 **필수** 필드가 생길 때 처음 필요해진다. `schemaVersion`/`algoVersion`은 쓰이기만 하고 읽는 곳이 없다

## Phase 3이 알아야 할 실측값

Phase 2 최종 리뷰가 엔진을 레포 밖으로 복사해 최대 5년치를 시뮬레이션하고 측정한 값이다. 추정이 아니다.

- **로그를 안 잘라도 비용이 없다.** 5년치(54,750 시도)에서 `deriveFacts` 16ms, `sprintStreak` 0.32ms, JSON 2.3MB. 선형이고, 화면 한 번 그리는 데 16ms는 안 보인다. "이력을 자르지 말 것" 제약은 공짜다
- **간격 반복이 식을 굶기지 않는다.** 도입 이후 재등장까지의 최대 공백이 60·120·365·730일 어디서나 **15일로 평평하다.** due가 밀린 fluent 식의 적체도 평균 0.1개·최대 3개이고 시간이 갈수록 줄어든다
- **다만 상한은 14일이 아니라 15~16일이다.** 설계 302행이 "8살은 2주 쉬면 잊는다"를 걱정하면서 14일 천장을 전제하는데, due가 된 식이 8칸을 두고 경쟁하므로 실제 천장은 하루이틀 높다. 적체가 쌓이지 않으므로 결함은 아니다 — **Phase 3의 점검의 날은 14일이 아니라 15~16일 기준으로 설계할 것**
- **한 세션 안에서 유창 판정이 날 수 있다.** `composeSprint`가 같은 식을 반복 출제하므로 한자리에서 빠르게 3번 맞으면 `fluent`가 된다. 설계 §6.1의 "최근 3회 연속 정답"을 문자 그대로 지킨 것이고 1→3→7→14 사다리가 이후의 지속성을 요구하므로 결함은 아니지만, **분산이 아니라 집중 학습의 증거**다. 점검의 날을 조율할 때 알고 있을 것
- **Phase 2는 마이그레이션이 필요 없다 — 확인됐다.** Phase 2가 쓰는 모든 필드(`Day.sprint`, `SprintAttempt`, `Settings.sprintCount`/`fluentMs`, `FactState`)가 Phase 1의 `types.ts`에 이미 있었고 전부 optional이거나 기본값이 있다. `schemaVersion`을 건드릴 일이 없었다. Phase 3이 이걸 다시 유도하지 않아도 되도록 적어 둔다

## Phase 1에서 리뷰가 반복해서 잡은 실패 패턴

Phase 2 계획서의 Global Constraints에도 넣어뒀다. 테스트를 쓸 때마다 확인할 것.

1. **자기 자신을 검사하는 테스트** — 생성기가 이미 술어로 거른 값을 같은 술어로 단언하면 무엇을 바꿔도 통과한다
2. **느슨한 상한** — 실측 16에 상한 150이면 완전 정지만 잡힌다
3. **실패할 수 없는 단언** — `expect(x).toBeTruthy()`
4. **화면의 갇힘 경로** — 첫 `await`가 `try` 밖이면 실패 시 `#app`이 빈 채로 남는다. `showError`는 `document.body`에만 붙는다

Phase 2가 여기에 둘을 더했다.

5. **매달린 비동기 콜백도 갇힘 경로를 만든다.** 4번은 `await` 위치 문제라 정적으로 보이지만, Phase 2에서는 취소되지 않은 `setTimeout`이 이미 교체된 `#app`을 덮어써서 같은 결과에 도달했다. 화면을 떠날 수 있는 지연 작업에는 취소 경로를 붙일 것
6. **가장 값진 결함은 태스크 사이의 이음새에 있다.** Phase 2의 Critical은 `sprint.ts`의 쓰기가 `home.ts`의 읽기를 만나야 보였고, `✅` 결함은 구현이 아니라 *설계문서와 계획서*를 대조해야 보였다. 태스크별 리뷰는 각자 범위 안에서 모두 옳았다. **다음 계획을 세울 때, 새 코드가 쓸 필드를 이미 읽고 있는 모든 곳을 나열하는 단계를 태스크 0으로 둘 것**

Phase 3가 여기에 하나를 더했다(실은 반복이라 하나로 묶는다) — 이번엔 6건 중 5건이 같은 종류였다.

7. **테스트가 자기가 검사한다고 주장하는 것을 실제로는 검사하지 못한다.** 구현 로직은 옳았는데도: 검증기가 컨테이너 타입만 보고 값을 안 봄 / "기존 값이 살아남았다"를 단언하는데 새 값과 기존 값이 같은 객체라 항진명제 / `getMeta()`의 빈 스토어 폴백이 기본값과 구조적으로 같아 2차 마스킹 / 정렬 픽스처가 올바른 키와 그럴듯한 오류를 구별 못 함 / 자기증명 단언에 상한이 없어 폭주 회귀를 못 잡음. **각 단언마다 "구현이 그럴듯하게 틀렸다면 이 값이 무엇이 되는가"를 묻고, 같으면 픽스처를 고칠 것.** 고친 뒤에는 **변이 검증**(구현을 일부러 틀리게 바꿔 테스트가 실패하는지 확인하고 원복)으로 실제 효력을 확인할 것 — 이번 Phase에서 이 방법이 여러 번 값을 냈다
8. 나머지 1건은 다른 종류였다: 가져온 백업 데이터가 이스케이프 없이 `innerHTML`에 들어가던 XSS. 신뢰할 수 없는 값(가져오기·사용자 입력)을 다루는 코드를 새로 쓸 때는 `escapeHtml`을 거쳤는지 항상 확인할 것
