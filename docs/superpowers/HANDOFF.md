## Phase 1이 만든 것

매일 A4 1장(세로셈 8 + □ 채우기 2)을 인쇄해 풀고, 아빠가 탭 몇 번으로 채점하면 다음날 문제 구성이 조정된다. 홈 화면에 추가하면 오프라인으로 돈다.

**지켜야 할 두 불변식** — 코드 곳곳이 여기에 기대고 있다.

- **재인쇄는 같은 문제를 낸다.** `src/screens/print-sheet.ts`의 `if (!day || day.sheet.length === 0)`이 `sheet`를 **자동으로** 쓸 수 있는 유일한 게이트다. 이게 깨지면 아이 손의 종이와 채점 화면이 어긋나 데이터가 조용히 오염된다
  - **예외는 아빠가 직접 누르는 `다시 만들기` 하나뿐이다**(2026-08-04 추가). 종이가 이미 아이 손에 있는지는 코드가 알 수 없으므로 사람만 이 불변식을 깰 수 있게 했다 — 확인 배너를 거치고, **채점이 있는 날은 아예 거부**한다(저장된 grades가 다른 문항에 붙어 버린다). 문항 생성 로직이 바뀌었는데 그날 문제지가 이미 만들어져 있을 때(예: 이름을 서아로 바꾼 날의 `○○` 문제지) 쓰라고 만든 탈출구다. **자동 재생성을 새로 만들지 말 것** — 이 버튼이 그 자리를 이미 채운다
- **`derived`는 버릴 수 있는 캐시다.** 실제로 `Meta.derived`를 읽는 코드가 하나도 없고, 매번 `days` 로그에서 재계산한다. 덕분에 판정 규칙을 바꾸면 과거 전체가 새 규칙으로 재해석된다 — 마이그레이션이 필요 없다

## Phase 2가 만든 것

홈에서 `구구단 스프린트`를 누르면 30문제를 풀고, 반응시간 중앙값이 `fluentMs`(2500ms) 이하로 3회 연속 맞으면 그 식이 "정복"된다. 정복한 칸만 답이 채워지는 지도가 결과 화면과 `#/map`에 뜬다 — **지금은 72칸이다**(Phase 2 당시엔 81칸이었고 Phase 4에서 1단이 빠졌다). 홈에 `🔥 연속일수`가 붙었다.

**Phase 2가 세운 것 중 기억할 것**

- **`engine/facts.ts`가 식 id 형식의 유일한 주인이다.** `factId`가 만들고 `factAnswer`가 푼다. 곱셈 기호는 U+00D7이며 화면은 절대 직접 파싱하지 않는다. `factAnswer`는 형식이 어긋나면 **던진다** — `deriveFacts`가 알 수 없는 id를 조용히 건너뛰는 것과 의도적으로 반대다. `deriveFacts`는 오염됐을 수 있는 과거 로그를 재생하므로 던지면 앱이 안 열리고, `factAnswer`의 입력은 엔진이 방금 만든 큐라 어긋났다면 엔진이 자기모순인 것이다. 이 비대칭은 두 곳 주석에 적혀 있다
- **스프린트만 한 날은 `sheet: []`인 `Day`를 만든다.** 이게 코드베이스 최초의 빈 sheet 생산자다. `engine/report.ts`의 `pendingGradeDate`와 `grade.ts`가 둘 다 `sheet.length === 0`을 검사해야 하는 이유다 — 최종 리뷰가 이 조합에서 Critical을 찾았다. **`sheet`를 읽는 코드를 새로 쓸 때마다 빈 sheet를 어떻게 다룰지 정하라**
- **세션은 끝났을 때만 저장한다.** 중간에 나가면 없던 일이 된다(부분 세션이 반응시간 통계를 오염시킨다). 반대로 **다 푼 세션은 저장 실패해도 버리지 않는다** — 결과 화면에 재시도 버튼이 뜬다
- **반응시간은 문제가 보인 순간부터 첫 숫자 키까지다.** 확인 버튼까지의 시간은 손가락 속도라 노이즈다. 진행 중에는 타이머를 표시하지 않는다 — 시간 압박이 인출을 느리게 만들어 측정하려던 값을 오염시킨다
- **`navigate()`는 같은 해시로 불려도 `hashchange`를 쏜다.** 안 그러면 이미 `#/`인 화면의 "← 홈" 버튼이 죽고, 주소창 없는 아이패드에서는 강제 종료 말고 길이 없다

## Phase 3이 만든 것

시작 시 `navigator.storage.persist()`를 불러(`src/main.ts`) iOS의 저장공간 압박에 의한 evict 위험을 줄였다. 백업 내보내기·가져오기로 데이터 왕복이 가능해졌고(`src/engine/backup.ts`), 28일 주기 점검 스프린트(`src/engine/checkup.ts`)와 주간·월간 리포트 화면(`#/report`, `src/screens/report.ts`)이 생겼다. 일요일에 채점을 저장하면 `#/report`로 자동 전환된다.

**이번 Phase가 세운 것 중 기억할 것**

- **점검에는 강등 로직이 없고, 없는 것이 설계다.** 점검 시도도 그냥 `Day.sprint`에 기록될 뿐이고, `deriveFacts`가 로그를 재생하며 연속 3회가 깨지면 스스로 내린다. 강등 코드를 새로 쓰면 이중 처리가 된다
- **리포트는 아무것도 저장하지 않는다.** `weeklyReport`·`latestCheckupReport`(`src/engine/report.ts`) 모두 매번 로그에서 재계산한다 — `Meta.derived`를 배선하지 않는 것과 같은 원칙이다. 판정 규칙을 바꾸면 과거 주간·과거 점검이 소급 재해석된다. `derived`는 여전히 아무도 읽지 않는다
- **`kind: 'checkup'`은 그 날 스프린트가 점검이었다는 표시이고, 점검의 날엔 스프린트가 점검 하나뿐이어야 한다.** 월간 리포트가 "점검일 전날까지 vs 점검일까지"의 차이를 점검 세션으로 간주하기 때문이다
- **가져오기는 병합하지 않고 전체 교체다.** `src/data/db.ts`의 `replaceAll`이 `days`·`meta` 두 스토어를 한 트랜잭션으로 바꾼다. **`tx.abort()`가 없으면 "clear만 커밋"되어 데이터가 조용히 사라진다** — 이 함정이 테스트로 고정돼 있다. 검증 실패 시에는 기존 데이터가 보존된다(원자성 테스트로 고정)
- **초기화(`resetAll`)는 `replaceAll([], defaultMeta())`다.** 파괴적 쓰기 경로를 하나로 유지한다 — `replaceAll`의 `tx.abort()` 함정이 테스트로 고정돼 있어서, 두 번째 경로를 만들면 그 함정을 다시 밟을 자리가 생긴다. `defaultMeta()`는 `getMeta()`의 기본값 생성을 뽑은 것이라 "초기화된 상태"와 "한 번도 안 쓴 상태"가 같은 출처에서 나온다. 버튼은 `#/report` 하단에 있고 **기록이 0일이면 그려지지 않는다**. 확인 배너는 지울 일수·날짜 범위와 함께 채점 안 된 문제지 수(`ungradedSheetCount`)·마지막 백업(`daysSinceExport`)을 병기하지만 **막지는 않는다** — `lastExportedAt`이 "저장했나요? → 네"에만 의존해 강제 게이트로 쓰면 거짓 안전감을 준다(설계 `specs/2026-08-04-data-reset-design.md`)
- **월간 리포트의 유지/탈락은 그 세션이 실제로 물어본 식만 분모로 삼는다.** `latestCheckupReport`(`src/engine/report.ts`)의 `kept`는 "이전에 fluent였고, 이 점검 세션이 실제로 물어봤고, 지금도 fluent"인 식만 센다 — `composeCheckup`이 fluent가 `sprintCount`를 넘으면 오래된 판정부터 잘라내므로, "이전에 fluent였던 전부"를 분모로 쓰면 그날 안 물어본 식까지 "유지"로 잡힌다(최종 리뷰가 잡은 Important: 구구단을 다 뗀 뒤가 정확히 이 상태였다). `CheckupReport.tested`가 분모를 담고, 화면(`#/report`)은 "점검한 N개 중 유지 K · 다시 연습 M"으로 분모를 함께 보여준다
- **점검은 fluent가 `CHECKUP_MIN_FLUENT`(현재 10) 이상 쌓인 뒤에만 돈다.** `nextCheckupDate`(`src/engine/checkup.ts`)의 게이트가 원래 "fluent 1개 이상"이었는데, 그러면 드릴이 가장 필요한 더디게 크는 아이일수록 점검일에 fluent가 한두 개뿐이라 한두 문제짜리 점검을 받았다 — 그 하루를 통째로 잃는데 `sprintStreak`은 스프린트가 있었다는 사실만 보고 🔥 연속일수로 정상 보상해줬다(최종 리뷰가 잡은 Important). 앵커 로직(마지막 점검일 ?? 첫 스프린트일)은 그대로다 — 게이트는 "측정할 게 쌓일 때까지 미루는" 역할만 한다
- **내보내기는 "저장했나요?" 확인을 받고서야 `lastExportedAt`을 갱신한다.** Download API에는 완료 신호가 없어서, 무조건 갱신하면 `EXPORT_OVERDUE_DAYS`(30일) 배지가 거짓이 된다 — 사용자 결정
- **백업 검증은 계량돼 있다.** `grades` 값은 전수 boolean 검사, `sheet` 항목은 `id`+`kind`만, `settings`는 코드가 실제로 읽는 필드만 본다. **변형별 sheet 필드는 의도적으로 미검사** — types.ts 스키마를 검증기에 복제하면 Phase 4에서 문항 종류가 늘 때 정상 백업을 거부하게 된다. 그 트레이드오프로 **손상된 sheet 항목은 복구 후 렌더 시점에 throw할 수 있다**
- **`el()`이 `innerHTML`을 쓰므로 신뢰할 수 없는 값(가져온 백업 등)은 반드시 `ui.ts`의 `escapeHtml`을 통과시켜야 한다.** 리뷰가 실제로 이스케이프 누락 XSS를 한 건 잡았다
- **배포됐다.** `main` 머지 후 push하여 Pages 워크플로가 성공했고(커밋 `ff30e3c`), `https://watson-develop.github.io/haruchi/`가 Phase 3 코드를 서빙한다 — 배포된 번들에 리포트 화면 청크(`report-*.js`)가 들어 있는 것까지 확인했다. **origin은 한 번 정했으니 바꾸지 않는다** — IndexedDB가 origin별로 격리되므로 주소를 바꾸면 딸의 기록에 접근할 수 없다

## Phase 4가 만든 것

구구단 지도 옆에 "생각하는 문제"를 얹었다. 매일 세로셈 8 + □ 채우기 2 뒤에 전략 2문항 + 문장제 2문항이 이어져 **하루 14문항, 2장짜리 문제지**가 된다. 구구단 풀은 81식에서 72식으로 줄었다. 12개 태스크 + 전체 브랜치 최종 리뷰 + 수정 웨이브까지 끝났다.

**이번 Phase가 세운 것 중 기억할 것**

- **구구단 풀이 81식(1×1부터 9×9까지)에서 72식(2×1부터 9×9까지)으로 줄었다(사용자 결정).** 1단은 규칙이 하나뿐이라 반복 인출 훈련의 대상이 아니다 — 0단을 뺐던 Phase 2의 사유를 1단에 적용했다. 곱하는 수 ×1은 남겼다 — 외우는 구구단이 "2×1은 2"부터 시작해서다. 신규 식 도입도 무작위로 바뀌었다 — 교과서 도입 순서(옛 `FACT_ORDER`, 인천교육청 지도서 근거)는 폐기했다(사용자 결정). 과거 로그의 1×n 시도는 `deriveFacts`가 모르는 id로 조용히 건너뛴다 — **마이그레이션이 필요 없다**
- **풀 경계가 `engine/facts.ts` 한 곳으로 좁혀졌다(사용자 결정).** `DAN_MIN`/`DAN_MAX`/`FACTOR_MIN`/`FACTOR_MAX`를 export하고 `FACT_IDS` 생성 루프가 그 값을 쓴다. 지도 화면(`src/screens/fact-map.ts`)은 그 네 상수와 `FACT_IDS.length`를 import해 행·열·칸 수를 유도하고, 리포트 문구(`src/screens/report.ts`)는 **`FACT_IDS.length`만** import한다(분모, 즉 칸 수만 필요해서다 — 경계 상수는 안 쓴다). 어느 쪽도 숫자를 자기 것으로 복제하지 않는다 — `facts.ts` 하나만 바꾸면 지도와 리포트가 따라온다(변이 검증으로 확인)
- **전략 존(하루 2문항)은 `engine/strategy.ts`의 선언적 카탈로그 `STRATEGY_CATALOG`가 유일한 출처다.** 이름·도입 순서·조건(`applicable`)·빈칸 뼈대(`steps`)가 배열 하나에 모여 있고, 렌더러·채점·리포트는 이 카탈로그 내부를 모른 채 `steps`가 돌려주는 `{}`와 `blanks`만 본다. **새 전략을 추가하려면 배열에 항목 하나 + `StrategyId` 유니온에 멤버 하나만 더하면 된다** — 인쇄·채점 코드는 손대지 않는다
- **전략 도입 게이트는 등장 횟수(3회)이지 채점이 아니다.** `composeStrategyItems`는 `strategies[latest.id].appearances`만 보고 다음 전략으로 넘어간다 — 숙련 판정이 아니라 노출 페이스 조절이라, 아빠가 채점을 며칠 밀려도 새 전략 도입이 멈추지 않는다. 문항2는 어제의 방법(도입된 것 중 `lastAppearedAt`이 가장 오래된 것)이다. 낮은 확률(`SAME_EXPR_CHANCE` = 0.2)로 두 문항이 같은 수식을 다른 방법으로 푼다. 곱셈 전략 2종(`double`·`minus-one`)은 fluent가 `MUL_STRATEGY_MIN_FLUENT`(10) 미만이면 열리지 않는다 — 구구단표가 머리에 없으면 7×4×2는 우회로가 아니라 짐이다
- **문항1("오늘의 방법")은 새 전략을 열 수 있을 때만 고정석이다 — 사용자 결정(2026-08-03)으로 스펙 §3의 "문항1 = 최신 도입"이 갱신됐다.** 이 결정은 이후 스펙 본문에도 반영됐다(§0 개정 ⑥ · §3 "정착기" 절 — 2026-08-04 교육과정 리뷰 개정에 실려 들어갔고, ⑥의 출처가 사용자 결정임은 §0에 명시돼 있다). 스펙 §3과 코드가 이제 같은 말을 하니, 세부 근거는 `composeStrategyItems`의 주석을 볼 것. 갓 도입한 전략은 등장 3회를 채울 때까지 문항1에 머물지만(도입 페이스는 이 게이트가 정한다), 더 열 게 없으면(카탈로그 소진이거나 곱셈 게이트가 닫힘) **문항1도 로테이션에 합류**해 두 문항 모두 `lastAppearedAt`이 오래된 순으로 뽑힌다. 최종 리뷰 실측이 이유다: 옛 동작에서는 8종 도입 후 `minus-one`이 60일 중 40일 문항1을 독점했는데 그 전략의 유효 문제는 총 8개(`b === 9`, `2 ≤ a ≤ 9`)뿐이라 같은 문제가 계속 재등장했고, 곱셈 게이트가 영영 안 열리는 아이(정답률 0.45)는 `count-up`이 15일째부터 영구 고정됐다. 변경 후 실측(fluent 20, 60일): `make-ten:22, split-place:17, round-adjust:16, split-subtrahend:14, anchor:14, count-up:13, double:12, minus-one:12`(전에는 `minus-one:40 … double:8`). **도입 페이스는 불변**임을 확인했다 — 8종 도입일이 d1·d3·d6·d9·d12·d15·d18·d21로 변경 전과 같고, `simulation.test.ts`의 6종 도달일도 9개 시드 전부 15일 그대로다
- **전략 step의 표기는 "2학년이 이미 배운 형식"만 쓴다 — 값이 아니라 표기가 기준이다(2026-08-04 교육과정 리뷰).** `double`의 두 배 step은 `28 × 2`가 아니라 **`28 + 28`**로 찍는다(두 자리 × 한 자리는 3-1 [4수01-04]라 배운 적 없는 형식이고, 실제 행위도 "두 번 더하기"다). `minus-one`의 첫 step은 `10 × 7`이 아니라 **`10씩 7묶음`**으로 찍는다(10단은 곱셈구구 밖이지만 묶어 세기는 2-1 완료 개념 [2수01-10]이라, 같은 값을 배운 표기로 묻는다). **바뀐 것은 `steps[].text`뿐이다** — `blanks`도 `answer`도 그대로라 채점 계약(마지막 빈칸 == 최종 답)이 움직이지 않았고, 렌더러가 텍스트를 파싱하지 않고 `{}`만 치환하므로 인쇄·채점 코드는 한 줄도 안 건드렸다. 같은 리뷰가 `count-up`의 스펙 예시(`63−28`)도 `62−58`로 교체했다 — 차 35는 `applicable`(차 3\~15) 밖이라 `gen`이 절대 만들지 않는 조합이었다(예시가 다시 영역 밖으로 새지 않도록 테스트에 `applicable` 단언을 함께 뒀다). **반면 수의 크기는 좁히지 않았다** — 같은 리뷰의 "피연산자·결과 두 자리 제한"(⑧)은 사용자 결정으로 철회됐고, 코드는 의도적으로 세 자리를 낸다(`make-ten`·`round-adjust` 두 종뿐, 최대 179). 근거는 스펙 §3에 적어 뒀다 — **그 절을 읽고 코드를 좁히지 말 것**
- **등장인물 이름의 유일한 출처는 `word.ts`의 `WORD_NAMES`다(2026-08-04).** 이름 입력 화면을 없앤 직후, 기기에 남아 있던 `childName`(`'○○'`)을 고칠 방법이 없어 문장제가 `○○이가 …`로 나왔다. 그래서 `Settings.childName`·`friendNames`는 **읽지 않는다** — `derived`처럼 스키마 호환으로만 남은 필드다. `compose.test.ts`가 settings에 `○○`을 넣고 출력에 새지 않는지 고정한다(변이 검증 완료). 이름은 상수 직참조가 아니라 `composeWordItems`의 인자로 흐른다 — 받침 있는 이름(`서연이가`)의 조사 회귀 테스트가 받침 없는 `서아`로는 아무것도 못 잡기 때문이다
- **문장제 텍스트는 생성 시점에 완성돼 `sheet`에 박제된다.** `word.ts`가 그날 세션에 텍스트를 만들어 저장하므로, 이름을 나중에 바꿔도 이미 만든 날의 문제지는 그대로다(**이름을 바꾼 당일에는 옛 이름 문제지가 그대로 나온다** — 다음 날 문제지부터 반영된다) — Phase 1의 재인쇄 불변식이 문장제에도 그대로 적용된다. 하루 두 문항 중 하나엔 반드시 딸 이름이 들어가고, 받침 있는 이름엔 접미사 '이'를 붙인다(서연이가/서연이는/서연이를/서연이의 — 사용자 결정). 사물은 `josa`의 일반 조사 규칙을, 사람은 `personJosa`를 따로 쓴다. 몇 배의 배수는 2~5로 제한한다(시뮬레이션이 "8배 줄넘기"의 부자연을 잡았다)
- **하루 문제지가 2장이 됐지만, 옛 sheet를 재인쇄하면 2장을 만들지 않는다.** `print-sheet.ts`는 전략·문장제 항목이 하나도 없는 sheet(Phase 4 배포 전에 만들어진 10문항짜리 구버전 `composeSheet` 산출물)를 만나면 2쪽 자체를 그리지 않는다 — 재인쇄 불변식이 "이 날은 이제 2장짜리여야 한다"는 새 기대보다 우선한다. 인쇄 순서(세로셈→역연산→전략→문장제, ①~⑭)는 `compose.ts`의 id 순서, 채점 화면(`grade.ts`의 `markMap`)의 번호 순서와 셋 다 일치하도록 맞춰져 있다. **번호표 자체(`ITEM_MARKS`)는 `src/ui.ts`가 유일한 출처다** — 두 화면에 사본을 두면 어긋나도 잡을 방법이 없다(설계 §12가 화면 테스트를 두지 않는다). 두 화면이 각자 지켜야 하는 것은 **순서**뿐이다
- **`composeSheet`의 `seen`(수식 중복 회피 집합)을 세로셈·전략·문장제가 한 집합으로 공유한다.** 키 형식(`` `${a}${op}${b}` ``)이 같아서, 세로셈에 이미 나온 27+15가 전략에서 다시 나오는 것도 자동으로 막힌다. **역연산(□ 채우기)은 이 집합에 참여하지 않는다** — `compose.ts`의 역연산 루프(98~111행)는 `seen`을 읽지도 쓰지도 않는다. 즉 "한 집합"은 세 종류의 이야기이고, 역연산은 세로셈과 같은 수식을 낼 수 있다
- **`sheet` 항목의 값은 타입이 `number`여도 렌더 지점에서 이스케이프한다.** `validateBackup`은 `sheet[]`의 `id`(문자열)와 `kind`(4종)만 검사하고 **변형별 필드는 의도적으로 전부 미검증**이므로(위 Phase 3 항목의 트레이드오프), `a`·`b`·`c`·`answer`·`op` 같은 숫자·기호 필드에도 가져오기로 임의 문자열이 들어올 수 있다. 최종 리뷰가 정확히 여기서 Critical을 찾았다 — 문자열 필드(`text`·`unit`·`steps[].text`·`tag`·`expression`)만 이스케이프하고 숫자 필드는 "타입이 number니까"로 넘겼는데, 실제로는 `a = '<img src=x onerror=…>'`가 인쇄 화면에서 그대로 발화했고 채점 화면에서는 `id`가 `data-id="…"` **속성을 깨고 나왔다**. 그래서 `escapeHtml`의 인자를 `unknown`으로 넓혀(내부에서 `String()`) 렌더 지점 전부를 `escapeHtml(...)` 한 형태로 통일했다. **`src/screens/print-sheet.ts`·`src/screens/grade.ts`의 템플릿에 이스케이프 없이 들어가는 값은 우리가 만든 리터럴뿐이어야 한다** — 새 필드를 찍을 때마다 확인할 것

**이 브랜치가 세운 것 중 다음 사람이 알아야 할 것 — 실제로 겪은 SEED 함정들:**

1. **SEED 레시피는 상태·size 클래스가 없으면 선언이 통째로 빠진다.** 세 번 겪었다: `snackbar`는 `data-open`이 없으면 `:not([data-open])`(특정도 0,2,0)이 기본 규칙(0,1,0)을 이겨 **토스트가 100ms 뒤 opacity 0으로 죽은 채 3초를 보냈다.** `action-button`은 `size_*`가 없으면 `border-radius`와 `:active`의 scale 애니메이션이 **둘 다** 죽었다. `badge`는 `size_medium`이 padding·radius·font-size·line-height·min-height의 **유일한 출처**였다. → **레시피 클래스를 붙일 때 설치본에서 무엇이 어디에 gate돼 있는지 먼저 확인할 것.**
2. **"레이어 밖이 항상 이긴다"는 양날이다.** 네이티브 `<button>` 리셋에 `font: inherit`(shorthand)을 썼더니 font-size·font-weight·line-height까지 리셋해 **정작 도입하려던 segmented-control의 타이포를 무력화했다.** → **리셋은 개별 속성으로 좁게** 쓰고 `font`·`background`·`all` 같은 shorthand로 뭉뚱그리지 말 것.
3. **색이 root가 아니라 하위 슬롯에 붙는다.** `callout`의 tone 색은 `__root--tone_*`이 아니라 `__description--tone_*`에 있다. root만 붙이면 글자가 기본색을 상속한다.
4. **계획서의 대비 수치가 틀렸다.** 배지 neutral을 15.49로 적었으나 그 값은 다른 토큰 조합이고, 레시피가 실제 쓰는 `tone_neutral-variant_weak`는 **6.01**이다(AA 통과). → **설계 문서의 숫자도 설치본에서 재확인할 것.**
5. **오버레이가 `#app` 밖에 살면 화면 전환에서 살아남는다.** `confirmDialog`가 `document.body`에 붙어 `#app` 교체에도 남아, **다른 흐름이 화면을 바꾼 뒤에도 확인 버튼이 눌려 되돌릴 수 없는 작업이 도는 경로**가 생겼다. → `hashchange`에 스스로 닫고 `false`로 resolve하게 고쳤다. **`#app` 밖에 사는 것은 자기 수명을 스스로 관리해야 한다.**
6. **공유 컨테이너를 덮어쓰는 쪽이 파괴되는 것의 상태를 정리해야 한다.** `#confirm`을 여러 패널이 공유하는데, 덮어쓰면 이전 패널의 버튼과 리스너가 사라져 **그 패널이 들고 있던 플래그가 영영 해제되지 않아 버튼이 조용히 잠겼다.** → `showConfirmPanel(node, cleanup)` 단일 지점으로 모아 해결. **패널이 늘어도 재발하지 않는다.**

## 디자인 시스템 조사 (2026-08-04)

화면 컴포넌트를 계속 손으로 쌓는 대신 기성 디자인 시스템을 쓸 수 있는지 조사했다. 결론은 **SEED(당근)는 쓸 수 있고 TDS Mobile(토스)은 쓸 수 없다**이며, 갈린 이유는 라이선스다.

- **TDS Mobile은 배제됐다.** `@toss/tds-mobile@2.5.1`이 공개 npm에 있지만 `license` 필드가 비어 있고(라이선스 미표기 = 권리 유보가 기본), 공식 문서가 "토스가 TDS 사용을 허가하는 건 **앱인토스 서비스를 제공하기 위한 제한적인 권한**"이라고 범위를 명시한다. 하루치는 앱인토스 미니앱이 아니다. **취향이 아니라 조건이므로 다시 검토하지 말 것**
- **SEED는 Apache-2.0이고, `@seed-design/css`는 dependencies·peerDependencies가 모두 0인 순수 CSS다** — React가 필요 없다. 레시피 클래스가 평범한 BEM(`seed-action-button--variant_brandSolid`)이고 상태 스타일이 `:is(:hover, [data-hover])` 형태라 **네이티브 의사클래스가 살아 있다**. 정적 컴포넌트는 JS 0줄로 굴러간다. 프레임워크 없음·런타임 의존성 0이라는 이 레포의 전제와 충돌하지 않는 유일한 형태다
- 실측 비용(gzip): `base.min.css` 7.5KB + 하루치에 쓸 만한 레시피 12개 7.5KB = **약 15KB**. `all.css`(416KB)를 통째로 넣을 필요는 없다
- 색은 **역할 기반 토큰**(`--seed-color-fg-*`·`bg-*`·`stroke-*`)을 쓰고 팔레트 직접 참조(`--seed-color-palette-*`)는 피한다. 다크모드는 `<html>`의 `data-seed-color-mode` + `data-seed-user-color-scheme` 두 속성으로 걸린다. 상태는 `data-disabled`·`data-checked`·`data-open`·`data-state` 같은 `data-*` 계약을 우리가 토글한다
- **TDS에서 가져올 것은 코드가 아니라 API 사상이다.** 오버레이가 명령형 한 줄(`toast.openToast('저장했어요')`)이고, 토스트가 SafeArea와 하단 고정 CTA 높이를 **자동으로 피한다**는 설계. 선언형은 상태를 둘 자리가 필요한데 바닐라 DOM에는 그 자리가 없다 — 명령형이 이 레포에 맞다. SEED가 이미 `--seed-safe-area-bottom`을 주므로 하단 영역이 자기 높이를 CSS 변수로 내놓기만 하면 절반은 공짜다
- SEED 문서는 AI 연동이 갖춰져 있다(`/llms.txt`, 섹션별 `llms.txt`/`llms-full.txt`, Figma·Docs MCP, Claude Code 스킬). 컴포넌트 상세는 `https://seed-design.io/llms/react/components/{name}.txt`
- **SEED의 패턴 문서는 아직 비어 있다**(`/patterns`에 Loading 하나). 기대하지 말 것

## 동기화 1단계 (2026-08-06)

브랜치 `sync-phase1`(`main`에서 분기, 아직 머지되지 않음)이 IndexedDB → Supabase 단방향
업로드를 배선했다. 설계는 `specs/2026-08-06-sync-backend-design.md`(쉬운 말 버전
`-plain.md`도 있다). IndexedDB가 여전히 원본이고 Supabase는 **복제본**이다 — 이 기기가
쓰는 값을 서버로 밀어 올릴 뿐, 서버에서 받아오는 경로(pull)는 없다.

**들어간 것**

- `supabase/schema.sql` — 테이블 `days`·`meta`·`app_config`·`devices`·`snapshots`·
  `write_log`. 동사별 RLS 정책만 있고 **DELETE 정책은 어디에도 없다**(사유는 스키마 파일
  주석). `sheet` 불변 트리거가 서버 쪽에서도 재인쇄 불변식을 강제한다. RPC 둘: `replace_all`
  (자기 트랜잭션 안에서 자동으로 사전 스냅샷을 뜨고, `meta` 행은 절대 지우지 않는다)과
  `rewrite_sheet`. `supabase/README.md`가 사람이 따라 할 설정 절차서다
- `src/engine/outbox.ts` — `SyncBundle`(`'sheet' | 'grades' | 'sprint'`)·`OutboxEntry`·
  `foldOutbox`(같은 target을 하나로 접되 묶음별 최신 타임스탬프를 잃지 않는다)
- `src/engine/sync-status.ts` — 부모 홈 상태줄 문구를 판정하는 `syncStatus(...)`
- `src/data/db.ts`가 DB 버전 2로 올라갔다 — `outbox`·`device` 스토어 신설. **`putDay(day,
changed)`가 `changed: SyncBundle[]`를 요구하고, Day 쓰기와 아웃박스 표식을 같은
  트랜잭션에 담는다**(CLAUDE.md 불변식 절에도 적었다 — 선언을 빠뜨리거나 틀리면 그 변경이
  서버로 올라가지 않는다). `deleteOutboxThrough(target, maxKey)`는 push 시작 시점에 캡처한
  key까지만 지운다(그사이 새로 쌓인 표식은 남긴다). `replaceAll`(가져오기·초기화)은 아웃박스를
  비우지만 **`device` 스토어는 건드리지 않는다** — 기기 정체성은 백업 대상이 아니다. `open()`이
  업그레이드가 막히면(다른 탭이 옛 버전을 물고 있는 경우) 조용히 멈추는 대신 reject한다
- `src/data/sync.ts` + `src/data/sync-config.ts` — push 엔진. `rev` 낙관적 동시성
  프로토콜(INSERT는 rev=1, PATCH는 `rev=eq.N` 조건부 + `rev=N+1`, 3회 재시도 후 포기),
  스냅샷·`replace_all`·복구(snapshot 조회) 호출, 그리고 `configured()` 가드 —
  `SUPABASE_URL`·`SUPABASE_ANON_KEY` 둘 다 채워지기 전에는 **네트워크 진입점 전부가
  inert**하다. "설정됐다"의 정의가 이 함수 하나뿐이라 화면과 push가 서로 다른 기준으로
  갈라지지 않는다
- `src/main.ts` — 시작 시·`haruchi:outbox` 이벤트·`visibilitychange`(탭이 다시 보일 때) 세
  지점에서 `kickPush()`를 부른다
- `src/ui.ts` — `confirmDialog`에 `requireText`(타이핑 확인) 옵션이 붙었다
- `src/screens/home-parent.ts` — 동기화 상태줄과 기기 등록 블록
- `src/screens/report.ts` — 초기화·가져오기가 **온라인 확인 → 서버 스냅샷 → 타이핑 확인
  → 로컬 교체 → 서버 `replace_all`**(RPC가 자동 스냅샷을 겸하므로 이중 스냅샷이 아니다)
  순서로 바뀌었다. 스냅샷 목록에서 고른 시점으로 되돌리는 복구 경로도 이 화면에 생겼다
- `.github/workflows/ping-supabase.yml` — Supabase 무료 티어가 무요청 상태로 방치되면
  자동 일시정지되는 것을 막는 주간 ping. URL·anon 키는 사람이 채울 자리로 플레이스홀더인
  채 커밋돼 있다

**앱은 배선된 채로도 죽은 듯 배포된다 — 이게 이 브랜치가 머지·배포 가능한 이유다.**
`sync-config.ts`의 `SUPABASE_URL`·`SUPABASE_ANON_KEY`가 빈 문자열인 채로 두면
`configured()`가 항상 false를 돌려주고, push·스냅샷·복구를 포함한 **모든 네트워크 요청
경로가 그 자리에서 멈춘다** — 화면은 지금 배포된 것과 완전히 똑같이 동작한다. 그래서
Supabase 프로젝트가 아직 없어도, 심지어 사람이 `supabase/README.md`의 설정 절차를
아직 밟지 않았어도 이 브랜치를 main에 올려 배포할 수 있다. 실제로 동기화가 켜지는 시점은
사람이 프로젝트를 만들고 두 값을 채워 커밋하는 순간이다.

**최종 리뷰 수정 웨이브 (2026-08-06)** — 브랜치 전체 리뷰에서 나온 11건을 한 번에 고쳤다.
설계 문서에는 없던 사실이 넷 나왔으니 여기 남긴다.

- **한 target의 push 실패가 아웃박스 전체를 영구히 막았다.** 실패가 throw로 루프를 끊었고,
  실패한 표식은 맨 앞 key에 남아 이후 모든 패스가 같은 자리에서 죽었다. 지금은 target별로
  격리해 실패한 것만 남긴다. 「다시 만들기」는 서버 트리거가 막는 PATCH 대신 `rewrite_sheet`
  RPC로 우회한다 — **판정은 서버의 대답(`sheet_immutable`)으로 한다**(jsonb는 키 순서를
  보존하지 않아 클라이언트의 sheet 비교가 신뢰할 수 없다)
- **등록 이전의 기록에는 아웃박스 표식이 없어 영원히 안 올라갔다.** 표식은 `putDay`·`putMeta`만
  만들기 때문이다 — 지키려던 1년치가 정확히 그 사각지대였다. `db.ts`의 `seedOutbox()`가
  등록 후 첫 push에서 한 번(멱등, `device.seededAt`) 전량에 표식을 남긴다
- **되돌리기에는 사전 스냅샷이 없었다.** `replace_all`의 자동 스냅샷은 *이미 서버에 있는
  것*만 담으므로, 아직 안 올라간 로컬 기록은 어디에도 남지 않고 사라진다. 초기화·가져오기와
  같은 규칙(사전 스냅샷 없으면 진행 금지)으로 맞췄다
- **폐기된 키는 401이 아니라 200 + 빈 배열이다**(RLS의 전부-아니면-전무). `meta` 행이 항상
  하나라는 사실을 판별자로 써서 인증 실패로 승격하고 부모 홈에 표시한다
- 그 밖에: 모든 `fetch`에 15초 타임아웃(`AbortController`), `#/report`는 본문을 먼저 그리고
  스냅샷 목록을 나중에 채운다, 파괴적 작업 동안 `suspendPush()`로 push를 멈춘다(진행 중인
  비행은 기다린다), 스냅샷 payload가 백업 파일과 같은 모양이 되어 `Settings.schemaVersion`
  (아무도 갱신하지 않는 사본)에 의존하던 버전 게이트를 없앴다, 상태줄의 날짜 비교를 로컬
  기준으로 통일, `schema.sql`이 재적용 가능해졌다(throwaway Postgres에서 3회 연속 적용 확인)

**2단계로 미룬 것(이번에 의도적으로 안 한 것)**

- **pull** — 서버 값을 이 기기로 받아오는 경로 자체가 없다. 지금은 한 기기가 쓰고 나머지는
  구경만 하는 모양이 최선이다
- **`engine/merge.ts`와 병합 규칙 전체** — pull이 없으니 합칠 것도 아직 없다
- **`generation` 충돌 처리** — 같은 날을 두 기기가 동시에 고치는 경우의 해소 로직
- **채점 화면의 PIN**
- **완성형 기기 등록 화면** — 지금은 부모 홈의 인라인 블록 하나뿐이다
- **인쇄 화면 생성 게이트**를 동기화와 엮는 것
- **백업 경고의 기준 전환** — `daysSinceExport`(`lastExportedAt` 기반)가 여전히 30일
  배지의 근거다. 동기화가 켜져도 "마지막 동기화 시각" 기준으로 바뀌지 않는다 — 지금은
  두 신호가 독립이다

**사람이 확인할 것 — 머지 전에 `supabase/README.md` 절차를 실제로 밟아야 검증할 수 있다**

1. Supabase 프로젝트 생성 → 스키마 적용 → 아이패드 등록(README 1~6절)
2. 문제지 인쇄 → 서버 `days`에 행이 생기고 `sheet_at`만 찍히는지
3. 스프린트 → 같은 행이 갱신되고 `sprint_at`만 바뀌고 `sheet_at`은 그대로인지(아웃박스
   `bundles` 접기가 실제로 동작하는지의 증거)
4. 채점 저장 → `grades_at`만 갱신되는지
5. 비행기 모드에서 스프린트 → 부모 홈에 "안 올라간 기록 N건" → 와이파이 복귀 →
   올라가고 경고가 사라지는지
6. ~~초기화: 스냅샷 없이는 진행되지 않는지 · "지우기" 타이핑을 요구하는지 · 서버 `days`가
   비워지는지 · `snapshots`에 2건(사전 + `replace_all`의 auto)이 남는지 · 되돌리기로
   복구되는지~~ — **✅ 2026-08-12 실기기로 다섯 항목 전부 확인.** 오프라인에서는 문구
   (`서버에 연결할 수 없어요…`)만 뜨고 **확인 다이얼로그가 아예 안 뜬다** — 거부가 사전
   스냅샷보다 앞이라 `reason='reset'` 행조차 안 생기는 것으로 구별된다(실측). 「지우기」
   타이핑이 실제 게이트. `days` 4행 → 0행 → 되돌리기로 4행(2026-08-05\~08-12) 복구,
   `snapshots`에 초기화 `reset`+`auto` · 되돌리기 `restore`+`auto`, `generation` 1 → 2 → 3.
   **이 항목은 아래 `replace_all` 절의 결함을 정확히 겨냥하고 있었고, 그것을 고친 뒤에야
   통과할 수 있었다** — 되돌리기 쪽 `restore`·`auto`의 `day_count`가 0인 것은 정상이다
   (그 시점 로컬·서버가 비어 있어 담을 것이 없었다)
7. 기기 키를 `revoked_at`으로 폐기 → 부모 홈이 **"기기 키가 거부됐어요"**를 표시하는지.
   폐기는 401이 아니라 **200 + 빈 배열**로 나타난다(RLS가 행을 안 보여주는 방식이라 —
   throwaway Postgres에서 실측). `serverStatus()`가 "행이 하나뿐인 `meta`가 비어 보이면
   키가 거부된 것"으로 판정한다
8. `sync-config.ts`를 비운 빌드에서 앱이 지금과 완전히 동일하게 동작하는지(위 "죽은 듯
   배포된다" 절의 주장을 실물로 재확인. PIN을 캐시한 기기는 `#/grade`·`#/report`에서
   게이트 다이얼로그를 보는 것이 예외다 — 판정 기준은 여전히 fetch 0건, 2B 스펙 §4의
   명시된 부작용이다)
9. 등록 직후 **기존 기록 전체**가 서버 `days`에 올라오는지(`seedOutbox`) — 그리고 키를
   다시 저장해도 다시 올라가지 않는지
10. ~~`다시 만들기`를 한 날이 서버에 반영되는지(`write_log`에 `sheet-rewrite` 한 줄), 그리고
    그 뒤 다른 날의 스프린트도 계속 올라가는지(한 target의 실패가 전체를 막지 않는다)~~ —
    **✅ 2026-08-12 실기기 실측.** 「다시 만들기」 → `rewrite_sheet` RPC가 돌고 `rev` +1,
    `sheet_at`·`sheet_by` 갱신, **`grades_at`·`sprint_at`은 null 그대로**(RPC가 sheet
    스탬프만 찍는다는 계약이 실물로 확인됨). 이어서 스프린트 → `sprint_at`만 채워지고
    `sheet_at`은 불변.

    **정정 — "한 줄"이 아니라 두 줄이다.** 한 번의 `rewrite_sheet`가 `write_log`에
    `action='update'`와 `action='sheet-rewrite'`를 **같은 트랜잭션 타임스탬프로 함께**
    남긴다(실측: 마이크로초까지 동일). 앞엣것은 함수 안의 `update days`가 깨운 `days_log`
    트리거가, 뒤엣것은 함수 본문이 직접 넣는다. 아래 2A 「일부러 안 고치고 넘긴 것」의
    *"평범한 경로로 해소된 「다시 만들기」는 `update`로만 남아 재작성 이력이 끊긴다"*와
    짝을 이루는 사실이다 — **RPC 경로는 둘 다, PATCH 경로는 `update`만.**

    **RPC로 가는 조건이 플래그가 아니라는 것도 같이 확인할 것**(`sync.ts:691`
    `rewrite && sheetConflict(local, server)`): 서버 sheet가 비어 있거나 로컬과 같으면
    평범한 PATCH로 새고 `sheet-rewrite`가 안 찍힌다. **이 검증을 다시 돌릴 때는 오늘 종이가
    서버에 이미 올라가 있는지 먼저 확인할 것** — 아니면 통과처럼 보이는 무효 검증이 된다.

    **덮이지 않은 것 하나**: 괄호의 *"한 target의 실패가 전체를 막지 않는다"*는 **실패를
    만들어야 걸리는 주장인데 이번엔 전부 성공 경로였다.** 확인된 것은 "rewrite 뒤 같은
    날짜의 다른 묶음이 계속 올라간다"까지다. 실패 격리 자체는 여전히 미검증이다

않음"은 그 시점의 서술이니 그대로 읽지 말 것.

**바뀐 관계.** IndexedDB는 여전히 원본이지만 흐름이 더 이상 단방향이 아니다. 서버 행이 이
기기로 내려와 로컬 값과 합쳐지고, **무엇이 이기는지는 `src/engine/merge.ts`가 묶음마다
결정한다**(`sheet`·`grades`·`sprint`·`settings`). 그래서 "서버 행을 근거로 로컬을 고치지
말 것"이라는 1단계의 금지는 이제 유효하지 않다 — 대신 "병합 규칙을 `merge.ts` 밖에서
다시 쓰지 말 것"이 그 자리를 대신한다.

**들어간 것**

- `src/engine/merge.ts` — 병합 의미의 유일한 주인. 입력은 Day가 아니라 `Stamped<Day>`
  (값 + 묶음별 스탬프)다. `sprint`는 세션 단위 **합집합**(sid 물질화 — 잘라내지 않는다),
  `grades`는 **존재 우선**(채점을 지운 적 없는 로그에서 빈 채점이 이길 수 없다), `sheet`는
  LWW이되 **양쪽이 다른 문제지면 병합하지 않고 격리**한다. 교환·결합·멱등·왕복 네 속성을
  속성 기반 테스트로 고정했다
- `src/data/db.ts` DB v3 — `stamps` 스토어 신설. 업그레이드는 null로 시작하되 **아웃박스
  표식의 `bundleAt`으로 시딩**해 미푸시 변경이 첫 pull에 지지 않게 한다. 쓰기 경로가
  셋으로 갈렸다: `putDay`·`putMeta`(이 기기가 쓴다 — 병합 경유), `applyPulledDay`·
  `applyPulledMeta`(서버가 내려줬다 — 병합 경유, **아웃박스 표식 없음**),
  `adoptServerDay`(아빠가 배너에서 골랐다 — 병합 없이 그대로 앉힌다). 셋의 차이는 *누가
  결정했는가*다
- `src/data/sync.ts` — push가 **항상 병합 결과를 보낸다**(자동 `rewrite_sheet` 추론은
  삭제하고 「다시 만들기」의 명시적 의도 플래그로 바꿨다). pull 엔진은 키셋 페이징 커서 ·
  행 검증 · 격리 판정 · `generation` 재기준화를 담당한다. 오케스트레이션은 전부 여기 있고
  `db.ts`에 넣지 않았다
- 화면 — 부모 홈의 **격리 배너**(「이 기기 종이 유지」/「다른 기기 종이 채택」 두 버튼),
  pull 트리거 배선(부모 화면은 최대 3초 기다렸다 그리고, 아이 화면은 배경, 문제지 생성
  게이트는 최대 15초 기다린 뒤 실패하면 확인 다이얼로그)
- `supabase/schema.sql` — 묶음별 `*_by` 열, `meta.settings_at`·`settings_by`(+백필),
  `days_guard_version`·`meta_guard_stamp` 트리거, RPC 둘에 스탬프 인자 추가 + **옛
  오버로드 drop**, `days(updated_at)` 인덱스

**서버 스키마는 이미 운영에 적용됐다** — 사람이 2026-08-10 SQL Editor에서 적용하고 실측
확인했다(열·인덱스·트리거 둘·`settings_at` 백필·`pg_proc`에 새 시그니처 정확히 2개, 옛
오버로드 없음). 다른 환경에서는 **스키마 먼저, 앱 배포는 그다음**이다(설계 §7).

**운영 제약 — `PULL_PAGE`는 PostgREST의 max-rows보다 작아야 한다.** `sync.ts`의 페이징은
페이지 끝을 `rows.length < PULL_PAGE`로 판정한다. 서버가 500을 요청받고 **캡 때문에** 그보다
적게 주면 앱은 그것을 「마지막 페이지」로 읽는다. 그 절단이 `updated_at`이 전부 같은 구간
(= `replace_all`이 한 트랜잭션에 쓴 행들) 한가운데에 떨어지면 커서가 그 시각을 넘지 못해
**매 pull이 같은 앞부분만 영원히 다시 받는다.** 2026-08-10 확인: `pg_db_role_setting`에
`pgrst.db_max_rows` 오버라이드가 없다(Supabase 기본 1000 > 500). 이 값을 500 미만으로
내리려면 `PULL_PAGE`도 함께 내릴 것. 같은 조회에서 `anon`에 `statement_timeout=3s`가 걸려
있는 것도 확인됐다 — 한 페이지 질의가 3초를 넘기면 서버가 끊고 그 pull은 `failed`가 된다.

**최종 리뷰가 고친 것** — 14개 태스크가 각자 리뷰를 통과한 뒤 전체 브랜치 리뷰를 돌렸다.
Critical 0, 머지 전 수정 7건이 나왔고 **한 건도 단일 태스크 범위 안에서는 보이지 않는
것이었다**(커밋 `5f0b14a`). 가장 무거운 셋: ① `serverReplaceAll`이 서버 `generation`을
올리는데 로컬에 새 값을 아무도 쓰지 않아 **초기화·가져오기·되돌리기마다 100%** 기기가 자기
업로드에 대해 재기준화했다(성공 후 로컬을 `null`로 두어 다음 pull이 「초기값」 분기로 채택하게
고쳤고, 설계 §3에 *로컬 파괴 작업 뒤 `generation`의 주인*을 한 문장으로 명시했다).
② rewrite 사전 검사가 격리만 하고 플래그 소거·배너 전환을 빠뜨려, 아빠에게 **항상 실패하는
버튼**을 보여주고 그 날짜가 영영 동기화되지 않았다. ③ `DeviceState`의 read-modify-write
7곳이 await를 가로질렀는데 2A가 두 번째 동시 비행을 추가했다 — `updateDeviceState(fn)`
한 트랜잭션 원시연산으로 전부 교체했다.

**2A에 없는 것 — 2B가 알고 시작해야 할 사실**

- **`app_config` pull은 구현되지 않았다.** 설계 §4가 PIN을 2B로 두고, 값을 담을 지속 슬롯이
  `db.ts`의 `DeviceState`뿐인데 그 확장은 2A 범위 밖이었다(메모리 캐시는 §4의 오프라인
  요구를 못 지킨다). 그런데 설계 :55는 2B의 선행조건을 "2A의 `app_config` pull"로 적어
  뒀다 — **2B는 `db.ts` 슬롯 하나 + pull 블록 하나를 자기 예산에 넣고 시작해야 한다.**
  이미 있다고 전제하면 첫날에 막힌다
- 2C(초대 기반 기기 등록)·2D(PC·폰 화면)는 그대로 남아 있다. **2C는 반드시 2A 앱 배포
  뒤**다(설계 §7 — 혼재 기간에 기기가 늘지 않아야 한다)
- 채점 화면 PIN도 2B다. 지금도 잠금은 없고, 아이/부모 소속 규칙이 유일한 방어선이다

**감수한 것** (설계 「감수한 것」절에 더해, 실행 중에 확정된 셋)

- **`getStamps('meta')`가 업그레이드된 기기 전부에서 null이다.** v1의 meta 아웃박스 표식은
  `bundleAt`이 `{}`라 시딩할 값 자체가 없다. 미푸시 설정 변경이 보호되지 않는다는 뜻이지만
  설정 편집 UI가 없어 실해가 없다
- **검증에 실패한 day 행은 재기준화 교체에서 통째로 빠진다.** 설계 §3의 replace 의미대로다
  (못 믿을 행을 심는 것보다 빼는 편이 낫다). 지금까지 이 사실은 코드 주석에만 있었다
- **혼재 기간**: `meta_guard_stamp`가 이미 서버에 살아 있으므로, 아직 2A가 배포되지 않은
  v1 앱에서 진짜 설정 변경이 일어나면 `meta_stamp_stale`로 거절된다. **잃는 것이 아니라
  늦는 것이다** — 아웃박스 표식이 남아 재시도되고 2A 배포와 함께 올라간다

**일부러 안 고치고 넘긴 것** (13개 태스크 리뷰가 Minor로 분류한 것들. 데이터 손실·죽은
화면으로 이어지지 않는다고 판단했다)

- **병합 엔진** — `serializeValue`가 NaN과 null을 똑같이 `'null'`로 찍는다(현재 타입에서는
  도달 불가). `mergeSprint([], undefined)`가 호출자의 배열을 그대로 돌려줘 `sprint` 키가
  없던 Day에 `sprint: []`가 붙을 수 있다. **`SprintAttempt`를 만들 때 `sid: undefined`를
  명시하지 말 것** — 명시된 undefined는 JSON 왕복본과 다른 해시를 내 한 세션이 둘로 갈린다.
  기형 sid(`'A:'`·`''`)가 정상 그룹으로 분류된다(전순서 자체는 유지). 병합 출력이 입력
  객체를 alias한다 — 엔진이 순수한 동안은 무해하나 호출자가 변형하면 입력이 오염된다
- **`db.ts`** — 업그레이드의 `oldVersion < 3` 가드는 불가능한 조건을 조용한 skip으로 만든다
  — 던지는 편이 낫다. `generation: 0`이 `??`를 타고 살아남는 것을 못박는 테스트가 없다
  (`putDay(day, [])`·`putMeta(meta, [])`의 빈 선언은 최종 리뷰에서 throw로 막았다)
- **push** — 서버가 만든 스탬프의 마이크로초가 ms로 잘려 되돌아가므로 갱신마다 1ms 미만씩
  과거로 흐른다(파싱 불가 문자열은 null이 되어 모든 LWW에 진다). 격리된 날짜가 하나라도
  있으면 `kickPush`의 확인 패스가 **모든** target에서 억제된다. "서버 스키마가 더 새로움" ·
  "행 검증 실패" 분기가 조용하다 — 설계 :416-422는 거절된 행을 부모 홈 경고로 띄우라고
  하는데 pull 쪽만 배선됐다. `pushMeta`의 `rev` 폴백이 0이라 행이 없을 때 아무것도 맞지
  않는 PATCH를 3회 돌고 던진다(`pushDay`는 같은 자리가 하드닝돼 있다 — **최종 리뷰가 볼
  항목**). 평범한 경로로 해소된 「다시 만들기」는 `write_log`에 `sheet-rewrite`가 아니라
  `update`로 남아 재작성 이력이 끊긴다
- **`sheetConflict`의 비교가 서버 `jsonb`의 `is distinct from`과 완전히 같지는 않다** —
  `serializeValue`가 own key 없는 객체를 전부 `{}`로 접고, 17자리를 넘는 수에서 IEEE-754
  손실을 물려받는다. 어긋나면 PATCH가 서버 트리거에 막혀 그 날짜가 격리된다(조용한 손실이
  아니라 아빠에게 보이는 배너)이라 넘겼지만, **두 판정이 항상 같다고 전제하는 코드를 새로
  쓰지 말 것**
- **pull** — 손상된 `date` 열이 500행 경계에 정확히 걸리면 페이징이 깨진다(이미 오염된 서버
  데이터 + 정확한 경계 + 재기준화 진행 중이 동시에 필요하다). 그렇게 페이징이 멈추면
  `runRebase`가 매 비행 끝마다 `rebaseNeeded`를 다시 세워 meta GET + 최대 40페이지 GET을
  **백오프 없이** 영원히 반복한다(`fetchServerState`가 포기한 채로 `replaceFromServer`를
  돌리는 문제 자체는 최종 리뷰에서 `null` 반환으로 막았다). 첫 pull에서 레거시 행이
  `changed`를 두 번 보고한다 — 3번째 패스에 수렴하므로 **병합 결함으로 오진하지 말 것**
- **격리·배너** — pull이 거절한 행이 `'알 수 없는 날짜'`
  자리표시자 키로 들어가면 **영영 지워지지 않는다** — 모든 해제가 진짜 날짜 키로 돌기
  때문에 새로고침 전까지 경고가 남는다. 서버 행이 사라진 사이 INSERT 경로로 넘어가면 격리가
  안 풀린다. 배너가 `configured()`와 무관하게 그려져, 미설정 기기가 낡은 목록을 들고 있으면
  두 버튼이 던진다. 「채택」이 서버 채점 때문에 거절된 사실은 지속되지 않아 재렌더 후 다시
  눌러 봐야 안다
- **화면·트리거** — 확인 다이얼로그가 이미 떠난 화면 위에 열릴 수 있다(다음 `hashchange`
  에만 자진 취소한다). 생성 게이트의 「취소」가 붙어 있지 않아, 다음 pull이 무언가를 바꾸면
  묻지 않고 만든다. pull이 적용되면 `#/report`가 재렌더돼 보고 있던 지난달이 사라진다.
  `route()`가 자기 자신과 겹쳐 돌 수 있다(마지막이 이기고, 부작용이 있는 `#/print`만 게이트로
  직렬화돼 있다)
- **`schema.sql`** — meta 가드는 "얼어붙은 스탬프"를 막지만 **뒤로 가는 스탬프는
  통과시킨다**(주석이 그보다 세게 주장한다). `p_settings_at`·`p_sheet_at`에 명시적 null을
  보내면 서버 스탬프가 지워진다 — SQL default는 인자를 **생략**했을 때만 걸리기 때문이다
  (클라이언트는 null을 보내지 않도록 고쳐져 있다. RPC를 새로 부를 때 확인할 것)

**사람이 실기기로 확인할 것** — 화면·네트워크 테스트가 없어 코드로는 확인되지 않는다.

1. `sync-config.ts`를 비운 빌드에서 화면 다섯 개를 돌아 전이가 오늘과 같은지, `fetch`
   스파이에 요청이 0건인지(부모 화면에 3초 지연이 없고 「확인 중」이 안 뜨는지가 신호다.
   단, PIN을 캐시한 기기는 예외다 — `#/grade`·`#/report`에서 게이트 다이얼로그를 보는
   것이 정상이고, 그래도 판정 기준은 그대로 fetch 0건이다: PIN 게이트는 로컬 캐시만
   보고 네트워크를 안 부른다는 것이 2B 스펙 §4의 명시된 부작용이다)
2. 아이패드 두 대로 같은 날 문제지를 각각 만들고, 두 번째 기기의 「문제지 인쇄」가 새 문항을
   만들지 않고 첫 기기의 종이를 보여주는지 — 그다음 격리 배너의 두 버튼을 각각 끝까지
3. 비행기 모드에서 「문제지 인쇄」 → 경고 다이얼로그 → 취소하면 아무것도 안 만들어지는지,
   확인하면 만든 뒤 온라인 복귀 시 격리 배너로 이어지는지
4. 부모 화면 진입의 3초 대기가 실기기에서 "탭이 안 먹었다"로 느껴지는지(느리면 대기를
   줄이거나 즉시 그리고 갱신하는 쪽으로 — 후자는 설계 변경이다)
5. 두 기기가 같은 날 각자 스프린트 → 양쪽 모두에 두 세션이 다 남는지(sid 합집합)
6. 스프린트·채점 중 탭 전환(`visibilitychange`가 pull을 찬다) → 화면·입력이 유지되는지

**키 붙여넣기 경로가 사라졌다**(사용자 결정 2026-08-13, 계획이 스펙에 더한 결정 1번). 스펙
§5의 목적("평문 키를 사람이 만지지 않는다")이 붙여넣기 UI가 남아 있으면 안 닫힌다는
판단이다. 첫 기기와 전 기기 폐기 복구는 SQL Editor에서 아는 코드의 해시를 `invites`에
직접 insert하는 한 줄로 해결된다(스펙 :541이 이미 이 길을 열어 뒀다) — 나머지는 전부 화면의
코드 입력으로 간다. **계획이 더한 결정 2번**: 코드·키 난수는 `gen_random_bytes`다(Postgres
`random()`은 암호학적 난수가 아니다, pgcrypto는 이미 로드돼 있어 비용이 없다).

**`claim_invite`의 사용자 수준 실패(코드 불일치·만료·5회 초과·경쟁 패배)는 `raise
exception`이 아니라 jsonb `{error: ...}` 반환이다.** `raise exception`은 트랜잭션을 통째로
되돌려 `fail_count`++까지 지운다 — 그러면 5회 만료(무차별 대입 방어)가 영영 안 걸린다.
컨테이너 시나리오 4번(틀린 코드 5번 → `fail_count` 5·`expires_at` 과거, 6번째는 정답이어도
거부)이 이 계약의 변이 검증이다. **이 계약을 예외로 되돌리지 말 것** — 서버 쪽 실패 분기를
고칠 일이 생기면 먼저 이 문단을 볼 것.

**리뷰가 잡은 Critical 하나**(커밋 `16a67c9`): `if inv.code_hash <> crypt(p_code,
inv.code_hash)`가 `p_code = null`에서 우회됐다. `crypt()`는 strict라 `crypt(null, hash)`가
null이고, `text <> null`도 null이며, plpgsql의 `if`는 null을 false로 다뤄 오답 분기를
건너뛰고 그대로 성공 경로로 떨어진다 — `claim_invite(null, 'attacker-device', ...)`가 코드
검증 없이 키를 내주는 원격 탈취 구멍이었다(anon 키는 공개돼 있고 `claim_invite`는 익명
호출이라 누구나 시도할 수 있었다). 컨테이너 실측: 수정 전은 키 반환 + `devices` 행 생성
(`fail_count` 0 그대로), 수정 후(`is distinct from`)는 `{"error": "코드가 맞지 않아요"}` +
`fail_count` 증가 + `devices` 행 없음. **일반형이 다음 사람에게 남을 교훈이다** — SQL의
3값 논리(null이 섞이면 비교가 unknown이 된다)와 plpgsql의 `if`(unknown을 false로 접는다)가
겹치면, "다르면 거부"라고 쓴 조건이 "null이면 통과"로 뒤집힌다. `<>`로 null과 비교하는
자리가 있으면 `is distinct from`인지부터 의심할 것.

**「서버 쓰기 경로 감사」 절 갱신** — 아래 절 참고. 판정은 **2C는 `pushMeta`를 깨우지
않는다**이고, `issue_invite`·`claim_invite` 두 행을 감사 표에 추가했다.

    **→ `extensions`.** 리뷰의 경고가 사실이었다 — 흔히 쓰는 `public, pg_temp`로 고정했으면

    `security definer` 여섯 전부에 `set search_path = public, extensions, pg_temp`를 넣었다
    (`f95ae3f`). 자세한 것은 `supabase/schema.sql`의 그 주석 블록에 있다.
    **운영에 적용 완료(2026-08-13)** — 사람이 SQL Editor에서 스키마를 재적용하고
    `pg_proc`으로 확인했다: 여섯 전부 `proconfig = {search_path=public, extensions,
pg_temp}`. **2026-08-13에 `list_devices`·`remove_device`가 더해져 여덟이 됐다** —
    아래 쿼리 목록에도 넣었다. 빠뜨리면 「RLS의 뿌리」라 부른 이 감사에서 새 익명 RPC가
    조용히 제외된다. 이 감사를 다시 돌릴 때 쓸 쿼리다:

    ```sql
    select proname, proconfig from pg_proc
    where proname in ('haruchi_device','issue_invite','claim_invite',
                      'replace_all','rewrite_sheet','haruchi_log',
                      'list_devices','remove_device');
    ```

    **이 확인이 예상 밖의 것을 하나 더 드러냈다.** 고정 전에는 이 함수들이 **호출자의
    `search_path`에 얹혀** 돌고 있었다 — 운영과 같은 배치(pgcrypto를 `extensions`에)로
    컨테이너를 세워 재현하니, 호출자 경로에서 그 스키마를 빼는 순간 `claim_invite`가
    `function crypt(text, text) does not exist`로 죽는다. 운영이 멀쩡했던 것은 Supabase가
    PostgREST에 `db_extra_search_path`를 넣어 두기 때문이다. **즉 우리 서버 규칙의 동작이
    우리가 소유하지 않은 설정 한 줄에 매달려 있었다** — 2C가 만든 문제가 아니라 1단계부터
    있던 것이고, 익명 RPC가 생기면서 들여다본 김에 드러났다

**시딩 순서 — `claimInvite`는 pull보다 먼저 `seedOutbox()`를 부른다(`6f11b9c`). 이 항목은 2026-08-13 로테이션 실측으로 닫혔다**(아래 「기기 상한」절 사람 확인 3번 — 재연결 뒤 서버 쓰기 0 + 아웃박스 0). 최종
리뷰가 잡은 이음새다. `seedOutbox`는 그 시점 `days`에 있는 것 **전부**에 표식을 만드는데,
pull이 먼저 돌면 방금 내려온 서버 날짜까지 「이 기기가 올릴 것」이 된다 — 두 번째 기기를
붙이는 순간 서버의 1년치가 아웃박스로 들어가 부모 홈이 「안 올라간 기록 401건」을 띄우고,
push가 날짜마다 GET+PATCH를 돌려 **내용이 그대로인 행의 `updated_at`을 전부 갱신한다.**
그러면 다른 기기들이 다음 pull에서 그 전부를 다시 내려받는다(데이터 손실은 없다 — 병합이
멱등이고 `days_guard_sheet`도 sheet가 같아 안 걸린다. 비용과 오해가 문제다).
**단일 태스크 안에서는 보이지 않는 종류다**: Task 2가 순서를 바꿨고 그 순서가 `db.ts`의
시딩 범위를 바꿨는데, 두 파일 어느 쪽을 봐도 드러나지 않는다.

**2A가 "2B가 알고 시작해야 할 사실"로 남긴 목록의 2C 항목이 이제 완료됐다** — 위 「동기화
2A」절의 "2A에 없는 것" 목록의 "2C(초대 기반 기기 등록)·2D(PC·폰 화면)는 그대로 남아 있다"는
그 시점의 기록이라 고치지 않는다. **2C는 이 절이 채웠다. 2D는 아래 절이 채웠다.**

## 동기화 2D — PC·폰 화면 (2026-08-13)

설계 §6이 "점검 기준과 제약만 확정 — 구체 수정은 2A 배포 후 실기기로 써 본 뒤"로 미뤄 둔
것이다. 2C까지 배포되고 기기가 둘이 된 지금 그 점검을 돌렸다.

**결론부터: 스펙이 세운 기준 다섯 중 셋은 이미 통과하고 있었다.** SEED 도입(2026-08-05)이
`#app` 최대 폭 사다리(560 / 720@768 / 840@1280)를 깔았고 `.mark`가 52×52px이며 우리 CSS에
`:hover` 규칙이 **하나도 없다**. 그래서 2D는 새 화면 작업이 아니라 **실측 두 건과 수정 두
줄**로 끝났다. 다음에 비슷한 「대응」 항목을 만나면 **먼저 재 볼 것** — 이미 되어 있을 수 있다.

**점검 방법 — 헤드리스 Chrome + CDP.** 브라우저 확장이 이 세션에 안 붙어 실기기 클릭
검증을 못 했다. 대신 `--headless=new --remote-debugging-port`로 띄우고 CDP로 잰다
(`Emulation.setDeviceMetricsOverride`로 폭을 바꾸고, `Page.printToPDF`로 페이지 수를 센다).
인쇄 3페이지 건(`5c1c893`)이 쓴 것과 같은 길이다. **`#/print`를 먼저 들르면 생성 게이트가
오늘 문제지를 만들어 주므로**(`print-sheet.ts`) 빈 IndexedDB에서도 실제 14문항으로 잴 수 있다.

| 스펙 §6 기준                           | 결과                                           |
| -------------------------------------- | ---------------------------------------------- |
| 폰 360px 부모 화면 넷 가로 스크롤 없음 | ❌ → ✅ `#/print`가 398 > 360으로 넘쳤다(아래) |
| 채점 O/X 44×44px 이상                  | ✅ 52×52 (SEED `size_large` = x13)             |
| PC 1280px+ 콘텐츠 최대 폭              | ✅ 840px (`#app` 사다리, 설계 §8.1)            |
| hover 전용 상호작용 금지               | ✅ 우리 CSS에 `:hover` 0건                     |
| PC 인쇄 A4 2페이지                     | ✅ 실측 2페이지 (1280·768·360px 전부)          |

**고친 것 하나 — 폰에서 문제지 미리보기가 가로로 넘쳤다**(`2542c14`·`7306cd2`). `.vgrid`의 두
열이 각각 min-content 153px 아래로 못 줄고 gap 40을 더해 **346px를 요구**하는데, 360px 폰에서
시트 안쪽에 남는 폭은 256px다 — 90px가 모자라 문서 전체가 밀렸다. 좁은 화면(`width < 480px`)
에서만 `.vgrid`·`.strat-zone`을 한 열로 접는다. **`@media screen` 한정이 이 규칙의 핵심이다**
— 종이의 2단은 세로 예산이 빡빡해 한 열로 접으면 곧장 3페이지가 되는데(`5c1c893`), `screen`이면
인쇄에 안 걸리므로 **폰에서 공유 → 프린트로 뽑을 때도** 종이는 2단이다(실측 확인).

**이 수정이 두 번 걸린 이유를 남긴다 — 측정이 못 보고 스크린샷이 봤다.** 처음에는 미디어
블록을 `.vgrid` 정의 바로 아래에 뒀는데, `.strat-zone` 정의가 파일 **뒤쪽**에 있어 특정도가
같은 그 규칙이 이겼다. 그런데 `.strat-zone`은 250 대 256으로 어차피 넘치지 않아 **가로 스크롤
측정은 통과했다** — 스크린샷에서 전략 존만 2단으로 남은 것을 보고서야 잡혔다. 지금은 블록이
파일 끝에 있고, **그 자리가 취향이 아니라 조건이라는 것**이 주석에 적혀 있다.

**고친 것 둘 — 부모 홈 하단 링크의 누르는 면적**(사용자 결정). 「EBS 강의」·「← 아이 화면」·
「새 기기 추가」가 25px이었다. 보이는 밑줄 글자는 그대로 두고 상자만 44px로 세웠다. 폰에서
「← 아이 화면」은 아빠가 아이에게 넘겨주는 길이다.

**일부러 안 고친 것**: 채점 화면의 기분 버튼(😀·😐·😫)이 높이 34px다. SEED
segmented-control 레시피의 높이라 덮으려면 레이어 밖에서 레시피를 건드려야 하는데, 이 레포가
한 번 데인 자리다(shorthand `font`로 그 컴포넌트가 죽었던 전례 — 「CSS 레이어 전략」).
스펙이 44×44를 요구한 대상은 O/X이고 그쪽은 통과한다. **바꾸기로 하면 개별 속성으로 좁게 쓸 것.**

**남은 사람 확인**: 실제 폰·아이패드로 부모 화면 넷을 열어 보기. 헤드리스 Chrome은 Safari가
아니다 — 특히 `@media screen and (width < 480px)`의 **범위 문법은 Safari 16.4+**이고, 이
파일들이 전제하는 하한은 `:has()`의 15.4다. `app.css`가 이미 `@media (width >= 768px)`로
같은 문법을 쓰고 있어 새로 생긴 위험은 아니지만, **아이패드가 16.3 이하라면 최대 폭 사다리도
함께 죽어 있다는 뜻**이므로 한 번은 확인할 값이 있다.

## 기기 상한 5대와 관리 화면 (2026-08-13)

설계 `specs/2026-08-13-device-cap-manage-design.md` — **적대적 리뷰 3라운드 합의본**
(1R: Critical 3·Important 12, 2R: Critical 3·Important 5, 3R: 합의·Critical 0). 등록
기기를 활성 5대로 제한하고, 목록·해제를 앱 안의 새 화면(`#/manage`)이 담당한다 —
**SQL 없이 5대 로테이션이 완결된다.**

**서버(RPC 4개).** `issue_invite`가 jsonb로 바뀌었고(미등록도 `{error}` — raise면
PostgREST 오류 본문이 화면까지 흘러가는 2C의 사마귀가 재현된다), `claim_invite`에
advisory lock + 상한이 붙었으며, `list_devices`·`remove_device`가 신설됐다.
`security definer`가 여섯에서 **여덟**이 됐다(search_path 재감사 쿼리도 함께 갱신 —
위 「서버 쓰기 경로 감사」).

**상한 검사의 위치가 계약이다** — 코드 검증 **뒤**(코드를 맞혀야 상한이 보인다: 익명
폴링으로 「가족이 가득 찼나」를 볼 수 없다) · `used_at` 마킹 **앞**(초대가 소모되지
않아 한 대 해제한 뒤 **같은 코드로** 재시도가 통한다). 변이로 확인했다: 마킹 뒤로
내리면 「해제 후 같은 코드 재시도」가 「유효한 초대가 없어요」로 죽는다.

**측정이 설계 서술 하나를 뒤집었다 — 이게 이 작업에서 가장 값진 발견이다.** 스펙 §1은
동시 claim이 6대를 못 만드는 이유를 「성공하는 claim들이 같은 최신 초대 행을 다투므로
행 락이 직렬화한다」로 적었다. **성립하지 않는다.** `LockRows`가 `Limit` **아래**에
있어, EPQ로 밀린 세션은 최신 초대를 포기하고 **그다음(옛) 초대로 흘러내린다.** 통제
실험(활성 초대 2개 + 2대, 상한 압력 없음): 두 세션이 **둘 다 성공**해 초대 둘이 모두
소모되고 4대가 됐다. 즉 2C 설계가 「옛 초대를 청구 불가로 만든다」고 부른 보증은
동시 상황에서 없다. **상한 5의 실보증은 전적으로 advisory lock + 카운트다** — 적대적
리뷰 1라운드가 "그 보장은 초대 선택 코드에 우연히 걸려 있다"며 락을 넣게 한 판단이
실측으로 옳았음이 증명됐다(락이 없었다면 이 실험이 6대를 냈을 것이다).

**동시성 변이 삼분할**(remove↔remove 상호 삭제, psql 두 세션):

| 변이               | 결과                         | 뜻                               |
| ------------------ | ---------------------------- | -------------------------------- |
| advisory lock 제거 | 둘 다 커밋 → **활성 0대**    | 락은 대체 불가                   |
| 자기 재확인 제거   | 사후 카운트가 잡는다(활성 1) | 6·8단계는 서로 독립적으로        |
| 사후 카운트 제거   | 자기 재확인이 잡는다(활성 1) | 충분하다 — 한 변이로는 못 가린다 |

**§6 무변경 push 생략 — 이 설계의 급소다.** 로테이션의 정상 경로(해제 → 다시 연결 →
재claim)에서 `seedOutbox`가 가족 전체 기록에 표식을 만들고, 내용이 같은 행의
`updated_at`까지 갱신하면 다른 기기 전부가 다음 pull에서 전량을 다시 내려받는다 —
2C가 「시딩 순서」로 피했던 폭풍이 **이 설계의 표준 흐름에서는 매 로테이션마다**
돌아온다. 해소는 「보낼 것이 서버와 같으면 PATCH를 안 보낸다」이고, 세 조건이 각각
계약이다(2라운드 리뷰가 각각의 위반을 Critical로 실증):

1. **비교 대상은 「보낼 것」이다** — 값은 `withoutEmptyBundles(merged.value)`,
   스탬프는 `sendStamps(merged, deviceId, now)`. `merged.at`끼리 비교하면 1단계
   업로드(2026-08-07)가 남긴 **스탬프 all-null 행의 보정이 영원히 멈추고** 그 묶음이
   이후 모든 LWW에서 진다. 좌변을 생으로 두면 `grades: {}`·`sprint: []`가 실린 날짜가
   영원히 「다름」이 되어 매 로테이션마다 다시 올라간다
2. **판정 위치는 격리 판정 뒤·PATCH 직전** — 앞이면 로컬·서버 sheet가 다른데 병합이
   서버를 택한 날이 배너 없이 생략되어 아이 손의 종이가 동기화에서 사라진다
3. **생략은 「PATCH만 건너뛴 성공」** — `rewrite`의 `clearQuarantine`을 지난다

판정은 `skipUnchangedPush`로 export하고 **`src/data/sync.test.ts`를 신설**해 회귀를
걸었다(테스트가 `engine/`에만 있다는 것은 이미 사실이 아니다 — `db.test.ts`·`ui.test.ts`
선례). 변이 둘이 각각 자기 테스트 **하나만** 죽인다.

**효과는 두 번째 로테이션부터 완전하다.** 첫 로테이션은 pre-2A 행의 sid·null 스탬프를
서버에 앉히는 **일회성 수렴 PATCH**를 낸다 — 정당한 쓰기다.

**클라이언트.** `#/manage` 신설(리포트의 데이터 관리 절 전체 이동 + 「연결된 기기」),
`issueInvite` 유니온화(+옛 스키마 문자열 폴백), `claimInvite`에 `quarantine: []`(§5),
부모 홈의 「다시 연결하기」. 게이트·소속은 `main.ts` **세 곳**(`GATED_HASHES`·
`PARENT_HASHES`·**route 분기**) — 목록 둘만 고치면 어느 `startsWith`에도 안 걸려
게이트 통과 뒤 `else`의 **아이 홈**이 그려진다.

**이동이 「도우미」보다 넓다.** 모듈 스코프 진행 플래그 `importBusy`·`resetBusy`와 그
동기화 함수들이 한 파일에 함께 있어야 한다(함수 스코프였을 때 재렌더마다 false로 열려
진행 중 가져오기 위에 활성 버튼이 다시 그려진 사고 이력 — 주석까지 함께 옮겼다).
`#/manage`는 게이트 대상이라 **wake 재게이트의 `route(false)` 재렌더를 리포트보다 자주
탄다.**

**`ui.ts` 재진입 항목이 처음으로 깨어났다.** 「어떤 화면이 자기 해시로 `navigate`하게
되면 다시 볼 것」(아래 「Phase 2 최종 리뷰가 남긴 잔여」)의 조건을, 기기 해제 성공 후의
`navigate('#/manage')`가 처음 밟는다. **확인 결과 안전하다**: `route()`가 `#app`을
`replaceChildren`으로 갈아 끼우고 상태를 다시 읽으며, `gateUnlocked()`가 포그라운드
세션 플래그라 PIN을 다시 묻지 않는다. 비용은 `PARENT_HASHES`의 `pullAndWait` 최대
3초뿐이다.

**`navigate` 감사에서 스펙과 숫자가 갈렸다.** 스펙 §3은 검사 대상을 「넷」이라 셌는데

## `replace_all`이 실사용 첫날 죽어 있었다 (2026-08-12)

되돌리기를 눌렀더니 **「로컬은 되돌렸지만 서버 반영에 실패했어요」**가 떴다. 원인은
`replace_all`의 `delete from days` 한 줄이고, **이 RPC는 배포 이후 단 한 번도 성공한 적이
없다** — 가져오기·초기화·되돌리기 셋이 전부 같은 자리에서 죽는다.

**근본 원인.** Supabase는 `authenticator` 역할에 `session_preload_libraries=supautils,
safeupdate`를 걸어 둔다(실측: `pg_roles.rolconfig`). safeupdate는 WHERE 없는 UPDATE·DELETE를
실행기 훅에서 거부한다 — `delete from days`가 SQLSTATE 21000 `DELETE requires a WHERE
clause`로 죽고 PostgREST가 400으로 내보낸다. **`security definer`는 면제가 아니다**: 그것은
권한 검사이고 훅은 세션에 걸리므로, 함수가 소유자(`postgres`) 권한으로 돌아도 세션 사용자가
`authenticator`인 한 그대로 산다.

**왜 검증을 통과했나 — 이게 진짜 교훈이다.** 스키마는 "throwaway Postgres에 3회 연속 적용"
으로 검증됐고(위 1단계 절), SQL Editor에서도 멀쩡히 돌았다. **둘 다 safeupdate 프리로드가
없다** — 맨 컨테이너에는 확장이 없고 SQL Editor는 `postgres` 역할이다. 밟는 경로는
`authenticator`로 들어오는 진짜 PostgREST 호출뿐이다. 즉 **검증한 것은 적용 가능성이지
실행 가능성이 아니었다.** Phase 1의 실패 패턴 7번("테스트가 자기가 검사한다고 주장하는 것을
실제로는 검사하지 못한다")의 인프라판이다. **RPC를 새로 쓸 때는 반드시 `authenticator`
경로로 한 번 태울 것.**

그리고 그 확인은 이미 목록에 있었다 — 1단계 「사람이 확인할 것」 6번이 *"초기화: … 서버
`days`가 비워지는지 · `snapshots`에 2건(사전 + `replace_all`의 auto)이 남는지"*를 지목한다.
**그 항목을 돌렸으면 첫날 잡혔다.** 미확인 항목이 쌓이면 그중 무엇이 결함을 덮고 있는지
알 수 없다는 실물 사례다. **고친 직후 그 6번을 실제로 돌려 전부 통과시켰다**(위 1단계
목록 6번에 실측값). 순서가 거꾸로였을 뿐, 결국 그 체크리스트가 옳았다.

**추적을 가능하게 한 두 증거**(다음에 같은 종류를 볼 때 쓸 것)

- **`snapshots.id`의 구멍.** 1·2·4·6·8만 있고 3·5·7이 없었다. `bigserial`은 롤백해도
  되감기지 않으므로, 구멍은 **시퀀스를 소비하고 롤백된 트랜잭션**의 흔적이다. `replace_all`의
  첫 쓰기가 auto 스냅샷 insert라, 구멍이 있다는 것은 **본문이 거기까지는 갔고 그 뒤에서
  죽었다**는 뜻이다 — 이것만으로 `unauthorized`(본문 첫 줄)와 PostgREST 계층 실패(호출 전)가
  배제됐다. **실패한 트랜잭션이 어디까지 갔는지를 기록하는 비의도적 계측기다**
- **Postgres 로그(`postgres_logs`), 엣지 로그가 아니다.** `edge_logs`는 상태 코드만 중계하고
  `logs: []`·`headers: {}`라 예외가 없다. raise 문구·`sql_state_code`·`context`(문장과 PL/pgSQL
  줄 번호)는 `postgres_logs`에만 있다

**고친 것 둘**

- `supabase/schema.sql` — `delete from days` → **`truncate days`**. safeupdate는 UPDATE·DELETE만
  보므로 유틸리티 문인 truncate는 훅을 안 탄다. **`where true`로 우회하지 말 것**(상수 폴딩으로
  qual이 사라져 여전히 "WHERE 없음"으로 읽힌다), `where date is not null`도 PG17이 NOT NULL
  제약으로 중복 제거할 수 있어 버전 의존이다. 동작은 같다 — `days`에 DELETE 트리거가 없고
  (`days_log`는 insert·update 전용) Postgres의 truncate는 트랜잭션 안에서 롤백된다.
  **다른 점 하나: ACCESS EXCLUSIVE 락을 잡는다**(delete는 ROW EXCLUSIVE라 SELECT와 안 부딪힌다)
  — 다른 기기의 pull과 겹치면 `authenticator`의 `lock_timeout=8s`에 걸릴 수 있고, 걸려도 통째
  롤백이라 손실은 없다
- `src/data/sync.ts` — `failed(label, res)`를 새로 두고 **4xx·5xx 본문을 에러 상세에 싣는다**
  (13곳 전부 교체, 300자 컷). 이 조사가 필요했던 이유가 정확히 이것이다: 서버는
  `DELETE requires a WHERE clause`라고 문장으로 말해 줬는데 `throw new Error(\`… 실패:
  ${res.status}\`)`가 그걸 버려, **서버가 이미 진단한 실패가 클라이언트에서 진단 불가능한
실패로 강등됐다.** 상태 코드만 남기는 에러를 새로 만들지 말 것.
**테스트는 없다** — `src/data/sync.ts`에는 테스트 파일 자체가 없고(`db.test.ts`만 있다)
  네트워크 하네스를 새로 만들지 않았다

**남은 것.** 서버 `statement_timeout`은 역할마다 다르다(실측: `anon` 3s — 1단계 절, `authenticator`·
`authenticated` 8s). `replace_all`은 **단일 문장**이라 기록이 커지면 여기 먼저 부딪힌다. 지금은
4일치라 무관하다.

**이 검증이 문구 하나도 드러냈다**(2026-08-13에 고침). 초기화 직후 되돌리기를 누르면 로컬이
비어 있어 사전 백업에 담을 것이 없고, 확인 다이얼로그가 **「방금 서버에 0일치 백업을
만들었어요」**라고 말했다. 사실은 맞지만 *안심시키려고 있는 자리*에서 0은 오히려 놀랍다.
`report.ts`의 `snapshotNotice(n)`가 세 흐름(가져오기·초기화·되돌리기)의 이 줄을 소유하고,
0일 때만 **왜 0인지**를 말한다(「지금 이 기기에 기록이 없어 백업할 것이 없었어요」). 초기화는
버튼이 0일에 안 그려져 0에 닿지 않지만 같은 함수를 쓴다 — 세 자리가 갈리면 어느 하나만 낡는다.

## 서버 쓰기 경로 감사 — 무엇이 실제로 실행됐나 (2026-08-12)

`replace_all`이 "배포됐지만 한 번도 안 돌았다"는 것이 드러난 직후, **나머지 서버 쓰기
경로도 같은 상태인지** 전수 확인했다. 결론은 둘이 남았다는 것이고, 그중 하나는 **트리거할
코드가 앱에 아예 없다.**

| 쓰기 경로                                    | 실행 확인                                |
| -------------------------------------------- | ---------------------------------------- |
| `POST /rpc/replace_all`                      | ✅ 3회(`generation = 3`과 교차 일치)     |
| `POST /rpc/rewrite_sheet`                    | ✅ 2회(2026-08-12 검증 1 + 그 이전 1)    |
| `POST /snapshots`                            | ✅ 다수                                  |
| `PATCH /days` 일반 갱신                      | ✅ `write_log`에 `update` 26건           |
| `POST /days` (INSERT)                        | ✅ 5회                                   |
| `PATCH /days` rewrite 후속 스탬프(`sync.ts`) | ❌ **미실행** — 조건이 안 섰다           |
| `PATCH /meta` (`pushMeta`)                   | ✅ **`meta.rev = 15`** — 실측(아래)      |
| `POST /rpc/issue_invite` (2C)                | ✅ 1회(`write_log` `invite-issue`)       |
| `POST /rpc/claim_invite` (2C)                | ✅ 1회(`write_log` `invite-claim`)       |
| `POST /rpc/remove_device` (기기 상한)        | ⏳ 배포 전 — `write_log` `device-remove` |

**`list_devices`는 이 표에 없다 — 읽기 전용이라서다.** 이 표의 단위는 「서버에 쓰는가」이고,
그 함수는 `select`만 한다(그래서 `write_log`에도 아무것도 안 남긴다). 새 RPC를 더할 때
이 표에 넣을지는 그 기준 하나로 판정한다.

**판정 방법을 남긴다 — `action='insert'`는 두 출처가 섞인다.** `days_log` 트리거가 클라이언트
`POST /days`와 `replace_all`의 `insert into days` 양쪽에서 똑같이 `'insert'`를 남기기 때문이다.
**구별자는 `at`이다**: RPC의 재삽입은 한 트랜잭션이라 타임스탬프가 마이크로초까지 동일한
뭉치로 나오고, 클라이언트 INSERT는 서로 다른 시각의 낱개다. 실측에서 12건이 낱개 5 + 뭉치
3 + 뭉치 4로 정확히 갈렸다.

```sql
-- 이 감사를 다시 돌릴 때
select action, count(*) from write_log group by action order by 2 desc;
select at, target from write_log where action = 'insert' order by id;  -- 낱개 vs 뭉치
```

**~~`pushMeta`는 프로덕션에서 절대 실행되지 않는다~~ — 이 결론은 틀렸다(2C 최종 리뷰가
정정, 2026-08-13).** 원래 근거 셋 중 둘은 참이다:

1. 앱 안의 `putMeta` 호출은 `screens/report.ts` 두 곳뿐이고 **둘 다 `['export']`** — 참
2. `'export'`는 계약상 스탬프도 아웃박스 표식도 남기지 않는다(CLAUDE.md — `lastExportedAt`은
   기기 로컬 사실이라 동기화 대상이 아니다) — 참
3. ~~`seedOutbox`가 여는 스토어는 `days`·`outbox`·`device`뿐이다 — meta target을 시딩하지
   않는다~~ — **여는 스토어는 맞지만 결론이 거짓이다.** meta 아웃박스 *항목*을 만드는 데
   meta *스토어*는 필요 없다. `db.ts`의 `seedOutbox`가 days 커서를 다 훑은 뒤
   `outboxStore.add({ target: 'meta', bundleAt: {}, at })`을 무조건 더한다(주석까지 달려
   있다 — "meta는 항상 올린다"). **레포 안의 기존 테스트가 이것을 단언한다**:
   `db.test.ts`의 `expect(await seedOutbox()).toBe(3) // 이틀 + meta`

`pushOutbox`는 `entry.target === 'meta'`를 `pushMeta()`로 보내므로, **`pushMeta`는 기기가
등록된 뒤 첫 push에서 실행된다** — 즉 아이패드에서 2026-08-07에 이미 돌았을 가능성이 높다.

**왜 실측 감사가 이걸 놓쳤나 — 근거가 `write_log`였는데 `meta`에는 로그 트리거가 없다.**
`haruchi_log`를 거는 `create or replace trigger days_log`는 `days`에만 붙어 있다(`schema.sql`).
그래서 `PATCH /meta`는 성공해도 `write_log`에 한 줄도 남기지 않는다. **증거가 없는 것을
증거의 부재로 읽은 것이다** — 이 표를 다시 셀 때 반드시 각 경로의 *관측 수단*이 실재하는지
먼저 확인할 것. 이 감사가 남긴 진짜 교훈은 「적용 가능성 ≠ 실행 가능성」에 더해
**「로그에 없음 ≠ 실행되지 않음」**이다.

**실측으로 닫혔다(2026-08-13): `select rev, device from meta where id = 1` → `rev = 15`,
`device = '59a58aa5'`.** 스키마 seed는 `rev 0`·`device 'schema'`로 넣으므로, 15번의 개정과
8자리 기기 id는 전부 `pushMeta`가 쓴 것이다(`replace_all`은 `meta.rev`를 이렇게 누적시키지
않는다). **「절대 실행되지 않는다」는 정반대였고, 실제로는 이 앱에서 가장 조용히 자주 도는
쓰기 경로 중 하나였다.**

**판정(2C, 2026-08-13): 2C는 `pushMeta`를 「깨우지」 않는다 — 이미 깨어 있었기 때문이다.**
기기 라벨은 위 문단이 유력한 후보로 짚었던 그 값이지만, 실제로는 `claim_invite`의
인자(`p_label`)로 서버 `devices.label`에 직접 앉는다 — 클라이언트 `Settings`를 거치지 않는다.
`src/screens/home-parent.ts`의 `#device-label` 입력값은 `claimInvite(code, label)` 호출로 바로
RPC 인자가 되고, `putMeta` 호출은 하나도 늘지 않았다. 즉 **2C가 새 meta 쓰기 경로를 만들지는
않았다**는 판정은 유효하다. 다만 원래 걱정의 대상이던 *"`pushMeta`의 `rev` 폴백이 0이라 행이
없을 때 아무것도 맞지 않는 PATCH를 3회 돌고 던진다"*는 도달 불가 코드가 아니라 **이미 도는
코드 안의 결함**이다. 지금까지 터지지 않은 이유는 서버 `meta` 행이 스키마의 seed insert로
항상 존재해 폴백이 쓰이지 않기 때문이다 — 그 행이 없는 환경(새 프로젝트에 스키마를 반만
적용한 경우)에서만 드러난다.

**2C가 이 자리에 더한 것 하나**: `claimInvite`가 `seededAt`을 비우므로 **재등록마다
`seedOutbox`가 다시 돌아 meta 표식이 다시 생긴다.** 2C 이전 키 붙여넣기 경로는 `seededAt`을
건드리지 않아 재등록이 재시딩을 만들지 않았다. 의도된 동작이다(재등록은 서버 관점에서 첫
등록이므로 로컬 전부가 올라갈 대상이 맞다) — 다만 `pushMeta`가 그만큼 더 자주 돈다.

**읽기 쪽에도 하나**: `pullConfig`의 「행이 있는」 분기는 `app_config`에 PIN을 넣기 전까지
한 번도 안 탄다(늘 빈 배열). 2B 스모크 2번이 그것이다. `app_config`의 INSERT·UPDATE 정책은
앱이 쓰지 않는다 — PIN은 SQL로만 쓰므로 정상이다.

**이 표를 목록으로 유지할 것.** 「적용 가능성 ≠ 실행 가능성」은 `replace_all` 한 건의 교훈이
아니라 이 레포의 서버 코드 전체에 걸리는 성질이고, 사례로 적어 두면 다음 사람이 자기 경로를
다시 세어야 한다.

### Phase 2 최종 리뷰가 남긴 잔여 (병합 승인됨, 데이터 손실·죽은 화면·리스너 누수 없음)

- **`ui.ts` — 홈 버튼 연타 시 대상 화면에 재진입한다.** 가드가 `location.hash === hash`를 보는데 해시는 첫 탭에서 동기적으로 바뀌고 버튼은 동적 import 동안 살아 있다. 결과는 전부 무해함이 추적으로 확인됐다(고아 스프린트 세션은 진행되지도 저장되지도 않고 다음 해시 변경에 리스너가 자진 제거된다). **어떤 화면이 자기 해시로 `navigate`하게 되면 다시 볼 것**
- **`sprint.ts`의 `retrySave` 해시 스냅샷은 래치되지 않는다.** `cancelled` 플래그를 쓸 수 없어서다(`finish()`가 재시도 버튼이 생기기 전에 리스너를 제거한다). `#/sprint → #/ → #/sprint`를 IndexedDB 쓰기 하나가 도는 동안 해내야 재현되고, 최악이어도 "← 홈"이 살아 있는 낡은 결과 화면이다
- **`simulation.test.ts`의 등장 횟수 관련 주석 숫자("9/10 vs 7/10")가 재현되지 않는다.** 결론은 맞고, 단언이 실제로 기대는 숫자(건강 15~16, 결함 20)는 정확히 재현된다. 주석만의 문제
- **`facts.test.ts`의 `factAnswer` 왕복 테스트가 `FACT_IDS` 대신 `1..9`를 돈다.** Phase 4에서 다시 보고 **루프는 그대로 두었다** — 그 범위는 하드코딩이 아니라 파서 정의역(`FACT_ID_RE = /^([1-9])×([1-9])$/`)이고, 풀(72식)은 그 부분집합이라 `FACT_IDS`를 돌면 검사 범위가 오히려 좁아진다(테스트 이름이 "81식"이라고 거짓말하던 것만 고쳤다). 원래 걱정("풀이 확장되면 죽은 스프린트 화면으로 드러난다")은 **풀이 정의역 밖으로 넓어지는 경우**(예: 10단, 0단)에만 성립하므로, 그건 별개 단언으로 두는 편이 맞다 — `for (const id of FACT_IDS) expect(() => factAnswer(id)).not.toThrow()` 한 줄이면 된다. ~~아직 안 넣었다~~ — **넣었다**(2026-08-13, 「풀 전체가 파서 정의역 안에 있다」). **변이 검증에서 배운 것을 함께 남긴다**: 단순 변이(풀에 `10×1`을 더하거나 `DAN_MIN`/`DAN_MAX`를 옮기기)는 길이·센티널 단언이 먼저 잡아 이 테스트를 격리하지 못한다. 이 단언이 홀로 값을 내는 자리는 **풀을 의도적으로 넓히는 커밋**이다 — `DAN_MAX = 10`으로 올리고 길이 단언까지 81로 함께 고친 상태를 만들어 보면 **이 테스트 하나만 빨개진다**(실측: 1 failed / 33 passed). 즉 이것은 회귀 탐지기가 아니라 **풀 경계를 옮기는 사람에게 `FACT_ID_RE`도 같이 넓히라고 말해 주는 장치**다

## 3~6학년 확장에서 깨지는 지점

시점까지 붙인 판은 `integrated-arithmetic-ladder.md` §8에 있다. 요약하면 **2027-01 역연산 확장(작음) → 2027-05 나눗셈 엔진(큼) → 2027-07 분수·소수(큼)**.

- **나눗셈이 첫 번째 벽이고, 시점이 확정됐다.** 개념 도입 **3-1**, 나머지 있는 나눗셈·(두 자리)÷(한 자리) **3-2**, (세 자리)÷(두 자리) **4-1**. `vertical.ts`의 `Spec`은 `op: '+' | '−'`로 닫혀 있고 판정 술어가 `carryCount`/`borrowCount`다. 세로 나눗셈은 레이아웃도 완전히 다르다. 태그 추가가 아니라 새 엔진이다
- **분수·소수는 `answer: number`를 깨뜨린다.** 다만 `answer`는 채점 화면 표시 전용이고 `derive`가 쓰지 않아 파급은 제한적이다
- **`print-sheet.ts`는 문항 종류별 분기 구조**라 새 종류마다 손대야 한다
- 유형이 20개를 넘으면 하루 8문항으로는 회전 전략이 필요해진다
- 마이그레이션은 `Day`에 **필수** 필드가 생길 때 처음 필요해진다. `schemaVersion`/`algoVersion`은 쓰이기만 하고 읽는 곳이 없다

## Phase 3이 알아야 할 실측값

Phase 2 최종 리뷰가 엔진을 레포 밖으로 복사해 최대 5년치를 시뮬레이션하고 측정한 값이다. 추정이 아니다.

- **로그를 안 잘라도 비용이 없다.** 5년치(54,750 시도)에서 `deriveFacts` 16ms, `sprintStreak` 0.32ms, JSON 2.3MB. 선형이고, 화면 한 번 그리는 데 16ms는 안 보인다. "이력을 자르지 말 것" 제약은 공짜다
- **간격 반복이 식을 굶기지 않는다.** 도입 이후 재등장까지의 최대 공백이 60·120·365·730일 어디서나 **15일로 평평하다.** due가 밀린 fluent 식의 적체도 평균 0.1개·최대 3개이고 시간이 갈수록 줄어든다
- **다만 상한은 14일이 아니라 15~16일이다.** 설계 302행이 "8살은 2주 쉬면 잊는다"를 걱정하면서 14일 천장을 전제하는데, due가 된 식이 8칸을 두고 경쟁하므로 실제 천장은 하루이틀 높다. 적체가 쌓이지 않으므로 결함은 아니다 — **Phase 3의 점검의 날은 14일이 아니라 15~16일 기준으로 설계할 것**
- **한 세션 안에서 유창 판정이 날 수 있다.** `composeSprint`가 같은 식을 반복 출제하므로 한자리에서 빠르게 3번 맞으면 `fluent`가 된다. 설계 §6.1의 "최근 3회 연속 정답"을 문자 그대로 지킨 것이고 1→3→7→14 사다리가 이후의 지속성을 요구하므로 결함은 아니지만, **분산이 아니라 집중 학습의 증거**다. 점검의 날을 조율할 때 알고 있을 것
- **Phase 2는 마이그레이션이 필요 없다 — 확인됐다.** Phase 2가 쓰는 모든 필드(`Day.sprint`, `SprintAttempt`, `Settings.sprintCount`/`fluentMs`, `FactState`)가 Phase 1의 `types.ts`에 이미 있었고 전부 optional이거나 기본값이 있다. `schemaVersion`을 건드릴 일이 없었다. Phase 3이 이걸 다시 유도하지 않아도 되도록 적어 둔다

## Phase 1에서 리뷰가 반복해서 잡은 실패 패턴

테스트를 쓸 때마다 확인할 것.

1. **자기 자신을 검사하는 테스트** — 생성기가 이미 술어로 거른 값을 같은 술어로 단언하면 무엇을 바꿔도 통과한다
2. **느슨한 상한** — 실측 16에 상한 150이면 완전 정지만 잡힌다
3. **실패할 수 없는 단언** — `expect(x).toBeTruthy()`
4. **화면의 갇힘 경로** — 첫 `await`가 `try` 밖이면 실패 시 `#app`이 빈 채로 남는다. `showError`는 `document.body`에만 붙는다

Phase 2가 여기에 둘을 더했다.

5. **매달린 비동기 콜백도 갇힘 경로를 만든다.** 4번은 `await` 위치 문제라 정적으로 보이지만, Phase 2에서는 취소되지 않은 `setTimeout`이 이미 교체된 `#app`을 덮어써서 같은 결과에 도달했다. 화면을 떠날 수 있는 지연 작업에는 취소 경로를 붙일 것
6. **가장 값진 결함은 태스크 사이의 이음새에 있다.** Phase 2의 Critical은 `sprint.ts`의 쓰기가 `home.ts`의 읽기를 만나야 보였고, `✅` 결함은 구현이 아니라 *설계문서와 계획서*를 대조해야 보였다. 태스크별 리뷰는 각자 범위 안에서 모두 옳았다. **다음 계획을 세울 때, 새 코드가 쓸 필드를 이미 읽고 있는 모든 곳을 나열하는 단계를 태스크 0으로 둘 것**

Phase 3가 여기에 하나를 더했다(실은 반복이라 하나로 묶는다) — 이번엔 6건 중 5건이 같은 종류였다.

7. **테스트가 자기가 검사한다고 주장하는 것을 실제로는 검사하지 못한다.** 구현 로직은 옳았는데도: 검증기가 컨테이너 타입만 보고 값을 안 봄 / "기존 값이 살아남았다"를 단언하는데 새 값과 기존 값이 같은 객체라 항진명제 / `getMeta()`의 빈 스토어 폴백이 기본값과 구조적으로 같아 2차 마스킹 / 정렬 픽스처가 올바른 키와 그럴듯한 오류를 구별 못 함 / 자기증명 단언에 상한이 없어 폭주 회귀를 못 잡음. **각 단언마다 "구현이 그럴듯하게 틀렸다면 이 값이 무엇이 되는가"를 묻고, 같으면 픽스처를 고칠 것.** 고친 뒤에는 **변이 검증**(구현을 일부러 틀리게 바꿔 테스트가 실패하는지 확인하고 원복)으로 실제 효력을 확인할 것 — 이번 Phase에서 이 방법이 여러 번 값을 냈다
8. 나머지 1건은 다른 종류였다: 가져온 백업 데이터가 이스케이프 없이 `innerHTML`에 들어가던 XSS. 신뢰할 수 없는 값(가져오기·사용자 입력)을 다루는 코드를 새로 쓸 때는 `escapeHtml`을 거쳤는지 항상 확인할 것
