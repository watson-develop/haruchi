# Supabase 설정 절차 (사람이 한다)

Supabase를 한 번도 안 써 봤어도 이 순서대로 하면 끝까지 갈 수 있다. 실제 URL·키·비밀번호는
어디에도 적지 않는다 — 아래 예시는 전부 자리표시자(`<...>`)다.

**순서를 지킬 것.** 4단계(접속 정보 기입·배포)를 끝내야 5단계에서 기기 id가 화면에 나타난다.
앱은 접속 정보가 비어 있는 동안 동기화를 통째로 끄기 때문이다 — 그래서 서버를 준비하기
전에 이 앱을 배포해도 오늘까지와 똑같이 동작한다.

전체 흐름: 프로젝트 만들기 → 스키마 넣기 → 키 확인 → **앱에 넣고 배포** → 기기 등록 →
동작 확인.

## 0. 사전 준비

- 계정은 GitHub 로그인으로 바로 만들 수 있다. 별도 이메일 가입도 되지만 GitHub 쪽이 더
  빠르다.
- 무료 티어(Free plan)로 충분하다. 이 앱은 하루에 문제지 인쇄·채점·스프린트 결과를 합쳐도
  전송량이 수십 KB 수준이라 유료 플랜으로 올릴 이유가 없다.
- 무료 티어는 1주일 동안 아무 요청이 없으면 프로젝트가 자동으로 일시정지(pause)된다는 점만
  기억해 둔다 — 예방은 4단계 2번(주간 ping), 이미 멈춘 경우의 복구는 8단계에서 다룬다.

## 1. 프로젝트 생성

1. https://supabase.com 에 로그인한다.
2. 대시보드에서 **New project**를 누른다.
3. 조직(Organization)은 개인 계정 것을 그대로 쓰면 된다.
4. 프로젝트 이름은 아무 문자열이나 괜찮다(예: `haruchi`) — 앱 코드가 이 이름을 참조하지
   않는다.
5. **Database Password**는 Supabase가 자동 생성해 주는 걸 그대로 써도 되고 직접 입력해도
   된다. 이 앱은 REST API(publishable 키)로만 통신하고 이 비밀번호를 코드 어디에서도 쓰지
   않는다 — 그래도 비밀번호 관리자에 보관해 둔다. 분실하면 나중에 Supabase 대시보드에서
   DB에 직접 접속하거나 비밀번호를 재설정해야 하는 상황(예: 마이그레이션 트러블슈팅)에서
   막힌다.
6. **Region**은 반드시 **Seoul (ap-northeast-2)**를 고른다 — 나중에 바꿀 수 없고, 다른
   리전을 고르면 왕복 지연이 늘어난다.
7. **Create new project**를 누르고 몇 분 기다린다. 프로젝트가 준비되면 대시보드가 열린다.

## 2. 스키마 적용

1. 왼쪽 사이드바에서 **SQL Editor**를 연다.
2. **New query**를 누르고, 이 저장소의 `schema.sql` 파일 전체 내용을 복사해 붙여 넣는다.
3. 오른쪽 아래(또는 우측 상단)의 **Run**을 누른다. 성공하면 "Success. No rows returned" 같은
   메시지가 뜬다.
4. 왼쪽 사이드바의 **Table Editor**를 열어 확인한다 — `days`·`meta`·`app_config`·`devices`·
   `snapshots`·`write_log`, 이렇게 6개 테이블이 보이면 스키마가 정상 적용된 것이다.
5. 스키마를 고친 뒤에는 같은 파일을 다시 Run하면 된다(멱등). **2A 배포 전에 반드시 먼저
   적용한다**(설계 §7).

## 3. 키 확인

1. 왼쪽 사이드바에서 **Settings → Data API**를 열고 **Project URL**을 복사해 둔다
   (`https://<프로젝트ref>.supabase.co` 모양이다).
2. 왼쪽 사이드바에서 **Settings → API Keys**를 연다.
3. **Publishable key** 아래의 `sb_publishable_...` 값을 복사한다. 이 키는 브라우저에
   노출돼도 되는 키이고(화면 설명도 "safe to use in a browser if you have enabled Row
   Level Security" — 2단계에서 정책을 깔았으므로 조건은 충족돼 있다), 이 앱이 쓰는 것이
   이 키다.
4. **바로 아래 `Secret keys`의 `sb_secret_...`은 절대 복사하지 않는다.** 이 키는 RLS(행
   단위 보안)를 통째로 우회하는 관리자 키라서, 앱 코드나 이 저장소에 들어가면 누구나
   전체 데이터를 읽고 쓸 수 있게 된다. 두 키가 같은 화면에 위아래로 붙어 있고 이름도
   `sb_`로 똑같이 시작해서 실제로 헷갈리기 쉬운 지점이니, 붙여 넣기 전에 값이
   `sb_publishable_`로 시작하는지 한 번 더 본다.

> 이름이 다르게 보인다면: Supabase가 키 이름을 바꿨다. 옛 이름은 `anon` `public`(=
> publishable)과 `service_role`(= secret)이고, 같은 화면의 **「Legacy anon, service_role
> API keys」** 탭에 남아 있다. 둘 다 동작하지만 새 프로젝트는 `sb_publishable_...` 쪽을
> 쓴다. 이 저장소의 코드가 쓰는 상수 이름(`SUPABASE_ANON_KEY`)은 옛 이름을 따르지만
> 담기는 값은 publishable 키다.

## 4. 앱에 접속 정보를 넣고 배포

**이 단계를 5단계보다 먼저 해야 한다.** 앱은 접속 정보가 비어 있는 동안 동기화 기능을
통째로 끄고, 등록 안내도 기기 id도 화면에 그리지 않는다. 즉 여기를 건너뛰면 5단계에서
확인해야 할 기기 id가 아예 보이지 않는다.

1. `src/data/sync-config.ts`에 3단계의 Project URL과 publishable 키를 채운다
   (`SUPABASE_ANON_KEY` 상수에 `sb_publishable_...` 값이 들어간다).
2. `.github/workflows/ping-supabase.yml`의 URL·키 자리표시자도 같은 값으로 채운다 —
   이 워크플로가 매주 프로젝트에 요청을 보내 무료 티어 일시정지를 막아 준다.
3. 두 파일을 커밋하고 `main`에 push한다.
4. **배포가 끝날 때까지 기다린다.** 아이패드가 여는 것은 GitHub Pages에 배포된 앱이라,
   push만 하고 배포가 안 끝났으면 기기에서는 여전히 옛 버전이 돌아 등록 안내가 안 보인다.
   GitHub의 Actions 탭에서 초록불을 확인한다.
5. 아이패드에서 앱을 새로고침한다. PWA가 옛 버전을 캐시하고 있으면 「새 버전이 있어요」
   배너의 **업데이트**를 누른다.

## 5. 기기 등록 (기기마다 반복)

1. 그 기기에서 앱의 부모 홈을 연다. 아직 등록되지 않은 기기면 진행 상태 대신
   **"이 기기는 아직 연결되지 않았어요"**와 함께 기기 id가 표시된다. 이 id를 복사해 둔다.
   - 이 안내가 안 보이면 4단계가 덜 끝난 것이다(설정 미기입 또는 배포 미반영).
2. 그 기기용 랜덤 키를 만든다. 방법은 둘 중 아무거나:
   - 터미널에서 `openssl rand -base64 32`
   - 비밀번호 관리자의 비밀번호 생성기(32자 이상, 특수문자 포함해도 무방)
3. 생성한 랜덤 키는 비밀번호 관리자에 보관한다 — 평문 키는 서버에 저장되지 않고 해시만
   남으므로, 이 키를 잃어버리면 같은 값으로 다시 넣을 방법이 없다(재발급은 7단계).
4. SQL Editor에서 다음을 실행한다. `<기기id>`는 1번에서 확인한 값, `<랜덤키>`는 2번에서
   만든 값으로 바꿔 넣는다. `label`은 나중에 어느 기기였는지 알아보기 위한 메모다:

   ```sql
   insert into devices (id, label, key_hash)
     values ('<기기id>', '아이패드', crypt('<랜덤키>', gen_salt('bf')));
   ```

5. **실행한 쿼리 탭을 지운다.** SQL Editor는 실행한 쿼리를 스니펫으로 저장해 두기 때문에,
   그냥 두면 평문 키가 대시보드에 계속 남는다 — 서버가 해시만 갖도록 설계한 의미가
   사라진다. 탭을 삭제하거나 내용을 지워 둔다.
6. 앱의 키 입력란에 랜덤 키(해시가 아니라 원래 값)를 붙여 넣고 저장한다.

### 두 번째 기기부터 — 등록 **전에** 그 기기의 로컬을 확인한다

등록은 그 기기에 **그때까지 쌓인 기록 전체를 올릴 대상으로 심는다**(6단계 첫 문단). 첫
기기에서는 그게 정확히 원하는 동작이지만, 두 번째 기기부터는 **그 기기에 들어 있던 것이
가족 기록으로 섞여 올라간다**는 뜻이 된다. 폰에서 앱을 구경하다 문제지를 한 번 만들어 봤다면
그 문제지가 올라가고, 같은 날짜에 아이패드가 만든 것과 다르면 격리 배너가 뜬다.

그래서 키를 넣기 **전에** 그 기기의 부모 → 리포트를 연다.

- **「모든 기록 지우기」 버튼이 안 보이면** 그 기기는 비어 있다(이 버튼은 기록이 하나라도
  있을 때만 그려진다). 그대로 등록하면 된다.
- **버튼이 보이는데 그 기록이 필요 없으면** 등록 전에 눌러서 지운다. **미등록 상태에서는 이
  초기화가 로컬에만 적용되고 서버는 건드리지 않는다** — 파괴적 경로가 `syncEnabled()`
  (`configured() && deviceKey !== null`)로 갈라지는데, 기기 키가 없으면 서버 교체 단계를
  아예 타지 않는다.
- **그 기록을 살려야 하면** 지우지 말고 그냥 등록한다. 병합이 양쪽을 합친다. 다만 같은
  날짜에 서로 다른 문제지가 있으면 그 날짜가 격리되고, 부모 홈 배너에서 어느 종이로 채점할지
  골라야 한다. 등록 전에 그 기기에서 **파일 내보내기로 백업**을 떠 두는 편이 안전하다.

**등록한 뒤에는 같은 버튼의 의미가 달라진다.** 이제 `syncEnabled()`가 참이므로 「모든 기록
지우기」는 로컬과 **서버를 함께** 비운다. 등록 전과 후를 헷갈리지 말 것.

## 6. 동작 확인

**첫 기기를 등록하면 그때까지 쌓인 기록 전체가 한 번에 올라간다.** 아웃박스 표식은 등록
이후의 쓰기에만 생기므로, 등록 시점에 앱이 기존 기록 전부를 올릴 대상으로 심어 둔다.
그래서 아래 1번에서 보이는 것은 오늘 한 줄이 아니라 그동안의 날짜 전부다(두 번째 기기부터는
이 동작이 함정이 된다 — 5단계 끝의 「두 번째 기기부터」를 먼저 읽을 것).

1. Supabase Table Editor의 `days`를 연다 — 기존 기록 일수만큼 행이 있어야 한다.
2. 부모 홈의 동기화 줄이 「아직 안 올라간 기록 N건」이 아니라 「마지막 동기화: 오늘」로
   바뀌는지 확인한다. N이 줄지 않고 멈춰 있으면 7단계를 본다.
3. 앱에서 문제지를 인쇄한 뒤 `days`의 오늘 행이 갱신되는지 본다.
4. `write_log`를 열어 쓰기가 기록으로 남는지 확인한다 — 여기 행이 안 늘어나면 RLS나 키
   설정이 잘못됐을 가능성이 크다(7단계 참고).

## 6.5 채점 화면 PIN (선택)

채점 화면(`#/grade`)과 리포트 화면(`#/report`)에 PIN 잠금을 켠다. 앱에는 설정
화면이 없다 — SQL Editor에서 켜고 끄고 바꾼다(분실 복구와 같은 길, 2B 설계 §5).

**정확히 4자리 숫자로 정한다** — 앱의 입력 칸이 4자리 숫자 키패드다. 다른 길이를
넣으면 게이트가 열리지 않는다(고치는 길은 아래 같은 SQL이다).

```sql
-- 설정·변경
insert into app_config (id, pin, device) values (1, '1234', 'sql')
on conflict (id) do update set pin = excluded.pin, device = 'sql';

-- 잠금 해제
update app_config set pin = '' where id = 1;
```

각 기기는 다음 pull에서 PIN을 받아 간다(오프라인 검증용 캐시). 초기화·가져오기·
되돌리기는 PIN을 건드리지 않는다.

## 7. 폐기·재발급

- 기기를 더 이상 쓰지 않게 되면 폐기한다. 다음 요청부터 즉시 막힌다:

  ```sql
  update devices set revoked_at = now() where id = '<기기id>';
  ```

- 같은 기기를 다시 쓰게 하려면 새 랜덤 키로 5단계를 처음부터 다시 밟아 새 `insert`를
  실행한다 — 기존 키를 재사용하지 않는다.

| 부모 홈에 「다른 기기에서 기록이 교체되어 이 기기를 맞췄어요」가 뜨고 기록이 달라졌다         | 다른 기기가 **초기화나 백업 가져오기**(전체 교체)를 했다. 서버의 `generation`이 올라가면 나머지 기기는 서버 상태로 다시 맞춘다(재기준화)                           | 정상 동작이다 — 「확인」을 누르면 된다. **다만 이 기기에만 있고 아직 안 올라간 기록은 자동으로 살아나지 않는다.** 되돌리려면 `#/report`의 되돌리기에서 교체 직전 스냅샷을 고른다(전체 교체는 항상 사전 스냅샷을 남긴다)                                                                                                                                                                                                   |

> 폐기된 키는 HTTP 401이 아니라 **빈 응답**으로 거절된다(행 단위 보안이 행을 안 내주는
> 방식이라 그렇다). 그래서 앱은 그 상태를 따로 판별해 부모 홈에 인증 경고로 표시한다 —
> 브라우저 개발자도구에서 401을 찾으면 안 나온다.
